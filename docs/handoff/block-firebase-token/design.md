# design: 自社ログイン中は、サーバーが Firebase のログイン札を断る

- 書いた日: 2026-11-04（Opus）
- 状態: 設計案作成済み → 設計審査（§9）済み。PO の進める判断: 2026-11-04「2」（Opus が出した選択肢「サーバーの直しを先に急いで作る　プログラムの直し・審査・本番への反映で、数時間かかります。」）。
- 根拠: [recon.md](./recon.md)（`docs/handoff/block-firebase-token/recon.md`）。親 ADR: ADR-1013（Decision 6）。関係する設計: `docs/handoff/auth-self-hosted-passkey/design.md` §4・`:120`。

## 1. 目的（PO の言葉で）

Firebase は使わない設定に切り替えた（PO 2026-11-04「firebaseは使わない設定に切り替えている」）。それなのに、サーバーは Firebase の札をまだ受け付けている（recon R3）。この裏口を閉じる。

利用者から見た変化は無い。画面は自社の札しか送らないからだ（recon R11）。

## 2. 成功条件（○×で判定できる形）

本番での限界: 本物の Firebase の札で 401 になることは、本番では確かめられない。試すには本物のパスワードが要るからだ。偽の札は、直す前も直した後も 401 になるので、違いが出ない。K1・K2 は単体試験で確かめ、K7・K8 で「本番に入って正規の利用が止まっていない」ことを確かめる。

## 3. 対象と対象外

対象（触るのはこの 3 つだけ）:

- `backend/tests/test_smoke_auth_least_privilege.py`（末尾に試験を 1 つ足すだけ）

対象外（便6 でまとめて行う。今回は触らない）:
- `firebase-admin` の除去・`_init_firebase()` の除去・Firebase 分岐の削除
- 画面の Firebase SDK の除去
- Firebase の利用者の削除（戻せない。PO の GO が要る）
- `AUTH_PROVIDER` の既定値（`firebase` のまま。試験と戻し方 R15 が既定に頼っている）

## 4. 変更の前と後

### 4-1. 今の順序（`backend/app/auth/dependencies.py:155-283`）

smoke → ① 消した札の一覧 → ①b 失効した組 → ② 一時記憶 → ③ IP の回数 → 自社の札なら自社の確かめ → ④ Firebase の確かめ

### 4-2. 直した後の順序

smoke → ① → ①b → **自社ログイン中かと、札の発行元を先に読む** → ② 一時記憶（**自社ログイン中は、自社の札のときだけ使う**）→ ③ IP の回数 → 自社の札なら自社の確かめ → **自社ログイン中なら、ここで 401（Firebase に進まない）** → ④ Firebase の確かめ

- 断る場所を③の後に置く。回数超えは今までどおり 429 を返し、失敗も今までどおり数える（K5）。
- ② の一時記憶は、自社ログイン中に自社以外の札を読まない。直す前に記憶に載った Firebase の札（最大 300 秒・recon R5）も通らない（K2）。
- 断るときは、今の自社の札を断る関数 `_reject_self_token`（`backend/app/auth/dependencies.py:76-81`）を使う。失敗を数えて、同じ文言の 401 を返す。新しい文言は作らない。
- 断ったときは警告を記録に 1 行残す。IP だけを書き、札の中身は書かない。数は ③ の回数制限で抑えられる。

### 4-3. コード（変更の前と後）は [card.md](./card.md) §2 に全文を書く。

## 5. 代わりの案と選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| A. 便6（Firebase の全撤去）を待つ | 118 ファイルに及び、Firebase の利用者削除（戻せない）も含む。裏口が開いたまま日が過ぎる |
| B. Firebase の画面で利用者を今すぐ無効にする | 外部の画面の操作で PO の手作業が要り、戻すのも手作業になる。今の戻し方（R15）も効かなくなる |
| C. 断る所を一時記憶（②）の前に 1 か所だけ置く | 回数超えの 429 が 401 に変わる（R18 の既存試験が赤になる）。順序（ADR-127）を変えることにもなる |
| D（採用）. スイッチが self のときだけ、②で読まず、④の直前で断る | 1 ファイル・数行で済む。スイッチを firebase に戻せば元どおり（R15）。既存の順序と回数制限を変えない |

## 6. リスクと対処

| リスク | 対処 |
|---|---|
| 正規の利用者が Firebase の札を送っていて、締め出される | 画面は self のとき自社の札しか送らない（R11）。Termux の取り込みは Firebase を使わない。qa-smoke は自社ログインの画面を通る。deploy 後に K8 で確かめる |
| 試験の多くが壊れる | 試験の既定は firebase（R16）なので、既存の試験の動きは変わらない。CI の全件で確かめる |
| 自社ログインの試験の一時記憶の扱いが変わる | 自社の札は今までどおり一時記憶を使う（T4） |
| 戻したくなった | この PR を revert して deploy する。または R15 の手順でスイッチを firebase に戻す |

## 7. 移行の設計との関係

`docs/handoff/auth-self-hosted-passkey/design.md:120` は「API の受け付けは便2〜便5 の間、両方の札を受ける」と決めていた。この直しで、本番が self の間は Firebase の札を受けないように改める。firebase に戻したときは、今までどおり両方を受ける。理由: 画面が自社の札しか送らないので、両方を受けても正規の利用者の役に立たず、裏口だけが残る（recon §2）。同じ行に、この設計への参照を書き足す。

## 9. 設計審査（同じ Opus が自分で審査した。独立した審査ではない）

判定: APPROVE。

- 既存の仕様との整合: ADR-1013 Decision 6（スイッチで切り替える）に合う。ADR-127 の順序（①→②→③→④）は変えていない。ADR-1017 の smoke は①より前なので影響しない（R17）。ADR-1055 の①b は②より前なので影響しない。
- 根拠: Firebase を確かめる所が 1 か所だけであることを、コード全体の検索で確かめた（R7）。
- 受け入れ基準: K1〜K6 は単体試験で○×が出る。K7・K8 は本番の記録と PO のログインで○×が出る。本物の Firebase の札で本番を試せない限界は §2 に書いた。
- 実装の範囲: 3 ファイル。コードは card.md に全文がある。
- 残る事項: recon §3 の未確認 3 件は、この直しの合否には関わらない。便6 の設計で扱う。
