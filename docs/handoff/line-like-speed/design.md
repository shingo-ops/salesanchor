## 1. KGI（PO 承認済み 2026-10-31「1」）

PO の言葉: 「LINEみたいな使い心地は出来る？」（意味は「押した瞬間に開く速さ」）。承認時の条件（原文）:「推測は禁止して事実確認を怠らずに確実性を重視して最も効果があり、現状把握の粒度が細く、精度が高いエビデンスを確立して安全に進めてくれ。また配線とDBのSSOTは遵守してデータを分散させることは禁止。フロントエンドのパーツもデザイントークンとデザインシステム を遵守して、金型登録のないハードコードを禁止する。」

| K3 | 押してから、画面に何か変化が出るまで | 0.1 秒以内 | 毎朝の記録に「押してから最初の変化までの秒」を足して測る |
| K4 | ほかの人が変えた中身が、開いている画面に出るまで | 5 秒以内 | tenant 001 で別の人として変更し、開いている画面に出るまでを測る |
| K5 | ログアウト後・別の会社で、前の人の中身が見える | 0 件 | ログアウト→別の人でログイン、会社切替のあとに前の中身が出ないかを試験で確かめる |
| K6 | PO のスマホで触って「LINEみたい」と感じる | ○ | PO が 3 画面を触って判定 |

## 2. 守ること（PO 条件の言い換え）
- データの正本はサーバーの DB だけ。画面が手元に残す中身は「表示のための写し」で、合図（ADR-1016）と時間で必ず取り直す。写しを正本として書き戻したり、別の保存先に持ったりしない。
- 画面の部品はデザイントークンと金型（components/）だけで作る。新しい見た目の部品は金型に登録してから使う（ADR-067・ADR-144）。
- 分からないことは推測で埋めず、recon の未確認に書いて確かめるか PO に聞く。

## 3. 作り方（設計案・審査前）

### 3-1. 今と変えた後
| | 今（recon §2・§4 U1） | 変えた後 |
|---|---|---|
| 画面を開く | 毎回 useEffect で api.get、終わるまで中身を消して LoadingBlock（93 本中 61 本） | 前に取った写しがあれば**すぐ出し**、裏で必ず取り直して差し替える。写しが無い初回だけ LoadingBlock |
| 取り直す時 | 中身を消す | 中身を残したまま（InventoryPage.tsx:636 の手本と同じ） |
| ほかの人の変更 | 合図を受ける画面は 3 か所 | 合図（ADR-1016）で写しを取り直す。合図の無い画面は、開いた時・タブに戻った時に必ず取り直す |
| ログアウト | メモリの session を消すだけ（selfAuth.ts:67） | 同じ時に写しも全部消す |

### 3-2. 部品
- 写しの置き場: TanStack Query（@tanstack/react-query 5 系）を 1 つ入れる。新しい部品の追加なので ADR を起こす（下書き: docs/adr/ 新番号、本件 PR に同梱）。選んだ理由と比べたもの → §3-6。
- 置き場は 1 つだけ: frontend/src/lib/query/ に QueryClient を 1 個作り、App.tsx の AuthProvider の内側・BrowserRouter の外側に QueryClientProvider を置く（App.tsx:151-152 の間）。ほかの場所で QueryClient を作らない。
- 取り方は 1 つだけ: 同じ場所に `useApiQuery(path)` を作り、中で今の `api.get`（frontend/src/lib/api.ts:150）を呼ぶ。通信・再送・401 の扱いは api.ts のまま（二重にしない）。TanStack 側の再送は 0 にする（api.ts が既に 3 回送り直すため。既定 retry 3 のままだと最大 16 回になる）。
- 写しの名前（key）: `[ログイン中の人の id, path]`。人が変われば別の写しになる（X3 対策の二重目）。
- 写しを正本にしない: staleTime 0（既定のまま）＝写しは「出すだけ」で、画面を開くたび・タブに戻るたびに必ずサーバーから取り直す。写しはメモリだけに持ち、ブラウザの保存に書かない（persist の追加はしない）。使われない写しは 5 分で捨てる（gcTime 既定）。useQuery の結果を useState に写し替えない（X5）。
- 書き込みの後: 今の api.post/patch/delete はそのまま。成功したら、その画面の写しを invalidateQueries で取り直す（自分の変更は SSE の合図では来ないため・useRealtimeRefresh.ts の origin 判定）。
- 合図: useRealtimeRefresh(topics, () => queryClient.invalidateQueries(...)) で受ける。合図の名前の表（topics.py / topics.ts）は今のまま 1 か所。
- ログアウト・人の入れ替わり: AuthContext の user が変わった時（AuthContext.tsx:90 と :105 の 2 つの道の両方）に、cancelQueries → resetQueries → queryClient.clear()・mutation の写しも消す（X4 の順）。
- 見た目: 新しい部品は作らない。初回は今の LoadingBlock 金型、取り直し中は InventoryPage と同じ「中身を残して印を重ねる」形を金型として components/loading に登録してから使う（ADR-067・ADR-144。色・大きさはトークンだけ）。

### 3-3. 触らない範囲
- backend・DB・migrations・deploy.yml・本番 scripts は触らない（段 5 の合図追加だけは backend の topics.py に載せる。別便・別審査）。
- api.ts の通信の中身・ログインの仕組み・閲覧ページ（viewer/）は触らない。
- 画面の見た目・文言は変えない（i18n キーも増やさない。印の金型に文言が要るときは ja/en 同時に足す）。

### 3-4. 段階（1 便 1 PR・変更→反映→測定→次）
| 段 | 中身 | 合格の線 |
|---|---|---|
| 0 | 測る仕組みだけ足す: page-speed.spec.ts に「同じページの中で 2 回目に開いた時、中身が出るまでの秒」（K1）と「押してから最初の変化までの秒」（K3）を足し、今の値を基準として 1 回記録 | 135 画面の基準値が記録に出る |
| 1 | 置き場・取り方・ログアウトで消す、の土台だけ（画面はまだ変えない）＋ K5 の試験 | 試験: A でログイン→画面を開く→ログアウト→B でログイン→A の中身が 0 件。単体試験で retry が 1 回の失敗で 4 回以内 |
| 2 | 試しに 3 画面だけ変える（ChannelMastersPage・CompaniesPage・ほか 1 つ。使う頻度は PO に聞かず、中身を消す形の代表を選ぶ） | 3 画面で K1 ≤0.1 秒、K2 ≤2 秒、取り直した後の中身が DB と一致（tenant 001） |
| 3 | 残りを 10 画面ずつ（中身を消す 61・ほかの印 13・印なし 4・子で取る 15） | 毎便の後に毎朝の記録で K1・K2 が悪化していない |
| 4 | 見張り: 「読み込み中に中身を消す形」の数を数える検査を CI に足し、数が増えたら赤（減るのは可）。段 3 の最後で 0 にして固定 | CI に検査があり、わざと 1 本足すと赤 |
| 5 | K4: 合図の無い画面の書き込みに合図を足す（画面のまとまりごと・backend 便） | tenant 001 で別の人として変更→開いている画面に 5 秒以内 |

### 3-5. 測り方（|基準|検証方法|）
| 基準 | 検証方法 |

| K1 戻った時 0.1 秒以内 | 段 0 で足す測定。page-speed.spec.ts の goInApp（:72-79）で同じページの中で A→B→A と移り、2 回目の A で LoadingBlock が出ずに中身が出るまでの秒 |

### 3-6. ほかの案と選んだ理由
- 案 A（選ぶ）TanStack Query: 開いた時に写しを出し裏で取り直す・合図で取り直す・人が変わった時に消す、が部品に揃っている。X1 で画面移動時の追加通信 0 の実測がある。危ない点（X3・X4）は消し方の順で避けられる。
- 案 B SWR: 同じ形だが、ログアウト時に全部を消す・開いている画面に知らせる手順を自分で書く量が多い（公式資料の確認は ADR 審査で行う・未確認）。
- 案 C 自前の写し置き場: 新しい部品を入れずに済むが、取り直し・重複の束ね・消し方を全部自作することになり、X3・X4 と同じ失敗を自分で踏む危険がある。
- 案 D 先読みだけ（押す前に取る）: 初回は速くなるが、戻った時の写しが無いので K1 を満たせない。

### 3-7. 弊害と対処
- 古い中身が一瞬見える: 写しを出した直後に取り直すので、取り直しの間（今の秒＝最大 1.4 秒）は前の中身。→ 取り直し中は印を重ねて分かるようにする。お金・在庫の数を確定する画面（送信ボタンのある画面）では、送る前にサーバーの値で確かめる今の作りを変えない。
- 前の人の中身が見える（X3）: key に人の id＋ログアウトで消す、の二重。段 1 の試験で 0 件を確かめる。
- 再送が増える: TanStack の retry を 0 にして api.ts の 3 回だけにする。単体試験で数を固定。
- 一括移行の衝突（X1 で rebase の直しが要った）: 10 画面ずつ・1 便 1 PR。
- メモリ: 写しは 5 分で捨てる。段 3 の途中で 1 回、ブラウザのメモリの量を測る（基準は段 0 で取る）。

### 3-8. 戻し方
- 段 1: PR を戻す（画面はまだ使っていないので影響なし）。
- 段 2・3: 便ごとに PR を戻せば、その画面だけ今の useEffect の形に戻る（画面ごとに独立）。
- 段 4: 検査を外す PR。

### 3-9. 維持する仕組み
- 段 4 の CI の検査（中身を消す形の数を増やさない）。
- 段 0 の毎朝の記録に K1・K3 を足し、2 秒・0.1 秒を超えた画面を知らせる（知らせの作りは別便）。
- 新しい画面は useApiQuery を使う、を frontend/CLAUDE.md ではなく CI の検査で強制する（CLAUDE.md の追加判定 1 に従う）。
