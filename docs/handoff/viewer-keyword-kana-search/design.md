- 状態（2026-10-05）
  - 設計：Opus が作成し、自分で審査した（同じAIによる審査で、独立した第三者のレビューではない）。判定は §10。
  - PO：方針（products に列を足さず、検索ワードを検索対象にし、ひらがな・カタカナを同一視する）は承認済み（2026-10-05「y」）。成功条件（§2）・シートに検索ワードが見えることの了承（§5）・実装は、2026-10-05 に PO が「ｙ」で承認した（設計全体を示して y/n を尋ねた質問への返答）。
  - 実装：SA 側（§4-1）を Sonnet に委任した。GAS 側（§4-2・4-3）は SA の反映後に行う。
- 根拠：[recon.md](recon.md)
- 関係する ADR：ADR-1001（検索ワード表を public に統一）、ADR-154（配信は needs_review=false の行に限る）、ADR-158（配信クエリの is_current）。配信の列数を定めた ADR は無い（recon §2）。
- 直前の設計：`docs/handoff/gas-viewer-series-tabs/design.md`（同じ GAS に Series 列を足した）。

## 1. 目的（POの言葉）
「ひらがなでもカタカナでもヒットするように」「読み方でも検索にヒットするように」
→ PO 決定（2026-10-05）：読み方の列は作らない。すでにある検索ワードを検索の対象にする。

## 2. 成功条件（PO 承認待ち）
テスト用 URL で、「24時間以内のみ」のチェックを外して確かめる。

## 4. 変更内容（前と後）

### 4-1. SA：`backend/app/services/tcg_distribution_svc.py`
1. `:46-60` の `DIST_HEADERS`：末尾に `"Search Keywords"` を足して13列にする。コメントの「確定・12列」を「13列」にする。既存12列の順は変えない。
2. `:224-237` の SELECT：`provider` の後に1列足す。
   ```sql
   COALESCE((
       SELECT string_agg(psk.keyword, ' | ' ORDER BY psk.position, psk.id)
       FROM public.product_search_keywords psk
       WHERE psk.product_id = p.id
   ), '')                                                  AS search_keywords
   ```
   - 正本は public.product_search_keywords（recon §4）。products.search_keywords 列は使わない（照合が読んでいない列で、中身が食い違っているため）。
   - 区切りは ` | `。語どうしをまたいで当たることを防ぐ。
   - 大きさの見込み：最大13語×最長57文字で、1セル約800文字。シートの1セルの上限（5万文字）に対して十分小さい。
3. `:267-282` の返却リスト：末尾に `row["search_keywords"]` を足す。
4. `:188-200` の docstring の「12列」を「13列」にする。
5. テスト
   - `backend/tests/test_tcg_result_order.py:104`：`len(r) == 12` を `13` にする。
   - `backend/tests/test_tcg_distribution.py:184`：`DIST_HEADERS` を参照しているので、そのままで通る見込み。通らなければ直す。
   - 追加：検索ワードが2語ある商品は ` | ` でつながり、position の順に並ぶ。語の無い商品は空文字になる（PG を使うテスト。`backend/tests/test_tcg_distribution_pg.py` に足す）。

### 4-2. GAS：Code.js（本番は Code.js、テスト用は「コード.js」。中身は同じ）
- `:10-23` の `ALLOWED_HEADERS`：末尾に `'Search Keywords'` を足して13列にする。冒頭コメントの「12 列」を「13 列」にする。
- シートにこの列がまだ無いときは、既存の仕組み（:78,83）で空文字になり、そのまま動く。

### 4-3. GAS：index.html（本番とテスト用の両方。`<script>` 部分は同じ）
1. `:848-861` の `COL`：末尾に `searchKeywords: 12` を足す。コメントを13列にする。
2. 正規化の関数を足す（ES5 の書き方。既存のコードに合わせる）。
   ```js
   // 検索用の正規化：全角/半角・大文字/小文字・ひらがな/カタカナの違いをなくす
   function normalizeForSearch(s) {
     var t = String(s || '');
     if (t.normalize) t = t.normalize('NFKC');
     t = t.toLowerCase();
     return t.replace(/[ぁ-ゖ]/g, function(c) {
       return String.fromCharCode(c.charCodeAt(0) + 0x60);
     });
   }
   ```
   - NFKC で、全角英数は半角に、半角カナは全角カナに、全角空白は半角空白になる。
   - ひらがな（ぁ〜ゖ）はカタカナに寄せる。
3. 検索用の文字列を、読み込みのときに1回だけ作る：`:1032-1034` で `ALL_ROWS` を作った直後に、`SEARCH_TEXTS` を作る。
   ```js
   SEARCH_TEXTS = ALL_ROWS.map(function(row) {
     return normalizeForSearch([row[COL.japaneseTitle], row[COL.englishTitle], row[COL.mark], row[COL.searchKeywords]].join('\n'));
   });
   ```
   - `var SEARCH_TEXTS = [];` を `:809` の `ALL_ROWS` の隣で宣言する。
4. `:1187` の query：`normalizeForSearch(...).trim()` にして、空白で区切った語の配列（`queryTerms`）にする。
5. `:1204-1210` の検索：`ALL_ROWS.filter(function(row, i) {...})` とし、`queryTerms` のすべての語が `SEARCH_TEXTS[i]` に含まれる行だけを残す。
   - 今まで当たっていた語は今後も当たる（検索の対象は増える一方で、比べ方は大小・かなの違いをなくす方向だけ）。空白を含む語だけは、「ひと続きの一致」から「すべての語を含む」に変わる（前より広く当たる）。
6. `:699` の検索窓の案内文：「商品名・別名で検索（ひらがな・カタカナどちらでも）」にする。`aria-label` は「商品名・別名を検索」にする。
7. 表の列（`:1285-1290`）は変えない。Search Keywords は表に出さない。

## 5. 影響の範囲
- シート：3つの配信先のシートすべてで、「在庫集計」タブの末尾（13列目）に「Search Keywords」列が出る。配信は毎回タブ全体を書き直すので、次の配信から出る（recon §3）。
  - **シートを直接開く人には、検索ワードが見える**。検索ワードは商品の別名・略称で、内部の秘密情報は含まない想定。ただし、1語ずつの中身までは確かめていない。
- 在庫一覧 GAS：許可リスト方式なので、許可したこの1列だけが増える。在庫一覧は URL を知っていれば誰でも見られる（ANYONE_ANONYMOUS）。検索ワードはブラウザに送られるが、画面の表には出ない。
- 「在庫集計」タブをほかに読む仕組みがあるかは未確認（recon §8）。列は末尾に足すので、ヘッダー名で列を引く仕組みには影響しない。列の数を数えて決め打ちしている仕組みがあれば影響が出る。
- 反映の順番：どちらを先に出しても動く。SA が先なら GAS は新しい列を読まないだけで、GAS が先なら新しい列が空文字になるだけ。手順は SA → GAS とする（GAS の確認のときに、検索ワードが入った状態で見られるようにするため）。

## 6. 代替案と選んだ理由
| 案 | 結果 |
|---|---|
| A. products に読み方の列を足す | 採らない。列数が上限 1,600 に近い 1,543（2026-10-03 の障害）で、1,323件に読みを入れる作業も必要になる（PO 決定 2026-10-05） |
| B. 検索ワードをシートに出し、GAS で検索する（採用） | 検索ワードはすでに全 active 商品にある（recon §5）。DB を変えない |
| C. GAS から直接 DB や SA の API を読む | 採らない。GAS は匿名公開で、認証の設計が新しく必要になる |
| D. products.search_keywords 列を使う | 採らない。照合が読んでいない列で、値のある 221件すべてが正本と食い違う（recon §4） |

## 7. リスクと対処
| リスク | 対処 |
|---|---|
| テスト用 GAS の CSS の変更（未公開）を、本番の写しで上書きして消す | 本番とテスト用で、それぞれの写しに同じ `<script>` の変更を当てる。テスト用に本番のファイルを丸ごと反映しない |

| 検索が重くなる | 検索用の文字列は読み込みのときに1回だけ作る。約800行×1行あたり約1,000文字で、入力のたびの計算は部分一致だけ |
| 古いブラウザに `String.prototype.normalize` が無い | 無ければ NFKC を飛ばし、小文字化とひらがな→カタカナだけ行う（関数の中で分岐済み） |

## 9. 実装と反映の手順（カードの元）
1. SA：4-1 を実装し、backend のテストを通して PR を出す。`migrations/`・`.github/workflows/deploy.yml`・本番 `scripts/` を含まない通常の PR。
2. SA の反映後、配信を1回待ち、シートのヘッダーが13列であることを確かめる（K7）。
3. 変更前の基準値を取る：テスト用 URL で K5 の10語の件数を記録し、K6 の画面写真を撮る。
4. GAS：本番の写しとテスト用の写しのそれぞれに 4-2・4-3 を当てる。
5. テスト用へ反映する（PO の permit-danger「clasp push」チケットが要る）→ 版を作る → テスト用のデプロイを差し替える → K1〜K6 を Playwright と PO の目視で確かめる。
6. PO の確認の後、本番に同じ手順で反映する（もう一度 PO のチケットが要る）。
7. コードの正本（`shingo-ops/tcg-client-viewer`）が古いままの問題は、今回の範囲の外。§11 に記録する。
