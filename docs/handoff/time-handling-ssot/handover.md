## 2. 確定した事実（すべて 2026-09-08 の実測）

### 2-1. 同型の誤りは3度目だった

2026-05-13（ADR-021 J2 fix）、2026-09-01（ADR-151）、2026-09-08（本件）。過去2回はいずれも該当箇所を名指しで個別修正しており、再発を止める仕組みが無かった。

### 2-2. 真の違反は11件だった

recon.md では6件と見積もっていたが、実測で11件だった。内訳は `utcnow()` 4件、`AT TIME ZONE 'UTC'` 7件。recon.md §6-3 は `AT TIME ZONE` を1箇所としていたが、実際は `backend/app/routers/tcg_line_import.py` に7箇所あった。**recon の grep が不完全だった。**

### 2-3. 入口の誤りは並行セッションが既に修正していた

recon 実測時（SHA 65b13bb8）の `backend/app/services/tcg_line_import_svc.py:435` は `.replace(tzinfo=timezone.utc)` だったが、本日の作業台（起点 a5acd7c1）では `.replace(tzinfo=JST)` に変わっていた。台帳に `release-fix-tcg-received-at-jst` の記録がある。

### 2-4. 静的検査の規則は精度で2段に分ける必要がある

当初 T2（解釈直後の tzinfo 決めつけ）を停止規則に入れたが、実測で検出2件・真の違反0件（精度0%）だった。除去し、design.md §3-3 の警告規則へ移した。

外部調査（MSR 2025 の CodeQL 実測）と一致する。非推奨API検出は精度100%、文脈依存の規則は4〜5%。

### 2-5. `source_messages` は1社1行の上書き方式

「メッセージ1件=1行」ではなく「仕入元1社=1行」。取り込みのたびに既存行を `is_active=FALSE` にして差し替える。日付で件数を数えると、その日に投稿した仕入元の数になる。取り込み件数ではない。

2026-09-08 02:01 の取り込みでは48行（仕入元48社分）が作成され、01:01 の回の48行のうち46行が無効化された。

### 3-3. `_JST` の3重複解消（K1）

- `backend/app/routers/goals.py:41`

- `backend/app/routers/quotes.py:20`

### 3-4. CI のタイムゾーン追加（design.md §3-5）

CI のテスト実行を UTC 以外でも1回走らせる。現在の CI は単一タイムゾーンであり、これが誤りを隠していた。

## 5. 実行環境の制約（本日新たに実測）

次セッションが即座に使えるもの。すべて本日の停止から得た。

### 5-1. 実行役の作業領域

実行役はファイル書き込み時に本文全文を1入力に載せる。**セッション後半では作業領域が不足し、長い本文が書けなくなる。**

実測: recon.md 180行は成功。design.md 185行は同一セッション後半で失敗し、セッションを新しくして成功。

**対策**: 目安200行超の本文を書かせるカードは、実行役セッションの序盤に出す。

### 5-2. `new-worktree.sh` の出力を絞らない

出力を `head` や `tail` や `grep` に通すと、完了行が遅れて届き、次手順の確認が作成前に走って誤判定する（guards/04-worktree.md・PR #3362）。

**対策**: 出力を全文報告させる。作業台の実在は `ls -1d` と `git worktree list` の両方で確認する。片方だけで判定しない。

### 5-3. `/tmp` は消える

`/tmp/CC報告ファイル/` のファイルは、セッションをまたぐと消えることがある。実測: PR本文ファイル `pr-body-time-lint.md` が次便で見つからず停止した。

**対策**: PR本文の編集は `gh pr edit --body` で直接行い、ファイル経由にしない。

### 5-4. バッククォートが `\t` に化ける

カード内のバッククォートが、運搬途中でエスケープとして解釈されることがある。実測: 置換前テキストの `` `tcg_line_import_svc.py` `` が `\tcg_line_import_svc.py` になり、置換が失敗した。

**対策**: バッククォートを含む行を置換対象にしない。`sed` で置換し、パターンにバッククォートを含めない。

### 5-5. `rm -rf` は二重にブロックされる

PreToolUse hook（`permit-danger.sh` で解除可）と、実行環境そのもの（`rm -f style commands are not permitted`・解除不可）の2層。**許可チケットを取っても実行できない。**

**対策**: ディレクトリの削除を伴う片付けは、別の名前で作り直す方式に切り替える。

### 5-6. `sleep 150` は完走しない

`sleep 90` と `sleep 120` は完走したが、`sleep 150` を含む便は途中で終わった。

**対策**: 待機を含めない。関所の確認は待機せずに実行し、`pending` が残れば次便で再確認する。

### 5-7. `gh-pr-merge-safe.sh` の挙動

マージ成功後に worktree とローカルブランチを自動削除する。**リモートブランチは残す。**

`mergeStateStatus=BEHIND` のときは自動で追従（merge と push）するが、**追従直後のマージは新SHAのCIが未完了のため失敗する。** `12 of 12 required status checks are expected` で拒否される。

**対策**: マージ後の手順は `cd` 先をリポジトリ直下にする。追従が走ったら、その便では停止し、次便で新SHAのCI完了を確認してからマージする。

### 5-8. 関所の既知欠陥（見出し直下の `###`）

`scripts/check-process-artifacts.js` の next-section 検索 `/\n##/` が `###` にも一致する。「外部・過去事例と応用」欄の直下に `###` を置くと、内容が空と判定されて fail する。

記録: `docs/handoff/sop-kpi2/design.md:106-112`（ADR-133 PR #1970 で同型を実測）。

**対策**: 見出しの直下に平文を1行以上置く。恒久修正（正規表現の変更）は別テーマ。

### 5-9. Python の起動

`python` は存在しない。`python3`（3.14.3）を使う。`pytest` を単体で走らせるとカバレッジ不足（`--cov-fail-under=60`）で赤になるため、検査だけを見るときは `--no-cov` を付ける。

`-p no:xdist` は使えない。

### 5-10. CI は `backend/tests/` を丸ごと拾う

`.github/workflows/test.yml:241` が `pytest -q --tb=short`（ファイル指定なし）。`backend/pyproject.toml:54` が `testpaths = ["tests"]`。

**帰結**: 新しいテストを追加した時点で CI に接続される。「検査を作ってから接続する」という段階を分けられない。違反を直してからマージする必要がある。

### 5-11. PR本文の上書き事故

別セッションが `gh pr edit <番号> --body-file` を実行し、本PRの本文が上書きされた（2026-09-08 15:20頃）。GO記録が二重になった。

**対策候補**: PR番号を扱うコマンドの前に `gh pr view <番号> --json headRefName` で自セッションのブランチか確認する。guards.md §05-pr への記載は所有セッションの判断待ち。
