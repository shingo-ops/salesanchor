# 時刻の扱いのSSOT化（time-handling-ssot）— design

> この文書は何か（専門用語なしの1行）:
> 日本時間とUTCの取り違えを、人の注意ではなく機械で止めるための設計。

- 対象ADR: ADR-151（バックエンド全域で「今日」の基準を JST に統一）
- recon: docs/handoff/time-handling-ssot/recon.md
- 起票日: 2026-09-08
- 区分: 既存の延長・修正（STANDARD-WORKFLOW §1.8）。新しい設計仕様書は作らない。

## 1. あるべき姿（PO自筆・2026-09-08）

内部はUTCで統一する。日本時間への変換は、入口と出口だけで行う。それ以外の場所では変換しない。

## 2. KGI（○×で測る・PO承認 2026-09-08）

判定は本番相当環境での実測。○×は一義。抽象語禁止。

| # | 合格条件 | 測り方 | 合格ライン |
|---|---|---|---|
| K1 | 時刻変換の正本が1か所に定まっている | `ZoneInfo("Asia/Tokyo")` の定義箇所数（backend/app 配下） | 1 |
| K2 | 取り込みの3か所が正本経由になっている | `tcg_line_import_svc.py` と `tcg_line_import.py` に残る、正本を通らない時刻変換の数 | 0 |
| K3 | 非推奨APIが残っていない | `utcnow()` の出現数（backend/app 配下） | 0 |
| K4 | 誤りを機械で止める検査が動いている | 時刻検査テストが存在し CI で実行される | 在る=1 |
| K5 | 入口から出口までの結果が保証されている | 境界テストの本数（日本時間の入力→UTC保存→JST表示を検証） | 1本以上 |

KPI: 達成KGI数 ◯/5

## 3. design（技術How）

### 3-1. 変換の経路を1本にする

`backend/app/services/time.py` を時刻の正本とし、次の2関数を追加する。

- 日本時間の文字列を受け取り、UTC の aware datetime を返す関数
- UTC の aware datetime を受け取り、日本時間の表示用文字列を返す関数

既存の `JST = ZoneInfo("Asia/Tokyo")`（`time.py:26`）を唯一の定義とし、`goals.py:41`・`analytics.py:34`・`quotes.py:20` の `_JST` 重複を、この import に置き換える。

### 3-2. 取り込みの3か所を正本経由にする

| 箇所 | 現状 | 変更後 |
|---|---|---|
| `tcg_line_import_svc.py:433-435` | `strptime` 直後に `.replace(tzinfo=timezone.utc)` | 正本の変換関数を通す（日本時間として解釈しUTCへ変換） |
| `tcg_line_import_svc.py:367-372` | UTC起点の文字列と日本時間文字列を文字列比較 | 両辺を aware datetime に揃えて比較する |
| `tcg_line_import.py:156` | `created_at AT TIME ZONE 'UTC'` | `AT TIME ZONE` を外し、`timestamptz` のまま `isoformat()` で返す |

`tcg_line_import.py:156` の変更により、APIの返す文字列にオフセットが付く。フロントエンドは `toLocaleString` で表示しているため、オフセット付きの値を正しく日本時間で描画する。

### 3-3. 静的検査を作る

`backend/tests/test_time_handling.py` を新設する。方式は `backend/tests/test_tcg_schema_qualification.py`（148行）と同じく、ソースを正規表現で読む静的検査とする。DB接続を要さず、既存の pytest 環境で動く。

規則は精度で2段に分ける。

停止させる規則（精度が高い・書き方そのものが常に誤り）

| 規則 | 検出対象 | 現在の違反数 |
|---|---|---|
| T1 | `utcnow()` の使用 | 4 |
| T2 | `strptime` または `fromisoformat` の直後に、`tzinfo is None` の確認なしで `.replace(tzinfo=` を呼ぶ形 | 1 |
| T3 | `AT TIME ZONE 'UTC'`（印を剥がす形） | 1 |

警告にとどめる規則（文脈依存・誤検知が多い）

| 規則 | 検出対象 | 備考 |
|---|---|---|
| T4 | `ZoneInfo("Asia/Tokyo")` の `time.py` 以外での定義 | K1 達成後は 0 になる |
| T5 | `datetime.now(timezone.utc)` の結果を文字列に整形して比較に使う形 | 正当な用途が多い |

T2 の判定基準は recon §6-1 の実測に基づく。安全な15箇所はいずれも直前に `if 値.tzinfo is None:` の確認があり、危険な1箇所のみ確認がない。

### 3-4. 境界テストを作る

日本時間の入力が、UTCで保存され、日本時間で表示されることを、値で検証する。

例: LINEエクスポート形式の `2026/09/08 08:04` を取り込むと、`source_messages.received_at` が `2026-09-07 23:04:00+00` になる。

### 3-5. テスト環境のタイムゾーンを変える

CI のテスト実行を、UTC 以外のタイムゾーンでも1回走らせる。現在の CI は単一タイムゾーンであり、これが誤りを隠していた（recon §5-2）。

## 4. 導入順序（この順を守る）

1. 検査を作る（CIに接続しない状態で）
2. 既存の違反6件を直す（T1: 4件、T2: 1件、T3: 1件）
3. 検査をCIに接続する

逆順にすると全PRが赤になる。この順序は tcg-keyword-quality の design.md で確立された教訓による。

## 5. 弊害・トレードオフ（空欄不可）

- `tcg_line_import.py:156` の変更により、APIの返す日時文字列の形式が変わる。フロントエンドが古い形式を前提にしていた場合、表示が壊れる可能性がある。フロントエンドの実装を確認してから変更する。
- `_JST` の3重複解消は、`goals.py`・`analytics.py`・`quotes.py` に触る。いずれも今回の不具合とは別の場所であり、変更の必要がないコードに手を入れることになる。動作は変わらないが、レビュー範囲が広がる。
- T2 の検査は正規表現による構文照合であり、`strptime` と `.replace(tzinfo=` の間に複数行が挟まる書き方は検出できない。完全ではない。
- 検査規則を追加すると、正当な理由で違反せざるを得ない箇所が将来出る。ADR-144 の `ui-allow` と同じく、理由と番号を添えた許可の印を用意する必要がある。理由なしの例外は認めない。
- テストを複数のタイムゾーンで走らせると、CI の実行時間が増える。

## 6. 外部・過去事例

### 6-1. 不具合の分布は実測されている

Tiwari ら "It's About Time: An Empirical Study of Date and Time Bugs in Open-Source Python Software"（MSR 2025、カーネギーメロン大学ほか）が、Python製オープンソース102プロジェクトの151件の日時バグを手作業で分類している。

- 時刻帯に関わるものが 53.6%（最大の要因）
- datetime の構築時の誤りが 58.9%
- 根本原因の最大は naive な datetime の誤用 27.8%、次いでタイムゾーン情報の欠落 13.9%、非推奨API 15.2%
- 修正の約82%が単一関数内に収まる
- 約60%は入力に関係なく最初の実行で症状が出る
- 深刻度と発見の難しさの相関は -0.11（深刻なバグほど見つけにくいわけではない）

salesanchor の3か所は、上位3つの根本原因にそのまま該当する。特殊な失敗ではない。

### 6-2. 静的検査の精度は規則の種類で桁が違う

同論文が CodeQL で1000リポジトリを検査した結果。

| 規則 | 検出数 | 本物 | 精度 |
|---|---|---|---|
| 非推奨API | 617 | 全件 | 100% |
| 固定オフセットのタイムゾーン | 23 | 1 | 4% |
| 日付要素の部分置換 | 37 | 2 | 5% |

論文の結論は、パターン照合は「コードの臭い」を見つけられるが、本物と誤検知の区別には追加の文脈が要る、というもの。

本設計で規則を停止用と警告用に分けるのは、この実測に基づく。

### 6-3. 既製の道具

Ruff に flake8-datetimez 由来の DTZ 規則群が存在する（DTZ001: タイムゾーン未指定の datetime 生成、DTZ002: `today()` の使用 など）。T1 相当は既製品で代替できる可能性がある。

time_unifier（PyPI）は、内部UTC・境界でのみゾーン付き・naive禁止・暗黙変換禁止を掲げた専用パッケージ。本設計のあるべき姿と一致する。この方針が定石であることの裏付け。

### 6-4. 導入の失敗要因

RuboCop の `.rubocop_todo.yml`（既存違反を除外して新規のみ止める仕組み）の運用で記録されている失敗。違反数が閾値（既定15件）を超えると、その規則ごと無効化される。既存違反が多いという理由で新しいコードまで検査されなくなる。

対策として、除外リストに関係なく全ファイルで有効にする規則群を分ける方式がある。本設計の「停止させる規則」がこれにあたる。

GitLab は timezone に関する静的検査の導入時、新規の使用のみを止め、既存違反の修正は別課題として追跡する手順を採っている。§4 の導入順序と同じ形。

### 6-5. 型で防ぐ方式（本設計では採らない）

whenever および heliclockter は、aware と naive を別々の型にすることで混同を型エラーにする。検出ではなく、書けなくする方式。

本設計で採らない理由: 既存コードの全面書き換えを伴い、今回の6箇所の修正に対して規模が釣り合わない。将来の検討事項として記録する。

### 6-6. 見つからなかったもの

静的検査を導入した組織の、導入前後の不具合率の定量データは見つからなかった。得られたのは不具合の分布、検査規則の精度、導入手順の事例であり、効果の追跡データは公開されていない。

## 7. 受入基準

| 基準 | 検証方法 |
|---|---|
| `ZoneInfo("Asia/Tokyo")` の定義が1箇所 | `grep -rn 'ZoneInfo("Asia/Tokyo")' backend/app/` の件数が1 |
| `utcnow()` が0件 | `grep -rn "utcnow()" backend/app/` の件数が0 |
| 取り込みの3か所が正本経由 | 該当ファイルの diff で、正本の import と関数呼び出しを確認 |
| 静的検査が動く | `pytest backend/tests/test_time_handling.py` が緑 |
| 境界テストが動く | 日本時間の入力に対し、期待するUTC値が保存されることをテストで確認 |
| 取り込み幅の表示と実測が一致 | 画面で24を指定し、`import_jobs.window_start` が実行時刻の24時間前になる |
| 画面表示が日本時間 | 取り込み履歴の日時が、実際の操作時刻と一致する |

## 8. 維持の仕組み

- 守り手1: `backend/tests/test_time_handling.py` が、停止規則T1〜T3の違反を CI で止める。
- 守り手2: 境界テストが、書き方に関係なく結果の誤りを止める。
- 守り手3: CI をUTC以外のタイムゾーンでも実行し、単一タイムゾーン環境が誤りを隠す状態を解消する。
- 未確立（正直な明記）: 警告規則T4・T5は人が読む。機械強制はしない。誤検知が多いため。

## 9. 接触面分析（6面走査）

- 人: 取り込み画面の操作者。表示される日時が9時間ずれている状態が解消される。手順の変更はない。
- エージェント: 実装役が時刻を扱うコードを書く際、正本経由が必須になる。executor-checklist への追記は不要（CI で止まるため）。並行セッションへの周知は、guards.md 所有セッションと協議済み（recon §10）。
- 機械: CI に検査テストが1本増える。`migration-full-dryrun` には影響しない。DB migration は発生しない。
- データ: tenant_004 の既存 `source_messages.received_at` に、9時間ずれた値が保存されている可能性がある。過去データの補正は本設計の範囲外とし、別途判断する。
- 本番: バックエンドのデプロイが必要。DB スキーマ変更はなし。
- 外部: 配信先のGoogleスプレッドシート（tcg-client-viewer）。`tcg_distribution_svc.py:210` は既に `AT TIME ZONE 'Asia/Tokyo'` で正しく変換しており、本設計では触らない。

## 10. 範囲外（このテーマで扱わない）

- 過去データの補正。既に保存された9時間ずれの値をどうするかは別途判断する。
- フロントエンド48ファイルの日時整形の共通化。今回は取り込み画面のみ。
- 型で防ぐ方式への移行（§6-5）。
- 2026-09-08 02:01 以降の投稿が反映されなかった理由（recon §8）。時刻の誤りだけでは説明がつかず、別途調査を要する。
