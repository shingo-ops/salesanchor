## 1. 目的（KGI）
- Gemini の役割を「商品ブロックの行番号と、価格・数量の文字」だけに絞る。
- 商品名・単位・状態・ステータス・発送は、システムが原文の行と本番のマスタから取る。
- 比較試験の道具（prompt_ab）の中だけで動かし、正解表と比べて v9 より良いかを数字で確かめる。
- 本番の解析の経路は変えない。

## 2. 現在地（事実）
- 正解表と本番のコード・マスタを使った試算（費用0円、社外秘の記録は手元のみ）
  - 状態・単位を原文の行から取った場合、正解と同じ結果：162/162件。
  - 発送を原文の行から取った場合、正解と同じ：164/164件。正解の行からの切り出し：48/48件。
  - 商品名を見出しの行から取った場合、正解と同じ：157/164件。
    - 同じ商品を指すもの：4件。
    - 別の決まりが要るもの：2件（価格の行の中の「Vol.2」、前の件の行にしか名前が無い「OP-14 → カートン」）。
- trial1（PR #3967、11投稿）で、指示書の決まりにより、その件だけの行が範囲の外に置かれた件は 31件 → 0件。冒頭・末尾の混入は0件。
- trial1 で分かった受け取りの問題
  - 同じ見出しの複数件にかかる行（【9/28発送】）の値を、持ち主の確認が空にした（8件）。
  - 見出しのすぐ上の行を範囲に入れた件を、見出しと重なるとして捨てた（3件）。
  - 原因：範囲が「連続した行」で、見出し・共有の行と重ねられない型だから。
- 1つの行に価格が2つある件：3,696件中3件。どれも「セット価格／1個あたり価格」。
- 今のシステムの判定の材料（origin/main:backend/app/services/extraction_shadow_svc.py:265-317）
  - 単位・状態・ステータスは Gemini の写しを使う。
  - 発送・商品照合・価格数量の確認は、原文のブロックを使う。

## 3. 変更
### 3-1. Gemini に出させるもの（新しい型 V10_RESPONSE_SCHEMA）
- 件ごとに、次の8つだけを出させる。

| 欄 | 型 | 中身 |
|---|---|---|
| price | 文字 | 価格の文字をそのまま。無ければ "none"。1行に価格が2つある（セット価格／1個あたり）ときは、両方を原文のまま「／」でつなぐ |
| quantity | 文字 | 数量の文字をそのまま（残り・在庫の言葉を含めてよい）。無ければ "none" |
| price_line | 整数 | 価格（無ければ「完売」などの言葉）が書かれた行 |
| item_lines | 整数の配列 | その件だけの行。price_line を必ず含む。価格の上下のメモ、見出しのすぐ上のその件だけの行も含める |
| heading_lines | 整数の配列 | 商品名の見出しの行。無ければ空の配列。同じ見出しの複数件で同じ行を指してよい |
| shared_lines | 整数の配列 | 同じ見出しの下の全部の件にかかる行（例：見出しと最初の価格の行の間の【9/28発送】）。無ければ空の配列 |
| name_lines | 整数の配列 | 商品名が書かれている行。ふつうは見出しの行。名前が価格の行にもあれば、その行も入れる。前の件の行にしか名前が無いときは、その行を入れる |

- 配列にするので、見出し・共有の行と、その件だけの行が連続していなくてよい（trial1 の3件の問題を型でなくす）。
- 商品名・単位・状態・発送は Gemini に写させない。

### 3-2. 受け取り（parse_v10_response）
- 件を捨てる誤り（errors に理由を残す）
  - JSON として読めない／items が配列でない。
  - 欄が足りない、型が違う。
  - 行番号が 1〜行数の外。
  - item_lines が空、または price_line が item_lines に無い。
  - 2つ以上の件の item_lines が同じ行を含む（先に出た件を残し、後の件を捨てる）。
  - ある件の heading_lines・shared_lines が、ほかの件の item_lines と重なる。
- 認めるもの
  - heading_lines・shared_lines は、複数の件で同じ行を指してよい。
  - name_lines は、自分の item_lines・heading_lines・shared_lines と、ほかの件の item_lines を指してよい（前の件の名前の引き継ぎ）。それ以外の行は誤りとして、その件の name_lines から外して残す。
- 冒頭・末尾の混入は、受け取りでは判定できない。正解表で測る（§5）。

### 3-3. システムが原文から取る（extract_v10_item、純粋関数）
- 材料（すべて原文の行。Gemini の文字は価格・数量だけ）
  - 件の行 = item_lines の行
  - ブロック = item_lines ＋ heading_lines ＋ shared_lines の行（行番号の順）
- 商品名：name_lines の行をつなぐ。
  - その行がどれかの件の price_line なら、その件について次を除き、残りを使う。
    - price の文字（最初の1か所）。
    - quantity の文字。ただし、単位・×・@ のすぐ隣にある1か所だけ。名前の中の数字（OP-14 の 14 など）は消さない。
    - quantity のすぐ後ろの単位の別名（1か所）。
    - 記号 @ ＠ ¥ ￥ と「円」。数字のすぐ隣の × x X。「残り」「在庫」「在庫数」と、そのすぐ後ろの数字・単位。
  - 前後の空白・記号（/ ／ : ： ×）を除く。
  - 根拠：費用0円の試算（見出しの無い件で、正解の名前と同じ 406/429件）。この試算で「数字をすべて消す」決まりは名前を壊したので使わない。
- 単位：件の行から、単位の別名（unit_alias_to_info、load_lookup_maps）を、長いものから探す。
  - 「数字の直後」、または「直後に価格（/ @ ¥ のあとに数字）が続く」位置にあるものだけを使う。
  - resolve_unit_v2 で canonical と区分を出す。無ければ none。
- 状態：resolve_condition_v2(raw_state=ブロックの文字, raw_product_name="", kubun=単位の区分, cond_entries, cond_canonical_to_uuid, raw_memo=ブロックの文字)。
- ステータス：resolve_status_v2(raw_state=ブロックの文字, status_entries, raw_memo=ブロックの文字)。
- 発送：件の行 → heading_lines → shared_lines の順に、「発送|出荷|入荷|発売|着」を含む最初の行を探す。
  - 括弧（( （ 【 [）の中にその言葉があり、括弧の外にも文字があるときは、括弧の中身を取る。
  - 価格の行なら、価格より後ろの文字を取る。
  - それ以外は、行の全体を取る。
  - 見つからなければ none。
- 価格・数量：resolve_price_quantity(block=件の行の文字, gemini_price, gemini_quantity, unit_aliases=set(unit_alias_to_info), order=order_from_pattern(仕入元の並び), gemini_product_name=システムの商品名)。今と同じ関数で、確認の理由（reasons）も残す。
- マスタの読み込みは、今の関数（load_condition_entries・load_status_master・load_lookup_maps）を1回の実行で1回だけ呼ぶ。新しい表や写しは作らない（SSOT）。

### 3-4. 指示書 raw_copy_v10.txt
- 本文は設計者（Opus）が書いたものを、そのまま置く（実装担当は1文字も変えない。cmp で一致を確かめる）。
- trial1 の「商品ブロック」と「同じ見出しの下に価格の行が複数あるとき」の決まりを、そのまま使う。
- 例の46行のうち、試験に使う30投稿（正解表の19投稿＋試験の11投稿）の原文と同じ文の行は「シュリ無し」「発送日相談」「完売」の3行だけ（短い一般的な言葉）。
- 出させるのは §3-1 の8つだけ。商品名・単位・状態・発送は写さないと明記する。
- 例は trial1 の例を v10 の型に書き換える。
- 次の例を足す。
  - 価格の行に名前の続きがある形（Vol.1／Vol.2）。
  - 名前が前の件の行にしかない形（OP-14 → カートン）。
- 文は試験の投稿と同じにしない。

### 3-5. prompt_ab
- --config に v10 を足す。
  - 指示書は raw_copy_v10.txt、型は V10_RESPONSE_SCHEMA。
  - 呼び出しは call_gemini_raw_copy_v8(response_schema=V10_RESPONSE_SCHEMA) をそのまま使う。
  - --prompt-name は v9 のまま（v10 では使えない）。
- v10 のときだけ、実行の最初にマスタを読む（読み取りのみ）。
- JSONL の行に "v10_items" を足す。中身は、件ごとの行番号・price・quantity と、システムが取った値。
  - 値：name・unit・unit_kubun・condition・condition_basis・status・ship・price_normalized・quantity_normalized・price_reasons
  - 採点に使う。本番の表には書かない。
- 既存の v7・v8・v9 の動きは変えない。

## 5. 試験と受入条件
### 5-1. 試験（マージと本番反映の後）
- A：試験の11投稿 × 2回（揺れを見る）
- B：正解表の19投稿（001〜019）× 1回
- C：残りの T2・T3・T4 の投稿 × 1回。v9 と件数・価格・数量を比べる（悪くなっていないか）
- 費用の上限：合計 2.5 USD
- 正解表と同じ採点の決まりで、v9 と比べる（社外秘の記録は手元のみ）。

### 5-2. 受入条件
| 基準 | 検証方法 |
|---|---|
| v7・v8・v9 の動きが変わらない | 既存のテストがすべて通る |
| v10 の受け取りの誤りの判定（§3-2）が決まりどおり | test_gemini_raw_copy_v10.py（重なり・範囲外・price_line なし・共有の行の重複を認める・name_lines の引き継ぎ） |
| システムの取り出し（§3-3）が決まりどおり | 純粋関数のテスト（Vol.2、OP-14→カートン、【9/28発送】の共有、見出しのすぐ上の行、価格の下の発送の行、状態の行、単位） |
| prompt_ab の v10 が JSONL に v10_items を書き、v9 には書かない | test_prompt_ab.py |
| 本番の経路が変わらない | 差分のファイルが §3 のものと tests・docs・台帳だけ |
| CI が緑 | gh pr checks |
| 試験で、正解の価格の行を含む件が1件ずつある（抜け・重複なし） | 採点（A・B） |
| 試験で、発送・状態・単位・商品名の正答率が v9 以上 | 採点（A・B） |
| 冒頭・末尾の行がどの件の item_lines・heading_lines・shared_lines にも入らない | 採点（A・B） |
