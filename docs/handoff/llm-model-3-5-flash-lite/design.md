## 2026-09-11 在庫補助解析を2.5 Flash-Liteへ変更

PO原文: 「変更理由も記録して2.5 Flash-Lite に変更をしてくれ」。対象はinventory_parser_llm.pyの既定モデル。翻訳とTCG抽出は別用途であり変更しない。従前の3.5への変更理由は404障害対応で、在庫精度の比較改善ではない。

Why: PO報告「レガシー時代は2.5 flash liteを使っていたが精度は確保できていた」を採用判断に用いる。報告の正解データ・件数・現行処理での再現は未確認。公式通常単価は入力/出力100万token当たり2.5 Lite=$0.10/$0.40、3.5 Lite=$0.30/$2.50。同token量なら入力約67%・出力84%削減。実際の請求額削減率は未計測。出典 https://ai.google.dev/gemini-api/docs/pricing （2026-09-11確認）。外部導入事例は不要。自社の用途実績と費用、現行コードを根拠とし、一般ベンチマークを在庫精度の保証に転用しない。

実装契約: 既定引数と結果データ型の既定値をgemini-2.5-flash-liteへ変更。既存のモデル指定引数、JSON出力構造、prompt、認証、予算制御は維持。費用表に2.5 Liteは既存登録済み。本番呼出側は結果のmodelをrecord_costへ渡す。共有DEFAULT_MODELは変更せず、実APIテストの概算にも結果modelを明示する。

| 基準 | 検証方法 |
|------|---------|
| 既定呼出と結果modelが2.5 Lite | 既存SDKモック試験のモデル指定と返値を照合 |
| 2.5 Liteの単価で計算 | 100万入力+100万出力がDecimal 0.50となることを試験 |
| 他用途と出力形式を維持 | 差分照合と既存LLM parser / budget試験 |
| 実APIが利用できる | CI実API試験。skip/残高不足/404は精度検証成功に数えない |

リスク: 同じAPIキーで2.5 Liteが利用可能か未確認。過去の2.5 Flashの404をLiteの提供終了とは断定しない。API失敗時の既存ルール処理への戻りを維持。現在のデータでの精度・応答時間・消費token数は未測定。提供可否、課金状態、精度は別の判定項目。必要なら前の3.5既定へ戻すPRを作成する。

代替案: 3.5維持は現状の費用を維持する。3.1は安くなるが当用途で2.5より優れる比較実績がない。今回はPOの2.5採用判断に従う。

同一AIによる自己審査: APPROVE（限定モデル変更の実装設計）。既定値2箇所、料金伝達、検証箇所が明確。現行在庫精度の合格や本番反映承認ではない。参照ADR-110と既存本書のうち在庫補助解析のみ本追補で更新する。守り手は既存parser/budgetテストと本recon。新CIや例外を増設しない。
