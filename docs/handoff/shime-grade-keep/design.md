## 1. 目的と成功条件

- 目的: 仕入元が同じ商品を品質違いで2行出し、片方だけを「〆」たとき、もう片方の在庫を売り切れ扱いにしない。今は両方が外に出なくなる（recon §1）。
- 利用者に見える変化: 在庫の画面と配信で、〆られていない品質の在庫が残る。
- 変えないもの:
  - 商品×状態の組ごとに最新の投稿の行が現行、という規則（ADR-1032 の守ること）。
  - 状態の辞書のほかの語。

| 基準 | 検証方法 |
|---|---|

## 2. 方針と、採らなかった案

- 採る: 状態の辞書に、品質の違いを表す言葉を足す（便1）。
  - 仕組みには手を入れない。状態の違いとして読ませれば、今の「組ごとに最新」の規則のままで、〆は自分の状態だけを閉じる（recon §2 の 1〜5・8）。
  - 影響は、直近180日で今回の2行だけ（recon §3）。
- 採らない案 A: 状態とは別に「品質の違い」を持たせ、現行の行を (商品, 状態, 品質) で決める。
  - 現行の決め方・配信・在庫の画面が全部変わる。ADR-1032 の守ることを変える大きな変更になる。
  - 同じ種類は直近30日で1組（recon §3）で、変更の大きさに見合わない。
- 採らない案 B: 〆の文に辞書に無い言葉が残り、前の投稿に同じ組の行が2行以上あるとき、〆を要確認にする。
  - 要確認の行も現行の決め方に入るので、A品は外れたまま（recon §2-6）。
  - 隠れる害は同じで、要確認が増えるだけ。
- 同じ種類の再発は、仕組みで防ぐ代わりに見つける（K4・K5）。新しい言葉が出たら、便1 と同じ手順で辞書に足す。

## 3. 変更の内容

### 3-1. 便1 状態の辞書に「切れ込み」を足す（本番のマスタの変更。コードは触らない）
- 対象: public.line_conditions の id 13 の1行。search_kw の末尾に「,切れ込み」を1語足す。
  - id 13 は、code CN0002・canonical Damaged case・app_kubun 箱系大・value_rank 2。
  - 足す先は PO が選んだ（2026-11-14「1」、§5）。
- 箱（Sealed box 系）には足さない。直近180日に、箱の行で「切れ込み」は無い（recon §3）。
- 手順は前例 `docs/handoff/condition-unit-booklet/data/` と同じ形の SQL で、`docs/handoff/shime-grade-keep/data/` に置く。
  - リポジトリの `.gitignore` は `*.sql` を外している（`.gitignore:35`）。前例と同じく `git add -f` で記録する。
  - 01_precheck: 対象の行の今の値を出し、「切れ込み」がどの行にも無いことを確かめる。直近180日の原文で、この語を含む行を数える（K2）。
  - 02_apply: 対象の行の search_kw の末尾に `,切れ込み` を足す。
    - 終わり方は `-v end=ROLLBACK|COMMIT` で必ず指定する。
    - 条件は、id・code・canonical がすべて合い、まだどの行にもこの語が無いこと。
    - 変わった行数が1でなければ 1/0 で失敗し、COMMIT に進まない。
  - 03_verify: 「切れ込み」を含む辞書の行が id 13 だけで、末尾が `,切れ込み` であることを確かめる。
  - 04_rollback: id 13 の末尾の `,切れ込み` だけを外す。変わった行数が1でなければ失敗する。
  - 05_detect: K4・K5 の見張りの問い合わせ。数えない物が3つある（`data/README.md`）。
  - 06_k1_posts: K1 の実際の投稿での確認。
- 2026-11-14 の 01_precheck の結果（作業記録 precheck_bin1.txt）:
  - 対象の行は1行、app_kubun は箱系大。
  - 「切れ込み」を含む辞書の行は0。
  - 直近180日の原文で「切れ込み」を含む行は2。
- 再起動・再解析は要らない。辞書は解析のたびに読み直されるため。
  - 解析の入口 `backend/app/services/line_analysis_v102_svc.py:1609` が、毎回 `load_v102_masters`（同 `:219`）でマスタを読む。
  - その中の `load_condition_entries`（`backend/app/services/tcg_analyzer_svc.py:662`）は `public.conditions` を読み、覚えておく仕組みは無い。
  - `public.conditions` は `public.line_conditions` の VIEW（`migrations/20261017_120000_line_conditions_value_rank.sql:47`）。
- 実行は設計審査の合格のあと。Opus が PO の委任（PO 合意済みの本番のデータの変更）に基づいて流す。
  - 順番は 01_precheck（K2）→ 02_apply の DRY-RUN → COMMIT → 03_verify。

### 3-2. 便2 今回の A品の在庫を戻す → 不要（2026-11-14 取りやめ）
- 仕入元が 11/14 07:08 JST の新しい投稿で、このカートンを「残1・175,000円」で出した。品質の書き分けは無い。
- その行が (420436, Case) の最新として現行になっている（作業記録 pre1.txt・raw_d.txt）。

- 過去の解析結果は再解析しない。ADR-1032 の見張りで、古い投稿の行は戻らない（recon §2-7）。

### 3-3. 便3 → 取りやめ（2026-11-15）
- 初めの案では、毎朝の〆の点検の手順に 2d を足すつもりだった。取りやめた理由は2つ。
  - 点検は 2026-11-26 以降の回で止まる。根拠は、定期実行の指示文の手順4と、`docs/handoff/shime-box-all-states/design.md` §3-4。
  - 毎日足しても続かない。
- 代わりに、見張りの問い合わせ 05_detect をリポジトリに残し、K5 で1回数える。
- 11/26 までは、点検の手順2b の「消しすぎ」の種類で、毎日見つかる。

## 4. リスクと対処

| リスク | 対処 |
|---|---|
| 「切れ込み」がほかの文脈に当たる（例: 箱でない商品の説明） | 足す先はカートンの状態の行（app_kubun 箱系大）だけ。K2 で、適用の直前に件数を数え直す |
| 選んだ状態が仕事の上の扱いと違う | 足す先は PO が選んだ。04_rollback で語だけを外せる |
| 同じ件に別の状態の語も入っていて、価値の低い方が選ばれる（`backend/app/services/tcg_analyzer_svc.py:875-885`） | 今回の2行では、当たる状態は Damaged case の1つだけ（recon §2-8）。今後の投稿は K5 で見る |
| 同じ種類の別の言葉が出る | K5 で数え、便1 と同じ手順で足す |
| 11/26 で毎朝の点検が止まった後は、毎日の見張りが無い | 頻度は30日で1組（recon §3）。K5 の1回の数えで0なら、ここで終える。1組以上なら、続け方を PO に聞く |

## 5. PO に決めてもらうこと

- 決定済み（2026-11-14 PO「1」）: 「テープに切れ込みがある品（正規品保証つき）」は、カートンの傷み（Damaged case）として扱う。

## 6. 戻し方と測り方

- 戻し方: 便1 は 04_rollback（足した語だけを外す）。
- 測り方: §1 の K1〜K5。基準値は recon §3（180日で2行・30日で11組中1組）。

## 7. 維持の仕組み

- 11/26 までは、毎朝の〆の点検（手順2b の「消しすぎ」）が当日に数える。
- 見張りの問い合わせ 05_detect は、K5 のあとも同じ形で流せる。
- 状態の辞書の変更は、前例と同じ形の SQL で残し、戻せる形にする。

## 8. 外部事例

該当なし。社内の状態の辞書の語の不足で、外部の事例は判断の根拠にならない。今回の影響の大きさは、本番の実測（recon §3）で決めた。
