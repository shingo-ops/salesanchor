# 議事録: 公開見本を手本にした Sales Anchor の見直し（受信箱・カルテから）

状態（2026-10-28 時点）: リードをまとめる機能 = 設計審査済み・PO 承認済み（方式・置き場所・確かめ方）・実装は承認済みで未着手／受信箱とカルテの見た目 = 見本で相談中

記録者: Claude Opus（設計担当）。PO の発言は原文のまま引用する。PO の決定の行には PO の言葉を添える。それ以外は Opus の調査と提案で、決定ではない。

## 1. PO の願い（原文）

- 「クローンからコードや構造を参照してsalesanchorをブラッシュアップしたい、非エンジニアなので知識がないので評価はあなたにしてもらう、まず記録しながら進めたいので議事録のように記録を取って、受信箱はwhatsappやmetaの受信箱のクローンを参考にしてPCでもモバイルでも使いやすくしたい。」
- 「カルテだがどう構成するといい？…成約後のリピート顧客になったら商談情報はどう表示させるのが最適？忖度無しであなたの意見を聞きたい…またシステムやAIが自動で埋めたり出来る？」
- 「相手の国と販売形態と取扱商材は重要なので見えやすいところに置きたい」
- 「販売形態と取扱商材は複数選択される場合もあるが表示が崩れたり見えなくなったりしない？」
- 「カルテ側に既存顧客の特性を書くことは出来る？」（箱で買う・1回の量・シュリンクの有無・新作の予約量などを、DB の情報から誰が見ても分かるように）
- 「新作は発売日の何日前の発送を買うとか発売後に買うとか表示できる？」
- 「まだスプレッドシートで管理しているからSAアプリの本番にデータがないかも、DB構造も整備しつつ実現できるようにしてほしい、推測は禁止して事実確認を怠らずに確実性を重視して最も効果があり、現状把握の粒度が細く、精度が高いエビデンスを確立して安全に進めてくれ。また配線とDBのSSOTは遵守してデータを分散させることは禁止。フロントエンドのパーツもデザイントークンとデザインシステム を遵守して、金型登録のないハードコードを禁止する。推測で自身で判断したり不透明無まま進めることは禁止、分からないことは聞いてくれ。確立したなら進める。」
- 「ADRに定義した通りリードが親でそこに商談や顧客情報が紐づいて顧客情報にオーダー情報などが紐づく設計を考えている、salesforceはどうなっている？」
- 「私は1クライアントに1リード歯科発生しないため、リードを親にして成約した顧客にしか会社を作成しないのでリードを親にしている、salesforceは会社を親にしている意図が知りたい、それぞれの利点と弊害があれば知りたい」
- リードをまとめる機能についての原文は [lead-merge の ideal-state.md](../../specs/transaction-flow/lead-merge/ideal-state.md) に全部ある。
- 次の回の議題（PO 指定）: AI に会話を読ませてカルテを埋める件、メッセージの送信予約（日付と時刻・条件「予約時刻まで相手から受信がなければ送る」など・送る内容）。

## PO の決定（2026-10-29）

- 会話の中の画面（吹き出し・入力欄）は、Android 実機で測った本物の WhatsApp の値に揃える。取りかかるのはリード統合の後。足りない値は取りかかるときに測り足す。
- リードの番号はアプリ全体で画面に出さない。CSV の取り込み・書き出しのときだけ使う（PO 原文「全体でリード番号は表示しなくて良い、CSVの取り込みや吐き出しの時だけ使用する」）。調べた結果、画面に番号を出していたのはまとめる窓だけで、PR #4843 で消した。番号で検索して当たる仕組みは画面に何も出ないので残す（設計担当の判断）。担当割当の Discord 通知の書き方は PO の回答待ち。
- まとめる窓の確認画面は、番号なし・赤い文字の1行・スマホは縦に2つのボタンの形にした。PO は写真6枚を見て合格とした（PO 回答「1」）。

正式な決定記録: [ADR-1049](../../adr/ADR-1049-lead-merge-all-tables-and-fill-blanks.md)、仕様書: [lead-merge](../../specs/transaction-flow/lead-merge/README.md)

## 4. 確かめた事実

### 4-1 見本（クローン）の評価（Opus の評価）
- 受信箱の手本: chatwoot（enterprise/ 以外 MIT。機能が最多）を機能の手本に、zernio-dev/unified-inbox（MIT・React）を画面の手本に、FallenDeity/WhatsAppClone（MIT）をスマホの一覧と会話の切り替えの手本にする。
- 見本を使う決まり（Opus の判断）: MIT など自由に使える約束の見本だけコードを写してよく、写したら出典を残す。約束の無い見本と AGPL の見本は考え方だけ参考にする。鍵らしいファイルが公開されている見本は、そのファイルを開かない。
- 使わない見本: venu123143/whatsapp、lra8dev/WhatsApp-Clone、mercari-build-training、mercari-bot、invoify、react-invoice-generator、invoice-app、modern-erp-nextjs、logistics-dashboard。
- 請求→入金→仕入れ→発送→配送を本当に保存して動かす見本は 0/5。この流れは今の SA の方が進んでいる。

### 4-2 画面の大きさ（[evidence/size-compare.md](evidence/size-compare.md)。コードのクラスから読んだ値で、画面での実測ではない）
- SA の押す場所は、スマホ 44〜48px で、見本（32〜36px）より大きい。
- SA の文字は、吹き出し 16px で見本（14px）より大きい。カルテの値 13.6px は chatwoot（14px）より小さい。
- SA のスマホの入力欄の文字は 14.4px。zernio はスマホだけ 16px にしている。iPhone では 16px 未満の入力欄を押すと画面が拡大される（実機ではまだ確かめていない）。受信箱の見直しの回で扱う。
- Opus の判断: SA の大きさの決まった値（デザイントークン）は見本より押しやすい側にある。見本の HTML と本番がずれる原因は、見本の HTML が手で描いた大きさで、本物の部品とつながっていないこと。対策は「本物の画面の写真を見てから本番へ」と「数で自動検査」（lead-merge の KGI K7・K8）。

### 4-3 リードをまとめる機能（[evidence/lead-merge-review.md](evidence/lead-merge-review.md)。Fable 5.1 の独立評価。中の生出力の置き場所は一時フォルダで、今は残っていない）
- 本番 tenant_004（2026-10-28 22:18〜22:54 JST、読むだけ）: 統合の記録 0 件、リード 56 件、窓口の記録があるリード 4 件、会話の記録を持つリード 4 件。
- リード番号を持つ表は 13。今の統合が付け替えるのは 4。会話の記録が付いたリードを消す方にすると止まる。

### 4-4 売上の記録（本番を読むだけ、2026-10-28 21:49〜21:51 JST）
- tenant_004 の請求書・受注・発送の記録は 0 件。ほかの会社も請求書の行は合わせて 2 行。お客さまの特徴を数える元は、まだ SA の中に無い。
