# 設計 — 添付後のフォーカス移動

> この文書は何か（専門用語なしの1行）:
> 画像を付けたらすぐ Enter で送れるようにする設計。

対象ADR: ADR-091
recon: docs/handoff/inbox-attach-focus/recon.md
親テーマ: docs/specs/attachment-storage/README.md

## 1. あるべき姿

顧客とのやり取りに必要な操作が、少ない手数で終わる。

## 2. recon（実測）

docs/handoff/inbox-attach-focus/recon.md を参照。要点は次の3つ。

- Enter の処理は入力欄にしか付いていない。
- クリップボタンにフォーカスが残る。
- フォーカスを制御する処理が無い。

## 3. design（技術How）

入力欄への参照を作り、添付の直後にフォーカスを戻す。

ファイル選択とドラッグ&ドロップの両方で同じ処理を行う。

frontend/src/pages/inbox/useInboxState.ts は変更しない。

## 4. 外部・過去事例の参照と我々への応用

ボタンを押して開いたダイアログを閉じた後、
フォーカスがボタンに残るのはブラウザの既定の挙動である。

キーボードだけで操作する利用者にとって、
次に行う操作の場所へフォーカスを移すことは
アクセシビリティの指針で推奨されている。

添付の次に行うのは本文の入力か送信であり、
どちらも入力欄にフォーカスがあれば行える。

我々への応用: 隠した入力要素をボタン経由で操作する場合、
操作の完了後にフォーカスの行き先を明示的に決める。

## 5. 弊害・トレードオフ

- 弊害: 添付の直後に画面が自動でスクロールする場合がある。
  入力欄が画面外にあるときにフォーカスが移るためである。
- 弊害: 続けて2枚目を添付したい場合、
  クリップボタンへ戻る操作が1回増える。
  ただし添付は1枚までのため実害は小さい。
- トレードオフ: フォーカスの移動先を入力欄に固定する。
  送信ボタンに移す案もあるが、本文を書けなくなる。

## 6. 受入基準

| 基準 | 検証方法 |
|---|---|
| 参照を作っている | grep で textareaRef が4件 |
| 2箇所でフォーカスを戻す | grep で focus の呼び出しが2件 |
| 入力欄に参照を付けた | grep で ref の指定が1件 |
| ドラッグ&ドロップを壊していない | grep で acceptDroppedFile が2件以上 |
| オーバーレイを壊していない | grep で inbox-drop-overlay が2件 |
| useInboxState を変更していない | git diff に当該ファイルが現れない |
| 実環境で動く | 添付後に Enter を押して送信されることを確認する |

## 7. 維持の仕組み

- 守り手: 人手で守る
- 理由: フォーカスの移動は実ブラウザでの操作を伴い、
  現在のテスト基盤では再現できない。
- 対象: 添付後の Enter で送信されなくなること。
- 検知方法: PO による実機確認。添付して Enter を押す。
