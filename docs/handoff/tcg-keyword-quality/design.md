## 技術 How・KPI

### KPI
- 停止規則の現行違反: R1=1・R3=1・R4=8組・R6=1 → データ migration 後に **0**
- 検査が接続された後、規則違反の migration がマージされた件数: **0**（接続後の全期間）
- 達成KGI数: 受け入れ基準 8/8

### 規則（7本・確定）

判定の区分:
- **停止**: 該当があれば migration はマージできない（検査が exit 1）
- **警告**: 一覧を出すが止めない。PR 本文に一覧を貼り、PO が○を出せば通る
- **情報**: 表示のみ

対象: is_active=TRUE の商品のみ（照合が読む範囲と同じ）。正規化は `normalize_en`（全角→半角・小文字）を通してから判定する。

| # | 規則 | 区分 | 判定の条件 | 根拠（recon file:line） |
|---|---|---|---|---|
| R1 | 有効商品に検索語が1つ以上ある | 停止 | 検索語0件の有効商品が存在する | :276 検索語が空の商品は候補にならない |
| R2 | 日本語混じりの語は短すぎない | 1文字=停止 / 2文字=警告 | 空白で分割した各トークンの長さで判定。英数字のみの語は対象外 | :238 部分一致 / :256 英数字は単語境界 |
| R3 | 同じ語を2商品以上に登録しない | 停止 | 正規化後の語が2つ以上の有効商品に存在する | :346 候補2つ以上は要確認 |
| R4 | 除外語が自商品の検索語を殺さない | 停止 | 除外語が、同じ商品のいずれかの検索語（正規化後）に `match_one_kw` で当たる | :276 除外が先 |
| R5 | 別商品の語に相乗りする語は除外語で守る | 警告 | Aの検索語がBの検索語に `match_one_kw` で当たり、かつAの除外語のどれもBのその検索語に当たらない | :346 相乗りは両方を要確認に落とす |
| R6 | 同一商品内で同じ語を二重登録しない | 停止 | 正規化後に同じ語が同一商品に2つ以上 | UNIQUE 制約は正規化前の文字列にしか効かない |
| R7 | 空白を含む日本語混じりの語は AND 分解される | 情報 | 該当語を一覧表示。各トークンに R2 を適用 | :238 |

### R4 の運用ルール（登録者向け・規則の背景）
除外語は「自分と紛らわしい他の商品を書く欄」ではない。
正しい使い方: 紛らわしい方（例: 通常版）に、**自分と相手を区別する語**（例: `プロモ`）を除外語として書く。
recon R4 の8組は、この逆の使い方で登録されており、5商品の検索語が実際に死んでいる。

### 判断を PO に委ねる現行違反（規則ではなく、データの直し方）
| 該当 | 直し方の候補 | 決める人 |
|---|---|---|
| PM0146 検索語0件 | 検索語を追加する migration | PO（語の選定） |
| `AR` の3商品 | 3商品から `AR` を外し、区別できる語に置き換える | PO（3商品の違いを知る人） |

| `枕`（1文字） | 別の語に置き換えるか、PO が明示的に許可 | PO |

### 技術選択
- 検査の本体は純関数 `backend/app/services/tcg_keyword_lint.py`（新規）。入力は `load_product_keywords` が返すのと同じ辞書2つ（search_kw / exclude_kw）と有効商品コードの集合。出力は `{rule: [violation]}` と終了コード。（理由: DB なしで単体テストでき、照合の意味を既存関数と共有できる）
- 照合は既存の `normalize_en` / `match_one_kw` を import して使う。再実装しない。（理由: 独自実装はコードとずれた瞬間に検査が嘘をつく）
- 実行入口 `backend/scripts/check_keyword_quality.py`（新規）: DB から `load_product_keywords(session)` で読み、純関数に渡し、結果を表示して終了コードを返す。書き込みは一切しない。
- 単体テスト `backend/tests/test_tcg_keyword_lint.py`（新規）: 辞書を直接組んで7規則を1件ずつ検証。
- 出力に含めるのは商品コードと語のみ。商品名・仕入元・原文は出さない。

### 出力の形（例）
```
R1 STOP  検索語0件の有効商品: 1件  [PM0146]
R2 STOP  1文字の日本語トークン: 1件  [PM0201:枕]
R2 WARN  2文字の日本語トークン: 12件  [PM0054:仰天, ...]
R3 STOP  複数商品に同じ語: 1語  [ar → PM0007,PM0008,PM0009]
R4 STOP  除外語が自商品の検索語を殺す: 8組  [PM0003: 'RR バルク' kills 'RRR バルク', ...]
R5 WARN  除外語で守られていない相乗り: N組  [...]
R6 STOP  同一商品内の重複: 1組  [PM0069: 切手Box / 切手BOX]
R7 INFO  空白を含む日本語語: 163件
RESULT: STOP=4 rules, exit 1
```

### 検査を動かす場所（確定・recon「CI の migration ジョブ」による）
| 案 | 場所 | 成立条件（実測） | 長所 | 短所 |
|---|---|---|---|---|
| **A（採用）** | `.github/workflows/migration-test.yml` のジョブ `migration-full-dryrun`（687行〜）の**直後**に1ステップ追加 | 同ジョブが `run_all_migrations.sh` 188本を全件流す（実読済み）。キーワードは migration でしか変わらないので、変更のある PR では必ず起動する | PR の段階で止まる。本番に触れない。データは CI の一時DBにしか無い | migrations に変更が無い PR では走らない（＝キーワードが変わらない PR なので問題ない） |
| B | 物差しの関所（blue-green Step 3〜4 の間・bench_ro） | precision-benchmark 段階4の実装後 | サーバー内で完結 | マージ後にしか止まらない |
| 方針 | **A を先に、B は物差し段階4で** | | A で早く止め、B で最後に確認 | — |

注意（実測）: 集約ジョブ `migration-test` は skipping を pass 扱いにする。PR #3323（文書のみ）の「マイグレーションSQL 実行テスト（実DB）pass」は実行ではなく skipping だった。本検査も migrations 変更の無い PR では走らないことを、受け入れ基準の読み方として明記する。

### 導入順序（現行違反があるうちは検査が常に赤になるため）
1. 検査コードと単体テストを入れる（CI/関所には**まだ接続しない**）
2. 現行違反を直すデータ migration を規則ごとに1本ずつ入れる（PO 判断のあるものは判断後）
3. 現行DBで検査が exit 0 になったことを確認してから、CI/関所に接続する

## 弊害・トレードオフ

- R2 の閾値は経験則のリスク（2文字の日本語は拡張パックの略称で必要な語がある）→ 対策: 停止ではなく警告にし、PO の○で通す。
- R5 が警告止まりで、68組を全部除外語で守るのは手間 → 対策: 相乗りする商品数が多い語（`ar`×3・`vmax`・`vol.1`）から優先。
- 検査は登録データしか見ず、原文にどう書かれるかは見ない → 対策: 良い語の最終判断は物差し（precision-benchmark）の差分行数で行う。
- 現行違反を直すまで検査が赤で、順序を違えると全PRが赤になる → 対策: 導入順序を守る（上記）。
- UNIQUE 制約と正規化のずれ（`切手Box`/`切手BOX` を DB は別物と見る）→ 対策: 本設計では DB 制約を変えない（既存 migration の再実行に影響するため）。R6 で検出する。
- 警告の○を機械が覚える仕組み（許可リスト）が無い → 対策: 本設計に含めない（含めるとリポジトリに語のリストが増える）。必要なら次の改版。
- 警告の○は PO の手間になる → 対策: 一覧を PR 本文に貼る形にし、確認を1か所に集める。
