# design — 予定の画面に Google カレンダーのつなぐボタンを戻す

recon: docs/handoff/schedule-gcal-connect/recon.md ／ 決定の記録: ADR-1057 ／ 関連: ADR-1056（秘書）・ADR-1018（RLS）・ADR-027（i18n）・ADR-144（UI 金型）・ADR-067（デザイントークン）
状態: 設計担当（Opus）作成・自己審査済み。PO 決定 2026-11-02「2」（先に Google をつなぐ）・「1」（ボタンを戻す・本番まで）・「1」（PO が入れた予定だけ送る）。

## 1. 目的（PO の言葉）
秘書で入れた予定を、しんごさんの Google カレンダーでも見られるようにする。

## 2. 成功条件
| 基準 | 検証方法 |
|---|---|
| K1 オーナー・システム管理者にだけ、予定の画面の右上に「Googleカレンダー連携」ボタンが出る | 画面の試験（管理者で出る／そうでない人で出ない）＋本番で PO の画面に出る |
| K2 押すと Google のログインに進み、終わると予定の画面に戻って「接続が完了しました」が出る。ボタンは「✔︎連携済」になり押せない | PO が本番で 1 回押す。本番 DB の接続の行が 1 行・つないだ人が user 3（読み取り） |
| K3 PO が入れた新しい予定が PO の Google カレンダーに入る | 本番の新しい予定の行に google_event_id が入る（読み取り）＋PO の Google で見える |
| K4 ほかの人が入れた予定は Google に送られない | 裏側の試験（つないだ人と別の人 → Google を呼ばない） |
| K5 つないだ本人以外は、Google の予定を直接読む・書く 4 つの口で 403 になる | 裏側の試験（4 つの口の `user` の既定値が新しい確かめ。本人でない人・未接続で 403） |
| K7 Google の予定をアプリへ取り込む設定（同期方式を bidirectional・read_only に変える）は 422 で断られ、取り込みの登録が行われない | 裏側の試験（同期方式の口を直接呼ぶ → 422・取り込みの登録を呼ばない。write_only・none は今どおり通る） |
| K6 既存の試験・検査がすべて通る | CI 全部緑 |

## 3. 対象と対象外
対象:
- 画面: 予定の画面のヘッダー右に、Button 金型（ghost）でつなぐボタンを 1 つ足す。
- 画面: `usePermissions` に `isTenantAdmin` を足す（同じ `/me/permissions` の答えから読む。新しい呼び出しは作らない）。
- 裏側: 予定を作るとき、Google に送るのは「Google をつないだ人が作った予定」だけにする。
- 裏側: Google の予定を直接読む・書く 4 つの口（recon 1-4）を、つないだ本人だけが使えるようにする。つなぐ前に塞がないと、ほかの人が PO の Google の予定を読めてしまう。
- 裏側: 同期方式を変える口（`PATCH /calendar/sync-mode`・recon 1-5）で、Google→アプリの取り込みを始める 2 つの方式（bidirectional・read_only）を 422 で断る。取り込みが始まると、PO の Google の予定が「会社の予定」として全員に見えるからである。

対象外（今回は作らない）:
- Google→アプリの取り込みを作ること（今回は上のとおり止める。recon 1-5）。
- 今ある 9 件を後から Google に送ること。
- 接続を外すボタン。`GoogleCalendarStatusBar` の作り直し・削除。

## 4. 変更前後
| | 変更前 | 変更後 |
|---|---|---|
| つなぐボタン | 無い | オーナー・システム管理者に出る |
| Google に送る予定 | つないだ後は会社の全員の予定（個人の予定も） | つないだ人が作った予定だけ |
| 変更・削除 | Google に送った予定だけ送る | 同じ（変えない）。PO が作った予定を、ほかの管理者が直す・消すと、それも PO の Google に反映される（今の予定の画面の権限どおり。PO の Google の中身がほかの人に見えるわけではないので受け入れる） |
| Google→アプリの取り込みを始める設定 | 管理者なら誰でも始められる（始めると PO の Google の予定が会社の予定として全員に見える） | 断る（422）。write_only・none への切り替えは今どおり |
| Google の予定を直接読む・書く口 | 会社でログインできる人なら誰でも | つないだ本人だけ（ほかは 403。未接続も 403） |

## 5. 選んだ形と理由
- 表示の条件は `is_tenant_admin` にする。押した先の口が `require_tenant_admin` だからである。`channels.manage` にすると、その権限を持つ別の役割の人に押しても失敗するボタンが出る。
- 管理者かどうかは `/me/permissions` の答えから読む。`usePermissions` がすでに同じ口を読んでいるので、置き場は 1 つのまま。
- 接続の状態は `GET /google-calendar/status` を `useApiQuery` で 1 回読む。`GoogleCalendarStatusBar` は使わない。手書きの style を持つ。起きない状態のために 30 秒ごとに読みに行く。
- ボタンは ghost。page-header-v2 §2 の住人表の「設定系ボタン（そのページの設定・補助メニューを開く用途のみ）」にあたるとした。根拠: このボタンが開くのは Google の接続の設定画面で、予定のデータを作る・消す操作ではない。予定の画面の「設定」ボタン（同じ行の ghost）と同じ種類の操作である。
- 送る相手を絞る判定は `create_event` の中で行う。接続の行の `connected_by_user_id` と作った人を比べる。新しい列や表は作らない。

- 4 つの口の確かめは「接続の行の `connected_by_user_id` がログインしている人と同じか」にする。管理者かどうかでは足りない。システム管理者が別の人だと、PO の Google を読めてしまうからである。未接続のときも 403 にする（今は 502）。画面から呼ぶところが無いので、画面への影響は無い。

- 取り込みを止める場所は同期方式の口にする。管理者の口であることは今の試験（`backend/tests/test_tenant_admin_ssot.py:184-185`）が守っているので、確かめ方は変えず、受け付ける方式だけを絞る。この口の呼び手を本人に絞るだけでは足りない。PO 本人が取り込みを始めても、PO の Google の予定が全員に見えるからである。

ほかの案:
- 案 B: 会社の全員の予定を送る → PO が選ばなかった（ほかの人の個人の予定が PO の Google に入る）。
- 案 C: 設定の画面（/schedule/settings）に置く → PO は「予定の画面に戻す」を選んだ。

## 6. 影響範囲
- `create_event` を呼ぶのは `backend/app/routers/calendar.py:350` だけ（git grep で確かめた）。秘書もこの口を通る。
- `_get_sync_mode` はほかの場所（update・delete・通知の登録）でも使う。だから変えずに残し、新しい関数を足す。
- 今は接続が 0 行である。だから本番での動きは、PO がつなぐまで何も変わらない。

## 7. リスクと対処
- Google の側で戻り先 URL が登録されていないと K2 で失敗する → 画面に「接続に失敗しました」が出る。そのとき止めて PO に伝える。
- つないだ後に PO 以外が予定を作ると、その予定は `sync_status='pending'` のまま残る。今の 9 件と同じ状態で、画面には出ない（`sync_status` は画面で使っていない）。
- PO 以外のシステム管理者が「つなぐ」を押すと、接続の行がその人に入れ替わる（callback の upsert）。その後は PO の予定が送られなくなる。ほかの人の予定が PO の Google に入ることは無い。今の tenant_004 の管理者は PO だけで（recon 1-3）、製品は PO 本人が使う前提（PO 決定）なので受け入れる。
- 本番の取り込み登録（`public.google_webhook_subscriptions`）は 0 件（2026-11-03 読み取り）。定期の更新（`renew_expiring_webhooks`）は登録済みのものを更新するだけなので、新しい取り込みは始まらない。

## 8. 戻し方
- PR を revert する。DB の形は変えない。
- つないだ後に戻すときは、`DELETE /google-calendar/connect`（管理者だけ）で接続の行を消す。

## 9. 測り方
- K3: PO が予定を 1 件作った後、本番を読み取りで見る。`SELECT id, created_by_user_id, google_event_id IS NOT NULL, sync_status FROM tenant_004.calendar_events ORDER BY id DESC LIMIT 3`。

今回は使わない。理由: 今あるつなぐ仕組みを画面に戻す作業である。新しいやり方は選ばない。
