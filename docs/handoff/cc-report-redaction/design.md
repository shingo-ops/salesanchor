---

## 技術 How・KPI

- KPI: 報告ファイル経由の秘密露出 0件（運用開始後）。
- 技術選択: 新しい検出ルールは作らず、既存の gitleaks 設定を再利用する
  （理由: ルールの二重管理を避け、CI と同じ判定にそろえるため）。
- 伏せ字の対象パターン: `key=` に続く値、`gho_` / `ghp_` / `github_pat_` / `AIza` / `AQ.` で始まる文字列、
  `Authorization:` ヘッダの値。

---

## 弊害・トレードオフ

- 既知の形式しか捕まえられない → 対策: ②の検査を別ルール（gitleaks）で重ねる。
- 伏せ字が強すぎると調査に必要な情報まで消える → 対策: 置換は値のみとし、前置きの語（`key=` 等）は残す。
- カードごとにフィルタを書く負担が増える → 対策: 共通スクリプト化は別便で行い、それまでは定型文で写す。
