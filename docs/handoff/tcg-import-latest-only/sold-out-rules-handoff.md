## 最初に読むこと

このファイルを、完売ルールについてのPOとの認識合わせの再開入口とする。合意履歴はC01〜C86に記録（C79はC80で置換済み）。個別の設計案や未決事項はPO合意と区別する。§9の接続プラン合意・条件付き実装承認は別記し、マージ・本番変更のGOとは扱わない。設計パートナーの範囲で進め、自動で実装役に切り替わらない。同一AIの自己審査を独立レビューとは称さない。

現在地（2026-09-16）: 投稿日不明データの限定削除は§47で完了。C66修正理由必須、C67全角数字半角化は回答済み。統合設計図と全合意の接続は[design§56](sold-out-rules-design.md#integrated-blueprint)。次工程は図上の未接続を詳細設計と検証で閉じる。製品改修は未着手、全体自己審査REVISE、追記文書はローカル保存/PR未反映。過去節の未回答/未削除は当時の経過であり、最新の決定節を優先して読む。

POの目的（原文）:
> 完売ルールページでは完売商品の一覧を見せるのではなくて完売を判定するルールを確認したり追加・修正・削除するためのページとして使いたい

進め方（原文）:
> 1つずつ明確にしていきたいので順番に詳細を素人に理解できるように質問してくれ、推測はせずに売切のルールをまず認識をすり合わせて確定冴えたい

接続プランへの回答（原文、§9）:
> 合意、推測は禁止して事実確認を怠らずに確実性を重視して最も効果があり、現状把握の粒度が細く、精度が高いエビデンスを確立して安全に進めてくれ、確立したなら実装を進める

今回依頼: 接続プランへの合意と、根拠確立を条件とする実装承認。根拠確立・設計合格・正式カードは未完了（§9）。

今回の保存依頼を根拠に、合意を以下へ転記する。引用以外は記録者の要約。PO発言の日時は会話に時刻がないため創作しない。新たなモデル呼出し・製品変更は実施していない。


**現在の担当範囲（C25/C34/C42で明確化）**: Geminiによる完売の判断のみを管理するページ。指示文・検索ワード・除外ワードの編集は完売と判断する/しない基準に限定し、商品名・価格・数量の抽出方法は編集対象外。完売商品の一覧は不要で、別ページへ移して残す対象にもしない。個別商品の判定修正は別ページであり、今回は触れない。原文/解析結果のDBデータ削除は承認されていない。以下の過去の質問案より、この最新の範囲を優先する。

### 不明点の扱い（PO追加指示）

PO原文:
> 不透明なことは推測で進めず全て聞いて記録してくれ

運用: 不明点は未決事項へ追加し、具体例を添えて一問ずつ質問する。回答原文と適用範囲を保存する。未回答を承認とせず、既に合意した内容を再質問しない。コード/DB等で確認できる事実は実物調査し、確認できない前提や判断を推測で埋めない。新しい不明点が出たら、一覧に追加してから確認する。Q22/Q23は回答済み。Q19の追加調査結果は§6。詳細設計案と自己審査は[sold-out-rules-design.md](sold-out-rules-design.md)。判定REVISE。Q24はC44として回答済み。残る技術条件は詳細設計§12/14。

## 83. 共通テーブル方式の採用（C92、2026-09-17）

PO指示「今後、状態や単位もマスタを作って随時追加していこうと考えている、その場合拡張性、メンテナンス、安定性を考えて推奨はどの形がいいか」→ 設計パートナーが共通テーブル方式（推奨）と別テーブル方式の2案を提示 → PO「推奨で進める」。

C92として記録。DB設計を以下の方針に確定:

1. 旧名 `sold_out_*` → 共通名 `analysis_*` に改名
2. `analysis_policies.policy_type` 列で種別を区別（`sold_out` / `date_format` / 将来追加）
3. `analysis_rule_words.kind` 列で語句の種類を区別（`search`/`exclude` = 完売、`format_template`/`apply_condition` = 日付）
4. テーブル構造は13テーブル＋既存audit_logで固定。種別追加時にテーブルを複製しない
5. ワークフロー（下書き→テスト→適用）のコードも1つの仕組みで全種別を処理
6. design.md §4を§4.1〜§4.7に再構成済み

理由: 種別ごとに13テーブルを複製すると、4種別で52テーブルになりメンテナンス・バグ修正の負担が種別数に比例する。共通テーブル方式なら種別追加は列の値追加のみで、DB SSOT・データ分散禁止の原則を維持できる。

design.md §4の旧テーブル名を参照している他のセクション（§53/§56等）は、具体DDL作成時に整合更新する。本節はDB方針の確定記録であり、DDL・migration・API・テストの完成ではない。自己審査REVISE継続。製品/DB変更なし。


## 84. 配信部分の設計決定（C93-C96、2026-09-17）

配信（Google Sheetsへの書き込み）と既存パイプラインとの接続について、PO回答を記録する。

**C93: 商品手動修正時の完売判断無効化**

PO回答:「修正したら即座に判断結果を無効にして、やり直しが必要にする」

管理画面から商品の紐付けを修正した場合（`item_corrections_svc.py:56-70`）、その商品に関連する完売判断結果（`analysis_rule_run_results`）を無効化し、再判断が必要な状態にする。修正前の判断結果は履歴として残すが、配信には使わない。

**C94: 在庫情報の有無の判定方法**

PO回答:「Geminiに任せる」

在庫に関係ないメッセージ（あいさつ等）かどうかの判定はGeminiに任せる。Geminiが商品を検出しなければ0件（status='empty'）で完売判断はスキップされる。空テキスト（文字が1文字もない）だけはGeminiに渡す前にシステムで弾く。キーワードによる事前フィルターは作らない。

根拠: 仕入先のメッセージは書き方がバラバラで、キーワードリストでは在庫情報を見逃すリスクがある。Geminiは文脈で判断できるため見落としが少ない。

**C95: 再読み取り時の結果選択**

PO回答:「最新の成功した読み取り結果だけを使う」

読み取り失敗後に再実行した場合、完売判断は最新の成功した読み取り結果（extraction_job status='done'のうち最新のcreated_at）のextraction_itemsのみを対象とする。古い読み取り結果は判断対象に含めない。

背景事実: 現在のコード（`tcg_diagnostics_svc.py:207-219`）は再実行時に古いextraction_itemsを削除しない。同一source_messageに複数世代のitemsが蓄積する。完売判断クエリで最新jobのitemsだけをフィルターする。

**C96: スプレッドシート書き込みエラー時のリトライ**

PO回答:「エラーを検知したら自動で再実行、4回再試行して失敗した場合はエラーとして人間に報告、アプリ上でエラー表記を出す」

現在の仕組み（1回失敗→記録して終了）を変更:
1. Google Sheets API書き込み失敗を検知したら自動で再実行する
2. 最大4回まで再試行する
3. 4回失敗したらエラーとして記録し、Discord通知に加えてアプリ画面上にもエラー表示を出す
4. 完売判断実行中（`analysis_rule_runs` が pending/running）は配信を停止する安全装置を追加する（既存の安全装置#8/#8bと同列）

本節は配信設計の決定記録。design.md §14/§86に設計として反映する。製品/DB変更なし。
