## 最初に読むこと

このファイルを、完売ルールについてのPOとの認識合わせの再開入口とする。以下の「合意」は業務上の意味の合意であり、製品実装・DB変更・マージ・本番変更のGOではない。設計パートナーの範囲で進め、自動で実装役に切り替わらない。同一AIの自己審査を独立レビューとは称さない。

POの目的（原文）:
> 完売ルールページでは完売商品の一覧を見せるのではなくて完売を判定するルールを確認したり追加・修正・削除するためのページとして使いたい

進め方（原文）:
> 1つずつ明確にしていきたいので順番に詳細を素人に理解できるように質問してくれ、推測はせずに売切のルールをまず認識をすり合わせて確定冴えたい

最新回答（原文）:
> 商品が特定できていれば更新する、特定できない場合は人間が確認する

今回の保存依頼を根拠に、合意を以下へ転記する。引用以外は記録者の要約。PO発言の日時は会話に時刻がないため創作しない。新たなモデル呼出し・製品変更は実施していない。

## 1. 今回の一問ずつの確認で合意済み（聞き直さない）

「在庫0」は業務上の意味。DB行の物理削除や過去原文の削除まで合意した意味ではない。

| ID | 合意内容 | 確認に使った例 | PO回答原文 |
|---|---|---|---|
| C01 | 商品の現状を明確に伝える完売・売り切れ・在庫なし・欠品・〆は、その対象の在庫0 | 予告・否定・注文締切の説明を含まない商品Aの状態連絡 | その認識であっている |
| C02 | 完売の可能性・予告だけでは完売にしない | 在庫あり。ただし予告なく完売となる場合があります | 合っている |
| C03 | 注文受付の時刻締切を理由に在庫0にしない | 在庫の有無にかかわらず17時30分で受付を〆る | 合っている |
| C04 | 完売の否定は完売として扱わない | 完売ではありません。まだ在庫があります | 合っている |
| C05 | 完売した商品だけを0にし、ほかの商品は維持 | 商品A完売・商品B在庫10個 | 合っている |
| C06 | 同じ商品でも発送分を区別 | 商品Aの9月20日発送分完売・9月25日発送分10個は維持 | 合っている |
| C07 | 対象が特定できなければ在庫を変更せず確認待ち、人間が確認 | 複数の商品/発送分がある中で完売しましたとだけ届く | 合っている、特定できない場合は人間が確認する |
| C08 | 単位を区別 | 商品AのBOX完売・カートン3個は維持 | 合っている |
| C09 | 仕入元を区別 | 仕入元Aの商品X完売・仕入元Bの商品X5個は維持 | 合っている |
| C10 | 商品状態を区別 | 商品AのシュリンクありBOX完売・なしBOX5個は維持 | 合っている |
| C11 | 後から明確な再入荷/在庫連絡が届いた場合、対象が特定できれば更新。特定できなければ人間が確認 | 同じ仕入元・商品・発送分・単位・状態について、先に完売、後に再入荷しました/在庫5個 | 商品が特定できていれば更新する、特定できない場合は人間が確認する |
| C12 | 取込順ではなく投稿日で新旧を判断し、新しい在庫連絡を維持する | 同じ対象の9月20日完売を、9月21日再入荷/在庫5個より後に取り込んでも5個を維持 | 合っている |
| C13 | 投稿日が不明な場合はシステムエラーとして確認待ちにする | 投稿日不明で新旧を判断できない連絡。投稿日時を取込日時等で推測補完しない | 投稿日が不明な場合はシステムエラーなので確認待ちにする |
| C14 | 同じ対象の投稿日時が重複し在庫あり/完売の新旧を判別できない場合は、完売を優先する | 日時は存在するが同時刻。同一対象に限定し、別商品/仕入元/発送分/単位/状態へ適用しない。投稿日不明はC13 | 同じ日時で投稿されることはまずない、無いが仮に重複した場合は完売を優先 |

重要: C06/C08/C09/C10の区別は、商品名だけで対象を決めないという要件。具体的なDBキー・同定方法・同日複数発送枠の扱いの設計完了を意味しない。対象の区別が不明な場合はC07/C11へ戻す。C02/C03の文が含まれる投稿全体を一律に捨てる合意でもない。C05の混在投稿では商品ごとに見る。

## 4. 実物確認済みの現状と設計上の注意

以下は2026-09-15の観測記録。再開時には現在のHEAD/配備/DBを再確認する。台帳やこの文書だけで今も同じ状態と断定しない。

- 公開済みPR3505はルール管理ではなく、analysis_results.status='Sold out'の閲覧ページ。マージa7188a13、Deploy34917303585成功をroot実確認。これを新CRUD要件の実装完了としない。
- 調査基点origin/main d29c1ab5。backend/app/services/tcg_analyzer_svc.py:1047はtcg_status_masterを読み、:1093で状態/備考から判定、:1328で適用、:1428で解析結果へ保存。
- 本番READ ONLY照会でtcg_status_masterは9行（完売5、予約3、在庫既定1）。完売語はsoldout/在庫なし/売り切れ/完売/欠品。C01の〆はその5行にない。これだけで抽出を含む全システムが〆を扱えないとは断定しない。
- loaderはexclude_patternをSELECTするが返却辞書に含めず、resolverも参照しない。状態欄は部分一致、備考はEXCLUDE/LITERAL完全一致。
- origin/mainの実関数をAST抽出して人工例6件で再現: 状態「完売ではありません」と状態「予告なく完売となる場合があります」はSold out。備考の同じ予告文はIn Stock。人工ルールを渡した限定再現であり原文の正答率ではない。保存前テストは本処理と同じ判定関数を使う設計が必要。
- migrations/20260903_150000_tcg_status_master_t004.sql:140-145はST%の件数9を固定検証する。seedのON CONFLICT DO NOTHINGは削除した既定行を再挿入する。scripts/run_all_migrations.sh:551に実行登録。追加/削除の維持を含めて設計しないと、画面のCRUDだけでは安全に成立しない。

## 5. 誰でも再開する手順

1. AGENTS.md、docs/ai-agents/design-partner.md、docs/STANDARD-WORKFLOW.md、docs/specs/README.mdを読む。必須preflightでbranch/未保存変更/origin/mainを確認。他者の変更を保持する。
2. tasks/todo.mdと現行active-work.d/公式ledger-viewを確認する。旧台帳は凍結アーカイブの場合がある。
3. 本書C01〜C14を読み直す。合意済みを再質問しない。H01〜H06の合意/希望/未決の区別を保つ。
4. Q03から未回答の項目を一問ずつ、具体例と日常語で聞く。答えがない項目を推測で決定しない。質問に依存しない読取調査は継続する。
5. 回答のたびに対象Qを「回答済み」へ変え、回答原文/対象範囲/合意IDを追記。既存項目を黙って削除しない。解釈や新しい例が必要な場合はPOへ確認する。
6. design/recon/tasks/evidence-registryの現在地を更新する。会話メモリだけに保存しない。本書を合意・未決の正本とし、別ファイルへ独立した決定一覧を増殖させない。
7. ルールが揃ったら仕様・受入試験・実装範囲・維持策を完成し、Plannerの後にArchitect自己審査を行う。未決の前提がある間は設計合格を出さない。

保存の状態は最終報告のcommit/PR URLと突き合わせる。文書保存・PO業務合意・設計合格・実装承認・本番反映は別の状態。
