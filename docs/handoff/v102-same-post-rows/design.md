## 0. 範囲の変更（2026-10-12、PO の決定による）
- まとめ方は、画面側で ON／OFF を切り替えられるようにします（card-PO.md）。そのため、この便（SP1）で入れるのは §3-1（is_current）だけです。
- §3-2（配信の SQL でまとめる）は入れません。次の便（SP2）で、「まとめる番号を配信の列として出し、画面で切り替える」形に作り直します。
- 受入条件のうち、この便で判定するのは T1・T3・T4（is_current の部分）・T5（同じ投稿の行がすべて出ること）です。T2 は SP2 に移します。

## 1. 目的
同じ投稿の同じ商品・同じ状態の行について、PO の決まりどおりに在庫一覧へ出します。
- 括弧（備考）が違う行は分けて出す。
- ランクだけが違う行はまとめて出す。
あわせて、解析し直しても表示する行が入れ替わらないようにします。

## 2. 対象と対象外
- 対象
  - backend/app/services/tcg_analyzer_svc.py `_merge_supplier_products`（is_current の決め方）
  - backend/app/services/tcg_distribution_svc.py `fetch_output_rows` と `fetch_preview_data` の配信候補件数（配信のまとめ方）
  - 上の2つのテスト
- 対象外
  - 解析の値（商品・単位・状態・価格・数量・備考）
  - DB の列
  - migration
  - 在庫一覧 GAS
  - 除外の内訳（:374-405 は解析の行単位の数えのまま）
  - 「ダメージ小／大」をランクとして扱う語の登録（card-PO.md の R1）
  - 発送の括弧が備考に入らない件（recon §5 の S-a。Gemini の書き写しの問題で、別の便）

## 3. 変更前と変更後
### 3-1. is_current（ADR-158 に合わせる）
- 変更前: 組（商品と状態）ごとに、先頭の1行だけを TRUE にしている（tcg_analyzer_svc.py:1849-1852）。同じ投稿の行どうしは順位が同じなので、どれが TRUE になるかは決まらない。
- 変更後: 組ごとに「いちばん新しい投稿」を1つ決め、その投稿の組の行をすべて TRUE にする。
  - 投稿の決め方は次の順に並べた先頭。最後の extraction_job_id で必ず1つに決まる。
    1. received_at の新しい順
    2. その投稿でその組の行の computed_at の最大値の新しい順
    3. extraction_job_id の大きい順
  - 仮の行（id NULL）は、親の行の投稿の一員として順位付けに加わる。UPDATE しないのは今と同じ。
  - これは ADR-158:26 の「新メッセージにも存在する product_id の旧行を FALSE」にコードを寄せる直しです。新しいメッセージの行は全部残ります。

### 3-2. 配信のまとめ方（新規）
- 配信の対象になる行（今の WHERE は変えない）に、次の鍵を付けます: 投稿（extraction_job_id）・product_id・condition_id・unit_canonical・note_ja（空は空として扱う）・status。
- 鍵が同じ行が2行以上あり、次の3つがすべて成り立つ組を「ランク違い」とみなし、1行にまとめます。
  - 組の中で condition_basis がすべて違う。
  - condition_basis が NULL の行が無い。
  - quantity_normalized が NULL の行が無い。
- まとめた行の値:
  - 数量は合計（SUM）、価格は最大（MAX）。
  - 他の列（投稿日時・商品・状態・備考・状態欄・発売日・作品・仕入元・検索ワード）は組の中で同じなので、その値を使う。
- それ以外の行は、今のまま1行ずつ出します。
- 並び順: まとめる前に、今の `result_order_sql()` で行に通し番号を付けます。まとめた行は組の中の最小の番号の位置に置きます。まとめない行の並びは、今と同じです。
- 配信候補の件数（`fetch_preview_data` の output_count）は、同じまとめ方をした後の行数にします。配信の SQL と件数の SQL が同じ1つの定義を使うようにします（定義を2か所に持たない）。
- ランクを表す語は、コードに書きません。根拠の語が違う（R2:状態A- と R2:状態B）ことを、マスタ（状態の規則）が既に出している condition_basis で判定します。

## 4. 代替案と選んだ理由
| 案 | 中身 | 不採用・採用の理由 |
|---|---|---|
| A（採用） | is_current を投稿単位にし、配信の SQL でランク違いだけをまとめる | 解析の値を変えない（DB は1行＝原文の1件のまま）。ADR-158 の書き方に合う。ランクの判定がマスタの出力（condition_basis）だけで済む |
| B | 解析のときに、ランク違いの行を1行に合成して保存する | 原文の1件と DB の1行の対応が崩れ、要確認の画面や修正の経路に影響する。値を変えるので K4 に反する |
| C | is_current は今のまま、ORDER BY に extraction_items.id を足すだけ | 入れ替わりは止まる。しかし備考の違う行は今と同じく1行しか出ず、PO の決まりに合わない |
| D | 在庫一覧 GAS でまとめる | まとめ方の定義が backend（件数）と GAS に分かれ、SSOT に反する |

## 5. 影響範囲（呼び出し元を全部見た結果。recon §6）
- 配信の行数と件数（tcg_distribution_svc.py:292・:363）
  - 現在の行が増え、ランク違いはまとまる。
  - 差は置き換え試験で数えます（§7 の T2）。
- ダッシュボードの件数（tcg_analysis_dashboard_svc.py:713）: 現在の行の数が増える分だけ増える。
- 相場の確認（v102_unit_price_check_svc.py:62）: 中央値の母数が増える。試験で、要確認の付き方が変わる行を数える（T4）。
- 旧 v6 の呼び出し（tcg_analyzer_svc.py:1736）も同じ関数を通る。v6 は今は新しい解析をしていない（既定は v102）。変えるのは同じ投稿の行の扱いだけ。

## 6. リスクと対処
- R-a: 同じ投稿に、単位が違う同じ商品・同じ状態の行（Box と Case など）があると、今は1行しか出ていなかったものが、両方出るようになる。
  → 正しい挙動です（別の在庫）。件数は T2 で数えて示します。
- R-b: 同じ時刻の重複投稿（本文が同じ2通）は、extraction_job_id の大きい方に決まる。値は同じなので、見え方は変わらない。
- R-c: まとめる条件を外れる組（数量が空のもの、根拠が同じもの）は、まとめずに出す。
  → 情報を落とさない側に倒しています。
- R-d: デプロイの後、今ある行は解析し直すまで今の印のまま残る。
  → 直近48時間の投稿を解析し直して付け直す（前回と同じ作業用コンテナ）。

## 7. 受入条件と検証方法
| 基準 | 検証方法 |
|---|---|
| T1 is_current が投稿単位で決まる（K3） | 単体テスト: 同じ投稿の同じ組が2行のとき、2行とも TRUE。別の新しい投稿があれば両方 FALSE。2回続けて呼んでも結果が同じ。received_at と computed_at が同じ2投稿は、job id の大きい方になる。仮の行を含む既存のテストが通る |
| T2 配信のまとめ方（K1・K2・K5） | PostgreSQL のテスト（既存 test_tcg_condition_review.py の作法）で次の3つを確かめる。N（備考違い）は2行出る。R（根拠違い）は1行で、数量が合計・価格が最大になる。S（根拠同じ）は2行出る。数量が NULL ならまとめない。件数の値が出力の行数と一致する |
| T3 解析の値が変わらない（K4） | 本番で解析し直す前と後に、全行の値の写しを取る。product_id・unit・condition・price・quantity・note_ja・status の変化が0行であることを確かめる（前回の cmp の作法） |
| T4 置き換え試験（マージ前） | 本番の読み取りで、新しい is_current を SQL で計算する（書き込まない）。今と比べて増える行と減る行、配信の行数の差、型 N・R・S ごとの出方、相場の確認の中央値が変わる組の数を出す |
| T4 の結果（2026-10-12、実装 a6e6317b0、本番の読み取り、/tmp/CC報告ファイル/same-post-rows/test/） | 全部の行を付け直したと仮定した計算で、今 TRUE → 新 FALSE は0行。今 FALSE → 新 TRUE は v102 で27行。型 N・R・S のどの組でも、新しくは組の全行が TRUE になる。配信（48時間）の行は 824 → 847 で、増えた23行・消えた0行。相場の確認で要確認の判定が変わる行は、1,058行中0行。旧エンジン（v9 374行・v8 1行・v7 2行）も、組に触れたときに同じ投稿の行が TRUE に戻る。いずれも48時間より前の投稿なので、配信には出ない |
| T5 本番の確認（デプロイ後） | 直近48時間を解析し直した後、本番の解析結果で次を確かめる。T4 で増えるとされた v102 の27行が is_current=TRUE になっている。同じ投稿の同じ組で、TRUE が組の一部だけの組が0組。配信の行数が T4 の 847 と比べて説明できる（その間に届いた新しい投稿の分を除く）。投稿 0b32f3e7 は48時間の窓の外なので、例としては使わない |

## 8. 外部事例
- 直接使える事例はありません。これは、この業務の原文の書き方（同じ投稿に同じ商品を、発送条件やランクで書き分ける）と、このシステムの印の付け方に固有の問題です。
- 一般的な考え方として、「最新のスナップショットで置き換える」単位を、個々の行ではなく取り込みの単位（投稿）にするのは、ADR-158 自身が書いている方針です。そのため、外部事例で設計の正しさを示すことはしません。成功の根拠は T1〜T5 の実測で示します。

## 9. 維持する担当と仕組み
- 決め方の正本は2つです: `_merge_supplier_products`（is_current）と、配信の SQL の定義1か所（まとめ方）。
- テスト T1・T2 は CI（backend の pytest）で毎回回ります。
- ランクを表す語は、condition_basis を出す状態の規則マスタに登録された語だけです。新しいランクの語をマスタに足せば、コードを変えずにまとまる、という前提で設計しています。この前提（condition_basis の R2:<語> がマスタから来ること）は、実装カードの 0 で file:line を付けて確かめます。
