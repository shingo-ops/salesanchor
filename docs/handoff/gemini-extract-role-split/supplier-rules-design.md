## 4. なぜ仕入元ごとのルールが要るか（原文の証拠）
- 同じ見た目の行が、仕入元によって逆の意味になる。
  - SIG 系：`肉ルフィカード… 1000@1100` は、数量1000・単価1,100（数量@価格）
  - まー：`頂上の強者パック 2500@1000` は、単価2,500・数量1000（価格@数量）
  - どちらも「数字@数字」で、原文だけでは向きを決められない。仕入元ルールがあって初めて決まる。
- 並びの型は 15種類以上ある。
  - 価格×数量（伊石、Yasu Kishi、H、KMS）
  - 数量@価格（Rikiya、下司、シンソク ほか多数）
  - 価格@数量（N&U、AXIS、まー、東）
  - @価格 在庫数量（yusuke、吉田、馬場 ほか）
  - 在庫数量/価格（貞弘、INスタッフ）
  - ラベル形式（達也、SAMURAI-T）
  - 単位/¥価格 → 残り（倉田、T）
  - 価格/数量（竹内スタッフ）と数量/価格（吉田翔）。スラッシュの向きが逆。
  - 「24万」のような万単位（竹内）
- 1社の中でも書き方が揺れる例がある（末吉、MASAKI、Yuki）。こうした揺れは notes に書く。

## 5. 設計（変更の前後）
### 5-1. ルールの置き場所（SSOT）
- 置き場所は `public.suppliers.extraction_*` の8列だけ。新しい表や別の置き場所は作らない。
- 登録先は、投稿の紐付け先の行とする。紐付けは `supplier_channels.supplier_id` で決まる。

### 5-2. 各列に書くもの（書式の統一）
| 列 | 書くもの |
|---|---|
| extraction_order_pattern | JSON 配列（既存の新形式）。トークンは `_PATTERN_MAP` の語彙（quantity/unit/price/status/@/yen/yen_prefix/space/slash/stock_label/newline）だけを使う |
| extraction_price_format | 例：`@{数値}円` / `¥{数値}` / `{数値}（円なし）` / `{数値}万` |
| extraction_qty_format | 例：`在庫{数値}` / `{数値}BOX` / `残り{数値}` |
| extraction_default_unit | 単位が書かれていないときの単位（多くは BOX） |
| extraction_state_format | 状態の書き場所（商品名に付く／次の行／※の後ろ／[状態A-]） |
| extraction_notes | 揺れ・誤記・＠の向き・見出し記号・完売の書き方・定型文の区切り |
| extraction_example_text | その仕入元の実投稿から、2〜3商品分の原文をそのまま写したもの |
| extraction_ship_format | 発送日の書き方（例：冒頭「明日N日発送」／商品ごとの `✅発送日`） |

- 既存10件の略語形式（price_at_qty など）は、同じ意味の JSON 配列に書き換える。書き換える前の値は、取り消し用 SQL に残す。

### 5-3. 作り方と確かめ方（推測で書かない）
1. Opus が、原文の読み取り記録（evidence）からルール案を書く。案は仕入元ごとに1行とする。
2. Sonnet が、機械的な照合試験を行う。
   - 対象：その仕入元の本番の全投稿（約1か月分、読み取りのみ）
   - 方法：在庫行らしき行（数字を含み、定型文の区切りより前）について、ルールの並びに当てはまる行の割合を数える。
   - 報告：数字の生出力をそのまま出す。
3. 合格ラインは、当てはまる割合が 90%以上。
   - 90%未満の仕入元は、外れた行の原文を Opus が読み、notes を直して再試験する。
   - 2回直しても届かない仕入元は、PO に報告し、保留にする。
4. 本番への登録
   - 1本の SQL ファイル（UPDATE 105件＋既存10件の書き換え）にまとめる。
   - あわせて、件数の検査と、取り消し用 SQL を用意する。
   - 手順：DRY-RUN（最後を ROLLBACK にする）→ 件数が一致したら実行 → 実行後に読み取りで確認
   - 手順は ADR-1003 と autoMode の「本番データ変更」の手順に従う。PO の合意が要る。

### 5-4. ルールのない仕入元の抽出禁止（新方式）
- 変更前：`backend/app/tasks/tcg_extraction.py:520-530`。試運転は、どの仕入元にも実行される。
- 変更後：試運転を呼ぶ前に、supplier_context の price・qty・order の3欄を確かめる。どれかが空なら、試運転を行わない。
  - その場合、`extraction_shadow_runs` に run を作らず、ログに「ルール未登録のため試運転を省略」と仕入元コードを出す。
- 旧方式（本番）は変えない。PO の決定どおり、整備後に別便で適用する。
- 触らない範囲：v7 の判定関数、v6 の経路、画面。

### 5-5. 試運転の再開
- K1 と K2 を満たしたら、#3864 の値を1に戻す PR を出す。
- 停止前の23 run は評価に使わない（design.md:267-271）。

## 7. 見つかった別の問題（今回の範囲外。記録して別のカードにする）
1. **同じ投稿が2件ずつ取り込まれている**（インポートの整備の本題）
   - 事実：同じ仕入元・同じ送信時刻・同じ本文で、空行の数だけが違う投稿が2件ずつある。確認できたのは30社以上で、両方とも解析に回っている。
   - 原因（2026-09-30、コードと本番の5組の照合で確認）
     - PC 版の読み込み（`backend/app/services/tcg_line_import_svc.py:158-160,195`）は、空行を捨てたうえで、行を `\n\n` でつなぐ。
     - Android 版の読み込み（`backend/app/services/tcg_line_android_parser.py:47`）は、空行を残し、行を `\n` でつなぐ。
     - raw_sha256 は本文をそのまま使い、正規化していない（`backend/app/services/tcg_line_import_svc.py:57-59`）。
     - 一意制約 `(supplier_channel_id, line_posted_at, raw_sha256)`（`migrations/20260921_110000_pipeline_tables_public.sql:31`）は、2つの経路から入った同じ投稿を別の行として扱う。
     - 5組とも、片方が PC 型、もう片方が Android 型の改行だった（`/tmp/CC報告ファイル/import-dup/p1-p5.txt`）。古いほうは superseded_by で置き換わるが、どちらにも extraction_jobs が作られる。
   - 【未確認】
     - どのアップロードがどの経路から入ったか（`import_job_messages` との照合）
     - 重複の全件数
   - 直し方の案（別カード）：ハッシュを取る前に、改行と空行を正規化する。既存の重複行の扱いは、PO の判断が必要。
2. **仕入元マスタの重複**
   - 投稿者の行と、会社名の行（投稿0件）が別々にある。例：アントネスト、PAPP、ALC、モノウリ、fun labo、SUP-xxx の旧コード。
   - 既存ルールにも、supplier_code が空の重複行が5件ある。
3. **在庫と無関係な投稿にも job=done が付いている**
   - 例：個別連絡、グループのシステム文。
   - 旧方式が、それらも解析に回している。
4. **完売・残数・価格変更の投稿**
   - 仕入元をまたいで書き方が共通している。
   - 対象が書かれていない `〆` もある。
   - PO の構想（メッセージの種類ごとの説明書）の根拠になる。今回は記録だけにする。
