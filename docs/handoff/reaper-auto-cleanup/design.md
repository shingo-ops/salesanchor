## 1. 設計（3かたまり）

### かたまり① 配線を本店に向ける（K1・K2）

.github/workflows/reaper-schedule.yml の reaper 実行ステップに env を注入する。

    env:
      REAPER_WORKTREES_DIR: /Users/tanizawashingo/worktrees/salesanchor

採用理由: 2026-07-22 の実測で、この指定により本店の87件を正常走査できることを実証済み。checkout 廃止案・reaper 本体自衛案は未実測のため採らない（実測で効くと分かっている最小の変更を採る）。

### かたまり③ 見張りの自動化（K7・K8）

reaper-schedule.yml の掃除ステップの後に scripts/ghost-count.sh を呼ぶステップを追加する。
ghost-count は exit 値を変えない見張り専用設計のため、掃除本体の成否に影響しない。

### かたまり② 異物の名指し報告（K3・K9）

recon 観点6 の「ブランチ名が空なら無言で continue」を、SKIP_NOT_WORKTREE 欄に名前を記録してから continue する形に変更する。
異物は SKIP_ 欄に入るため削除ルートに載らない（既存の保護と同じ仕組みに乗せ、削除判定は一切変更しない）。

## 2. 受け入れ基準

| 基準 | 検証方法 |
|---|---|
| 定期reaperの対象worktree数が本店フォルダ実数と一致する（0件でない） | 定期実行ログの「対象 worktree 数」を実測 |
| 本物のworktreeの取りこぼしが0件 | is worktree=true の総数と reaper 解決数を突合 |
| 異物が名指しで出力される | reaper 出力に異物欄が在り、空箱3件が名前つきで出る |
| 異物・要注意1件が自動掃除で消えない | execute 実行後に残存を全数確認 |
| 見張りが手叩きなしで自動実行される | 定期job のログに ghost-count の出力が在る |
| 閾値超で警告が出る | GHOST_THRESHOLD を下げて発報を実測 |

## 3. 外部・過去事例の参照と我々への応用

外部事例: AIエージェント運用の実証研究および実務記録で、自然言語の指示だけでは規約遵守が担保されず、決定論的なガードレールへ移行すべきと結論づけられている。
我々への応用: 本設計でも「reaper 本体の削除判定は変更せず、保護欄（SKIP_）という既存の機械的分類に異物を乗せる」方式を採る。人の注意ではなく既存の機械分類で守る。

## 4. 弊害・トレードオフ（空欄不可）

- 即時掃除は Mac がオンであることが前提。留守中のマージは即時起動しない。定期がバックアップするが、定期が回るまで最大1日は溜まる。タイミング方式（二段構え）を選んだ時点で受け入れた弱点。
- かたまり①③は .github/workflows 変更＝危険操作。PO の GO 必須・関所の再採点必須・全緑確認後にマージ。
- かたまり②は番人（reaper 本体）に手を入れる。「報告欄を足すだけ・削除判定は不変」を厳守し、配布原本との逐語 diff で検収する。
- かたまり①の弱点: 「なぜ本店指定が効くか」がコメントなしでは読み取れず将来壊れやすい。コメントで理由を明記して補う。
- 接触面17ファイル（recon 観点7）のうち、動線・手順を変える場合は案内書の同時更新要否を判断する。

## 5. 実施順序

かたまり①（K1・K2）→ かたまり③（K7・K8）→ かたまり②（K3・K9）。
K4・K5・K6（実削除の実測）は、消せる worktree が1件以上出現してから別便で実測する（2026-07-22 時点の実測では削除対象0件のため実測不能）。

## 6. 既知の弱点（別テーマ切り出し）

即時掃除・定期掃除とも self-hosted runner（PO の Mac）上でのみ動作する。Mac 電源オフ中はどちらも動かず、あるべき姿の「毎回もれなく」を完全には満たさない。
本テーマの合格ラインは「Mac がオンの間は確実に動く」とし、電源依存の解消は別テーマとする（2026-07-22 PO決定）。
