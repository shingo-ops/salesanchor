- 対象: design.md §19-1 件3（D8・D11・D14）の 3 つの推奨が一般的な運用に合うか
- 区別: 【事実】は出典の文面。【適用】は本件への当てはめ（Opus の判断）。数値は出典にあるものだけ。

## 1. 一般的な運用（公式資料）

| 項目 | 【事実】 | 出典 |
|---|---|---|
| live-restore の働き | 「デーモンが使えない間も箱（コンテナ）を動かし続ける」。無効だと、デーモン終了時に動いている箱を止める | https://docs.docker.com/engine/daemon/live-restore/ |
| 入れ方 | `/etc/docker/daemon.json` に `"live-restore": true`。止めずに反映するには `systemctl reload docker`（SIGHUP） | 同上 |
| 限界1 | パッチ版（YY.MM.x）の入れ替えだけ対応。大きな版（YY.MM）の入れ替えは対象外 | 同上 |
| 限界2 | ブリッジの IP・保存方式など、デーモンの設定を変えると戻せないことがある | 同上 |
| 限界3 | デーモンが長く止まると、箱のログの通り道（既定 64K）が詰まり、箱がログを書けなくなる | 同上 |
| 限界4（第三者） | 入れ直しの間は箱の名前の引き当て（DNS）が一瞬失敗しうる。ヘルスチェックは動かない | https://oneuptime.com/blog/post/2026-02-08-how-to-enable-docker-container-live-restore/view （2026-02） |
| 採用例 | Ceph の公式資料: Docker Engine の入れ替えや予定外の入れ直しでも、Ceph の常駐役は止まらず動き続ける | https://docs.ceph.com/en/latest/cephadm/docker-live-restore/ |
| マシンの数値の記録 | node_exporter の textfile collector は「定期作業（cron）の数値」と「その機械に固有の数値」用。一時ファイルに書いて `mv` で置き換えるのが公式の書き方 | https://github.com/prometheus/node_exporter#textfile-collector |
| 障害のきっかけ | Google の数千件の事後報告（2010〜2017）: プログラムの入れ替え 37%・設定の入れ替え 31%（合わせて 68%） | https://sre.google/workbook/postmortem-analysis/ |

## 4. 本件への当てはめ

| 推奨 | 【適用】 | 判定 |
|---|---|---|
| (1) live-restore を先に入れてから入れ直す | 公式の方法そのもの。reload なら箱は止まらない。限界1〜4 のうち、本件は版の入れ替えでもネットワーク設定の変更でもない（限界1・2 に当たらない）。止まるのは数秒のため限界3 も当たりにくい。限界4（名前の引き当て・ヘルスチェック）は入れ直しの数秒だけ起きうる | 適切 |
| (2) 夜中の利用が少ない時間に、最初の 1 回は PO が待機 | 「利用が少ない時間」は影響を小さくする点で事例C〜E の教訓（影響が広がる前に止める）に合う。一方、夜中の手作業は事例F のような取り違えの余地がある。本件は手順を台本にして機械が行い、人は見守るだけにする | 一部見直し: 「夜中」ではなく「利用が少なく、PO が起きていて見守れる時間」を利用の記録から選ぶ |
| (3) dockerd のメモリを自動で記録 | 事例G は 3.7GB の機械で dockerd が 1.8GB（47%）まで膨らみ、箱が強制終了された。prod1 の dockerd は RSS 1,778,000 KiB・VmRSS 1,913,336 kB（recon.md §2。2026-09-20 から入れ直しなし）。prod1 の版は 29.4.0 で、事例G の 27.4.0 の不具合と同じものかは確かめていない。過去の推移の記録が無いため、増え続けているのかを今は判定できない。記録の方法は node_exporter の公式の書き方 | 適切 |

## 5. 時間帯の実測（PO の候補 14〜16 時・4〜6 時）

- 取り方: Grafana の Prometheus（読み取り専用の鍵）。`sum(increase(http_requests_total{job="backend",handler!~"/api/health|/api/v1/ops/alertmanager|/api/v1/tcg/line-devices/import|/metrics"}[1h]))` を 1 時間ごと、2026-10-07〜11-04 の 28 日分。機械の呼び出し（死活確認・警報・LINE 端末の取り込み）は除いた。
- 本番への入れ替え（deploy）の回数は recon.md §2 と同じ一覧（1,000 件・26 日）を日本時間で数えた。

| 時間帯（日本時間） | 2 時間の呼び出し数 中央値 | 平均 | 最大 | ほぼ 0（10 未満）の日 | 入れ替えの回数（26 日） |
|---|---|---|---|---|---|
| 14:00〜16:00 | 21 | 210 | 3,073 | 28 日中 14 日 | 110 |
| 04:00〜06:00 | 7 | 133 | 1,319 | 28 日中 15 日 | 40 |

- 【事実】どちらも呼び出しは少ない。中央値の差は 2 時間で 14 回。
- 【未確認】最大の日（14〜16 時の 3,073・4〜6 時の 1,319）が人の操作か、自動の点検（毎朝の画面の速さの記録など）かは分けていない。
- 【適用】14〜16 時を選ぶ。理由: (1) PO が起きていて見守れる（§4 の判定・事例F）。(2) 呼び出し数の差は小さい。(3) 入れ替えの回数が多い点は、作業中だけ入れ替えを止めれば当たらない。
