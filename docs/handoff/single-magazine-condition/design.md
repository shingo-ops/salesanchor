# design: シングル系にも状態「雑誌付き」を使う（v102）

状態: **PO 承認済み**（2026-10-25、PO「1」＝この設計で進める）。設計審査済み。目標（K1〜K6）は PO 承認済み（2026-10-25、PO「1」）。方針は PO が決めた（2026-10-25「状態で判別してくれ、マスタを増やすと分析が分散する」）。起案は 2026-10-25、Opus。
- 現状の調べは [recon.md](./recon.md)
- 親の設計は [magazine-promo-condition/design.md](../magazine-promo-condition/design.md)（プロモパック系に「雑誌付き」CN0025 を足した前例。同 :24 でシングル系を対象外にしていた所を、今回広げる）
- 判断の根拠は ADR-1007、ADR-1023、ADR-1031、ADR-1035。新しい ADR は作らない。既存の群（single）に1行足すだけで、ADR-1023・1035 の「維持の仕組み」（群・順位・単位を同時に決め、記録 SQL で入れる）の範囲に収まるため。親の設計も同じ理由で ADR を作っていない（recon §0）

## 目的（PO の言葉）

> 状態で判別してくれ、マスタを増やすと分析が分散する

使う人から見て変わること:

- 区分がシングル系のカードでも、原文に「雑誌付き」「雑誌プロモ付き」「本付き」「付録付き」と書かれた行は、状態が「雑誌付き」になる。
- 同じ仕入元が「本付き 1冊 完売」と「プロモのみ 1枚 残り102」を並べたとき、2つは別の在庫として数えられる。本付きが完売しても、カードだけの在庫は残る。
- 商品は増やさない（K5）。

発端: 毎朝点検（2026-10-25）で、CHOPPER's の「雑誌プロモ付き 1冊 完売」と「プロモのみ 1枚 残り102」が、同じ商品・同じ状態（Single）になっていた（recon §5）。

## 対象と対象外

| 対象 | 対象外 |
|---|---|
| 状態の辞書に1行足す（群 single・区分シングル系） | コードの変更、migration、画面の変更、i18n |
| | 既存の CN0025（プロモパック系の雑誌付き）。言い回しも変えない（K3 を仕組みで守るため） |
| | 過去の行の再解析。次の投稿から効く（K1・K6 は次の同じ投稿で測る） |
| | 状態バッジの色。「雑誌付き」は CN0025 のときから灰色（conditionBadge.ts に無い）で、今回も同じ |
| | 組の箱（メガブレイブ・メガシンフォニア）の扱い。別に PO に確かめる |

## 変更前と変更後

### 足す1行（public.line_conditions）

| 列 | 値 | 理由 |
|---|---|---|
| code | CN0027 | 固定の番号。最大値から採らない（前例）。CN0026 はテストの仮データ（backend/tests/test_supply_category.py:34）と字面が同じで紛らわしいため飛ばす。本番に CN0027 が無いことを 01_precheck で確かめる |
| canonical | 雑誌付き | CN0025 と同じ名前にする。出力名は canonical そのもの（tcg_distribution_svc.py:326）なので、届け先に新しい名前が増えない。同名が別の群に並ぶ前例は PSA10（single 55／promo_pack 62。line_analysis_v102_svc.py:656） |
| app_kubun | シングル系 | 群 single の既存行と同じ |
| priority | 2 | CN0025 と同じ。検索で当たる状態（R2）にする |
| match_type / search_kw | REGEX `雑誌(プロモ)?[\s　]*(付き\|つき)\|本[\s　]*(付き\|つき)\|付録[\s　]*(付き\|つき)` | PO が挙げた4つの言い方を拾う。「プロモのみ」「雑誌無し」は拾わない。試算で熟語の一部への誤った当たり（「日本付き」など）は0（recon §5） |
| exclude_kw | 空 | |
| effect | OUTPUT | 既存行と同じ |
| unit_id | 17（Booklet＝冊） | 品物は本・雑誌とカードの組なので冊で数える。単位表は canonical をキーにする（gemini_raw_copy_v102_product_first.py:155,379）ので、どちらにしても CN0025 の Booklet を引く。値を揃えて食い違いを作らない |
| value_group / value_rank | single / 6 | 群の末尾に置く。既存5行（PSA10〜Single）の順位は変えない |
| note | 「シングル系で雑誌付き・本付き・付録付きと書かれた行の状態。単位は冊（ADR-1023/1031/1035、2026-10-25 PO）」 | |

在庫をまとめる鍵は (product_id, condition_id)（tcg_analyzer_svc.py:1964）。新しい行は CN0025 と別の id になるので、同じ商品でも「雑誌付き」と「Single」は別の在庫になる。これが K1 の土台。

### 判定の変わり方（origin/main の実コードでの試算・recon §5）

直近90日の v102 の行で比べた。

| 区分 | 行数 | 変わる行 | 変わり方 |
|---|---|---|---|
| シングル系 | 1395 | 45 | すべて Single → 雑誌付き。ほかの変わり方は0 |
| プロモパック系 | 968 | 0 | — |

変わる45行の内訳:
- CHOPPER's 1 プロモカード: 37行。当たった語は「雑誌プロモ付き」29行と「本付き」8行。
- ONE PIECE学園 10: 8行。当たった語は「雑誌付き袋とじ未開封」。

ONE PIECE学園 10 は本の商品で、原文は雑誌付きと書いている。「雑誌付き」にするのは書かれたとおりなので、対象に含める。

同じ投稿の中で、言葉を書いていない CHOPPER's の行（「プロモのみ」など）176行は Single のまま。

## 代替案と、選ばなかった理由

| 案 | 選ばなかった理由 |
|---|---|
| 本付きの商品を新しく作る | PO が「マスタを増やすと分析が分散する」として退けた |
| CN0025 の適用をシングル系にも広げる（案B） | コード（gemini_raw_copy_v102_product_first.py:641、tcg_analyzer_svc.py:653,882）を変える必要がある。さらに言い回しを広げると、プロモパック系の判定も一緒に動く。試算では今は0行だが、K3 を仕組みで守れない |
| 「本付き」という新しい名前の状態を作る | 届け先・画面に新しい名前が1つ増える。PO が「雑誌付き」を使い回す案（2026-10-25「1」）を選んだ |
| 単位を空にする | 単位表が canonical キーなので、どちらにしても Booklet を引く。値だけ空にすると、表と行が食い違う |
| 順位を5にして Single をずらす | 既存の1行を書き換えることになり、変更が増える |

## リスクと対処

| リスク | 対処 |
|---|---|
| 「本付き」が別の意味の言葉（「見本付き」など）を拾う | 90日分の試算では誤った当たりは0。見つかったら exclude_kw に足す（記録 SQL 1文）。毎朝点検でも見つかる |
| 単位が空だった24行が冊に変わる | 品物は本・雑誌とカードの組なので、冊が正しい数え方。値段の単位の読みには影響しない（値段は raw_price から読む） |
| 並び順の表も canonical キーで、同じ名前は小さい id（CN0025・promo_pack の順位4）が勝つ（tcg_result_order.py:18） | 影響するのは在庫表の並びだけ。シングル群では Single（順位5）より上に並ぶことがある。並べ替えたいと言われたら、表の作り方を直す別の作業にする |
| 「PSA10 雑誌付き」のように2つ当たる | 群の中で複数当たったら、価値の低いほう（順位が大きいほう）を採り、要確認を付ける（tcg_analyzer_svc.py:861,882）。試算では0行。要確認で人が見る |
| GAS 在庫一覧で表示が崩れる | 「雑誌付き」という名前は CN0025 のときから届いている。名前は増えないので、崩れないはず。K1 の目視で一緒に確かめる |
| 戻すとき、解析結果が状態の id を参照していて消せない | 戻しは is_active=false。01_precheck で外部キーを確かめ、参照が無ければ DELETE を併記する（前例どおり） |

## 手順（便は1つ）

1. Sonnet がこのフォルダに data/01_precheck.sql・02_apply.sql・03_verify.sql・04_rollback.sql を書く。書き方は docs/handoff/magazine-promo-condition/data/ に合わせる（件数が違えば 1/0 で止まり、終わり方は -v end で指定）。コードは書かない。
2. Opus が SQL を読んで確かめる。
3. 01_precheck を流し、02_apply を DRY-RUN（ROLLBACK）で流す。
4. COMMIT で流す。
5. 03_verify を流す。そのあと 04_rollback を DRY-RUN で流す（K7。CN0027 が入った後でないと試せないため、前例どおりこの順）。
   - 流すのは台本 cond.sh（前例 magazine3/cond.sh と同じ作り。順番と合格の印を見張る）。社外秘の保管場所 ~/CC報告ファイル-keep/shime-auto-check/daily/20261025_1200/state_split/apply/ に置く。
6. 次に同じ仕入元の同じ一覧が投稿されたら、K1・K6 を確かめる（毎朝点検の記録と、在庫行の読み取り）。
7. 記録を docs PR（results.md）にまとめる。

本番への書き込みは手順4の commit だけ。manual-only の鍵を使うため、PO が `!` で1行実行する（前例どおり）。

## 測り方と、変わったかどうか

- 基準値: 群 single は5行。CHOPPER's の現行行は14行とも Single（recon §5）。毎朝点検の連続日数は 0（2026-10-25）。
- 変わったかは、K1（在庫行が2つに分かれる）と K6（毎朝点検で○）で見る。正答率の採点では状態の細かい違いは採点外なので、正答率の数字は動かない見込み。

## 外部・過去事例の参照と我々への応用

- 外部事例: 使わない。社内の状態の辞書に1行足すだけの変更で、外の事例は判断材料にならない。
- 過去事例: 親の設計（magazine-promo-condition、2026-10-21 本番反映）。
  - 前例のやり方: 固定の code、記録 SQL 4本（precheck・apply・verify・rollback）、PO の `!` で COMMIT。results.md の K7 で、参照があるため戻しは無効化だった。
  - 今回への応用: 同じ4本の形をそのまま使う。戻しも同じく無効化を基本にする。

## 審査（Architect、同じ AI による自己審査）

判定: **APPROVE（設計合格）**。PO の承認、実装の開始、本番への反映はまだ。

- 既存の仕組みとの整合
  - 群 single は SCOPED_VALUE_GROUPS（tcg_analyzer_svc.py:653）にすでにあり、コードと migration は要らない。
  - 同じ名前が別の群に並ぶのは PSA10 の前例どおり。群の中では canonical が重ならないので、id は1件に決まる（line_analysis_v102_svc.py:656）。
- 根拠: 判定の変わり方は、origin/main の実コードの関数に仮の行を足した試算による（recon §5。再現性はシングル系 1395/1395 一致）。適用前に K2〜K4 でもう一度確かめる。
- 検証できるか: K2〜K5・K7 は SQL と試算で○×が出る。K1・K6 は次の投稿で観測する。
- 範囲: 足すのは1行だけ。既存の状態行と商品の区分は変えない。
- 未解決の事項。どれも設計の合否は変えない。
  - 並び順の表が canonical キーである点。並びにしか効かない。
  - GAS の表示。名前が増えないので、変化は無い見込み。K1 の目視で一緒に確かめる。
  - 外部キーの有無。01_precheck で確かめる。

## 維持の仕組み

- 状態を足すときの規則は、ADR-1023・1035 の「維持の仕組み」のとおり。この設計は、別の群に同じ名前を足す1件目の前例として、記録 SQL を残す。
- 言い方が増えたとき・誤って当たったときは、CN0027 の search_kw / exclude_kw を直す（記録 SQL 1文）。
- 毎朝点検（docs/handoff/shime-review-exclude/design.md §12-8）が〆の行を見続けるので、誤りはそこで見つかる。
- 守り手: 毎朝点検（Opus＋Sonnet、2026-11-10 まで）と、状態の辞書を変えるときの記録 SQL の手順（ADR-1023・1035）。
