# LINE自動書き出し（ADB方式）の登録と定時性の改善

対象ADR: ADR-156（商品分類ツリーと共用マスタ分離。本便が供給する取り込み経路の下流が同ADRの移行対象）
recon: `docs/handoff/line-auto-export-runtime/recon.md`（稼働中の構成・実測・制約の調査）

## 合意した範囲（PO合意 2026-09-19）

1. 実行周期を1時間から**15分**に変更する（実行回数 約4倍、1回あたり約40秒の端末操作）。
2. 周期のずれを**4時間ごとに揃え直す**。ウェイクロックは使わない（電池優先、数分の誤差は許容）。
   → **2026-09-23 に廃止**（下記「追補」）。
3. 稼働中のスクリプト一式を**リポジトリに登録**する（端末上にしか無い状態の解消）。

## 方式

```
Androidのジョブスケジューラ（15分周期・persisted・network none・battery-not-low false）
  └─ Termux ~/bin/line-auto-export
       └─ proot: auto-export.sh
            ├─ flow.sh      … LINEのUI操作
            └─ reanchor.sh  … 位相リセット（切り離して起動）
```

### 位相リセット（reanchor.sh）

ジョブスケジューラは時刻を指定できず、登録した瞬間が起点になる。この性質を利用し、
**次の15分境界（:00/:15/:30/:45）まで待ってから登録し直す**ことで位相を揃える。

- 起動判定は `auto-export.sh` が行う（前回から4時間経過。状態は `/root/line-auto-export/last-reanchor`）。
- 実処理は `setsid nohup` で切り離す。ジョブの実行時間制限（約10分）を受けないため。
- ウェイクロックを使わないため、端末が深く眠ると待ちが伸びる。
  実測（2026-09-19）: 狙い 20:15:00 に対し実際 20:15:44（44秒の遅れ）。
- リセット間の最大ずれは約9〜10分、追加実行は1日6回。

### 見送りと再試行

スマホ使用中（画面オン＋ロック解除）は実行を見送る。前面の操作を奪わないため。
15分周期では次の回が15分後に来るので、見送り専用の再試行機構は設けない。

## 受け入れ基準と検証

| 基準 | 検証方法 | 結果 |
| --- | --- | --- |
| 15分周期で登録されている | `dumpsys jobscheduler` の `JOB #u0a420/4203` | `PERIODIC: interval=+15m0s0ms` を確認 |
| 実際に約15分間隔で回る | `auto-export.log` の start 行の間隔 | 平均15.6分（n=32） |
| 成功率が実用に足る | 同上の done/FAIL/skip | 48回中 成功44・見送り2・失敗2 |
| 位相リセットが機能する | `reanchor.log` と登録内容 | 20:15:44 に登録し直し（狙い20:15:00） |
| 暗証番号が露出しない | スクリプトへの埋め込み有無、ファイル権限 | 埋め込みなし。600でなければ実行中止する判定あり |

## 外部・過去事例の参照と我々への応用

- 同一リポジトリの先行事例: 取り込み側の定期点検（`tools/termux-line-import`、PR #3538）。
  termux-job-scheduler を 15 分周期・`--persisted true --network none --battery-not-low false` で
  登録する形が既に稼働しており、本便の自動書き出しも同じ登録条件に揃えた。
- Android の公式仕様: JobScheduler の周期指定は Android N 以降 15 分が下限で、実行時刻は保証されない
  （`termux-job-scheduler --help` にも明記。実測でも 10 分指定は 15 分へ切り上げられた）。
  時刻を保証する手段はアプリ内の AlarmManager しかないが、本方式はアプリを持たないため採らない。
- 過去の失敗から学んだ点: 2026-09-19 に導入した位相リセット（次の境界まで待って登録し直す）は、
  切り離しても Android がジョブ終了後に配下プロセスを停止するため 22 回中 21 回が完走しなかった。
  「待つ処理を後ろに残す」設計は Android では成立しないという教訓として、追補に記録した。

## 弊害・トレードオフ

- 実行回数が4倍になり、端末操作と送信件数、電池消費が増える。
- 位相リセットのたびに1回余分に実行される（1日6回）。
- ワイヤレスデバッグの接続が切れると全滅する（ADB方式の根本的な弱点）。解消にはアプリ方式が必要だが未達。
- LINE/OSの更新でUIの配置が変わると `flow.sh` の調整が要る。

## 維持の仕組み

- 守り手: `tools/line-auto-export/README.md`（配置・登録手順・実測・弱点）、本design.md。
- 人手で守る: ワイヤレスデバッグの維持、LINE更新時のUI調整、端末交換時の再配置。
  理由: 端末のGUI状態と開発者設定はCIから検証できない。


## 追補 2026-09-23: 位相リセットの廃止と ADB 接続先の自動復旧

### 位相リセットを廃止した

`reanchor.sh` を `setsid nohup` で切り離しても、**ジョブの実行が終わると Android が配下のプロセスを
停止する**ため、次の15分境界を待つ間に必ず殺されていた。

| 記録 | 件数 |
| --- | --- |
| 「位相リセット開始」 | 22 |
| 「登録し直し 完了」 | 1（2026-09-19 の手動テストのみ） |

ウェイクロックで延命する案は、電池を削り部品が増えるため採らない。15分周期では1回の失敗が次の回で
埋まるため、実行時刻を揃える実用上の利点が無いと判断し、仕組みごと削除した。
`auto-export.sh` からの起動判定、`reanchor.sh`、`last-reanchor` を削除。

### ADB 接続先の自動復旧を追加した

Wi-Fi が切れて復帰すると、ワイヤレスデバッグは新しいポートで起動し直す（2026-09-23 実測:
40359 → 44861、約6時間停止）。保存済みの接続先で繋がらないとき `adb-discover.sh` が
30000-55000 を走査し、`adb connect` 後に `adb devices` が `device` になった先を採用する。

- 実測: 走査64秒・候補2個、全体で約97秒（故障状態を再現して検証）
- 候補の検証に `adb shell` を使うと `offline` 相手で待たされ、全体で24分かかった。`devices` の状態で判定する
- `adb mdns services` は何も返さず、`getprop` は proot から権限が無い（どちらも実測済み。代替手段として使えない）

### 送信結果の待ちを90秒から4分にした

Termux に「他のアプリの上に重ねて表示」権限が無いと、共有後のセッション起動が遅延する。
2026-09-23 は 10:16 と 10:31 の実行が90秒以内に記録されず失敗扱いになり、端末を触った 10:37 に
溜まっていた8件が一斉に処理された（1件 accepted・7件は重複として正しく除外）。
ログ: `Termux:PermissionUtils: com.termux does not have Display over other apps (SYSTEM_ALERT_WINDOW) permission`。

待ち時間の延長は誤判定を減らす保険で、根本対策は端末設定での権限付与（人手）。
