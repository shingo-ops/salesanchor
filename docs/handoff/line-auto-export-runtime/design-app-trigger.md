# 設計: 15分ジョブの中身を「ADB操作」から「アプリへの合図」へ差し替える

親: [design.md](design.md)（ADB方式の正本）/ [recon.md](recon.md)。アプリ側: [../line-auto-export-app/design.md](../line-auto-export-app/design.md)。
backend/DB/API の変更なし。

## 背景（PO合意 2026-10-08「①やって」）

- ADBのワイヤレスデバッグは**鍵が失効して接続不能**になり、本番は **2026-10-07 17:36 から停止**（再ペアリングには人の操作が必要で、しかも再発する型）。
- 一方、自作アプリ（`release/line-auto-export-app`、PR #4004）が **ADBを一切使わず**「画面消灯＋PINロックから解除→LINE書き出し→Termux取り込み→送信」を実機で通した（2026-10-08 11:48、Wi-Fiオフ・モバイル通信のみで受理200）。
- ただし**アプリにタイマーが無い**ため、いまは手で合図を撃つまで動かない。
- そこで **既存の15分ジョブ（termux-job-scheduler job 4203）はそのまま使い、その中身だけをアプリへの合図に差し替える**。
  これで今日から自動運転が戻り、ADB依存が消える。5分間隔化はアプリ内タイマー（段階3）で別途行う。

## KGI

| # | 基準 | 検証方法 |
|---|---|---|
| 1 | ADBを一度も使わずに、15分ジョブから自動で送信が完了する | `auto-export.log` に `adb` の記録が無く、`events` に `stage='auto' result='ok'` が入る。2回連続で確認 |
| 2 | スマホ使用中は実行されず、履歴に残る | 画面オン・ロック解除の状態でジョブを起動 → `events` に `stage='auto' result='skipped'` |
| 3 | 送信の失敗は従来どおり理由付きで残る | 送信が401等で失敗した回に `stage='auto' result='failed'` と理由が残る |
| 4 | 実行後にロック画面へ戻る | 実行後 `dumpsys window policy` 相当で施錠を確認（ADBが使えないため、当面は目視＋アプリの通知で確認） |
| 5 | ADB方式へ切り戻せる | `MODE=adb` で起動すると従来どおり動く（コードを消さない） |

## 方式

### モード切替（切り戻しを残す）

- `auto-export.sh` の先頭で `MODE=${LINE_AUTO_EXPORT_MODE:-app}`。既定は **app**。
- `MODE=adb` のときは**従来のコードをそのまま通す**（ADB探索・解除・flow.sh・EDITタップ・再ロック）。削除しない。
  理由: アプリ方式の実績がまだ各1回であり、戻せる道を残す（PO判断②は未回答のため、消さない側＝安全側を採る）。

### app モードの流れ

1. `flock -n`（従来どおり多重起動を防ぐ）。
2. `events` の現在の最大idを記録する。
3. **アプリへ合図を撃つ**（ADB不要）:
   ```
   CLASSPATH=/data/data/com.termux/files/usr/libexec/termux-am/am.apk \
   /system/bin/app_process -Xnoimage-dex2oat / com.termux.termuxam.Am \
     broadcast --user 0 -n jp.salesanchor.lineexport/.RunReceiver \
     -a jp.salesanchor.lineexport.RUN_ALL
   ```
   **`--user 0` と `-n`（宛先名指し）は両方必須**。2026-10-08 実測で、`-n` の無い暗黙ブロードキャストは**一度も届かなかった**（09:23・09:28）。
4. **最大180秒**、3秒間隔で `events` を見る。
   - `stage='send'` の終端結果（`accepted`/`pending_review` 以外も含む）が増えていれば、それを結果として採る → `ok` または `failed`（理由はそのsend行の理由）。
   - 180秒待って `send` 行が1行も増えなければ **`skipped`** として記録する。理由は
     `アプリが実行しなかった（スマホ使用中か、アプリ側の失敗。アプリの通知を確認）`。
5. **再ロックはスクリプトでは行わない**（ADBが無いため不可）。**アプリ側で行う**（下記）。

### なぜ「結果が来なければ failed ではなく skipped」なのか

- スマホ使用中の見送りと、アプリ側の失敗を、**スクリプトからは区別できない**（アプリの結果はアプリの通知にしか出ず、proot からは `/sdcard` が見えないため読めない）。
- 日中は使用中の見送りが頻繁に起きるため、これを `failed` にすると**失敗通知が鳴り続ける**（2026-10-06 に連続失敗で鳴らす改修を入れたばかりで、逆効果になる）。
- **アプリ自身が失敗を通知する**（`書き出し: 失敗` ＋ 段階名）。段階名まで出るぶん、スクリプトの汎用通知より情報が多い。
- 長時間の沈黙は `client.py` の定期点検（詰まり通知 4202）が拾う。したがって「見送り扱い」にしても見逃しにはならない。
- 将来、アプリが共有ストレージに結果を書き、Termux側（proot ではなく）がそれを読んで渡す形にすれば区別できる。**今回はやらない**（機構が増える）。

### アプリ側: 実行後の再ロック（この差し替えに必須）

- ADB方式は実行後に `KEYCODE_HOME` と `KEYCODE_SLEEP` を撃って施錠していた（`auto-export.sh` 旧 `:169-170`）。
  アプリ方式ではスクリプトから撃てないため、**何もしないと解除されたまま画面消灯待ち（最大約60秒）になる**。
- 対処: `RUN_ALL` の流れの最後に **`GLOBAL_ACTION_LOCK_SCREEN`（API28、定数値 8）** を実行して施錠する。
  ビルド環境の `android.jar` は API23 なので**定数を直書き**する（`GestureCompat` と同じ方針。実機は Android 16）。
- **`RUN_ALL` のときだけ施錠する**。`EXPORT` 単体（検証用・すでに解除して使っている状態）では施錠しない。
- 施錠は送信結果を待たずに行ってよい（送信は Termux 側が画面と無関係に続ける）。ただし **EDITタップの完了後**に行う。

## 弊害・トレードオフ

- 失敗の粒度がスクリプト側では粗くなる（上記のとおりアプリの通知が主になる）。
- `flow.sh`・`adb-discover.sh` は使われなくなるが**残す**（`MODE=adb` 用）。
- アプリのユーザー補助が無効化されると、アプリが「未接続」の通知を出すだけで、スクリプトは `skipped` を積む。詰まり通知で気づく形になる。
- 15分の間隔は変わらない（OSの定期ジョブの下限）。5分化は段階3。

## 計画

1. 本番 `/root/line-auto-export/` にある**未コミットの 2026-10-06 改修**（失敗理由の書き分け・連続失敗で鳴らす通知）を先にコミットして、リポジトリと本番を一致させる。
2. `auto-export.sh` に `MODE` を導入し、app モードを実装する。
3. アプリ側に実行後の施錠を入れる（`release/line-auto-export-app` 側の作業）。
4. 端末へ配置 → 手動で1回 → ジョブ任せで2回連続を確認。
5. 合格後、段階3（アプリ内タイマー5分）へ。
