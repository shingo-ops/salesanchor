# 設計：テナントの定義を1つにそろえる（ADR-1005 段階1、ADR-1007 段5、2026-10-07）

状態：設計案作成済み／Opus 自己審査 APPROVE（段階を区切った形。§6）／PO 承認済み（ADR-1007 の進め方「進めて良い」2026-10-05、ADR-1005 の方向性 2026-10-06）。新しいテナントの作成の DDL を変えるので、マージには PO の「GO #番号」が要る（ADR-136）。

**進め方（必須）**
1. コミット1（この時点）：失敗する試験だけを入れる（RED）。CI で、食い違いの正確な一覧を出す。
2. コミット2：設計担当が一覧を見る。わざと新しいテナントに入れていない列や表があれば、PO に確かめる。そのうえで、tenant.py のひな形を直して、試験を通す（GREEN）。
3. マージは、#4012 の後、#4020（段階2）の前。

## 1. 目的（PO に見える変化）
- 画面の見た目は変わらない。
- 新しく作ったテナントの表の形が、既存のテナント（migration を全部流したもの）と同じになる。
- これにより、migration を「1回だけ流す」形（段階2）に変えても、新しいテナントに足りない列や表が出ない。

## 2. 現在地（recon.md の要約）
- テナントの表の定義は2か所にある。
  - 新しいテナント用：backend/app/services/tenant.py のひな形
  - 既存のテナント用：テナントのループを持つ migration、103本
- 今は、デプロイのたびに全 migration を流し直しているので、新しいテナントの足りない分は、次のデプロイで補われている。
- 静的な比較では、ひな形の既知の表に無い列が 42（15ファイル）、ひな形に無い表が 20 あった（下限。試験の結果が正）。

## 3. 既存の ADR との関係
- ADR-1005 の段階1（テナントの正本を1つにする）。
- ADR-1007 の決定3（テナントの作成を完全にする）と、実施順序の段5。
- ADR-155：この PR は値を扱わない（構造だけ）。

## 4. 変更
- コミット1：backend/tests/test_tenant_template_parity_pg.py
  - CI で動く RLS_ADMIN_DATABASE_URL で、使い捨ての DB の中に新しいテナントを作る。
  - 表・列の型と既定値・索引を写し取る。
  - 登録済みのテナント向けの migration（103本）を、登録の順に流す。
  - もう一度写し取って、変わらないことを確かめる。
  - 失敗したときの表示が、食い違いの一覧になる。
- コミット2（一覧を見てから）：tenant.py のひな形に、足りない列・表・索引を足す。足さないと決めたものは、理由をこの文書に書く。
- 触らない：既存のテナント、migration の中身、本番。

## 5. 代替案と選んだ理由
- 静的な比較だけで直す：文字の組み合わせで作る文や、DO ブロックの中の DDL を見落とす。そのため、本物の DB に流した結果で比べる。
- ひな形をやめて、新しいテナントにも migration を全部流す：段階2（1回だけ流す）と合わない。テナントの作成も遅くなる。
- 一覧を見ずに機械的に全部足す：わざと入れていない列があった場合に、決めたことを壊す。そのため、コミットを2つに分けた。

## 6. リスクと対処
| リスク | 対処 |
|---|---|
| migration の中に、空の新しいテナントでは失敗するものがある | 失敗した migration は、最後に一覧で報告し、食い違いには数えない。報告を見て扱いを決める |
| 試験が、並んで動くほかの試験のテナントに触る | 別の使い捨ての DB の中で行う |
| ひな形に足した列が、新しいテナントの作成の時間を延ばす | 列と索引の追加だけで、データは入れない。CI の時間で確かめる |
| ローカルで PG を動かせない（ディスクの空き・安全の仕組み） | CI を、唯一の実行の場にする |

## 7. 受入条件と検証方法
| 基準 | 検証方法 |
|---|---|
| コミット1 で、試験が失敗して食い違いの一覧が出る | CI の pytest-run-internal のログ |
| コミット2 で、試験が通る | CI |
| 足さないと決めた列や表に、理由がある | この文書の追記と、PO の確認 |
| 既存の試験が壊れない | CI の全体の試験 |

## 8. 外部・過去事例の参照と我々への応用
- 外部事例：一般的な migration の道具では、新しい環境は migration を全部流して作り、別のひな形は持たない。ここでは、テナントの作成の速さのために、ひな形を残す（ADR-1005 の段階1の選択肢 1A）。そのかわり、試験で同じ形であることを保つ。特定の数値には依存しないため、外部の事例は挙げない。
- 過去事例
  - #3965 の調べ（main の docs/handoff/migration-runner-redesign/recon.md）で、「新しいテナントは、ひな形より約40列足りない」とされていた。
  - 今回は、それを本物の DB の試験で正確に測る。

## 維持の仕組み
- 守り手: backend/tests/test_tenant_template_parity_pg.py（新しいテナントと、migration を流したテナントの形が同じであることを、CI で毎回確かめる）。テナント向けの migration を足したら、ひな形も直さないと、この試験が失敗する。設計担当（Opus）が、一覧の判断を行う。
