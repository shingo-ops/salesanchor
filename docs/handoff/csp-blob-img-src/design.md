# 設計 — CSP への blob 追加（便4e）

> この文書は何か（専門用語なしの1行）:
> 取得した画像をブラウザが表示できるように、配信設定を1語だけ緩める設計。

対象ADR: ADR-091
recon: docs/handoff/csp-blob-img-src/recon.md
親テーマ: docs/specs/attachment-storage/README.md

## 1. あるべき姿

顧客が送った画像やファイルが、いつ見返しても受信箱に残っている。

## 2. recon（実測）

docs/handoff/csp-blob-img-src/recon.md を参照。要点は次の3つ。

- Blob の取得は成功している。backend が 200 を返している。
- 画面には壊れた画像アイコンが出ている。img は描画されている。
- CSP の img-src に blob が無いため、ブラウザが読み込みを止めている。

## 3. design（技術How）

nginx/nginx.conf:82 の img-src に blob を追加する。

同じファイルの177行目に既に同じ指定があり、書き方はそれに揃える。

DBの既存行は変更しない。新しく受信する画像から正しく表示される。

## 4. 外部・過去事例の参照と我々への応用

Content Security Policy の img-src は、画像の読み込み元を制限する仕組みである。
fetch で取得したデータを URL.createObjectURL で表示する構成では、
blob スキームを明示的に許可する必要がある。

blob は同一オリジンで生成されたデータのみを指し、
外部からの読み込み経路を新たに開くものではない。

本リポジトリでは Grafana 用のブロックが既に blob を許可している。
今回はアプリ本体のブロックにも同じ指定を加える。

我々への応用: 認証つきAPIから画像を取得して表示する設計を採る場合、
CSP の img-src に blob が必要になる。設計時に配信設定も合わせて確認する。

## 5. 弊害・トレードオフ

- 弊害: CSP を1語ぶん緩める。
  ただし blob は同一オリジンで生成したデータに限られ、
  外部からの読み込みは引き続き許可されない。
- 弊害: 既存2件の attachment_url は古い形式のまま残る。
  それらは引き続き表示されない。テストデータのため放置する。
- トレードオフ: CSP を緩めずに済ませる案として、
  画像を base64 の data URL に変換して埋め込む方法がある。
  ただしメモリ消費が増え、大きな画像で問題になる。
  blob の方が扱いが軽い。

## 6. 受入基準

| 基準 | 検証方法 |
|---|---|
| 2箇所とも blob を含む | grep で該当が2件 |
| blob 無しの指定が残っていない | grep で行末が data で終わる指定が0件 |
| 変更が1行のみである | git diff の追加1行 削除1行 |
| 本番に反映される | デプロイ後 nginx コンテナの設定を確認する |
| 画像が表示される | Discord へ画像を送り受信箱で表示を確認する |

## 7. 維持の仕組み

- 守り手: 人手で守る
- 理由: CSP の効果はブラウザでの描画時に現れる。
  現在のテスト基盤では実ブラウザでの CSP 適用を再現できない。
- 対象: img-src から blob が失われること。
- 検知方法: PO による実機確認。Discord へ画像を送り受信箱で表示されるかを見る。
