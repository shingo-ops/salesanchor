## 2. 結論：メモリの運用は「構造的に最適ではない」

| 判定の項目（データを見る前に計画書で決めた基準） | 基準 | 観測値 | 判定 |

**構造的な問題の核心（事実の組み合わせ）**
1. **上限が、実際に必要な量より小さい。**
   - backend：起動直後で 1 ワーカーが約 245MB。2 ワーカーと親プロセスで約 500MB 超になる。上限は 512M。
     - 証拠：`memory.peak` が上限と同じ値、`memory.events max=147`、cgroup の swap 159MiB（§4）。
   - celery：親が約 107MB、子が各約 257MB で、合計約 620MB。上限は 512M。
   - どちらも OOM で強制終了こそしていないが、上限に達して swap へ押し出されながら動いている。
2. **ADR-081 と実物が食い違っている。** ADR は workers=1 を標準とし、Scope IN で「1 に固定」としている。実物は 5/22 から workers=2 のまま（§7）。
3. **ただし今は、workers=1 にしてはいけない。** async のエンドポイント 609 個のうち、同期の処理でイベントループを塞ぐ箇所が少なくとも 9 か所ある（下の表）。
   - ワーカーが 1 つだと、その間は全ユーザーの要求と SSE（受信箱の自動更新）が止まる。
   - ADR-081 は、この前提を確認しないまま決められている。
4. **ホストで最大の消費者は dockerd（884MB）。** 過去の記録（EV-20260628-001、`docs/ai-agents/evidence-registry.md:1106`）と同じ傾向。
   - 8日で worker コンテナが 148 回作り直されており、デプロイの頻度が高い。

**注（判定 2 について）**
- 計画時の基準は × になった（最大 3）。
- 1 つの async ワーカーでも、複数の要求を同時に処理できる。そのため、「in_flight が 3」だけでは、workers=2 が必要とは言えない。
- 決め手になるのは、上の 3（塞ぐ処理があるかどうか）。基準を後から変えたわけではない。基準の結果（×）はそのまま記録し、そのうえで、判断の根拠には 3 を加えている。

## 5. Grafana の鍵
- 原因（確定。§1-5）：Grafana の DB の admin パスワードが、prod2 の env（30 文字）とも、手元の2つの値とも違う。旧トークンは期限切れ（`api-key.expired`）。
- PO の選択：「設定値にリセット」。
- 残っていること：エージェントからの実行は、Claude Code の安全判定に拒否された。PO が `!` で実行する。
  1. リセット：このセッションでコマンドを提示済み。期待値は `after_reset_auth=200`。
  2. `~/.claude-access.env` の `MGMT_GRAFANA_PASSWORD` を同じ値に合わせる。
  3. rotate_grafana_token.sh（リポジトリ外。前のセッションの scratchpad にある）を実行する。
- 再発防止：トークンの失効予定日を `docs/runbooks/claude-monitor-access.md` に記録する（復旧した後に追記する）。
- 2026-10-10 完了：パスワードリセット after_reset_auth=200／トークン再発行 http 200・失効 2027-01-08／runbook 追記は本 PR。

## 7. 審査（Architect の観点。同一の AI による自己審査）
- 判定：**REVISE → 指摘を反映して APPROVE（設計の範囲に限る）**
- 指摘と反映
  1. ①を入れずに workers=1 にする案は不可。§2 の表に、塞ぐ箇所を file:line で示し、①を②の前提にした。
  2. 「250MB は太った結果」という当初の仮説は、起動1分の実測（249〜282MB）と import の測定（245MB）で否定された。§2 に反映した。
  3. 計画時の基準 2 は ×。基準を後から変えたのではなく、注で判断の根拠を補った。
  4. ③の上限の値（768M）の根拠：celery の実測の合計 約620MB に、子が1回作り直されるときの余裕（約150MB）を加えた値。ホストの余力は、②の後で再度測ってから実施する。
- 残る未確認の事項
  - backend の「app」の 136MB の内訳（§4-1）。改善の候補にはなるが、今回の判定には影響しない。
  - `backend/app/routers/invoices.py:835` を含む関数の名前。
  - `backend/app/services/email_sender.py:70` が async の経路から呼ばれているか。①の実装カードを作る前に確認する。
  - prod1 の 9091 番ポートが外部から届くか（docker は ufw を迂回しうる）。④で撤去すれば問題ではなくなる。
- PO の承認が要る点：§4 の各便、§6 の各区分（それぞれ y/n）。
