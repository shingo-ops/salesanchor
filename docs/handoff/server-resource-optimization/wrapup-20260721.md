## 追記5: reaper並行実行の構造問題と改善設計(2026-07-23調査・次セッション実施)

### 問題(実測で確定)
- `scripts/reaper-worktree.sh` は冒頭31-35行で `/tmp/reaper-worktree.lock.d` の mkdir 排他を取り、取得失敗時は `echo "[reaper] another instance is running; skip."` の後 **exit 0(成功扱い)** で即終了する。
- 起動経路は4つ: `.github/workflows/reaper-schedule.yml`(定期) / `ops/launchd/jp.salesanchor.reaper-onlogin.plist`(ログイン時) / `scripts/new-worktree.sh`(作業台作成のたび自動) / 手動。**全経路が同一ロックを共有**。
- 帰結: 並行セッションが作業台を作るたびに衝突し、**掃除が黙ってスキップされ続ける**。exit 0 のため誰も気づかない。2026-07-23時点で worktree 101件・上限100到達で全便が着手不能になった。
- reaper は掃除だけでなく **active-work.md の IN_PROGRESS→DONE 自動更新も担う**(294-309行)。スキップが続くと台帳のDONE化も止まり、残骸予約(#2920/#2944 で実測)の温床になる。
- ADR矛盾: ADR-114 は「reaper は冪等なので concurrency 制御は不要」と明記。後発の ADR-029 で排他ロックが追加された。設計判断の整合が未整理。
- ロック残留の疑い: 2026-07-23 に「ロックあり・プロセスなし」を観測。mkdir+trap 方式は強制終了(kill -9・電源断)でロックが残り、以後の実行が永久に開始されない既知の失敗形。

### 改善設計(外部事実に基づく・次セッションで recon→設計→GO→避難訓練)
- **A. 待機方式へ変更**: 即スキップ(`-n` 相当)から、最大N秒待って取得を試みる(`flock -w` 相当)へ。並行時も掃除が実行される。実装は mkdir 自前ロックを `flock` に置き換える(カーネルがプロセス終了時に自動解放するためロック残留が構造的に消える)。
- **B. スキップの可視化**: 待っても取得できなかった場合、ログとメトリクスに記録する(exit 0 の黙殺をやめる)。
- **C. dead-man's-switch**: 最終成功時刻を textfile に記録 → prod2 の Prometheus/Alertmanager で鮮度監視 → 一定期間更新がなければ Discord 警報。**本テーマの f2-cleanup で完成済みの黒板方式と同型**(scripts/f2-cleanup.sh の write_blackboard・chmod 644・/home/ubuntu/node_exporter_textfile/ の実装をそのまま流用可能)。
- 外部エビデンス: 本番cron運用の要諦は「スケジュールが発火した」と「ジョブが成功した」の区別。静かな停止・古いロックの残留が典型的な障害要因。冪等なジョブでは重複より「実行されないこと」の方が損失が大きい。
