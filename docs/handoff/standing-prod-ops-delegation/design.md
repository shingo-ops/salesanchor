# design：本番サーバー上の作業の委任（ADR-1003 追記）

参照: docs/handoff/standing-prod-ops-delegation/recon.md、ADR-1003「追記（2026-11-02）」、ADR-1034、ADR-1033。

## 目的
PO が設計で合意した作業を、本番サーバーの段で PO の手を借りずに最後まで進める。危ない点は設計の段階で PO に説明する。

## 変更前 → 変更後
- 前: 無制限鍵での変更を伴う作業は、作業ごとに PO の GO（AGENTS.md:26）。自動の安全判定が毎回止め、PO の `!` 実行が要った（7件/週）。
- 後: PO が合意した設計の作業手順に書かれ、審査役が APPROVE した行は、Opus 本人が控えを取ってから実行してよい。除外は ADR-1003 追記のとおり PO 本人の GO。

## 対象と対象外
- 対象: AGENTS.md:26 の1行、ADR-1003 の追記、opus-delegation.md の節と履歴。マージ後に PO の `!` で自動の安全判定の許可の行を1つ足す。
- 対象外: コード・DB・CI・見張り（フック）の中身。担当（Sonnet）への無制限鍵の利用。

## 代替案
| 案 | 結果 | 理由 |
|---|---|---|
| A 作業ごとに期限付きの許可を足す（FNT-1 の形） | 不採用 | 足すたびに PO の `!` が要り、PO の「再度許可を取りに来なくてもいい」に反する |
| B 条件付きの常設の許可（本案） | 採用 | PO の手は最初の1回だけ。危ない点は設計の段階で説明済みのものに限る |
| C 無条件で無制限鍵を許す | 不採用 | 手順書に無い行や消す操作まで通る |

## 受入条件
| 基準 | 検証方法 |
|---|---|
| AGENTS.md の無制限鍵の行に委任の一文がある | `git show origin/main:AGENTS.md` で該当行を読む |
| ADR-1003 に条件6つと除外が書かれている | `git show origin/main:docs/adr/ADR-1003-go-delegation-to-opus.md` |
| 許可の行が設定に1つ入り、記録帳に本 PR 番号で記録される | 次の週次点検の consent-audit.py で、増えた1件が異常に出ない（記録あり） |
| 委任後の本番作業がすべて記録に残る | 週次点検で ~/CC報告ファイル-keep/prod-ops/ の行数と、手順書に無い行 0 件 |

## リスクと対処
ADR-1003 追記「弊害と対処」を正とする。

## 維持の仕組み
- 守り手: `scripts/dev/consent-audit.py`（週次の同意と権限の点検）と `~/CC報告ファイル-keep/prod-ops/` の記録の読み合わせ。
- 解除: PO の「委譲停止」。

## 外部・過去事例の参照と我々への応用
- 外部事例: 該当なし。理由: 自社の PO と AI の間の承認の決め方であり、数値の裏付けがある外部事例を当てはめられない。
- 過去事例（自社）: 2026-10-26 の Approve の許可（28793f25）と 11-01 のクラウドの担当の許可（0c57a9f8）は、足した後の止まりが 0 件になった。期限付きの FNT-1・FNX-1 では手順書の行が PO の手なしで流れた。
- 我々への応用: 同じ「条件を書いた許可の行」の形を常設にする。期限切れのまま残った反省（2026-11-02 点検）から、期限ではなく条件と毎週の記録の読み合わせで守る。
