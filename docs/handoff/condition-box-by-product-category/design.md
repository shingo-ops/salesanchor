# design: 状態判定 — 箱の商品を単品扱い（FLAG_SINGLE）にしない

- 状態（2026-10-06）
  - 設計：Opus が作成し、自分で審査した（同じ AI による審査で、独立した第三者のレビューではない）。判定は §10。
  - PO：整備の着手は承認済み（2026-10-06「整備したい」）。2段構え（§4）は 2026-10-06 に PO が「直し方（2段階）合意、あなたに任せて確実に箱化単品化の分類分けをすることは可能か？推測で進めないでほしい」で合意した。段階2の分類は §4-2 の証拠の基準で Opus が行い、本番への反映の前に一覧の要約で PO の「y」を得る。
  - 実装：段階1を Sonnet に委任した。段階2は Opus が分類案を作成中。
- 根拠：[recon.md](recon.md)（`docs/handoff/condition-box-by-product-category/recon.md`）
- 関係する ADR：状態判定を定めた ADR は無い（recon §2）。状態のルールは handoff の設計で管理されている前例（`docs/handoff/tcg-cond-r5-fix/design.md`）に合わせ、この設計書で管理する。ADR-1001-deprecate-tcg-products-unify-to-public（分類マスタを public に統一）を前提にする。

## 1. 目的（POの言葉）
「箱の商品を『単品』と誤って判定し、一覧に載せていなかった → これを整備したい」

## 2. 成功条件（PO 承認待ち）
| # | 基準 | 検証方法 |
|---|---|---|
| K1 | 反映後に解析された行で、商品の分類が箱系、かつ単位の区分が 条件つき・複合・数量専用 の行のうち、FLAG_SINGLE になったものが **0件** | 本番 DB で、反映後の computed_at の行を区分×分類で数える |
| K2 | 単位の区分が 単品系・冊子系 の行、商品の分類が空かシングル系の行、商品が見つからない行は、判定が**変わらない** | backend のテスト（既存の R4・R5 のテストがそのまま通る）＋反映前後で同じ区分の FLAG_SINGLE の割合を比べる |
| K3 | 段階2の分類の後、先日の標本と同じ条件（商品・単位とも解決済み・needs_review=false の FLAG_SINGLE）の行で、Opus の目視で「未開封の箱・セット」と判定されるものが **約245件 → 30件以下** | 分類の後に解析された行から同じ抽出をして、目視で数え直す |

## 3. 対象と対象外
- 対象
  - 段階1：状態判定の最後のフォールバック（`backend/app/services/tcg_analyzer_svc.py:879-880`）に、商品の分類を見る分岐を1つ足す。
  - 段階2：商品マスタの分類（`products.product_category_id`）の空欄を埋める（本番データの変更。一覧を PO に見せて承認を得てから）。
- 対象外（触らない）
  - 単位マスタ・状態マスタの中身、キーワードのルール（R1〜R3）、R4 の箱系・R5 のパック系の既定
  - 配信の絞り込み（include_flag_single は false のまま）
  - プロモカード・雑誌付録の扱い（PO の商売上の判断。別件）
  - 書き写し方式（gemini_raw_copy_v10・v101）と影の判定（extraction_shadow_svc）：商品の照合が無いか、本番の経路でないため
  - products に列を足すこと（列の数の上限のため。分類は既存の product_category_id を使う）
  - 過去の行の一括再解析（配信は直近48時間の行だけを見るので、新しい投稿で置き換わる）

## 4. 変更内容

### 4-1. 段階1（コード）
1. `resolve_condition_v2`（:787）に、省略できる引数 `product_kubun_type: str = ""` を足す。既定値なので、ほかの呼び出し元（recon §3）の挙動は変わらない。
2. :879 の FLAG_SINGLE を返す直前に、次の分岐を入れる。
   ```python
   # --- R4c: 商品分類既定 — 単位では箱か決まらないが、照合された商品が箱系 ---
   if product_kubun_type in {"箱系", "箱系大"} and kubun in {"条件つき", "複合", "数量専用"}:
       cid = _find_cond_id(cond_entries, "CN0003") or cond_canonical_to_uuid.get("Sealed box")
       return ("Sealed box", cid, b4_prefix + "R4c:商品分類既定")
   ```
   - キーワード（R1〜R3）に当たった行は、この前に返っている。
   - **訂正（2026-10-06、実装中に判明）**：CN0008（FLAG_SINGLE）の語は、適用区分が「枚系,単位不明」なので、単位の区分が 条件つき・複合・数量専用 の行では主ループで当たらない（`backend/app/services/tcg_analyzer_svc.py:846` の app_kubun_matches）。このままでは「PSA10 個」のような行が箱系の商品で Sealed box になる。そこで R4c には、**CN0008 の語（search_kw、exclude_kw を考慮）が、主ループと同じ照合対象の文字列に1つも当たらないこと**を条件に足す。適用区分は見ない。当たれば、今までどおり FLAG_SINGLE（basis も従来どおり）。
   - **訂正2（2026-10-06、本番の状態マスタの確認で判明）**：箱の状態の語（CN0003 Sealed box の「シュリ付き」等、Damaged sealed box の「難あり・箱痛み」等、Opened box の「開封済み」等）は適用区分が「箱系」で、単位が 条件つき 等の行では主ループで当たらない。R4c が一律に Sealed box を返すと、「難あり 個」「検品のため開封済み 個」も Sealed box と表示されてしまう（標本に実例あり）。そこで R4c は、CN0008 の語の確認を通った後、**同じ行を単位の区分「箱系」として状態判定をやり直し**（`resolve_condition_v2` を kubun="箱系"・product_kubun_type="" で呼ぶ）、その結果を返す。basis は `R4c:商品分類既定>` の後ろに、やり直しの basis を続ける（例 `R4c:商品分類既定>R2:難あり`、語が無ければ `R4c:商品分類既定>R4:単位既定`）。
   - 単品系（枚）・冊子系（冊）は対象外にする。標本では、枚 × 箱系の行に鑑定済みシングルがあった（recon §5）。
   - 単位が不明・空の行は対象外にする。単位が解決していない行は、どのみち配信されないため（`backend/app/services/tcg_distribution_svc.py:260-267`）。
   - 箱系大（ケース）の商品でも Sealed box にする。単位からケースと分からない以上、箱として扱うほうが安全なため。
3. 呼び出し（:1509）で、`pid_resolved` が真のときだけ、照合された商品の kubun_type を渡す。
   ```python
   product_kubun_type=(product_code_to_kubun_type.get(matched_code, "") if pid_resolved and matched_code else ""),
   ```
   - `product_code_to_kubun_type` は `load_product_kubun_type_map`（:156-174）の結果で、正本は product_category_id。作品名が入る category_class は使わない（recon §4）。
   - 候補が絞り切れていない（pid_resolved が偽の）行には渡さない。
4. テスト（`backend/tests/test_tcg_keyword_matching.py` に足す）
   - 箱系 × 条件つき・複合・数量専用 → Sealed box、basis が `R4c:商品分類既定`
   - 箱系 × 単品系・冊子系・不明・空 → FLAG_SINGLE（今までどおり）
   - シングル系・空の分類 × 条件つき → FLAG_SINGLE（今までどおり）
   - 箱系 × 条件つきでも、状態に PSA など CN0008 の語がある → FLAG_SINGLE（R1 が先）
   - 引数を省略した呼び出し → 今までと同じ結果（既存の 949-1021 がそのまま通る）
   - 解析全体で、pid_resolved が偽なら分類を渡さないこと

### 4-2. 段階2（商品マスタの分類を埋める）
- **分類の意味（PO の承認が要る）**
  - 箱系（PC_BOX）＝ 仕入元が数量の単位を「個」「セット」と書いたときに、未開封の箱・セットとして取引される商品。各弾（メガブレイブ、OP-17 など）、スターターセット・デッキ、特別BOX、プレミアムカードコレクション などが入る。
  - シングル系（PC_SINGLE）＝ シングルカード、または、まとめ売りのシングル（ARカード、SRカード、RRカード、AR/CHR、PSA 鑑定 など）。
  - 空のまま ＝ 判断がつかない商品と、プロモカード・雑誌付録（別件で PO が判断するまで）。
- 対象：is_current の行に出てくる、分類が空の 277 商品（recon §5）。Opus が商品名と取引の実例から1件ずつ分類案を作り、一覧（商品コード・名前・案・理由）を PO に見せる。
- 証拠の基準（推測で決めない。PO 2026-10-06）
  - 箱系：①商品マスタの名前・形式が未開封の商品（弾・スターターセット・デッキ・BOX・セット・コレクション）で、かつ ②取引の実例で単位が 個・BOX・セット、価格が箱の水準。
  - シングル系：①商品マスタの名前がカード単位、またはまとめ売りのシングル（ARカード・SRカード・PSA 鑑定 など）で、かつ ②取引の実例で単位が 枚、価格がカードの水準。
  - 保留（空のまま）：①と②が食い違う、箱と単品の両方の価格で取引されている、プロモカード・雑誌付録、実例が少なく判断できない。迷うものはメーカー公式の商品ページで中身を確かめ、それでも決まらなければ保留にする。
  - 一覧には、商品ごとに 分類・根拠（実例の件数・単位・価格の中央値）・確認した公式ページ を記録する。
- 本番への反映：PO の承認の後、既存の「PO 合意済みの本番データ変更」の手順（DRY-RUN → 件数確認 → COMMIT）で、`products.product_category_id` を更新する。戻すための控え（更新前の値の一覧）を先に取る。
- 段階2で、段階1の分岐が効く行の数が増える。段階1だけで直るのは、標本の 351件のうち 65件。

## 5. 影響の範囲
- 状態が FLAG_SINGLE から Sealed box に変わった行は、配信の条件をほかに満たしていれば、お客様の在庫一覧に「Sealed box」で出るようになる。
- `docs/handoff/condition-fallback-count/design.md` の「お手上げ」の数え方（`R4:単位既定:単位不明`）から、R4c の行は外れる。お手上げではなくなるので、数え方として正しい。
- `backend/app/services/tcg_unit_recovery_svc.py:476,935` は basis の完全一致で対象を選ぶ。R4c の行は対象から外れる。単位が解決済みの行だけが R4c になるので、単位を直す処理の対象から外れても問題はない。
- `is_current` は (商品, 状態) の組ごとに決まる（`backend/app/services/tcg_analyzer_svc.py:1708-1800`）。状態が変わると、同じ仕入元の同じ商品で Sealed box の組が新しくでき、古い FLAG_SINGLE の組が is_current のまま残ることがある。古い組の行は、配信では FLAG_SINGLE として除外される。

## 6. 代替案と選んだ理由
| 案 | 結果 |
|---|---|
| A. 単位「個」「セット」を箱系の単位に変える | 採らない。「AR素体 個」「SRバルク100枚セット」のようなまとめ売りのシングルも箱になる（標本に例がある） |
| B. FLAG_SINGLE を配信に含める（include_flag_single=true） | 採らない。お客様の画面に「FLAG_SINGLE」という状態が出るうえ、箱が単品と表示されたままになる |
| C. 商品の分類を見て決める（採用） | 照合された商品の分類で決まるので、まとめ売りのシングルはシングル系に分類すれば箱にならない。分類が空なら今までどおり |
| D. Gemini に箱か単品かを判断させる | 採らない。PO の決定（2026-09-30）で、Gemini は書き写しだけを行い、判定はシステムが行う |

## 7. リスクと対処
| リスク | 対処 |
|---|---|
| シングルが箱系の商品に誤って照合され、Sealed box になる | シングルの印があると箱系を候補から外す既存の防御（recon §3）、キーワード R1 が先に FLAG_SINGLE を返すこと、単品系を対象外にすること、の三重。K4 で目視して確かめる |
| 段階2の分類の誤り（シングルを箱系にする） | 一覧を PO が承認してから反映する。まとめ売りの商品はシングル系に入れる。判断がつかないものは空のまま |
| 弾（メガブレイブなど）を箱系にすると、「メガブレイブ 1パック」などがどうなるか | 単位がパック系なら、R5 が先に Searched pack を返す（:861-877）。単位が枚なら対象外。影響はない |

## 8. 戻し方
- 段階1：PR を revert して再デプロイする。新しい投稿から FLAG_SINGLE に戻る。
- 段階2：更新前の product_category_id の控えから、同じ手順（DRY-RUN → COMMIT）で戻す。

## 9. 進め方
1. PO が §2・§4-2 を承認する。
2. 段階1：Sonnet が実装し、PR を出す（DB の変更なし。`migrations/`・`.github/workflows/deploy.yml`・本番の scripts は含まない）。Reviewer の APPROVE と CI の通過の後、ADR-1003 の委任で Opus が GO を出し、マージする。反映後、新しい投稿で K1・K2 を確かめる。
3. 段階2：Opus が分類案の一覧を作る → PO が承認 → 控えを取る → DRY-RUN → COMMIT。反映後、新しい投稿で K3・K4・K5 を確かめる。

## 10. 設計審査（同じ AI による自己審査）

## 12. 外部・過去事例の参照と我々への応用
