# AT form-button contract research

Fixed source: `origin/main` object `a1cd9ea379cc7d85b797cca6b1cc092192296bc3`, read only with `git show` / `git grep`. The dirty checkout was not used. This is a contract study, not an implementation inventory; Sol1 owns the full AST count.

## Eligibility rule used

Included below only literal `btn-primary` / `btn-secondary` native buttons whose shared-Button mapping is explicit (`primary|secondary`, `size="md"`) and whose callback is local state or a mockable `api` boundary. I excluded deletion/bulk operations, external delivery/payment/authentication, imports, invoice/quote lifecycle actions, CSS-dynamic classes, bare `btn-sm`, and buttons with their own inline `style` or additional semantic class. This notably excludes ERP export, Google/PayPal connect/test/disconnect, invoice issue/pay/PayPal/PDF, quote send/approve/convert/PDF/FX, archive restore, purchase receive, Dex import preview/apply, GoalSetting's `gs-save-btn`, Knowledge new buttons with inline margin, and PurchaseOrders add-item with inline margin.

## Backend side-effect and authorization trace

### Invoice create: exclude from the next bounded batch

`backend/app/routers/invoices.py:325-435` protects `POST /invoices` with `require_permission("invoices.create")`, validates contact/company, writes invoice and item rows, records an audit log, commits, and invalidates the dashboard cache. It does not invoke PayPal, email, PDF delivery, or another payment operation in this handler. However, line 363 calls `get_fx_rate(data.currency)` for every non-JPY invoice. `backend/app/services/fx_rate.py:27,30-70` performs a synchronous outbound `httpx.get("https://open.er-api.com/v6/latest/JPY", timeout=5.0)`. Thus save can produce an external network request even though it does not send a customer message or charge money. A frontend-only API mock cannot prove that backend side effect. Exclude Invoice submit from this next migration batch; Invoice add-item remains local-state-only.

### Quote create: no external delivery/payment call found in the route

`backend/app/routers/quotes.py:146-261` protects `POST /quotes` with `require_permission("quotes.create")`, validates company/contact/lead relationships, writes a draft quote and item rows, records an audit log, commits, resets tenant context, invalidates dashboard cache, and reads the saved result. The handler contains no email, webhook, payment, authentication-provider, carrier, or other outbound client call. This is a DB write, but its observable frontend contract can be isolated with the existing `api` mock.

### Role permission save: separate security-sensitive candidate

The UI renders Save only when `canEditPerms = hasPermission("roles.update") && !isSystemRole` (`RolesPage.tsx:182,396-409`) and also disables it when clean or pending. Server `backend/app/routers/roles.py:378-454` independently requires `roles.update`, rejects missing/system roles, rejects roles at or above the caller's maximum priority, validates permission IDs, prevents granting permissions the caller lacks, replaces every `role_permissions` row, writes an audit record, commits, and invalidates tenant permission caches. This is an authorization-policy mutation rather than an ordinary form save. Keep it out of the uniform form batch and design/review it separately even though the JSX conversion itself is mechanical.

### Product create/update: suitable local DB form candidate

`ProductEditPage.tsx:119-192` sends the 34-key normalized payload to `POST /products` or `PATCH /products/{id}` and goes back on success. `backend/app/routers/products.py:356-492` separately requires `products.create` / `products.update`, validates `tcg_type`, writes the central product row, records an audit log, commits, resets tenant context, and invalidates dashboard cache. No external client, message delivery, payment, authentication-provider call, or bulk operation occurs in either handler. The `field-h-md` mapping to shared `size="md"` is already established by AS, and `form="product-edit-page-form"` plus explicit `type="submit"` can be preserved exactly. This is admissible, with the existing Commerce fixture reducing validation setup.

## Recommended bounded batch

Do not adopt all 13 as one risk class. After the backend trace, the largest clearly bounded group is **11 buttons in nine product files**: Profile (1), Company Basic/Channels (2), Invoice add-item only (1), Quote add-item/submit (2), PurchaseOrders submit (1), Dex edit save (1), TCG type/series submit (2), and ProductEdit submit (1). Invoice submit is excluded because non-JPY creation makes an outbound FX request; Roles permission Save is separated because it replaces authorization assignments and invalidates permission caches.

The lowest fixture-cost sub-group is **eight buttons in six existing page files**: Invoice add-item (1), Quote add-item/submit (2), PurchaseOrdersFormModal submit (1), Dex edit save (1), TCG type/series submit (2), and ProductEdit submit (1). These pages already have reusable AS fixtures. Profile and Company Basic/Channels (3 buttons) need new UiPrefs/full CompanyDetail fixtures and company reload/permission assertions, so root can split the 11 into 8+3 without changing product ownership semantics.

For the eight-button commerce/admin subgroup, meaningful additions are:

1. Extend CommerceNavigation for quote submit: required guards at zero writes; exact full payload; pending second click blocked; failure retains a representative input and retry; success exact destination. Click Invoice and Quote add-item controls and assert row count +1 with zero writes. Do not exercise Invoice submit as acceptance for this batch.
2. Extend PurchaseAdmin with PO success settlement (`onCreated` then close) in addition to its existing exact payload/pending/failure proof. Keep Roles permission Save out of this suite/batch unless a separate authorization card admits it.
3. Extend the same admin suite for Dex and TCG: exact PATCH/POST payloads, filtered/type reload increments, success reset/close, failure retention/retry. Explicitly preserve current repeat-submit behavior where the product has no pending guard; a migration test must not invent disabled/loading semantics.
4. Extend Commerce's existing ProductEdit case rather than adding a mirror suite: exact 34-key create payload and edit PATCH, pending duplicate prevention, failure retention/retry, and successful `navigate(-1)`. Preserve `form`, explicit submit type, loading/saving disabled state, and do not infer a UI permission gate that the page does not implement.

For the three-button account/company group (included in final AT scope), use real `ProfileSection` and `CompanyDetailPage` rather than mocking their handlers. Mock only `api` and Auth boundaries; use real permissions and real UiPrefsProvider/refresh. Do not mock patchMyProfile or UiPrefs. Assert the full 14-key company payload rather than partial matching, channels normalization for `,、，`, reload increments, dirty/pending disabling, failure retention, and denied-permission absence.

## Risks and stop conditions for design

- `Button.tsx:49-87` does **not** set a `type` default; it forwards `...rest` to the native element. An omitted type therefore remains omitted and follows native HTML form context. Every existing explicit `type="submit"` must remain explicit, and PO must retain `form="po-form"` because its button is outside the form.
- Do not add `disabled`, `loading`, `aria-busy`, or guards to Dex/TCG/Role behavior while migrating. That would change business behavior.
- Do not infer permission from route placement. Profile, Dex, and TCG expose no local permission predicate; tests should document that fact rather than fabricate one.
- Exclude any candidate whose final AST inventory reveals added class/style semantics beyond the literal cases above. In particular, do not strip inline margin or custom layout classes just to fit the batch.
- All deferred promises must settle. Initial GET counts must be separated from submit-triggered reloads, and permission-denial assertions must wait for `/me/permissions` settlement.

Final design correction: AT preserves existing suites and adds three focused suites, as specified by at-commerce-test-plan.md and at-admin-test-plan.md. Earlier proposals to extend existing suites are not the final implementation instruction. The canonical eleven targets are at-button-audit.json.
