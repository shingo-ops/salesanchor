【要対応・PO】デプロイ停止の復旧手順

対象: しんごさん（DB アクセス・本番判断）／作成: Hikky-dev（Claude Code）／関連: ADR-036, ADR-034, release #2081, deploy run 27432430556

✅ 本番サービスは稼働中です。 アプリ（app.salesanchor.jp）200・backend コンテナ正常・再起動ループなし。リリース #2081 のコード（PayPal ケース受信ハンドラ等）も反映済みです。
⚠️ ただし「デプロイ」は failure で終了し、DB マイグレーションが止まっています。このまま放置すると次回以降の全デプロイが同じ場所で失敗します。

何が起きたか

リリース #2081 のデプロイで、Run database migrations ステップが 2 個目の migration（013）で停止しました。ログの直接証拠:

ERROR:  column "source" does not exist
QUERY:  SELECT source FROM tenant_001.leads WHERE source LIKE 'messenger:%' ...

= tenant_001 の leads テーブルに source 列がありません。

原因（確定）: リリース #2081 は migration / script を 1 つも変更していません（16:44 の成功デプロイとコード同一）。変わったのは tenant_001 の DB 状態です。
本日 16:44〜17:41 の間に tenant_001 が「過去マイグレーション未適用の不完全スキーマ」で作成/リセットされたのが原因です（しんごさんがアカウント＝テナント操作をされていた時間帯と一致）。これは ADR-034 / ADR-036 が想定する「新規テナントに過去 migration が自動適用されない」既知欠陥の再発です。

復旧手順（推奨: ADR-036 の sync ツールで整合）

ADR-036 Level 1 の sync_tenant_schema.py（tenant_004 を基準に全テナント差分を冪等適用）で tenant_001 を整合させます。まず --dry-run で差分を確認してから適用してください。

STEP 1. VPS に SSH（しんごさんの鍵）:

ssh ubuntu@49.212.137.46

STEP 2. リポジトリへ移動:

cd /home/ubuntu/salesanchor

STEP 3. 差分プレビュー（適用なし）。tenant_001 が何を欠いているか一覧されます:

docker compose exec backend python /app/scripts/db/sync_tenant_schema.py --dry-run

※ DATABASE_URL が未設定 と出る場合は、DDL 権限のある URL を渡してください（run_all_migrations と同じ admin ロール）:
docker compose exec backend sh -lc 'python /app/scripts/db/sync_tenant_schema.py --dry-run'

STEP 3 の出力を確認してください。 tenant_001 以外（tenant_005 / 006 等）にも差分が出る場合があります。意図しない変更が無いか目視してから STEP 4 に進んでください。判断に迷ったら出力を Hikky-dev（私）に貼ってください — 一緒に確認します。

STEP 4. 差分を適用（--dry-run を外すだけ・冪等）:

docker compose exec backend python /app/scripts/db/sync_tenant_schema.py

STEP 5. 止まっていたデプロイを再実行（Mac 側 or GitHub UI から）。コードは反映済みなので、これは migration を通すための再走です:

gh run rerun 27432430556

※ Mac の Hikky-dev からでも実行できます。やっておきましょうか？と聞かれたら「お願い」でこちらで叩きます。

確認（復旧完了の判定）

確認項目期待
再デプロイの Run database migrations[145/145] まで完走・green
tenant_001.leads.source 列存在する（STEP 3 の dry-run で「差分なし」になる）
app.salesanchor.jp200（引き続き正常）

代替: tenant_001 が「お試し/不要」だった場合

STEP 3 の dry-run で tenant_001 が大量に欠けている＝実体のないテスト用なら、整合させるより削除が適切なこともあります。その場合は 削除して良いか Hikky-dev に一言ください（不可逆操作なので手順を一緒に確認します）。本番テナントは tenant_004（highlife-jpn）です。

恒久対応（別途・私が対応）

  • migration 013 の防御ガード（PR 準備済・GO 待ち）: 部分テナントが 1 つでもあるとデプロイ全体が止まる脆弱性を解消。leads.source が無いテナントは WARNING でスキップしデプロイ継続（整合性検出は schema-check が担当）。これがあれば今回のような全停止は起きません。
  • ADR-034 の deploy 配線（Proposed・別タスク）: sync_tenant_schema.py / schema-check を deploy パイプラインに組み込み、新規テナント作成時に過去 migration を自動適用。根本解決。PO 判断で着手。
