# design: Discord の知らせを、強い鍵を使わずに AI が読む道

- 状態: PO 承認済み・実施済み・受入の試し合格（2026-11-24）。方向は 2026-11-23 PO「2」（読むだけの鍵で読めるようにする設計を作る）。作り方は 2026-11-24 PO「1」（SA Bug Intake を使う）。保存は同日 PO「1」（正式な記録として残す）。
- 根拠: [recon.md](recon.md)（以下 recon）。
- 関連 ADR: ADR-079（AI の読むだけの監視の鍵）・ADR-1024（読むだけの専用の道・役目を混ぜない）・ADR-1012（24時間保守）。前の設計: `docs/handoff/discord-ops-intake/design.md:34`。
- 審査: 同じ AI（Opus）による自己審査。第二者の審査ではない。

## 1. 目的（KGI）
AI が、PO の許可も manual-only の鍵も使わずに、Discord の 🚨急ぎ・📋定期の報告・🛠開発の知らせ の投稿（送り手・時刻・題）を読める。その鍵では書き込み・設定の変更ができない。

## 2. 対象と対象外
- 対象: SA Bug Intake の役割の、3 部屋の権限の上書き。Mac の ~/.claude-access.env（このリポジトリの外）（ADR-079 の読む鍵の置き場）の `DISCORD_READER_TOKEN`。読む台本。
- 対象外: リポジトリのコード（0 行）。不具合受付・不具合報告の部屋の設定。見張り go-identity-guard（ゆるめない・recon F6）。部屋を作る・変える操作（これまでどおり Bot「Sales Anchor」と PO の許可）。

## 3. 変更前 → 変更後
| 項目 | 変更前 | 変更後 |
|---|---|---|
| AI が知らせを読む道 | 本番サーバーへ manual-only の鍵で入り、Bot「Sales Anchor」（部屋・役割・送り口の管理まで持つ・recon F2）の鍵で読む | Mac から SA Bug Intake の鍵の写しで読む |
| 3 部屋の SA Bug Intake の上書き | allow 67584（送る・履歴）deny 1024（見る）（recon F4） | allow 66560（見る・履歴）deny 377957181504（送る・反応・投稿の管理・リンク・ファイル・スレッド作成・スレッドで送る） |
| 鍵の置き場 | キーチェーンだけ（recon F5） | キーチェーン（受付が使う）＋ ~/.claude-access.env（このリポジトリの外）（AI が読む） |

## 4. 案と選んだ理由
| 案 | 判断 |
|---|---|
| A: AI がキーチェーンから受付の鍵を読む | 不採用。見張りがわざと止める（recon F6）。ゆるめると PO の GitHub の鍵の守りが弱くなる |
| A': PO が ! で受付の鍵を ~/.claude-access.env（このリポジトリの外） へ写す | **採用**（PO 11/24「1」）。PO の作業は ! 1 回。受付の Bot はもともと読むために作られた（`docs/handoff/discord-ops-intake/design.md:34`） |
| B: 読むだけの Bot を新しく作る | 不採用（PO の選択）。鍵は 1 か所になるが、PO の画面の作業が 5 つ要る |
| C: Bot「Sales Anchor」の鍵を Mac に写す | 不採用。強い鍵が増える（recon F2） |
| D: ADR-1024 の DB を読む道に足す | 不採用。役目が混ざる（ADR-1024 が監視の鍵への相乗りを断った理由と同じ） |

弊害: 同じ鍵が 2 か所にある。受付の鍵を作り直すと AI の写しが古くなり、読むと 401 になる → AI は強い鍵に切り替えず止め、PO に写し直しの ! を頼む（§7）。

## 5. 手順（実施済み）
1. PO が ! で写しの台本を流す（キーチェーン → ~/.claude-access.env（このリポジトリの外） の `DISCORD_READER_TOKEN`。鍵は画面に出さない。あわせて `/users/@me`・`/applications/@me` を読み、recon F7 を確かめた）。
2. Bot「Sales Anchor」で 3 部屋に `PUT /channels/{id}/permissions/{SA Bug Intake の役割}`（type 0・allow 66560・deny 377957181504・監査ログの理由を付ける）。前後を記録。
3. Mac の読む台本（読み始めの時刻と部屋を引数に取る。鍵は ~/.claude-access.env（このリポジトリの外） から読み、出さない）。
4. §6 の受入の試し。
5. 予約していた数え（11/29 の「点検失敗の知らせ 7日分」）の依頼文を、強い鍵の道からこの道へ書き換えた。

## 6. 受入条件（KPI）と結果
| 基準 | 検証方法 | 結果（2026-11-24） |
|---|---|---|
| G1 3 部屋の投稿を読め、題が空でない | 写した鍵で `GET /channels/{id}/messages?limit=5` | 3 部屋とも 200・5/5 件に題あり。合格 |
| G2 書けない・変えられない | 同じ鍵で投稿の POST・部屋の名前の PATCH・送り口の一覧の GET | 403・403・403。合格 |
| G3 お客様の部屋（チケット）などは読めない | サーバーの全 25 の文字の部屋を同じ鍵で 1 つずつ読む | 読めたのは 3 部屋＋もともとの不具合 2 部屋だけ。チケット 10・全体 6・その他 4 は 403。合格 |
| G4 鍵の値が記録に残らない | 鍵の値を作業の記録の置き場すべてから探す（件数だけ出す） | 0 件。合格 |

## 7. 戻し方
- 3 部屋の上書きを前の値（allow 67584・deny 1024）へ戻す（Bot「Sales Anchor」で PUT 3 回）。
- ~/.claude-access.env（このリポジトリの外） の `DISCORD_READER_TOKEN` の行を消す。

## 8. 外部・過去事例の参照と我々への応用
- 外部事例: 該当なし。理由: 1 つの Discord サーバーの権限の設定で、Discord 公式の説明（Message Content Intent・権限の上書き。Context7 /discord/discord-api-docs）と、このサーバーの実測（recon F2〜F7）で足りる。
- 過去事例: ADR-079（読むだけの鍵を AI の置き場に置く）・ADR-1024（専用の道・役目を混ぜない）を当てはめた。受付の Bot はもともと「読むだけ」の役目（`docs/handoff/discord-ops-intake/design.md:34`）なので、役目は混ざらない。

## 維持の仕組み
- 守り手: 人手で守る
- 持ち主: ccopusgo の設計担当（Opus）。鍵の写し直しは PO。
- AI の覚え書き（reference_discord_reader_path）に、この道と「読めないときは強い鍵に切り替えず止める」を書いた。
- 受付の Bot の鍵を作り直したら、PO が写しの台本を ! でもう一度流す。AI は 401 で気付いて PO に頼む。
- 3 部屋の上書きを誰かが変えたら G1〜G3 が崩れる。数えの予約が読めなかったときに止まって知らせるので、そこで気付く。
