# 設計 — 送信時の sender_id の是正

> この文書は何か（専門用語なしの1行）:
> 送信の記録が失敗する原因を1行だけ直す設計。

対象ADR: ADR-091
recon: docs/handoff/discord-image-sender-id/recon.md
親テーマ: docs/specs/attachment-storage/README.md

## 1. あるべき姿

顧客が送った画像やファイルが、いつ見返しても受信箱に残っている。
こちらから送った画像も同じように残る。

## 2. recon（実測）

docs/handoff/discord-image-sender-id/recon.md を参照。要点は次の3つ。

- Discord への送信は成功している。
- データベースへの記録で NOT NULL 制約に違反している。
- 既存のテキスト送信は正しい値を入れている。

## 3. design（技術How）

Discord 分岐の sender_id を、既存のテキスト送信と同じ値にする。

変更は1行である。他の処理には触れない。

## 4. 外部・過去事例の参照と我々への応用

データベースの NOT NULL 制約は、値が欠けた行を保存させないための仕組みである。
制約違反は保存の時点で検出され、その行は保存されない。

本件では、外部への送信が成功した後に保存で失敗した。
外部への送信は取り消せないため、送信済みで記録なしの状態になった。

この形の障害は部分的な失敗と呼ばれる。
本テーマでは保存の失敗を画面に伝える仕組みを既に入れているが、
今回はその手前のデータベース記録で失敗したため、
送信全体がエラーとして扱われた。

我々への応用: 新しい INSERT を書くときは、
対象テーブルの NOT NULL 制約を確認する。
同じテーブルへの既存の INSERT があれば、その値の入れ方を写す。

## 5. 弊害・トレードオフ

- 弊害: 既に送信済みで記録が無いメッセージが1件存在する。
  本便では復旧しない。手動での確認が必要になる。
- トレードオフ: sender_id にボットを示す固定値を入れる。
  実際の送信者は sent_by_staff_id で別に記録している。

## 6. 受入基準

| 基準 | 検証方法 |
|---|---|
| None を入れていない | grep で該当の記述が0件 |
| 既存と同じ値を使う | grep でボットを示す値が2件以上 |
| 構文が妥当である | python3 の ast.parse が例外を出さない |
| 既存テストを壊していない | pytest が全 pass |
| 実環境で送信できる | 受信箱から画像を送り、画面にエラーが出ないことを確認する |
| 記録が残る | meta_messages に outbound の行が増えることを確認する |

## 7. 維持の仕組み

- 守り手: 人手で守る
- 理由: Discord への実送信を伴うため、
  現在のテスト基盤では外部APIとの往復を再現できない。
  既存テストは SQLite を使っており、
  本番の PostgreSQL の NOT NULL 制約を再現していない。
- 対象: 送信の記録が失敗すること。
- 検知方法: PO による実機確認。受信箱から画像を送り、画面を見る。
