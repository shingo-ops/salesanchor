# design — data-durability（技術手段）

この文書は何か（専門用語なしの1行）: 営業データを失わないために、何を、どの順番で、どうやって作るかを決めた設計書。

## 1. この設計が満たす目標

docs/specs/data-durability/kgi.md の8項目。現在値はすべて未達（recon 実測）。

| KGI | 合格ライン | 現在値 |
|---|---|---|
| 1 障害の10分前まで戻せる | 欠損 0 件 | 不可（archive_mode = off） |
| 2 半日以内に戻せる | 720分以内 | 未測定 |
| 3 コピーが3つある | 3以上 | 1 |
| 4 離れた場所に1つある | 1以上 | 0 |
| 5 全データが対象に入っている | 3/3 | 1/3 |
| 6 失敗が届く | 1/1 | 0 |
| 7 復旧を1度やって見せる | 在る=1 | 0 |
| 8 演習が続く | 在る=1 | 0 |

## 2. 実施の順序（4工程）

外部事例の調査により、破滅の主因は道具の選択ではなく「静かな失敗」と「未検証の復旧」であることが確認された（§6）。よって通知と演習を先に置く。

| 工程 | 目的 | 対応KGI | 本番への書き込み |
|---|---|---|---|
| 1 | 失敗が人に届くようにする | 6 | あり（設定変更） |
| 2 | 3箇所目を確保し、コピー1箇所の状態を脱する | 3・4・5 | あり（AWS CLI導入・鍵確認） |
| 3 | 復旧を1度やって見せ、所要時間を測る | 2・7 | tenant_004 に触れない範囲 |
| 4 | 時点復旧へ移行する | 1・8 | あり（本番DB設定変更・再起動） |

各工程は独立した便とし、本番への書き込みを含む工程はPOの自筆GOを着手条件とする。

## 3. 工程1: 失敗が届くようにする

recon 実測により、scripts/backup_to_s3.sh:44 の通知は DISCORD_WEBHOOK_OPS が設定されているときのみ動く。prod1 の .env にも crontab にも当該変数は存在せず、2026-05-28 以降の失敗は誰にも届いていない。

- 対象: prod1 の .env に DISCORD_WEBHOOK_OPS を追加する
- 値の出どころ: .env に既存の ADMIN_NOTIFICATION_DISCORD_WEBHOOK を流用するか、新規のWebhookを作るかはPO判断とする（本設計では決めない）
- ○×基準: バックアップを1回わざと失敗させ、POの手元に通知が1件届くこと（KGI6）
- 触らない範囲: .env の他の行、crontab、scripts/ 配下

## 4. 工程2: 3箇所目を確保する

### 4-1. 未解消の不明点を先に埋める

recon の不明点 #2・#3 は AWS CLI が無いため未解消である。

- prod1 に AWS CLI を導入する。apt-cache policy awscli が Candidate: (none) を返すため、apt 以外の入手経路を用いる（具体的手段は実装カードで確定する）
- aws sts get-caller-identity で ~/.aws/credentials の鍵が有効かを確認する
- aws s3 ls でバケット salesanchor-backups の実在を確認する

### 4-2. 分岐

| 実測結果 | 取る道 |
|---|---|
| 鍵が有効・バケット実在 | 既存の scripts/backup_to_s3.sh がそのまま動く。cron は既に登録済みのため、翌日の s3_backup.log に「サイズ一致」が出ることで確認する |
| 鍵が無効またはバケット不在 | scripts/aws-setup/README.md の手順で作り直す。AWSアカウントの有無の確認から始める |

### 4-3. 対象を3層に広げる

recon 実測により、現在バックアップされているのは層1（DB）のみである。

| 層 | 現状 | 本工程での扱い |
|---|---|---|
| 1 データベース本体 | scripts/backup.sh が pg_dump している | 変更なし |
| 2 添付画像 | docker-compose.yml:411 の attachments_data に保存されるが、backup.sh は pg_dump のみのため対象外 | S3への転送を追加する。attachment-storage テーマと同じファイルを触るため、着手前に当該テーマの進行状況を確認する |
| 3 環境設定と鍵 | prod1 の .env は GitHub の追跡下に無い。METADATA_FERNET_KEY を含む | 暗号化した上でS3へ置く。置き方は docs/specs/secrets-permission-ssot/ と接点を持つため、当該テーマの正本を先に読む |

- ○×基準: 同一時点のコピーが3箇所（prod1ローカル・S3・月次アーカイブ）に在ること（KGI3）。うち1つがさくらインターネット大阪の外に在り、事業者名と所在が本文書に明記されていること（KGI4）。3層すべてが対象に入っていること（KGI5）

## 5. 工程3: 復旧を1度やって見せる

docs/B-09_restore_test_procedure.md:11 に月次リストアテストの手順が既に存在する。本工程はこれを実行し、結果を記録する。

- 実施環境: tenant_004（HIGH LIFE JPN 実データ）には触れない。tenant_006（QA）または tenant_001（空テスト）で行う
- 測る値: 演習開始から通常操作を受け付けるまでの分数
- ○×基準: 720分以内であること（KGI2）。手順と所要時間を記録した文書が在ること（KGI7）
- 記録先: docs/handoff/data-durability-design/restore-drill-YYYYMMDD.md

## 6. 工程4: 時点復旧へ移行する

### 6-1. 道具の選定

pgBackRest を第一候補、Barman を第二候補とする。WAL-G は採用しない。

| 判断軸 | pgBackRest | Barman | WAL-G |
|---|---|---|---|
| 最新版と日付 | 2.59.1 / 2026-08-17 | 3.20.0 / 2026-08-27 | v3.0.8 / 2026-01-21 |
| 保守主体 | 9社の出資による連合。主開発者1名 | EnterpriseDB（企業） | コミュニティ |
| 実名で依存を表明する企業 | AWS・Supabase・pgEdge・Tiger Data・Percona・Eon・Xata・Dalibo・Data Egret の9社 | EDB以外は未確認 | 未確認 |
| 我々が受けた失敗への備え | 2.59.0 でWALアーカイブの期限掃除機能を追加。ファイル単位の検査値検証あり | 3.17 でS3オブジェクトロック確認、3.19 でクラウドからの復元に対応 | 開発側が文書の詳細さ不足を明言 |
| 構成の相性 | 単体完結型 | 外部サーバーを操る形。利用者の準備が要る | 単一の実行ファイル |

選定理由: 実名で依存を表明している企業の数が最も多く、我々が実際に受けた失敗（アーカイブ詰まり・静かな破損）への備えが道具側に入っており、単体完結型で我々の1台構成に合う。

不採用理由（WAL-G）: タグ付きリリースが約7か月出ておらず、開発側自身が文書の詳細さ不足と商用サポートの不在を表明しているため。

### 6-2. 移行の手順（実装カードで詳細を確定する）

1. 隔離した環境で pgBackRest を試し置きし、Docker内のPostgreSQLに対して動くことを実測する
2. 実測が通った場合のみ、本番の archive_mode を on にする（再起動を伴う）
3. 基準バックアップを取り、S3へ送る
4. archive_timeout を設定し、失われる幅を10分未満に抑える
5. 復旧演習をもう一度行い、時点復旧が効くことを確認する

### 6-3. この工程が持ち込む新しい危険

PostgreSQL 公式文書に明記のとおり、アーカイブ先に書けない状態が続くと pg_wal が埋まり続け、その領域が満杯になると PostgreSQL は PANIC 停止する。すなわち本工程は、バックアップの失敗が本番停止に直結する経路を新たに作る。

歯止め:
- pg_wal の使用量とアーカイブの遅れを監視に載せる（prod2 の Prometheus）
- 閾値を超えたら人に通知する
- アーカイブの期限掃除を有効にする
- 上記3つが揃うまで archive_mode を on にしない

## 7. 弊害・トレードオフ

- 工程4は本番データベースの再起動を1回伴う。数十秒から数分、アプリが止まる
- 工程4は「バックアップの失敗が本番を止める」経路を作る（§6-3）。工程4以前には無かった危険である
- 工程2の層3（鍵）をS3へ置くことは、鍵の漏洩面を1つ増やす。暗号化と権限の設計を secrets-permission-ssot テーマと突き合わせる必要がある
- pgBackRest は2026年4月に一度保守が停止し、3週間後に復活した。主開発者は1名である。年1回、最新リリース日と資金提供者の一覧を確認する運用を維持の仕組みに含める
- pgBackRest は設定項目が多く日本語の文書が少ないため、導入の障壁が高いとの実務報告がある

## 8. 外部・過去事例

GitLab は 2017-01-31 に本番データベースを誤って削除した。5つのバックアップ手段が用意されていたが、どれも正しく動いていなかったか設定されていなかった。pg_dump のバージョンがデータベース本体と食い違い、失敗が通知されないまま続いていた。使えたのは手動で取った6時間前のもので、復旧に18時間かかった。

本テーマへの応用: 手段の数を増やすことは対策にならない。工程1（通知）と工程3（演習）を工程4（手段の追加）より先に置いたのはこの事例による。

成功側の事例として、2025年1月のPostgreSQLメーリングリストに、隔離した機械で毎日自動復元を回していた運用者が、復元結果が2日前で止まっていることを訓練によって検出した記録がある。事故ではなく訓練が異常を捕まえた例である。
