## 2. 4-1・4-2 で K1〜K7 を満たすか

- K1/K2（閲覧）: `InventoryView` は `ViewerApp.tsx:135-139` で `screen.name === "inventory"` のときだけ描画され、読み直し（`load()` `:65-80`）は必ず「loading」画面を通るので毎回作り直される。→ useState の初期化関数で data.rows を見る方式で、後から data.rows が変わる問題は起きない。○
- K1 のスマホ: セレクトの選択肢は `seriesTabs(data.rows)` 由来で、ポケモンの行があれば「ポケモン」が必ず含まれる。○
- 既存テスト: `InventoryView.test.tsx` の共通 data は series が全部 `"S"`（`:20`）なので既定は「すべて」のまま。seriesData を使う K3/K4/K5 テスト（`:138-182`）は選択中のタブを見ていないため、落ちるものは無い見込み。design の「data にポケモンの行しかない場合は直さずに通るはず」は事実と逆の書き方（修正点 6）。
- K3（GAS）: `var activeSeries = MAIN_SERIES[0];` を `:1003` の後に置けば、使われるのは全部 DOMContentLoaded 後の関数内なので巻き上げの問題は無い。`:1000` のまま値だけ変えると MAIN_SERIES が未定義で落ちるため、design の「移す」指示は正しい。○
- K5（更新ボタン）: activeSeries を保ったまま再取得、onDataLoaded で SEARCH_TEXTS を null に戻す。○
- K4（検索の漏れ）: 読み込み前に検索欄へ打つと、`render()` が ALL_ROWS=[] のまま呼ばれ（`:1068`）、`ensureSearchTexts` が `SEARCH_TEXTS=[]` を作る。onDataLoaded で null に戻すので漏れは無い。ロジックは○。ただし `ensureSearchTexts` を onDataLoaded の中に書くと render から呼べない（修正点 2）。
- 後回しの効果: `setTimeout(ensureSearchTexts, 0)` は Chrome では次の画面描画より先に実行されることがあり、その場合は表が画面に出るのは今と同じだけ遅れる。さらに m.js の「行が出た時刻」は DOM に行が入った時刻（画面に描かれた時刻ではない）なので、K6 では効果があるように見えて利用者には変わらない、ということが起こり得る（修正点 3）。
- 端の場合: タブの件数は24時間絞り込み前の全行で数える（`:1279-1283`）ので、ポケモンの行が24時間より古いものだけなら「ポケモン」が選ばれて表が空になる。閲覧ページも同じ（seriesTabs は data.rows 全体）。今の件数（直近24時間でポケモン約66%）では起きにくいので今回は許容、design のリスク表に1行足すこと（修正点 7）。
- K7: 差分にアプリ在庫表が無いことで確認でき、design もアプリを触らない。○

## 3. 案X を見送る理由と PO 依頼との整合

- 裏付けあり: 通信量 gzip 32.6KB・受信 7〜96ms（out.txt）、`Code.js:55-97` は引数なしで毎回 `getDataRange().getValues()` 全行。→ 呼び出しを分けてもシートの全行読みは減らない、は実物どおり。
- 裏付けが足りない所: TTFB 1.85秒のうち「シートを読む時間」と「334KB の結果をサーバーで詰める時間」の内訳は測っていない。「分けても応答待ちは減らない」は【推測】であり、design では事実として書かれている（修正点 5）。結論（今回は分けない）は変わらない。
- PO 依頼とのずれ: 依頼の後半「その他に統合されていないデータを優先的に読み込んで」の形（分けて読む）はやらない。design 3 章に理由はあるが、PO 承認の際に「分けて読むことはしない・見込みの短縮は画面側の1秒強の一部だけ」と平易に伝えて了承を取る必要がある（設計を依頼どおりから変える場合）（修正点 8）。前半「ポケモンをデフォルト」「裏で全件読む」は満たす。

## 4. K6 の測り方の公平さ

- テスト版と本番版は元のシートが違う。【事実】`verify_test_after/コード.js` と `verify_prod_after/Code.js` は中身が同じで（cmp 一致）、どちらも `SpreadsheetApp.getActiveSpreadsheet()`（`:56`）で紐づいたシートを読む。配信テストの紐づき先は本番とは別のシート（メモリ reference_tcg_client_viewer 記載）。【未確認】テスト用シートの行数・中身が本番と同じか。
- そのため「テスト版（新）の合計時間 と 本番（旧）の合計時間」を比べると、変更の効果とシートの違い（行数・応答待ち）を区別できない。K4 の「『すべて』タブで同じ語の件数が本番 版21 と同じ」も、シートが違えば件数は一致しない。
- 応答待ちのばらつき（今回の3回で 1.30〜2.43秒、前回は 4.5〜22秒）は見込みの短縮（画面側 1.04秒の一部）より大きく、5回ずつの合計時間の平均ではたまたま○×が出る。
- 交互に測ること自体（時間帯のかたよりを減らす）は良い。

## 5. 実装担当（Sonnet）が迷わず作れるか

- 閲覧ページ: 行番号ずれ（`:55`→`:56`）以外は、変更前後のコード・テストの追加内容まで書かれていて十分。
- GAS: `ensureSearchTexts` の置き場所、`:1236` の古いコメントの扱い、setTimeout の書き方が曖昧。stage/prod_stage の作り方・clasp を実行しないことは明確。

## 修正必要点

1. design 4-1・recon B の行番号を `InventoryView.tsx:56` に直す。あわせて「`const [tab, setTab] = useState(TAB_ALL);` の1行を置き換える」と中身で指定する（`:55` は `now` の state で、そのまま渡すと別の行を書き換える）。recon C のシリーズ絞り `:1451` → `:1452` も直す。
2. design 4-2-2: `ensureSearchTexts` は onDataLoaded の外（一番外側。例: `function onDataLoaded` の直前）に置く、と明記する。中に書くと render から呼べず、検索した時点で ReferenceError になる。`:1236` のコメント「読み込みのときに1回だけ作る」は消すか新しい説明に置き換える、と書く。
3. design 4-2-2: 後回しは「表が画面に描かれた後」に走る形にする。例: `requestAnimationFrame(function () { setTimeout(ensureSearchTexts, 0); });`（描画直前の rAF から次のタスクへ送るので、描画の後になる）。理由を1行コメントで残す。
4. K6 を、シートの違いと応答待ちのばらつきに左右されない形に直す。
   - 判定に使う値は「応答の受信完了 → 表のデータ行が画面に出るまで」（変えた部分だけ）。m.js の `__t0`（isSoldOut の最初の呼び出し）から、行が入った後の最初の `requestAnimationFrame`（＝描画の直前）までを測る形にし、合計時間は参考として並べて報告する。
   - 比べる両方で、応答の行数（Sold out 除外前）と表に描いた行数を記録する。行数が大きく違う場合は○×を出さずに PO に報告する。
   - できれば、テスト版を反映する前にテスト版（旧 版31）を5回測り、テスト版の新旧も比べる（同じシートどうし）。平均に加えて中央値も出す。
5. design 3 章 案X の「分けても最初の応答待ち 1.85秒は減らず」を【推測】と明記する（シートの全行読みは事実、サーバーで結果を詰める時間の内訳は未測定）。
6. design 4-1 のテストの説明を実物に合わせる: 既存テストの共通 data は series が `"S"` だけ（ポケモンの行が無い）ので「すべて」で開いたまま通る、seriesData を使う K3〜K5 テストは選択中のタブを見ていない、と書く。
7. K4 を同じ配信の中で確かめる形に直す: テスト版で (a) 読み込み中（表が出る前）に検索語を入れる、(b) 表が出た直後に入れる、(c) 2秒待ってから入れる、の3通りで表示件数が同じで、表示行がすべて検索語を含むこと。本番 版21 との件数比較はやめる（シートが違う）。あわせてリスク表に「ポケモンの行が24時間より古いものだけだと、ポケモンで開いて表が空になる（今の件数では起きにくい。タブ1回で『すべて』に戻せる）」を足す。
8. PO 承認の文面に、依頼の「その他でないデータを先に読む」（分けて読む）は今回やらないこと、その理由（分けても Google 側の待ち時間は減らない見込み）、短くなる見込みは画面側の1秒強の一部だけで「1秒」に届くかはまだ確かめていないこと、を日常語で入れる（PO の依頼の形から変えるため）。
