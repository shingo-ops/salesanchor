# 設計: 在庫表を最初からポケモンで開き、表示を早くする

- 状態: 設計案（Opus）。PO 依頼 2026-10-21（recon.md 冒頭の原文）。
- 現在地: docs/handoff/inventory-default-pokemon-tab/recon.md
- 対象 ADR: ADR-1019 項8（閲覧ページはアプリと同じ金型・同じ見え方）、ADR-1030（タブは中分類で絞る）、ADR-027（UI 文字列は t() 経由）、ADR-144（金型を使う）。新しい部品・文言・色は足さない。

## 1. 目的（PO の言葉）と成功条件
- 「ポケモンをデフォルトにして裏で全件読み取る」
- 「読み込みはタブ順にその他に統合されていないデータを優先的に読み込んでページが1秒でも早く表示されるようにしたい」

| 基準 | 検証方法 |
|---|---|
| K1 閲覧ページを開くと、PC はタブ「ポケモン」が選択中、スマホはセレクトが「ポケモン」。表はポケモンの行だけ | vitest（新規テスト）＋本番の配信 JS に変更が入っていること（deploy 後に取得して確認） |
| K2 閲覧ページで、ポケモンの行が1件も無いときは今までどおり「すべて」で開く | vitest |
| K3 シート版を開くと、タブ「ポケモン」が選択中（スマホのセレクトも「ポケモン」）。表はポケモンの行だけ | Playwright（匿名）でテスト版・本番版を開き、選択中のタブと表の行のシリーズを確認 |
| K4 シート版で、表示直後に検索欄へ打っても結果が正しい（検索用文字列を後回しにしても漏れない） | Playwright（テスト版・同じ読み込みの中で）: 「すべて」タブで同じ検索語を ①表が出た直後 ②2秒後 ③読み込み中（表が出る前）に入れておく、の3通りで、表示件数が一致し、表示行がすべて検索語を含むこと |
| K5 シート版の更新ボタンで、選んでいたタブのまま読み直す | Playwright: ワンピースを選び更新 → ワンピースのまま |
| K6 シート版の画面側の処理が、変更前より短い | 同じテスト版で、反映前（版31・旧）を10回、反映後（新）を10回、匿名 Chrome で開く（Mac で build・テストなど重い作業が走っていない時に測る。2026-10-21 の試し測定は実装担当の build と重なり 345ms〜20.8秒とばらついたため。スクリプト /tmp/CC報告ファイル/default-pokemon-k6-before/m6.js）（同じシートを読むので比べられる）。判定値は「サーバー応答の受信完了 → 表を描く直前（iframe 内の requestAnimationFrame）」の中央値で、新 < 旧 なら ○（最小値も併記）。参考として「表のデータ行が出た時刻」の合計・平均・中央値と、表示行数を並べる |
| K7 アプリ在庫表は変えない（今もポケモンで開き、開いたタブの50件だけ読む） | 差分にアプリ在庫表のファイルが無いこと |

- 本番とテスト版は読むシートが別（行数が違う可能性）なので、新旧の比較は同じテスト版の中で行う。サーバーの応答待ちは 1.3〜2.4秒ばらつき、短くなる見込みより大きいので、合計時間は判定に使わず参考にする。
- 期待の大きさ: 画面側の処理 1.04秒のうち、描く行が約3分の2になる分と検索用文字列の作成を後回しにする分が減る。外枠の読み込み（2.67秒）とサーバーの応答待ち（1.85秒）は Google 側で、この変更では減らない。「1秒」に届くかは【未測定】で、K6 の実測で報告する。

## 2. 変更前 → 変更後
| | 変更前 | 変更後 |
|---|---|---|
| アプリ在庫表 | ポケモンで開く。開いたタブの50件だけ読む | 変えない |
| 閲覧ページ（PC・スマホ） | 「すべて」で開く | 「ポケモン」で開く（ポケモンの行が無ければ「すべて」） |
| シート版（PC・スマホ） | 「すべて」で開く。受信直後に全行の検索用文字列を作ってから表を描く | 「ポケモン」で開く（行が無ければ「すべて」）。表を描いた後に検索用文字列を作る。描く前に検索語が入っていればその場で作る |

## 3. 選ばなかった案と理由
- **案X: サーバー呼び出しを「主な3つ」「その他」に分ける（依頼の言葉どおりの形）。** シート版は通信量が 33KB・20ms で（recon C）、サーバーは呼ばれるたびにシートを全行読む（`Code.js:55-97`）ため、分けても最初の応答待ち 1.85秒はほとんど減らず【推測：応答待ちの中のシート読み込みと結果を詰める時間の内訳は未測定】、呼び出しが1回増える。閲覧ページは応答時間が【未測定】で、分ける効果を測る手段（ログイン済みの計測）が今は無い。測れないものは変えない（変更は測ってから）。依頼の狙い「ポケモンが先に見える」は、ポケモンで開いて描く行を減らすことで満たす。
- **案Y: シート版でサーバー側の作り置き（CacheService）を使う。** 応答待ちを減らせる可能性はあるが、在庫の更新がどれだけ遅れて見えるかという事業判断を伴い、効果も【未測定】。今回は入れない（残件として記録）。

## 4. 変更内容

  ```ts
  // 既定はポケモン（MAIN_SERIES の先頭）。その行が無いときは「すべて」（docs/handoff/inventory-default-pokemon-tab/design.md）
  ```

- `ViewerApp.tsx` の読み込み、`api.ts`、バックエンドは変えない。

  - 追加 K2: ポケモンの行が無い data → 「すべて」が選択中・全行表示。
  - 既存テストの共通データはシリーズが "S" だけ（ポケモンの行が無い）なので、K2 の分岐で「すべて」で開き、落ちない見込み。もし落ちたものがあれば「すべて」タブを押してから確かめる形に直し、直した箇所を全部報告する（期待値そのものは変えない）。

### 4-2. シート版 index.html（テスト・本番とも同じファイル）

2. 検索用文字列の後回し: onDataLoaded の `SEARCH_TEXTS = ALL_ROWS.map(...)`（`:1237-1239`）と直前のコメント（`:1236`）を消し、次の関数を **onDataLoaded の外側（関数 onDataLoaded の直前、トップレベル）** に置く:
   ```js

   function ensureSearchTexts() {
   ```

## 6. リスクと対処
| リスク | 対処 |

## 8-2. PO への説明（報告に入れること）
- PO の扱い: 実装するのは PO が明示した「ポケモンをデフォルト」と、その狙い（早く表示）に沿う後回しだけで、依頼に無いものは足さない。依頼のうち「分けて読む」はやらないため、その判断を PO 報告で1問として確認する（PO が分けて読む形を望めば、閲覧ページの測定手段を用意して別便で設計する）。
- 依頼の「その他を後から読む」形（サーバーへの読み込みを分ける）はしない。理由: シート版は通信の量が小さく（約33KB）、待ち時間の大半が Google 側なので、分けても速くならないと見込むため（分けた場合の内訳は未測定）。
- 代わりに、ポケモンで開いて描く量を減らし、検索の下準備を表の後に回す。
- 「1秒」速くなるかはまだ確かめていない。直した後に測って伝える。
