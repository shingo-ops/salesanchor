# design — 予定のカルテ 直し1（時刻として読めない答えは空として扱う）

親: [../design.md](../design.md)（§4-3 ⑤ を本書で改める） ／ 現在地: [recon.md](recon.md) ／ 手順書: [card.md](card.md) ／ ADR: `docs/adr/ADR-1078-secretary-event-karte.md`（変更なし・recon.md §4）

状態: PO 承認済み（2026-11-15 チャット「1」。選択肢の文「時刻として読めない答えは「空いたまま」と扱うように直し、設計の書き直しから本番まで進める（「わからない」でも確かめの欄が出るようになります）」）。実装承認もこの「1」に含む。

## 1. 目的と目標

目的: 「終わりの時刻は？」に「わからない」と答えても、失敗の表示でなく確かめの欄が出る（親の目標 C6 を本番で満たす）。

| # | 条件（○×） | 判定のしかた |
|---|---|---|
| F1 | T10（「明日 10 時から棚卸し」→「うーん」→「わからない」）の 3 通目で、AI が終わりに「わからない」の文字を入れても 200・確かめの欄（`ask` null・終わり空・題名と始まりは残る） | backend の試験（AI の答えを差し替え）＋本番で T10 を 3 回流して 3 回とも ○ |
| F2 | 新しい画面の道で、AI の始まり・終わりが時刻として読めない文字なら、その欄は空になり、決まった順で聞く（失敗の表示にしない） | backend の試験 |
| F3 | 古い画面の道（karte の鍵が無い頼み）の動きは 1 つも変わらない | 既存の `backend/tests/test_assistant_router.py` が変更なしで緑 |
| F4 | ほかの答えは変わらない: 見本 69 件が 69 件一致・T1〜T9 が親の §8 の表どおり | 本番反映後に `docs/handoff/secretary-rulebook/bin0/run_baseline.py` と試しの会話を 1 回ずつ |
| F5 | 試しの前後で予定の件数が変わらない | 本番の予定の表の件数を前後で照合 |

## 2. 対象と対象外

- 対象: `backend/app/services/secretary_karte.py` の `settle_dates` だけ。試験 `backend/tests/test_assistant_karte.py`。
- 対象外: 容器の指示文（AI に「分からなければ null」を強く言う案は §5 で不採用）・画面・古い画面の道（`backend/app/routers/assistant.py:327-339`）・`merge_karte`・`next_ask`・`KarteIn`（カルテの読めない時刻は今どおり 422）。

## 3. 変更の中身（前と後）

- 前（`backend/app/services/secretary_karte.py:39-54`）: 始まり・終わりが読めなければ `ValueError` をそのまま出す。呼ぶ側（`backend/app/routers/assistant.py:324-326`）が 502 unreadable にする。
- 後: `settle_dates` は例外を出さない。
  - (1) 始まり・終わりのうち、時刻として読めない文字（`parse_iso` が `ValueError`）は null にする。
  - (2) 始まりが null なら、終わり（読めれば値・読めなければ null）だけ残して返す。
  - (3) 終日で終わりが空なら、終わり＝始まり（今と同じ）。
  - (4) 終わり < 始まりなら終わりを null（今と同じ）。片方だけ時差の印が無く比べられない（`TypeError`）ときも終わりを null にする。
  - (5) +1 時間は足さない（今と同じ）。
- 空になった欄は、今の `next_ask`（`backend/app/services/secretary_karte.py` の `next_ask`）が決まった順で聞く。同じ欄を 2 回聞いた後は 3 回目を聞かず確かめの欄（今と同じ）。
- 呼ぶ側の `try`/`except (ValueError, TypeError)`（`backend/app/routers/assistant.py:323-326`）は残す（触らない）。`settle_dates` が例外を出さなくなるので通らなくなるが、守りとして置いたままにする。
- 使用の記録: これまで failed だったこの場面は ok になる（AI は答えを返している。`backend/app/routers/assistant.py:343` の失敗の道を通らないため）。
- 試験の変更（card.md に全文）:
  - `test_settle_dates_all_day_end_equals_start_and_end_before_start_is_cleared` の `pytest.raises(ValueError)`（:105-106）を「始まり『あした』は null」「終わり『わからない』は null」「時差の印の無い終わりは null」に替える。
  - `test_unreadable_start_on_new_path_is_502`（:221-227）を `test_unreadable_start_on_new_path_is_200_and_asks_start` に替える（200・始まり空・`ask=start`）。
  - 足す: `test_unreadable_end_after_two_asks_shows_final_draft`（F1 の場面そのもの）。

## 4. 古い版と新しい版が混ざる間

- backend だけの変更。画面・容器は変えない。古い画面の道は `settle_dates` を通らない（recon.md §3）ので変わらない。
- 画面は、始まり・終わりが空の下書きを今も受け取って開ける（親の §4-5「下書きは空欄でも開き」・本番の T4・T7 の 1 通目で始まり空の下書きが 200 で返ったことを観測済み）。

## 5. 代わりの案と選んだ理由

| 案 | 選ばない／選ぶ理由 |
|---|---|
| A. `settle_dates` で読めない時刻を空にする（採用） | 直す場所が 1 か所。読めるかを見るのは今も `settle_dates` だけ（recon.md §2）。AI がどう答えても空欄→決まった順で聞く→2 回で確かめの欄、という親の流れに戻る |
| B. `merge_karte` で直前に聞いた欄だけ読めない値を捨てる | 1 通目（カルテが無い）で AI が始まりに文字を入れた場合が 502 のまま残る（F2 を満たさない） |
| C. 容器の指示文で「時刻が分からなければ null」を強く言う | AI の答えは毎回揺れる（直接 3 回呼んで 1 回だけ文字を入れた・recon.md §1）。指示を強めても 0 回にできる保証が無い。指示文は決まり帳の便3 も触る（親の §7）ので、混ざる危険も増える |
| D. 画面で 502 のとき確かめの欄を出す | 失敗と「分からない」の区別が画面では付かない。カルテの判断を backend に置く親の設計（AI に次の欄を決めさせない・試験で確かめる）から外れる |

## 6. 危ない点と手当て

| 危ない点 | 手当て |
|---|---|
| 本当に壊れた答え（AI が時刻を全部でたらめに返す）も失敗にならず、聞き直しになる | 聞き直しは同じ欄 2 回まで（`MAX_ASKS_PER_FIELD`）。その後は確かめの欄で人が手で入れる。予定は「作成」を押すまで作られない（親の C7）。失敗として数えられなくなる点は §9「残る見えない点」に書く |
| 直前に聞いた欄にカルテが値を持っていたとき、AI の読めない値がその値を上書きし、空になる（`backend/app/services/secretary_karte.py:28-31`） | 聞いた欄はふつう空なので起きにくい。起きても空になって聞き直すだけで、予定は作られない |
| 時差の印の無い時刻を空にすると、正しい時刻を捨てる | 本番の AI の答えは時差の印付き（本番の T1〜T10 の答えは全部 `+09:00`・recon.md §1）。印の無い答えは観測していない（recon.md §5）。捨てても聞き直すだけで、予定は間違って作られない |

## 7. 受け入れの条件と確かめ方

| 基準 | 検証方法 |
|---|---|
| F1 終わり「わからない」で確かめの欄 | backend の試験 `test_unreadable_end_after_two_asks_shows_final_draft`（200・`kind=event`・`ask` null・終わり null・題名「棚卸し」・始まりは S）。本番で T10 を 3 回流し 3 回とも 3 通目が `ask=None`・終わり空 |
| F2 読めない始まりは空にして聞く | backend の試験 `test_unreadable_start_on_new_path_is_200_and_asks_start`・`settle_dates` の直接の試験 |
| F3 古い画面の道は変わらない | `backend/tests/test_assistant_router.py` を変更せず CI で緑 |
| F4 ほかの答えは変わらない | 本番反映後に見本 69 件（69 一致）と T1〜T9（親の §8 の表どおり） |
| F5 予定が増えない | 本番の予定の表（tenant_001・tenant_004）の件数と最新の作成時刻を前後で照合 |

## 8. 外部・過去事例の参照と我々への応用

- 外部事例: 使わない。直すのは 1 つの関数の入力の扱いで、本番の観測（recon.md §1）と親の目標 C6 だけで判断できるため。
- 過去事例: 親の設計で、AI の答えを信じ切らず backend で検査する方針（親の §3「AI には次に聞く欄を決めさせない」）を採った。本件はその検査が「失敗にする」側に倒れすぎていたのを「空にして聞き直す」側に寄せる。

## 9. 維持の仕組み

- 守り手: 秘書チャットの持ち主（Opus の設計担当）。
- 仕組み: backend の試験 3 つ（§7）が CI の必須の pytest で毎回走る。読めない時刻で 502 に戻す変更をすると落ちる。
- 残る見えない点: 「読めない時刻を空にした」回数は記録に残らない。数える必要が出たら、秘書の記録の項目を足す別の便にする（今回は足さない・変更は一度に 1 つ）。

## 10. 進め方（1 便）

1. 本書と card.md を本線へ（設計の審査はクラウド）。
2. クラウドの Sonnet が card.md どおりに直す。
3. マージ前の審査役（Opus）→ CI → 確認済み → 合流 → 本番反映。
4. 本番で F1（T10 を 3 回）・F4・F5 を確かめて PO へ報告。
