## 1. 新設する金型: `ListRow`（一覧の1行）

### 用途（これが分かるように作る）

スマホで一覧を見せるときの1行。**行全体が押せる場所**になり、左に丸い画像、右上に日時、右下に印（未読の数など）を置く。受信箱の会話一覧で使い、将来は在庫表・受注管理の一覧でも使える。

お手本2本（WhatsApp / Meta Business Suite）がどちらもこの形で、**行の高さを76〜78dpに収束させ、区切り線を引かず、行をまるごと押させている**（観察メモの横断比較）。

### ファイル（ADR-144 §4-2 の作法）

```
frontend/src/components/ListRow.tsx          — 部品本体
frontend/src/components/ListRow.css          — 見た目（var() のみ。生の値を書かない）
frontend/src/components/ListRow.stories.tsx  — 見本（check:stories が存在を検査する）
```

### 受け取るもの（名前と説明で用途が分かるようにする）

```tsx
interface ListRowProps {
  /** 行の左に出す丸い画像。省略すると画像の場所を空けない */
  avatar?: ReactNode;
  /** 1行目の主役（会話相手の名前・商品名など）。太字で出る */
  title: ReactNode;
  /** 1行目の右端に出る補助（日時など）。title より小さい文字で出る */
  titleAside?: ReactNode;
  /** 2行目の説明（メッセージの冒頭・型番など）。1行で切る */
  subtitle?: ReactNode;
  /** 2行目の右端に出る印（未読の数など） */
  subtitleAside?: ReactNode;
  /** 2行目の文字の前に出す小さな印（既読・音声などの種類） */
  subtitleIcon?: ReactNode;
  /** 押したときの行き先。渡すと行全体が押せる場所になる */
  onClick?: () => void;
  /** 今開いている行であることを示す（PCの3列表示で使う） */
  selected?: boolean;
}
```

**この部品が決めないもの**（渡す側が決める）: 文字の内容、画像の中身、押したときの処理。
**この部品が決めるもの**（渡す側が上書きしない）: 行の高さ、余白、画像の大きさと丸み、文字の強弱、押せる範囲。

### 見た目（すべて既存トークンの参照）

| 項目 | 使うトークン | 根拠（観察メモ） |
|---|---|---|
| 行の最小高 | `--min-height-conv-item` | お手本は76〜78dp。現在の値92pxは §11-4 の判断待ち |

| 画像 | `--size-avatar-lg` ＋ `border-radius: 50%` | お手本は直径48dpの円 |
| 右の余白 | `--space-3`（§11-4 で `--space-4` にするか判断待ち） | お手本は16dp |

1. 画像あり・未読あり（受信箱の既定）
2. 画像あり・未読なし

5. 選択中

## 2. 直す金型: `PageLayout`（ページの枠）

### なぜ直すのか（実機実測）

実機（1080x2340・Chrome の salesanchor）で受信箱を測った結果、**一覧が始まるのは y=1086px（362dp）**で、お手本（161dp）より201dp 下だった。内訳は次のとおり。

| 帯 | 高さ | 中身 |
|---|---|---|
| 上部バー | 56dp | お手本も56dp＝同じ |
| **ページヘッダー** | **125dp** | `PageLayout` が出している。タイトル「受信箱」＋説明文「メッセージの管理と返信ができます。」（`ja.json:1271`）＋ボタン |
| ステータスタブ | 55dp | 受信箱固有 |
| 絞り込み（2段） | 69dp | 受信箱固有 |

**上部バーに既に「受信箱」と出ているのに、その下でもう一度タイトルと説明文を出している。** お手本にはこの帯が無い。

### 直し方（PO 判断待ち・§3 の問い1）

`PageLayout.css` に `@media (max-width: 767px)` を追加し、スマホ幅ではページヘッダーの帯を出さない。**PC・タブレットには1行も適用しない。**

効果（実測ベース）: 一覧に使える高さが 348dp → 473dp、見える会話が **3.8行 → 5.1行**。行の高さを76pxにすれば **6.2行**（お手本は6.9行）。

## 3. 決定（2026-10-11・事実に基づき設計担当が確定）

PO 指示「確立したなら進める／推測は禁止／PCに影響を出さない／安全に進める」に従い、事実で確定できた3点を決定した。

| # | 事項 | 決定 | 根拠（事実） |
|---|---|---|---|
| 1 | 行の右の余白 | **スマホ幅だけ `--space-4`(16px) にする** | お手本の実測は16dp。`--space-4` は既存トークン＝新規追加なし。スマホ幅だけに当てるので PC は不変 |
| 2 | 会話1行の高さ | **スマホ幅だけ 76px にする** | お手本の実測は76dp（Meta は78dp）で、PO 指示「見た目と使用感は WhatsApp と同じで作って欲しい」に該当。**76px のトークンは既存に存在しない**ため、**新トークンを1個追加する**（ハードコード禁止を守る唯一の方法）。`--min-height-conv-item`（92px）は `InboxPage.css:266` の1か所だけで使われているが PC にも効くため、**値は書き換えずスマホ幅だけ別トークンを当てる** |
| 3 | ページヘッダーの帯 | **受信箱だけスマホで出さない**（全ページへの拡大は別便で判断） | PO 指示「安全に進めてくれ」に照らし、他ページを巻き込まない方を選ぶ。`PageLayout` に指定を1つ増やし、受信箱だけが渡す |

### 追加するトークン（1個のみ）

```css
/* tokens.css の 部品の大きさ の節に追加 */
--min-height-conv-item-mobile: 76px;  /* 会話アイテム最小高（スマホ）。お手本実測76dp。PCは --min-height-conv-item 92px のまま */
```

`check:new-tokens` が PR 本文の「デザイントークン変更時」チェックリストを要求するため、これを満たす。

## 9. 維持の仕組み

- **守り手**: `frontend/package.json` の `check:all`（25項目）と、CI の `guard-hex-increase`（`scripts/check-design-token-ratchet.sh`）・`Process Artifacts Gate`・`UI Governance Gate`。
- **対象**: 金型外の直書き（`check:css-values` / `check:css-colors`）、見本の欠落（`check:stories`）、新トークンの無断追加（`check:new-tokens` がPR本文のチェックリストを要求）、色コードの増加（ラチェットは**コメント内の色コードも数える**）、ライト/ダークの片方欠落（`check:dark-parity`）。
- **関所が無い部分**: **3幅（390/768/1280）の画面崩れは機械で検査していない。** 段階1のPO決定（2026-10-02）でCIの画面検査を止めてあり、さらに作業端末（ubuntu26.04-arm64）では Playwright が chromium を提供しないため実行できない。**当面は Playwright が動く環境（Mac 側）での人手の実行で守る。** これを機械化するには、CIの画面検査を再開するか、arm64 で動く別のブラウザを用意する必要がある（未解決・design.md §9 の継続課題に追加すべき事項）。
- **金型の用途が分からなくなることへの対策**: `ListRow.stories.tsx` に6状態を並べ、props に日本語の説明を付け、「この部品が決めるもの／渡す側が決めるもの」を冒頭コメントに明記した。`check:stories` が見本の存在を機械的に要求する。
