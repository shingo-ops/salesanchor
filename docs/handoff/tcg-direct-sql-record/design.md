# design: 直接SQL復旧の記録（RECORD-01）

## 目的

本 PR は「記録の追いつき」である。**新たな変更を本番 DB に加えるものではない。**

2026-09-05 17:25〜17:45 に緊急対応として直接 SQL で適用した
仕入元マスタ変更4件を、migration として Git 履歴に残すことが唯一の目的。

---

## 設計判断

### なぜ migration で記録するか

- 「DB への書き込みは migration 経由のみ」の原則（ADR-025）を、今回の緊急対応で一時的に外した。
- その事実を migration として残さなければ、後から `run_all_migrations.sh` を
  新規環境（ステージング等）で実行したとき SP0203 / SP0204 が存在せず、
  FK エラーや import_jobs の不整合が起きる。
- 記録することで「migration さえ流せば本番と同じ状態を再現できる」という保証を維持する。

### 冪等性の設計

| 操作     | 冪等手段                                              |
|----------|------------------------------------------------------|
| UPDATE   | `WHERE code = 'SPXXXX' AND name <> '期待値'`（既に正しければ 0 行変更） |
| INSERT   | `ON CONFLICT (code) DO NOTHING`                      |
| channels | `NOT EXISTS (... WHERE channel='line' AND external_id IS NULL)` |

本番では既に正しい状態のため、再実行時は全操作が 0 行変更・0 行挿入になる。

## 弊害・リスク

- **弊害なし**: 既に本番適用済みの状態を migration で追いかけるだけ。
- **リスク**: migration ファイル内の期待値が実際の本番値と食い違う場合、
  UPDATE が誤った値を上書きする可能性がある。
  → 事前に本番 DB の実値を `SELECT code, name FROM tenant_004.tcg_suppliers WHERE code IN (...)` で確認済み（PO 立ち会い）。

## 戻し方

本 PR をリバートする場合:

1. `migrations/20260905_150000_record_manual_supplier_fixes_t004.sql` を削除する migration を作成する。
2. `run_all_migrations.sh` から該当 `run_sql` 行を削除する。
3. DB 上のデータは変更しない（冪等 migration の性質上、リバートしても本番 DB への影響はない）。
