# design: 解析の誤りの原因を切り分ける（回帰分析）

親: [kgi-regression.md](./kgi-regression.md)／[recon-regression.md](./recon-regression.md)／[解析の正答率を正しく測る仕組み](./design.md)／[LINE解析の調整記録](../../specs/line-analysis-tuning/README.md)

この文書は何か: 正解表 1,494 行の正誤と、その行の条件（長い投稿か・予約か など）を並べ、どの条件で誤りが何倍起きやすいかを計算で出すための設計です。

- 状態: 設計案作成済み・設計審査済み（同じ AI による自己審査・§13）・成功の条件 PO 承認済み（2026-10-31「1」）・設計 PO 承認済み（2026-10-31 チャット、選択肢「1. この進め方で進める」に「1」と回答）・段1の実装カード作成済み（[card-regression-bin1.md](./card-regression-bin1.md)）・実装未着手
- 区分: 既存テーマ（正答率の測定）の延長
- 社外秘: 仕入元名・投稿 id・行ごとの正誤・条件の表は `~/CC報告ファイル-keep/` とクラウドの scratchpad にだけ置く。リポジトリ・PR には決まり・全体の集計値・sha256 だけを書く。

## 1. 目的と利用者に見える変化

- 目的: どこを直すと誤りが一番減るかを数字で知る。PO がこの考え方を身につける。
- 見える変化: PO 本人だけが見られるページに、次の3つが出る。
  - 誤りを増やす条件の上位3つの表（何倍か・確かさの幅・減らせる誤りの見込み）
  - 試した条件すべての表（偶然と区別できなかった条件も含む）
  - 工場の例えで書いた読み方の説明（PO の目的(2) のため）

## 2. 成功の条件

[kgi-regression.md §3](./kgi-regression.md) の KGI-1〜5（PO 承認済み 2026-10-31）。ここでは再定義しない。

## 3. 対象と対象外

対象:
- `scripts/accuracy/score_v102.py` に、行ごとの判定を書き出す任意の出力を足す（§5 段1）。
- 新しい道具 scripts/accuracy/fetch_features.py（新しく作る。行ごとの条件を窓口から作る）と scripts/accuracy/regress.py（新しく作る。計算）とその試験（§5 段2）。
- 計算の実行と結果のページ（§5 段3）。

対象外:
- 製品のコード・DB・本番の設定。解析そのものの直し（結果を見て PO が次に決める）。
- 指示書の版・モデルの比較（recon: 1 種類しか無い）。
- 正解表を増やすこと。

## 4. 計算の考え方（素人向けの言い換えつき）

- 1 行＝正解表の 1 行。除外 ALL の行は入れない。
- 結果の列（誤りか）: その行の採点した項目に「違う」が1つでもあれば 1、無ければ 0。読み落とし（システムがその行を出していない）も 1。「答え無し」の項目は数えない。`scripts/accuracy/by_group.py` の「全項目」と同じ決め方（`docs/handoff/accuracy-measurement/card-by-group-bin1.md:38`）に読み落としを足したもの。
- 計算: ロジスティック回帰（結果が「誤りか・誤りでないか」の2択のときの回帰分析）。各条件の効き目を「オッズ比」で出す。言い換えは「その条件があると、誤りの起きやすさが何倍か」。誤りが少ないとき（1割前後）、オッズ比は「誤りが何倍になるか」とほぼ同じになる。ページにはこの注を1行添える。
- 同じ投稿の行は互いに似る（1つの投稿で読み間違えると、同じ投稿の何行もまとめて違う）。この偏りで幅が狭く出すぎるのを防ぐため、投稿を1つの群にした補正（群ごとの頑健な分散、CRV1）を使う。群は 100。
- 95% の幅: 推定値 ± 1.959964 × 標準誤差 を指数に戻したもの（`scripts/accuracy/by_group.py` の z と同じ値）。
- 上位3つの選び方: オッズ比が 1 より大きい条件を、「減らせる誤りの見込み」が大きい順に並べた上位3つ。見込み＝その条件がある行の誤りの数 ×（1 − 1 ÷ オッズ比）。言い換えは「その条件のせいで増えた分の誤りの数」。PO の問い「どこを直すと一番減るか」に直接答える並べ方のため、何倍かの大きさではなくこちらで並べる。

## 5. 段の分け方

### 段1: 行ごとの判定を出す（実装）
- `scripts/accuracy/score_v102.py` に `--verdicts-out <パス>` を足す。付けたときだけ、`row_no	項目	判定`（判定は OK / NG / NOWORD / SKIP、読み落としは項目 `C1`・判定 NG）を書く。row_no は正解表の行番号。
- 付けないときの出力は今と1字も変えない（既存の試験と、変更前後の `result.tsv`・`errors.tsv` の sha256 一致で確かめる）。
- 実行して、誤りの行数を数える。→ §6 の条件の数がここで決まる。

### 段2: 条件の表と計算の道具（実装）
- fetch_features.py: 正解表の投稿 id から窓口（ADR-1042）で投稿の本文・仕入元を読み、§6 の条件を行ごとに 0/1 で作る。本文はファイルに残さず、条件の 0/1 だけを書く。
- regress.py: 判定と条件を受けて §4 の計算をする。標準ライブラリだけで書く（既存の道具と同じ・同じ入力なら同じ出力にするため）。出力は `coef.tsv`（全条件）・`top3.tsv`・`inputs.sha256`。
- 試験は作り物のデータだけ。答え合わせの値は、クラウドで statsmodels 0.15.0（`GLM(Binomial)`・`cov_type='cluster'`）に同じ作り物を通して得た数を試験に書き込む。小数4桁まで一致で合格。

### 段3: 実行と結果のページ（実行）
- クラウドで段1→段2 を通し、結果を PO 本人だけが見られるページに出す（`scripts/accuracy/README.md` の持ち帰りの決まりどおり）。
- 2回通して全出力の sha256 一致を確かめる（KGI-4）。

## 6. 条件の候補（計算の前に固定する）

結果を見てから条件を足し引きすると、偶然の当たりを拾いやすい。そこで候補と並び順を先に固定する。どれも「はい／いいえ」の2択にする（PO が読みやすく、上位3つの見込みが計算しやすいため）。

| 優先 | 条件 | はいの決め方 | 出どころ |
|---|---|---|---|
| 1 | 長い投稿 | 投稿の行数が 100 投稿の中央値以上 | 投稿の本文 |
| 2 | 商品が多い投稿 | その投稿の正解表の行数が中央値以上 | 正解表 |
| 3 | 投稿の後半の行 | 値段の行の番号 ÷ 投稿の行数 が 0.5 より大きい | 正解表・本文 |
| 4 | 予約の行 | 正解の在庫の状態が「予約」 | 正解表 |
| 5 | 発送日がある行 | 正解の発送日が「無し」でない | 正解表 |
| 6 | 登録の無い商品の行 | 正解の商品が「未登録」 | 正解表 |
| 7 | 1つの値段に複数の商品が付く行 | 同じ投稿の正解表に、同じ値段の行番号を持つ行がほかにもある | 正解表 |
| 8 | 行数の多い仕入元 | 正解表の行数が上位 3 の仕入元の行（3つまとめて1つの条件） | 本文・仕入元 |

- 使う条件の数＝誤りの行数 ÷ 10 の切り捨て（最大 8）。上の優先の順に取る。原因1つにつき誤り 10 件が要る、という慣例（Peduzzi ほか 1996, Journal of Clinical Epidemiology 49(12):1373-1379）に従う。
- 「はい」か「いいえ」が 20 行未満の条件は外し、次の優先を繰り上げる（幅が広すぎて読めないため）。外した条件は表に「件数不足」と残す。
- 誤りが 30 行未満なら、計算はせず段1の数だけを PO に報告して止まる（条件が 2 つ以下では「上位3つ」が作れない）。

## 7. 選ばなかった案

- 仕入元を 46 個ばらばらの条件にする: 条件の数が誤りの数に対して多すぎ、幅が読めなくなる。仕入元ごとの正答率は `scripts/accuracy/by_group.py` の表で別に見る。
- statsmodels を道具に入れる: 既存の道具が標準ライブラリだけ・クラウドでの導入の手間が増える。答え合わせにだけ使う。
- 何倍かの大きさで並べる: 行数の少ない条件が上に来て、直しても減る誤りが少ない。PO の問いに合わない。
- 項目ごと（値段・数量…）に別々に計算する: 1項目あたりの誤りが少なく、条件をほとんど入れられない。全項目の結果が出たあとの次の段として残す。

## 8. リスクと対処

| リスク | 対処 |
|---|---|
| 8 つ試して上位3つを選ぶので、偶然の当たりが混じる | 試した条件の数と全条件の表をページに必ず出す。結果を見てから条件を足さない（§6 を固定） |
| 100 投稿は特定の時期の投稿だけ | ページに「10/23 版の正解表・100 投稿の範囲で言えること」と書く。ほかの時期に当てはまるかは言わない |
| 条件どうしが重なる（長い投稿は商品も多い） | 計算の前に条件どうしの重なり（両方はいの行の割合）を表に出す。0.9 を超える組があれば優先の低い方を外す |
| 自前の計算が間違う | §5 段2 の statsmodels との答え合わせ。合わなければ実行しない |
| 社外秘が漏れる | 出力はリポジトリの外だけ（既存の道具と同じ検査）。PR の差分を KGI-5 で確かめる |

## 9. 受入条件と検証方法

| 基準 | 検証方法 |
|---|---|
| 段1: 付けないときの出力が変わらない | 同じ入力で変更前後の `result.tsv`・`errors.tsv` の sha256 が一致 |
| 段1: 行ごとの判定の数が集計と合う | 判定表の OK・NG・NOWORD を項目ごとに数え、`result.tsv` の「通し」「Gemini」の段と一致。C1 の数が「C1読み落とし」と一致 |
| 段2: 計算が正しい | 作り物のデータで、オッズ比・幅が statsmodels の値と小数4桁まで一致（試験） |
| 段2: 条件の数の決まりどおり | 作り物で誤り 29 行→計算せず止まる、誤り 45 行→条件 4 つ、の試験 |
| KGI-1 | 条件の表の行数が 1,494 −（除外 ALL の行数）。除外 ALL の行数は段1の出力で数え、kgi に書き足す |
| KGI-2・3 | `top3.tsv` の3行・各行の幅の下限 |
| KGI-4 | 2回の全出力の sha256 一致 |
| KGI-5 | PR の差分を目で見て、投稿 id（UUID の形）が 0 件 |

KGI-1 の「1,494 行」は除外 ALL を除いた数で読む。除外の行は採点の対象外だから（`scripts/accuracy/score_v102.py:214-215`）。PO の決めた条件の意味は変わらない。

## 10. 未確認と、その扱い

- GLM の CRV1 の補正の式は公式の説明書に無い（recon）。自前の計算は statsmodels の出す数に合わせる。合わせ方（補正の有無）は段2の答え合わせで決め、カードに書く。
- 誤りの行数は段1のあとに分かる。条件の数は §6 の決まりで機械的に決まるので、設計の作り直しは要らない。
- A2・A3 の値の種類は使わない（§6 に入れていない）。

## 11. 外部・過去事例の参照と我々への応用

- Peduzzi P ほか（1996）"A simulation study of the number of events per variable in logistic regression analysis", Journal of Clinical Epidemiology 49(12):1373-1379。原因1つあたりの誤りが 10 件を下回ると、推定がずれやすいという模擬計算の結果。→ §6 の条件の数の上限に使う。数値は論文の要旨の範囲で引用し、ここで新しい数は作らない。
- statsmodels 0.15.0 の説明書（recon）。→ 答え合わせの基準。
- 同じ仕組みの社内の前例: `scripts/accuracy/by_group.py` の Wilson の幅（仕入元ごとの正答率）。→ 幅の z の値をそろえる。
- 他社の導入の数値事例は使わない。理由: 今回は自社の記録を計算するだけで、他社の成功を根拠にする判断が無いため。

## 12. 進め方とPOの判断

1. この設計の PO 承認 → 段1の実装カード → カード審査 → PO の実装承認 → クラウドの Sonnet が実装 → マージ前の審査。
2. 段1の数（誤りの行数）が出たら PO に報告。30 行未満なら止まる。
3. 段2・段3 も同じ流れ。結果のページを PO に見せて終わり。

## 維持の仕組み

- 守り手: scripts/accuracy/test_score_v102.py（段1の「付けないときは出力が変わらない」を試験で守る）。段2 以降は scripts/accuracy/test_regress.py を足す。
- 対象: 既存の正答率の数字が変わらないこと・自前の計算が statsmodels と一致し続けること。
- 結果の解釈（条件の選び方を後から変えない）は人手で守る。理由: 機械では「結果を見たあとに条件を足したか」を判定できないため。§6 の表を変えるときはこの文書を直す PR を通す。
