# design: 正答率を仕入元ごと・商品の種類ごとに分けて出す

親: [解析の正答率を正しく測る仕組み](./design.md)／[LINE解析の調整記録](../../specs/line-analysis-tuning/README.md)

この文書は何か: 今ある正答率の採点（正解表と採点の道具）を変えずに、同じ採点結果を仕入元ごと・商品の種類ごとにも分けて出すための設計です。あわせて、出た数字をどう確かめて根拠にするかを決めます。

- 状態: 設計案作成済み・設計審査済み（自己審査・下の §12）・成功の条件 PO 合意済み（2026-10-28 チャット「条件については合意」）・設計そのものは PO 承認待ち・実装未着手
- 区分: 既存テーマ line-analysis-tuning の延長（親 design.md の続き）
- 社外秘: 仕入元名・投稿 id・仕入元ごとの表は `~/CC報告ファイル-keep/` に置く。リポジトリには決まり・全体の集計値・sha256 だけを書く（親 design.md と同じ扱い）。

## 1. 目的（PO の言葉と経緯）

- 2026-10-28、外部の機械学習の教材（GokuMohandas/Made-With-ML の評価の章、DataTalksClub/mlops-zoomcamp の監視の章）を調べた。教材は「全体の点数だけで判断せず、種類ごと・条件ごとにも点数を出す」ことを勧めている（§11）。
- 今の採点の結果の表は、項目×段（Gemini／システム／通し）の全体の数字だけ（`scripts/accuracy/score_v102.py:285-300` の `result_rows()`）。仕入元ごと・商品の種類ごとの数字は出ない。
- PO の選択「1」（2026-10-28）: 仕入元ごと・商品の種類ごとの正答率を出す設計を作る。
- PO の問い（2026-10-28）:「測り方と精度はどう確立してエビデンスにする？」→ §5・§6・§7 で答える。

利用者に見える変化:
- 正答率を測るたびに、全体の表に加えて「仕入元ごとの表」「商品の種類ごとの表」が出る。
- どの仕入元のどの項目が弱いかが、表で分かる。
- 数字ごとに「本当の実力が入っていそうな幅」が付く。件数が少ない数字には「参考」の印が付く。

## 2. 成功の条件（KGI。PO 合意済み 2026-10-28）

| # | 基準 | 検証方法 |
|---|---|---|
| KGI-1 | 仕入元ごとに、9項目×段の正答率と件数（正しい・違う・答え無し）が表で出る | 仕入元ごとの表を開き、仕入元の数×項目の行があり、空欄が 0 |
| KGI-2 | 商品の種類ごと（中分類。ポケモン・ワンピースなど）にも、同じ形の表が出る | 種類ごとの表を開いて同じく数える |
| KGI-3 | 値段の行が20件未満の仕入元・種類には「参考」の印が付く | 件数 20 未満の行の「参考」列が全部「参考」、20 以上が全部空 |
| KGI-4 | 同じ材料で2回測ると、結果が1字も違わない | 2回の出力の sha256 が全ファイルで一致 |
| KGI-5 | 分けた数を足し合わせると、今の全体の数字と一致する | 項目×段ごとに、仕入元の表の正しい・違う・答え無しの合計が全体の表と一致（種類の表も同じ） |

§6 の「幅」の列は、KGI-3 の「参考」の判断を数字で裏づけるための追加。PO の設計承認で一緒に確かめてもらう。

## 3. 対象と対象外

対象:
- 採点の道具 `scripts/accuracy/score_v102.py` に、分けた表を出す働きを足す
- 投稿→仕入元、正解の商品→中分類 の対応を、読むだけの窓口（ADR-1042・ADR-1024 の ai_ro）から取り出す道具
- 測り方の確かめ（§5）と、記録の残し方（§7）

対象外:
- 正解表の中身を変えること（版は gold_v1 のまま）
- 見本を増やすこと（PO が選択肢3を選ばなかった。§10 のリスクで扱う）
- 解析そのものを直すこと
- 定期的な自動の測定（別の案。今回は測るときに一緒に出すだけ）
- agent-console で予約済みの測定（見出しの決まりの試し・売り切れの毎朝点検）。見る行も道具も重ならないので触らない

## 4. 変更の前後

| | 変更前 | 変更後 |
|---|---|---|
| 出力 | `result.tsv`（全体）・`errors.tsv`・`inputs.sha256` | 左の3つは1字も変えない＋`result_by_supplier.tsv`・`result_by_category.tsv` |
| 入力 | 正解表・写し | 左の2つ＋対応表 `groups.tsv`（投稿 id→仕入元の番号、商品番号→中分類）。引数 `--groups` を付けたときだけ分けた表を出す |
| 仕入元の表し方 | — | 表には仕入元の番号だけを書く。名前は社外秘の手元ファイルでだけ引く |

分け方の決まり:
- 仕入元: 投稿の仕入元（`source_messages.supplier_channel_id` → `supplier_channels.supplier_id`。`migrations/20260921_110000_pipeline_tables_public.sql:11-22`）。
- 商品の種類: **正解の**商品（正解表の A1）の中分類で分ける。システムが選んだ商品で分けると、商品を取り違えた件が別の種類に数えられ、弱い種類が見えなくなるため。正解が「未登録」「商品でない」の件は、その名前の種類にまとめる。
- 段の切り分けは今と同じ。システム段は「Gemini が行の範囲を正しく読めた件」だけで数える（`score_v102.py:227-244`, `:274-278` の `e1ok`）。分けた表でもこの決まりを変えない。

## 5. 測り方の確かめ方（物差しが正しいことの根拠）

分けた表を信じる前に、次の5つを全部通す。1つでも外れたら、その回の表は使わずに原因を直す。

| # | 確かめること | やり方 | 合格 |
|---|---|---|---|
| V1 | 道具の数え方が正しい | 作り物のデータ（仕入元3つ・種類3つ・答えを人が決めたもの）で試験を作り、表を手で計算した値と比べる | 全部一致。`python3 -m pytest scripts/accuracy -q` が通る |
| V2 | 分けても数が消えたり増えたりしない | KGI-5 の合計の照合を道具の中に入れ、合わなければ `STOP:` で止める | 本番の材料で止まらない |
| V3 | 何度測っても同じ | 同じ材料で2回流す | 出力の sha256 が全部一致（KGI-4） |
| V4 | 機械の数字と人の数え方が合う | 一番件数の多い仕入元を1つ選び、違う件の一覧と正解表から Opus が手で数える。Sonnet も別に、互いを見ずに数える | 3つ（道具・Opus・Sonnet）の数が全部一致 |
| V5 | 今の全体の数字が変わっていない | 足す前の道具と足した後の道具で、同じ材料の `result.tsv` を比べる | sha256 が一致 |

物差しの元になる正解表の確かさは、親 design.md §6 の作り方で確かめ済み（AI 2人が別々に付け、割れた件は PO が決め、割れなかった件からも20件を原文と照らす）。今回は正解表を変えないので、その確かさをそのまま引き継ぐ。

## 6. 精度（数字にどれだけ幅があるか）

件数が少ないと、1件の違いで点数が大きく動く。そこで、正答率ごとに「本当の実力が入っていそうな幅」を一緒に出す。

- 計算: Wilson の95%区間（件数が少ないときも幅が0〜100%の外に出ない計算）。標準ライブラリだけで計算する。
- 分母は今と同じ（正しい＋違う。答え無しは入れない）。
- 例（正答率90%のとき）:

| 件数 | 正答率 | 幅 |
|---|---|---|
| 10件中9件 | 90% | 約60%〜98% |
| 20件中18件 | 90% | 約70%〜97% |
| 100件中90件 | 90% | 約83%〜95% |

- 読み方の決まり:
  - 2つの仕入元の幅が重なっているときは「差があるとは言えない」と書く。
  - 「参考」の印（20件未満）が付いた数字だけで、直す・直さないを決めない。
- 表の列: `項目, 段, 正しい, 違う, 答え無し, 正答率, 幅の下, 幅の上, 参考`。全体の `result.tsv` の形は変えない。

## 7. 根拠（エビデンス）の残し方

測るたびに次を残す。あとで誰が流しても、同じ数字が出ることを確かめられるようにするため。

| 何を | どこに | 中身 |
|---|---|---|
| 測った条件 | `docs/specs/line-analysis-tuning/track-record.md` に1行 | 日付・正解表の版と sha256・解析の版（engine）・写しを取った時刻・マスタの更新時刻・道具のコミット・出力の sha256・V1〜V5 の合否 |
| 全体の数字 | 同じ1行 | 今と同じ全体の正答率 |
| 仕入元ごと・種類ごとの表 | `~/CC報告ファイル-keep/accuracy-by-supplier/<日付>/`（社外秘） | 表そのもの・対応表・V4 の手数えの記録 |
| PO に見せる表 | 本人だけが見られる非公開ページ（`scripts/accuracy/README.md` の「結果の持ち帰り」と同じ手順） | 仕入元の名前を引いた表。共有しない |

- リポジトリと PR には仕入元の名前・番号ごとの数字を書かない。PR の前に、差分に仕入元の名前が 0 件かを grep で確かめる。
- 正解表・マスタ・道具のどれかが変わったら、前の回と直接比べない。比べるときは同じ版で測り直す（memory feedback_compare_master_timestamps）。

## 8. 進め方

| 段 | 中身 | 変えるもの | PO にお願いすること |
|---|---|---|---|
| 1 | 道具を足す（`--groups` と分けた表・幅の列・合計の照合）＋対応表を取る道具＋作り物の試験 | `scripts/accuracy/` だけ。製品コード・DB は変えない | 無し |
| 2 | 本番の材料で測り、V2〜V5 を通す。結果を非公開ページで見せる | 何も変えない（読むだけ） | 表を見て、どこから直すかを決める |

実装の前に確かめること（未確認。段1のカードを出す前に Sonnet が読み取りで確かめる）:
- 読むだけの窓口に `source_messages`・`supplier_channels`・共用商品マスタの中分類の列が出ているか（ai_ro の表名は「スキーマ__表名」の形）。出ていなければ窓口の追加が要り、別の判断になる。
- 中分類の列名と、正解表の商品番号（A1）からたどる道。

## 9. 選ばなかった案

- **システムが選んだ商品の種類で分ける**: 取り違えた件が別の種類に入り、弱い種類が隠れる。正解の商品で分ける。
- **今の `result.tsv` に列を足す**: 前の回の結果と形が変わり、V5 で比べられなくなる。別のファイルにする。
- **正解表に仕入元の列を足す**: 正解表の版が上がり、今の確かさの記録を引き継げない。対応表を別に取る。
- **幅を出さず、件数だけで判断する**: 「20件」の線に根拠がなくなる。幅を出すと、線の意味を数字で示せる。

## 10. リスクと対処

| リスク | 対処 |
|---|---|
| 1つの仕入元が10投稿までなので、仕入元ごとの幅が広く、差が見えない | 幅を出し、重なれば「差があるとは言えない」と書く。弱そうな仕入元が見えたら、そこだけ見本を足す案を PO に出す（今回はしない） |
| 対応表の取り出しが壊れ、仕入元を取り違える | 対応表の行数と、正解表の投稿数の一致を確かめてから使う。合わなければ `STOP:` |
| マスタが直って中分類が変わる | 対応表にマスタの更新時刻を残す。変わったら前の回と直接比べない |
| 仕入元の名前が PR に混ざる | 道具は番号しか扱わない。PR の前に grep で 0 件を確かめる |

## 11. 外部事例の参照と我々への応用
