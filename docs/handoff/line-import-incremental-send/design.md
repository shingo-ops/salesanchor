# 設計: LINE取込の送信を「直近分だけ」に絞る

現在地: [recon.md](recon.md)。親トラック: [docs/handoff/line-android-import/design.md](../line-android-import/design.md)、
アプリ版: [docs/handoff/line-auto-export-app/design.md](../line-auto-export-app/design.md)。backend/DB/API の変更なし（ADR-072・ADR-154 の範囲内）。

## 背景（PO合意 2026-10-08）

アプリ経路（ADB不要）が実機で通り、**更新間隔を15分→5分に上げる**方針が決まった。
しかし現状は毎回 5.2MB を送っており（recon 事実1）、5分間隔では最大 1.4GB/日。モバイル通信では成立しない。
**先に送信量を絞ってから頻度を上げる**順で進める。

## KGI

| # | 基準 | 検証方法 |
|---|---|---|
| 1 | 新規メッセージが1件以上あるときだけ送信し、無ければ**一切送信しない** | 同じ内容で2回連続実行し、2回目は `events` に `send started` が無いこと（`send skipped` が記録される） |
| 2 | 1回の送信量が**20KB以下**（現状5.2MB） | `events.elapsed_seconds` とは別に、送信バイト数を `events.reason` に記録して確認。実測値を本書に追記 |
| 3 | 取りこぼしゼロ | 新規1件を追加して実行→サーバーの `message_count` が1以上。基準時刻の同一分に複数件ある履歴で、同一分の後続が取り込まれること（単体テスト） |
| 4 | 失敗した回は次回が取り戻す | 送信を失敗させた直後に新規を追加して実行→失敗分も含めて取り込まれること（単体テスト） |
| 5 | 10MiB上限に当たらない | 12MiB の書き出しファイルで `enqueue` が成功し、送信ペイロードが20KB以下であること（単体テスト） |
| 6 | 既存の回帰が壊れない | `tools/termux-line-import/test_android_import.py` が全て通る |

## 方式

### 基準時刻（watermark）

- **サーバーが受理（`accepted` / `pending_review`）した送信に含まれていた、最後のメッセージの時刻**を基準として保存する。
- 保存先は `outbox.sqlite3` に新テーブル `meta(key TEXT PRIMARY KEY, value TEXT)`。キーは `sent_watermark`（値はメッセージの `timestamp` 文字列そのまま）。
  既存 `jobs`/`events` のスキーマは変えない（`client.py:67-77`）。
- **受理されたときだけ**基準を進める。失敗（`retry`/`auth_required`）では進めない → 失敗した分は次回が自動で取り戻す（KGI 4）。

### 送るものの決め方

1. 原本を読み、digest の整合性を確認する（**現状どおり**。`client.py:300-302`）。
2. 原本を `parse_android_export()` で解析する。
3. 基準が無い（初回・移行直後）→ **原本をそのまま送る**（現状と同じ挙動）。送信が受理されたら基準を設定する。
4. 基準がある場合:
   - **基準より後のメッセージが1件も無ければ送信しない**。`events` に `send` / `skipped` を記録し、理由は `新規なし（基準: <時刻>）`。ジョブは `accepted` 相当として扱わず **`queued` のまま残さない**（下の「ジョブの扱い」参照）。
   - 1件以上あれば、**切り出し開始位置 = 基準時刻 − 60分**。この時刻以降の最初のメッセージを特定する。
5. **送信ペイロードは原本テキストの行スライスで作る**（辞書から再直列化してはならない。recon 事実4）。
   - 内容 = 「切り出し開始メッセージが属する日の日付行」＋「そのメッセージの開始行から原本末尾まで」。
   - 日付行を必ず先頭に置く理由: パーサは日付行が無いメッセージ行を受け付けない（`android_parser.py:31` の `and day`）。
   - 原本の改行はそのまま使う（`splitlines()` の結果を `\n` で再結合する）。
6. `window_hours` は **`0` のまま**（送った範囲を全部取り込ませる。`client.py:432`）。

### 重なりを60分にする根拠（実測）

| 重なり | 送り直す量（実測） |
|---|---|
| 1分（最低限） | 0〜**6.4KB**（同一分 最大4件 × 1,590B） |
| **60分（採用）** | **5.0KB**（直近1時間 8件） |
| 24時間 | 157.1KB |

- **必須の下限は1分**: 記録の時刻精度が分までで、同一分に最大4件入るため（recon 事実5）。境界を「基準より後」にすると同一分の後続が落ちる。
- 時刻が過去に巻き戻る並びは41日・3,277件で**0件**のため、長い重なりは本来不要。
- それでも**60分を採用**する: 1分（最大6.4KB）と60分（5.0KB）が**同じ桁**で、余裕を削る利得が無いため。想定外の挿し込みに対する保険を無料で持てる。

### ジョブの扱い（重要）

- `jobs` の主キーは**引き続き原本全体の digest**。送信ペイロードの digest ではない。原本の保持・整合性確認・重複判定（`client.py:189-197`）は現状のまま。
- 「新規なし」で送らなかった場合、そのジョブは `accepted` にしてはいけない（サーバーは何も受け取っていない）。**`skipped` という新しい state** にし、`finished_at` を入れて再送対象から外す（再送クエリは `client.py:297` の `('queued','retry','auth_required')`。`skipped` は含まれない）。
  - 理由: `queued` のまま残すと毎回「新規なし」で評価され続け、`supersede_and_cleanup`（`client.py:201`）の対象判定も濁る。
- 送信バイト数を `events.reason` に `送信 <N>バイト（基準 <時刻> / 全体 <M>バイト）` の形で残す（KGI 2 の計測用。本文は一切出さない）。

### 10MiB 上限（recon 事実3 の是正）

- `MAX_BYTES`（`client.py:23`）は**書き出しファイル自体**への判定なので、送信量を絞っても約66日後に当たる。
- **`MAX_BYTES` を 64MiB に引き上げる**。根拠: 送信ペイロードは20KB以下になるためサーバー側の負荷は無関係になり、この定数は端末の暴走検知（壊れたファイルを読み込まない）という役目だけが残る。1件平均1,590Bなら64MiBは約4万件＝数年分。
- 併せて `enqueue` の読み取り（`client.py:144`）も新しい上限に追従させる。

## 弊害・トレードオフ

- **送信内容がサーバー側の重複判定に依存する**（重なり60分ぶんは毎回重複として捨てられる）。サーバーの重複判定が壊れると二重取り込みになる。→ 判定はサーバーに残す現行方針を維持（スマホ側に重複判定を持たせない）。
- 基準（`sent_watermark`）が消えると、次の1回だけ原本全体（5.2MB）を送る。これは安全側の挙動（取りこぼさない）。
- 送信ペイロードが小さくなるため、サーバー側で「1回の取り込み件数」が減る。`message_count` を監視している画面・通知の見え方が変わる可能性がある（取り込み内容そのものは変わらない）。
- Wi-Fi↔モバイル切替直後の401（recon 事実6）は**本設計では扱わない**。別途PO判断。

## 外部事例の検討

- 一般的な差分同期（rsync の `--append`、ログ転送の tail 追従）と同じ考え方。**「送信側は範囲を絞るだけ、重複排除は受信側」**という責務分担も同じで、送信側の状態が失われても受信側が冪等なら安全に再送できる。
- LINE公式のトーク履歴書き出しは**常に全履歴**を出す仕様のため、書き出し側で差分にする手段は無い。したがって切り出しは取り込み側（端末）で行うほかない。

## 計画

1. `android_parser.py`: 各メッセージに**開始行番号**を持たせる（既存キーは変えず追加のみ。`parse_android_export` の戻り値に `line`）。
2. `client.py`: `meta` テーブル追加、`send()` の切り出し処理、`skipped` state、`MAX_BYTES` 引き上げ、送信バイト数の記録。
3. `test_android_import.py`: KGI 1・3・4・5 に対応する単体テストを追加。
4. 端末へ配置して実機確認（5分間隔の前に、まず手動実行で送信量とDB記録を確認）。
5. 合格後に段階3（アプリ内タイマーで5分間隔）へ進む。

## 維持の仕組み

- 守り手: `tools/termux-line-import/test_android_import.py`（KGI 1・3・4・5 の回帰）。
- 人手で守る: 端末への配置と実機確認（CIからは端末のGUI・通信を検証できない）。

## 追補 2026-10-08: 「同一分の孤立した新規」を取りこぼさないための追加状態

recon 事実7（毎回変わる `保存日時` 行）により、digest による重複判定は実運用で発動しない。
よって「新規の有無」は watermark 判定だけで決まる。ここに1点だけ穴が残るため閉じる。

**穴**: watermark と**同じ分**に新しいメッセージが1件増え、その後に**より新しい時刻のメッセージが続かない**場合、
「基準より後が0件」と判定して送信を見送ってしまう。次に新しいメッセージが届けば60分の重なりで一緒に送られる（＝失われない）が、**その間は遅れる**。
この群は平均17分に1件のため通常は数分〜数十分の遅れだが、**その日の最後のメッセージが翌朝まで遅れる**ことがあり得る。5分間隔にする目的（鮮度）と矛盾する。

**閉じ方**: `meta` に **`sent_watermark_tail_count`** を追加する。
- 値 = 受理された送信ペイロードの中で、**timestamp が watermark と等しいメッセージの件数**。
- 「新規あり」の判定を次の **いずれか** に変える:
  1. `timestamp > watermark` のメッセージが1件以上ある（従来）
  2. `timestamp == watermark` のメッセージ件数が **`sent_watermark_tail_count` より多い**（同一分に増えた＝新規）
- 切り出し開始位置（watermark − 60分）と、受理時の watermark 更新規則は**変更しない**。更新時に `sent_watermark_tail_count` も併せて書く。
- 実測の裏付け: 同一分に複数あるメッセージは17%、最大4件/分（recon 事実5）。件数比較で判定できる粒度である。
