## 0. 原則

**recon before write は、リポジトリと DB だけでなく、実行環境のガードと道具そのものにも適用する。**
本文書の教訓は、ほぼすべて「道具の仕様を実測せずにカードを書いた」ことに起因する停止から得た。

**ガードは意図ではなく形で判定する。** 読み取りだけの SQL でも、`clasp push --help` のようなヘルプ表示でも、パターンに一致すれば止まる（§11 事例2・3）。

## 1. 実行役ごとの挙動差（実測）

| 観点 | Claude Code（CC） | Codex |
|---|---|---|
| カードに無い確認 | 気を利かせて補うことがある（指示外のコマンド出力・注釈） | 補わない。書いていない確認は行われない |
| 報告の装飾 | 見出し・表・注釈を付ける（同じ手順で100〜300行） | 素のテキスト（同じ手順で40〜190行） |
| 0件の報告 | 「0件」と補足する | 空のまま報告する（推測で補わない） |
| `rm -f` | 実行する | 環境が拒否する（2026-09-07 実測） |
| ヒアドキュメント上書き | 通る（284行・md5 一致） | 通る（107行・2026-09-07 実測） |
| スクリプトの引数誤り | 自己修正して通す（`gh-pr-merge-safe.sh --merge`） | 未実測 |

帰結: **カードは省略せずに書く**。「当然やるだろう」は Codex には通らない。

カード形式でない指示書（実装指示書の体裁）は、実行役が正しく拒否する。常設ルールが機能した記録（§11 事例9）。

## 2. 実行役を交代したら、挙動確認カードを1便挟む

読み取り専用・5手順・DB接続なし・書き込みなし。測るのは次の7観点。

1. 受領確認の文言が一字一句そのままか
2. 指定した出力先に書き、チャットには指定の1行だけ返すか
3. 生出力を要約せず全文で書くか（`wc -l` の先頭空白まで残るか）
4. カードにないコマンドを足していないか
5. 0件を0件と報告できるか（意図的に空になる grep を1手順入れる）
6. 停止条件を理解しているか（実際には止まらない境界値の停止条件を1つ置く）
7. `SHA=$(git rev-parse origin/main)` を同一行内で固定する指示に従うか

雛形: CARD-CODEX-PROBE-01（2026-09-07・Codex で7観点通過）。

## 3. 報告の運び方

- 生出力はチャットに貼らず `/tmp/CC報告ファイル/<カードID>.txt` に全文書く（PR #3325 は `.md`。拡張子は PO 指示に従う）
- **完走時**: チャットには `wc -l` の結果だけを1行
- **停止・エラー時**: 1行ルールを適用しない。「停止した手順番号／最後のコマンド／画面の生出力全文」をチャットに書く（1行ルールが停止報告を封じた実測: CARD-DP-RECON-03・2026-09-07）
- 各手順の前後に目印行（`=== 手順N ===` / `=== 手順N 完了 ===`）を書く。途中で止まっても、どこまで走ったかがファイルに残る
- `/tmp` はOSの再起動で消える。書いたらすぐアップロード（`/tmp/CARD-BENCH-PR-01/` 消失を実測・2026-09-06）
- 出力が長いほど転記が崩れる。`tail` や `cat` より `git diff`・`grep -c` で量を絞る（§11 事例7）

**報告様式の定型句**（カード冒頭に置く。要約表だけの報告・同一報告の再送を防ぐ・§11 事例8）:

> 本カードは新規である。過去の報告の再送を禁止する。報告に executor-preamble.md の中身を含めることを禁止する。表・要約・チェックマークだけの報告を禁止する。各手順のコマンドの標準出力をそのまま貼ること。

## 4. 出力の上限と、自己参照の禁止（事故の記録）

**事故**: CARD-BENCH-RECON-01 手順12 で `cd DIR && for f in $(ls); do cat "$f"; done > report.md` と書いた。`report.md` が同じ DIR に作られ、`ls` に自分が含まれ、自分を自分に書き足し続けて **32GB** になった。ディスクが 100% になり、後続便が ENOSPC で停止した（2026-09-05〜06・PR #3325 recon に記録）。

決まり:
- 出力ファイルは**列挙対象のディレクトリに置かない**
- コマンド出力は `head -N` / `tail -N` で**必ず上限を付ける**（PR #3325: `tail -500`・10MB で停止）
- 束ねる処理を書くなら、束ね先を明示的に除外するか、別ディレクトリにする

## 5. カードは1つのコードブロックにまとめる

- **外側のフェンスは `~~~` を使う。** 本文に ``` が現れてもブロックが閉じない。外側を ``` にすると、内側の ``` で閉じられ、そこから先がコピー範囲から落ちる（CARD-OPS-PR-01 が本文の途中で切れて2便を空費・2026-09-07 実測）
- ブロックの中はカード本文のみ。投入手順・補足・弊害はブロックの外に書く
- 見出しの固定順: カードID／上書き宣言／目的／出力の置き場／禁止（名指し）／停止条件（2段）／受領確認／手順／報告様式／END OF CARD
- コピー前に、ブロックの末尾に `END OF CARD` が見えることを目視で確かめる
- 記号（`*` `_` `|`）はフェンス内に置く（輸送で消えるため・design-partner.md §5.5-1）
- 長いカードは分割する。ただし分割の前に、切れの原因がフェンスの入れ子でないかを先に疑う

## 6. 伏せ字フィルタを常設する

定型文（executor-preamble.md:24）は「カードに REDACT の定義があればそれを使い、無ければ設計パートナーに確認して止まる」と定める。カード側で定義を持つ。

定義例（`sed -E` で AIza / gh[pousr]_ / sk- で始まる長い文字列と、`password=` `token:` 等の右辺を `<REDACTED>` に置換する）。書き出しは `<コマンド> 2>&1 | eval "$REDACT" >> "$OUT"`。変数は各行の先頭で定義し、行をまたいで持ち越さない。網羅ではない（代表的な鍵の形のみ）。

## 7. 編集方式は「前後の文脈に依存しないもの」を選ぶ

| 変更の性質 | 方式 | 検算 |
|---|---|---|
| 新規ファイル | ヒアドキュメント上書き（`cat > FILE <<'EOF'`・引用符付き終端） | 行数（±1）と末尾3行の目視 |
| 既存ファイルの末尾に足すだけ | ヒアドキュメント追記（`cat >> FILE`） | 行数の差と `git diff --stat` の削除行が 0 |
| 既存ファイルの途中の書き換え・挿入 | 丸ごと上書き（短いファイル）、または**1か所だけ**の置換 | 同上 |

**ヒアドキュメントは末尾の改行を1つ落とす。** 手元より行数が1少なくなり、md5 は一致しない（107行→106行・2026-09-07 実測）。md5 一致を停止条件にしない。検算は行数±1と末尾3行で行う。

**禁止**: 1つのカードで複数箇所に差分（`apply_patch`）を当てる。1か所外れると後続が全部外れ、しかもファイルは無傷のまま「やったつもり」になる（§11 事例5-a）。

「末尾追記にする」は一般則ではない。HTML の末尾（`</body></html>`）には足せない。ファイルの性質で方式を選ぶ。

## 8. PR 本文の書式は実行役に委ねる

設計パートナーが指定するのは「触るファイルの全パス」「なぜ／何を変えたか の中身」「変更規模」のみ。欄の並び・区切り・記法は指定しない。根拠: executor-preamble.md §PR作成の手順に書式規則7項目が実測済みで、カードへの書き写しは崩れの元。書式で関所が赤になった場合、実行役の自己修正を許可する（別セッションで7往復した実測・2026-09-05）。

注: design-partner.md §5.5-6「書式は実例で示す」と向きが逆。正本を改版するときは、この理由を添えて §5.5-6 を書き換える。

## 9. コマンドの書き方（ガード対策・実測）

- **すべてのコマンドを `cd <作業台のフルパス> && <コマンド>` の形で書く。** worktree-only-guard は、コマンドが `cd <パス>` で始まる場合のみそのディレクトリのブランチを見る。始まっていなければフック自身の作業ディレクトリを見て、正しいブランチにいても止める（§11 事例4）
- `cd` の成否を先に確認してから後続を実行する（`cd` 失敗に気づかず本体リポジトリで `.pr-number` に別番号を書いた実測・2026-09-06）
- SSH 経由の psql では、`-c "... IN ('pending')"` のシングルクォートが `\047` のまま渡り構文エラーになる。ドル引用符 `$$...$$` を使うか、`WHERE` を避けて `GROUP BY` で全件集計する（§11 事例1）
- psql-write-guard は `psql -f`・不等号（`< <= <>`）・**ヒアドキュメント `<<'SQL'`** を書き込みと誤検知する。読み取り SQL は `-c` 方式で1クエリずつ、比較は `BETWEEN` を使う（§11 事例2）
- 先読み・後読み `(?<!` を含む SQL も、`<` で誤検知される。`substring()` で代用する（2026-09-06 実測）
- 合格基準の grep パターンは実測してから書く。インデントを決め打ちすると、内容が正しくても 0 件で偽停止する（§11 事例6）

## 10. マージ・PR 作成の正規経路（実測）

- PR 作成: `scripts/gh-pr-create-safe.sh --title ... --body-file ...`（`.pr-number` は `register-pr.sh` が worktree ルートに書く。直接 `gh pr create` すると書かれない）
- マージ: `scripts/gh-pr-merge-safe.sh --merge`（PR番号は `.pr-number` から読む。**番号を引数に渡すと `gh pr merge N N` になり失敗**・2026-09-06 実測）
- `.pr-number` は `.gitignore:110` で除外。PR 差分には乗らない
