# 設計：ADR-1006 の起票（商品コード PM-00001 と、mark だけの照合）

状態：ADR を起票（PO の方針の承認 2026-10-05「1,はい」）／実装は未着手（PR-0〜PR-3 は ADR-1006「実施順序」のとおり別の PR で行う）。

## 1. 目的
- 商品の固有 ID（product_code）を、意味を持たない連番 PM-00001 にそろえる方針を、ADR として正式にする。
- 品番の照合を mark（公式の品番）だけで行う方針も、あわせて ADR にする。
- この PR は文書だけである（ADR-1006 の追加、ADR-1002 の状態の更新、索引の作り直し）。

## 2. 現在地（recon.md の要約）
- product_code の形はそろっていない（本番 1,347行）。採番の経路は2つある（PM＋4桁、PD-{id:05d}）。sequence は使われていない。
- 照合は、v6 が mark→id を引き、product_code で上書きする（tcg_analyzer_svc.py:1219-1224, :1431）。v7 は品番か mark で候補を作る（extraction_judgement_svc.py:140-148）。
- 投稿に出る品番で、product_code にしか一致しないものは 0件。
- 共有されている mark の決まり方は、DB が返す順しだいで、今も定まっていない（34組のうち 29組）。
- seed_product_marks migration が、デプロイのたびに mark を上書きしている（MEGAドリームex を M3 に戻した）。

## 3. 既存の ADR との関係
- ADR-1002 §4（PM＋4桁の自動採番）を、ADR-1006 で変更する（Amends）。
- ADR-1001（PM0001〜PM0297 の引き継ぎ）：旧コードは legacy_product_code で辿れるようにする。
- ADR-155（mark＝型番、値の変更を migration で行わない）：これに従う。

## 5. 代替案と選んだ理由
- PM＋4桁（ADR-1002 のまま）：PO が5桁を選んだ（2026-10-05「はい」）。4桁は 9999 で上限に当たる。
- product_code に公式の品番を残す：ID と型番の二重の持ち方が、記号の誤りと二重登録の温床だった（#3966・#3968・#3969・#3975）。そのため分けた。

## 6. リスクと対処
- ADR-1006 の「弊害・トレードオフ」を参照する。この PR は文書だけなので、本番には影響しない。

## 8. 外部・過去事例の参照と我々への応用
- 外部事例：サロゲートキーと業務キーを分けるのは、データベースの設計の一般的な原則である。特定の数値に依存しないため、外部の事例は挙げない。
- 過去事例
  - ADR-1002 で、ID を integer に一本化した。
  - 今回の調査（2026-10-04〜05）で、品番が二重の持ち方になっていることが照合の誤りを生む実例が見つかった：記号の誤り、ARD が CARD の中に当たる、DB の順しだいで決まる。
