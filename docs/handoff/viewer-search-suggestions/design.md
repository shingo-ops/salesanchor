# design: 打つと出る候補（便12b）

> この文書は何か（1行）: 閲覧ページ（/viewer/）の検索画面で、**打っている間だけ候補を並べ**、
> 候補を押すとその語で検索が走るようにする。**空のときは今までどおり「最近使った語」**。

**recon**: docs/handoff/viewer-search-suggestions/recon.md
**土台**: `release/viewer-search-suggestions`（`origin/main` = ff6787294＝便12a #4828 を含む）

## ① 区分：A（見た目と操作の変更）

データの読み書きは変えない。PC は1px も動かさない（検索画面はスマホだけ）。

## ② KGI（PO が実機で○×を判定できる粒度）

PO 指示「検索欄をお手本と同じ作りに」の続き。お手本は**2段構え**＝空なら履歴／**打つと候補**（recon §1）。
PO 決定（2026-10-28）: **件数は出さない**／**打った語で始まるものを優先**。

| # | PO が見て○×を言えること |
|---|---|
| K1 | 検索画面で文字を打つと、**その場で候補が並ぶ**（最近使った語は消える） |
| K2 | 候補を**押すとその語で一覧が絞られる**（検索画面は閉じ、語が札になる） |
| K3 | 入力を**空に戻すと、また「最近使った語」に戻る** |
| K4 | 候補は**打った語で始まるものが上**に出る |
| K5 | 当たる候補が無いときは**何も並ばない**（空のまま。誤った候補を出さない） |
| K6 | PC は今までどおり（検索画面も候補も出ない） |
| K7 | 語を**確定したあとに検索欄を押して開き直す**と、**入力に語が残ったまま候補が出る**（お手本の実測と同じ。✕ を押した場合は「最近使った語」） |

## ④ 設計（How）

### 4-1. 候補の作り方 ― 検索が実際に見ている4つからだけ作る

**`frontend/src/pages/viewer/searchSuggestions.ts`（新規・純関数）**:

```
buildSuggestions(rows: ViewerRow[], draft: string, limit = 10): string[]
```

1. `draft` を `normalizeForSearch` で正規化し、空白で分けた語（AND）にする。空なら `[]` を返す。
2. 各行について `matchesQuery(row, draft)` が真かを見る（**既存の関数をそのまま使う**＝
   候補を押したときに必ず1件以上当たることを作りで保証する。recon §2 の「シリーズ・提供者は検索対象外」の罠を踏まない）。
3. 当たった行の**表示名**を集める。表示名は `japanese_title`（空なら `english_title`、それも空なら `mark`）。
4. 同じ表示名はまとめる（件数を数えるが、**画面には出さない**＝PO 決定）。
5. 並べ替え: **先頭一致（正規化した表示名が、正規化した `draft` の先頭の語で始まる）を先**、
   その中は**件数の多い順**、同数なら**表示名の昇順**（`localeCompare`）。**決定論的**にする。
6. 先頭から `limit`（10）件。

**件数は画面に出さないが、並べ替えの材料としては使う**（PO 決定は「出さない」であって「数えない」ではない）。

### 4-2. 画面の切り替え ― 空なら履歴・打っていれば候補

`InventoryView.tsx` の検索画面の中身を次の形にする（**お手本どおり。見出しは候補には付けない**＝recon §1 F1）:

| `draft` | 出すもの |
|---|---|
| 空 | 「最近使った語」（便12a のまま・見出しと「すべて消す」つき） |
| 1文字以上 | **候補**（見出し無し）。当たらなければ**何も出さない** |

- 候補は `useMemo(() => buildSuggestions(allRows, draft), [allRows, draft])` で作る。
  **698件の走査1回ぶん**。debounce は入れない（入れると「打った瞬間に出る」お手本の感じが崩れる）。
- 候補の行を押したら **`confirmSearch(その語)`**（便12a の確定と同じ道）＝検索画面が閉じ、札が出て、履歴にも積まれる。
- 行の testid は `viewer-suggestion-row-<語>`。印は**虫眼鏡**（履歴は時計＝お手本の描き分け）。

### 4-3. 触らないもの（この便の境界）

| 触らない | 理由 |
|---|---|
| 「最近使った語」の作り | 便12a のまま。空のときだけ出す |
| 確定の流れ・札・✕ | 便12a で実機確認済み |
| PC | 検索画面そのものがスマホだけ |
| 絞り込みパネルの中身 | 別便（札の横並び・幅83%） |

## ⑤ Acceptance Criteria

`B` は画面検査（本物の Chromium・360px と 390px）。`U` は単体。

| # | 基準 | 測り方 |

| B2 | 候補を押すと検索画面が閉じ、**一覧の件数が変わり**、札にその語が出る | 画面検査・2幅（**直す前は赤**） |
| B3 | 入力を**空に戻すと**、候補が消えて**最近使った語が戻る** | 画面検査・2幅（**直す前は赤**） |

| U5 | 候補は**必ず1件以上の行に当たる語**だけを返す（`matchesQuery` と一致） | 単体（シリーズ名・提供者名だけに含まれる語では候補が出ないことを固定） |

## ⑩ 弊害・トレードオフ

- **打つたびに698件を走査する**。**実測（2026-10-28・この端末の jsdom・698行・500回の平均）**:
  当たる語で **3.2ms/回**、当たらない語で **1.3ms/回**（`buildSuggestions` 単体）。
  見込み（1ms 前後）より3倍遅いが、1打鍵あたり3ms なので **debounce は入れない**（お手本の「打った瞬間に出る」を保つ）。
  重さの正体は行ごとの `normalizeForSearch`（NFKC）で、**検索の絞り込み（`filterRows`）が以前からやっている仕事と同量**。
- **候補は「商品名」に寄せる**ので、型番や検索ワードだけに当たった行も商品名で出る。
  利用者から見ると「打った文字が候補の中に見えない」ことが起こりうる（例: 型番で当たったとき）。
  **当たる語しか出さない**ことを優先した（押して0件になるほうが害が大きい）。
- **件数を出さない**（PO 決定）。お手本と同じ見た目になるが、押すまで何件あるか分からない。
- **当たらないときは何も出ない**。お手本の同じ状況は**未確認**なので、「見つかりません」の文言は作らない
  （確かめていない形を真似しない）。
