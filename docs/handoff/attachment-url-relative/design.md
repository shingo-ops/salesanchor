# 設計 — 配信URLの形式是正（便4c）

> この文書は何か（専門用語なしの1行）:
> 保存する画像の住所から、クライアントが自分で付ける部分を取り除く設計。

対象ADR: ADR-091
recon: docs/handoff/attachment-url-relative/recon.md
親テーマ: docs/specs/attachment-storage/README.md

## 1. あるべき姿

顧客が送った画像やファイルが、いつ見返しても受信箱に残っている。

## 2. recon（実測）

docs/handoff/attachment-url-relative/recon.md を参照。要点は次の2つ。

- 保存と記録は正しく動いている。
- URLに api/v1 が二重に入り、404 になっている。

## 3. design（技術How）

DBに保存する attachment_url を、API のベース部分を含まない形にする。

変更前: api/v1 を含む絶対パス
変更後: leads で始まる相対パス

画面側の判定も同じ文字列に合わせる。

frontend/src/lib/api.ts と backend/app/routers/leads.py は変更しない。

既存2件のデータは古い形式のまま残す。テストデータであり実害がないため（PO決定）。

## 4. 外部・過去事例の参照と我々への応用

APIクライアントがベースURLを保持し、呼び出し側は相対パスのみを渡す設計は
広く用いられている。ベースURLは環境ごとに変わりうる設定値であり、
サーバーが保存するデータに埋め込むべきではない。

本リポジトリでも frontend/src/lib/api.ts が API_BASE を保持し、
各呼び出しは相対パスを渡す形になっている。
今回はその原則から外れたことで二重付与が起きた。

我々への応用: サーバーが保存するURLは、クライアントのベースURLを含めない。
将来 API_BASE が変わっても、保存済みデータが古くならない。

## 5. 弊害・トレードオフ

- 弊害: 既存2件の attachment_url が古い形式のまま残る。
  その2件は表示されない。テストデータのため放置する（PO決定）。
- 弊害: attachment_url の値だけを見ても、どのAPIを叩けばよいか自明でない。
  クライアント側の API_BASE を知る必要がある。
- トレードオフ: DBの値を書き換えず、今後の受信分から正しくなる形を採る。
  即座の修復より、書き込みを伴わない安全側を選んだ。

## 6. 受入基準

| 基準 | 検証方法 |
|---|---|
| 保存するURLに api/v1 を含まない | grep で serve_url の行に api/v1 が現れない |
| 画面の判定が新形式に揃っている | grep で startsWith が2件とも leads になっている |
| 構文が妥当である | python3 の ast.parse が例外を出さない |
| 既存テストを壊していない | 3つのテストファイルが全 pass |
| 実環境で表示される | デプロイ後、Discord へ画像を送り受信箱で表示を確認する |

## 7. 維持の仕組み

- 守り手: 人手で守る
- 理由: URLの二重付与は実際にリクエストを送らないと検出できない。
  単体テストでは API_BASE の連結を再現できない。
- 対象: 保存するURLに API のベース部分が混入すること。
- 検知方法: PO による実機確認。Discord へ画像を送り受信箱で表示されるかを見る。
