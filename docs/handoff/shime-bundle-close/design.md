# design: まとめて〆る投稿で、上に並んだ商品をすべて閉じる

関連 recon: `docs/handoff/shime-bundle-close/recon.md`

関連 ADR（既存 ADR の検索結果。recon §6）: ADR-1003（委任 GO）、ADR-136-cc-bot-github-identity.md（GO 記録の形）、ADR-135（main にマージ＝本番投入可）。指示書の既定 key・価格の行の重なりを定める ADR は無い。前例の設計: `docs/handoff/v102-prompt-fdm/design.md`、`docs/handoff/v102-shime-same-post-stock/design.md`。

状態: 設計案作成済み（2026-11-12）。PO の方針の承認 2026-11-12（「指示文と受け取り側の両方を直す」に「1」）。設計審査・実装は未着手。

## 1. 目的と成功条件
- 目的: 「型番だけの行が何行か並び、その下に〆だけの行」という投稿で、並んだ商品をすべて Sold out にする。今は一番下の商品だけが閉じ、上の商品は前の投稿の In Stock のまま残る（recon §1）。
- 利用者に見える変化: 在庫の画面で、まとめて〆られた商品が全部「売り切れ」になる。要確認には増えない。
- 変えないもの: 価格のある件、〆が無い投稿、〆が1商品だけの投稿の読み方。

| 基準 | 検証方法 |
|---|---|
| K0 受け取り側を直しても、ほかの投稿の結果が変わらない | 便1の前に、読み取り鍵で直近30日の v102 の件のうち rejected が duplicate_price_line のものを数え、そのうち「2件とも価格 none・重なった行が売り切れの言葉だけの行」に当たる数 N0 を記録する。便1の反映後14日、同じ数え方で duplicate_price_line の件が「N0 の形以外」で減っていない（増減が N0 の形の分だけ）こと |
| K1 単体試験 | §3-2 の試験を含め、`backend/tests/test_gemini_raw_copy_v101.py`・`test_line_analysis_v102_svc.py`・`test_v102_gap_lines.py`・`test_prompt_ab.py` が CI で緑。既存の重複の試験（recon §4）は書き換えずに緑 |
| K2 試験でまとめ〆が全部閉じる | 直近30日の「型番だけの行2行以上＋〆だけの行」の投稿（K2 集合。件数は便2の前に数える。10件に満たなければ全部）を、新しい指示書で2回読む。並んだ商品の名前の行ごとに Sold out の件ができた割合が、2回とも100% |
| K3 試験でほかの投稿が悪くならない | 前例と同じ157投稿を新しい指示書と f_dm で2回ずつ読み、前例の判定（judge、FINAL=PASS の形）で f_dm に比べて合格。status='none' の行は前例と同じ数え方で0行 |
| K4 本番でまとめ〆の閉じ漏れが無い | 切り替えの反映から14日、毎朝の〆の点検の手順2c で「まとめ〆の閉じ漏れ」0件、かつ「消しすぎ」0件 |
| K5 本番で落とした件が増えない | 前例 S3 と同じ（新しい指示書の行が2,000行か72時間の早い方で、status='none' が3行以上かつ0.1%以上なら戻す） |

## 2. 方針と、採らなかった案
- 指示書と受け取り側の両方を直す（PO 承認済み）。指示書だけでは、2件目が「価格の行の重なり」で落ちる（recon §3）。受け取り側だけでは、Gemini が1件しか返さないので直らない。
- 受け取り側は 案A（2件が同じ〆の行を価格の行として持つことを、狭い条件でだけ許す）を採る。
  - 案B（2件目の価格の行を自分の型番の行にする）は採らない。型番の行が「価格の行」として扱われ、名前の取り方・単位・発送日・F2 の名前の付け足しの5か所が非対称になる（クラウド調べ recon-raw.md §(c)。案A は4か所）。
  - 案A の4か所は、辞書を「先に来た件を残す」に替えるだけで、重なりが無い投稿の動きは1文字も変わらない。
- 指示書は、本番の f_dm の行を書き換えず、新しい key `raw_copy_v101_f_bc` の行を足す（前例どおり。戻すときは定数を戻すだけ）。

## 3. 変更の内容

### 3-1. 便1 受け取り側（コードの PR。backend/app/services を触るので GO 記録が要る）
1. `backend/app/services/gemini_raw_copy_v101.py` の `parse_v101_response`（:240-277）
   - `seen_price_lines: set[int]` を「価格の行 → 先に受理した件」の辞書に替える。
   - 価格の行が重なったとき、次の4つが全部当てはまれば落とさずに受理する。1つでも外れれば、今までどおり duplicate_price_line で落とす。
     1. `keep_rejected` が True（v102 の経路だけ。v101 の出力は変えない）。
     2. 今の件も、先に受理した件も、price が none。
     3. 重なった行が売り切れの行である（`_is_sold_out(lines[price_line - 1], status_entries)` が True）。
     4. 今の件の lines に、先に受理した件の lines に無い行が1つ以上あり、その行は売り切れの行ではない（自分の型番の行がある）。
   - 受理した件には、ほかの件と同じキーだけを付ける（新しいキーは足さない）。
2. 同じファイルの価格の行の辞書4か所を「先に来た件を残す」にする（重なりが無いときの中身は今と同じ）。
   - `:602` `by_price_line`、`:1212` `by_price_line`、`:1474` `owners`、`:1571` `owners`
   - 書き方は、内包表記を `for` と `setdefault` に替える。行番号は実装の時点の origin/main で読み直す。
3. 触らないもの: `_unpriced_line`（:189-196）、規則13（`line_analysis_v102_svc.py:1135-1165`）、価格の行を集合で使う所（recon §3）、`gemini_raw_copy_v10.py`、DB、migrations/、deploy.yml、scripts/、指示書の定数。

### 3-2. 便1 の試験（新しく足す。既存の試験は書き換えない）
- T1: 3行「型番A／型番B／〆」に、Gemini が [1,3] と [2,3] の価格 none の2件を返す → 2件とも受理、price_line は2件とも3、rejected なし。
- T2: T1 を v102 の抽出まで通す → 2件とも status が sold_out、名前は型番A・型番B。
- T3: 価格のある2件が同じ行を取り合う → 今までどおり duplicate_price_line（既存の :820-870 と同じ形を、価格 none の件と混ぜても変わらないこと）。
- T4: 価格 none の2件だが、重なった行が売り切れの行ではない（例「残り2」）→ duplicate_price_line。
- T5: 価格 none の2件で、2件目の lines が1件目と同じ（自分の行が無い）→ duplicate_price_line。
- T6: keep_rejected=False（v101）では T1 と同じ入力でも今までどおり落とす。
- T7: 4か所の辞書は、重なりがあるとき先の件を返す（`:1474` の owners で、〆の行から作る名前が1件目と2件目で同じになる）。

### 3-3. 便2 新しい指示書の行を足す（本番 DB への書き込み。PO が `!` で流す）
- 本文: f_dm の本文（sha256 84afd2e4…ac8b0c）の手順1の「完売の投稿」の行（pdm_decoded.txt:13）のすぐ下に、次の1項目を足す。ほかの行は1文字も変えない。

```
- まとめて〆る投稿：「〆」「〆切」「完売」だけの行のすぐ上に、価格も数量も売り切れの言葉も無い商品名の行が、空行やほかの行をはさまずに続けて並んでいるときは、並んだ商品名の行ごとに1件を作る。各件の lines は [その商品名の行, 〆の行]、price・quantity は none。並びは、空行・価格や数量のある行・区切りの行（「【〇〇】」「＝＝＝」のように記号で囲んだ見出し）で止まる。商品名の行が1行だけなら、今までどおり1件である。
例:
[L0001] サンプル弾A
[L0002] サンプル弾B
[L0003] 〆
出力例（2件。どちらも 〆 の行 L0003 を持つ）:
{"lines":[1,3],"price":"none","quantity":"none"}
{"lines":[2,3],"price":"none","quantity":"none"}
```

- 書き込み台本: 前例の write_fct 一式（社外秘の作業記録 prompts/write_fct/）と同じ4段（precheck → dryrun → commit → verify）。key・本文ファイル・sha256 の3つの値だけ替える。作るのは Sonnet、Opus は差分を読んで確かめる。新しい key の行を1行足すだけで、既存の行は触らない。
- この行を足しても、定数が f_dm のあいだは本番の解析は変わらない（試験の道具だけが使える）。

## 4. 影響範囲
- 便1: 4つの条件が全部当てはまる「価格 none の件どうしが売り切れの行を取り合う」形だけで結果が変わる。今の f_dm でこの形が出たときは、2件目が要確認から外れて Sold out になる（K0 で数える）。
- 便3: 指示書が少し長くなる（1項目と例1つ）。前例の失敗の見張り（F1〜F3）で、指示書が原因の失敗が増えていないかを見る。
- 呼び出し元: `parse_v101_response` は v101・v102 と prompt_ab から呼ばれる。v101 は条件1で変わらない。

## 5. リスクと対処
- まとめ〆でない投稿で、Gemini が記号で囲んだ見出しの行まで1件にしてしまう → 指示書で「区切りの行で止まる」と書き、K3 と K4 の「消しすぎ」で見る。消しすぎが1件でも出たら、便3を戻す（定数を f_dm に戻す PR）。
- 先に来た件を残す辞書で、迷う行の付け直し（:602）が1件目にだけ寄る → 重なりは「価格 none・売り切れの行」に限るので、付け直す行は〆の行の前後の空行か区切りだけ。T7 で確かめる。
- 便2の書き込みは本番の DB を変える。新しい行を1行足すだけで、precheck で同じ key があれば止まる。戻すときは、その行を使わなければよい（消さない）。

## 6. 進め方と GO
- 順番: 設計審査（クラウドの architect）→ 便1の実装カード → クラウドの Sonnet が実装 → CI・reviewer(opus) → GO（ADR-1003 の委任発行）→ マージ・反映 → 便2（PO が `!`）→ 便3の試験 → 結果を PO に報告 → 切り替え PR → GO → マージ・反映 → K4・K5 を見る。
- 便1・便3の GO は、ADR-1003 の3条件（必須 CI 緑、新しく起動した reviewer opus の APPROVE、PO への3行のまとめ）が揃ってから、Opus が委任に基づいて出す。
- 便3（本番の解析の指示書を替える）は、PO に「本番に入れる前にもう一度報告する」と約束しているので、試験の結果を PO に報告してから GO を出す。

## 7. 維持の仕組み
- 毎朝の〆の点検（agent-console の定期実行、手順2c）が「まとめ〆の閉じ漏れ」を毎日数える。K4 はこれで見る。
- 便1の T1〜T7 が、受け取り側の条件が崩れたら CI で止める。

## 8. 外部・過去事例の参照と我々への応用
- 外部事例: 該当なし。理由: 仕入元ごとの書き方に合わせた指示書の決まりの話で、外の事例に同じ数字の根拠は無い。
