# design: まとめて〆る投稿で、上に並んだ商品をすべて閉じる

関連 recon: `docs/handoff/shime-bundle-close/recon.md`

関連 ADR（既存 ADR の検索結果。recon §6）: ADR-1003（委任 GO）、ADR-136-cc-bot-github-identity.md（GO 記録の形）、ADR-135（main にマージ＝本番投入可）。指示書の既定 key・価格の行の重なりを定める ADR は無い。前例の設計: `docs/handoff/v102-prompt-fdm/design.md`、`docs/handoff/v102-shime-same-post-stock/design.md`。

状態: 設計案作成済み（2026-11-12）。PO の方針の承認 2026-11-12（「指示文と受け取り側の両方を直す」に「1」）。設計審査1回目 REVISE（クラウド architect opus、02ecbb101）→ 第2版。設計審査2回目 REVISE（249c9d180）→ 条件4（重なりは価格の行だけ）・T12・指示書の例の名前・〆切り・K2の報告の書き方を直した第3版。実装は未着手。

## 1. 目的と成功条件
- 目的: 「型番だけの行が何行か並び、その下に〆だけの行」という投稿で、並んだ商品をすべて Sold out にする。今は一番下の商品だけが閉じ、上の商品は前の投稿の In Stock のまま残る（recon §1）。
- 利用者に見える変化: 在庫の画面で、まとめて〆られた商品が全部「売り切れ」になる。要確認には増えない。
- 変えないもの: 価格のある件、〆が無い投稿、〆が1商品だけの投稿の読み方。

## 2. 方針と、採らなかった案
- 指示書と受け取り側の両方を直す（PO 承認済み）。指示書だけでは、2件目が「価格の行の重なり」で落ちる（recon §3）。受け取り側だけでは、Gemini が1件しか返さないので直らない。
- 受け取り側は 案A（2件が同じ〆の行を価格の行として持つことを、狭い条件でだけ許す）を採る。
  - 案B（2件目の価格の行を自分の型番の行にする）は採らない。型番の行が「価格の行」として扱われ、名前の取り方・単位・発送日・F2 の名前の付け足しの5か所が非対称になる（クラウド調べ recon-raw.md §(c)。案A は4か所）。
  - 案A の4か所は、辞書を「先に来た件を残す」に替えるだけで、重なりが無い投稿の動きは1文字も変わらない。
- 指示書は、本番の f_dm の行を書き換えず、新しい key `raw_copy_v101_f_bc` の行を足す（前例どおり。戻すときは定数を戻すだけ）。

## 3. 変更の内容

### 3-1. 便1 受け取り側（コードの PR。backend/app/services を触るので GO 記録が要る）
1. `backend/app/services/gemini_raw_copy_v101.py` の `parse_v101_response`（:240-277）
   - `seen_price_lines: set[int]` を「価格の行 → その行を価格の行に持つ受理済みの件の一覧」の辞書に替える。
   - 価格の行が重なったとき、次の5つが全部当てはまれば落とさずに受理する。1つでも外れれば、今までどおり duplicate_price_line で落とす。
     1. `keep_rejected` が True（v102 の経路だけ。v101 の出力は変えない）。
     2. 今の件も、同じ価格の行を持つ受理済みの件の全部も、price が none。
     3. 重なった行が売り切れの行である（`_is_sold_out(lines[price_line - 1], status_entries)` が True）。
     4. 今の件の lines と、同じ価格の行を持つ受理済みの件のそれぞれの lines とで、重なる行は価格の行だけである（[2,3] のあとの [1,2,3] は行2も重なるので落とす）。
     5. 今の件に「自分の名前の行」が1行以上ある。自分の名前の行とは、次の全部に当たる行: 同じ価格の行を持つ受理済みの件の**どれの** lines にも入っていない／前後の空白を除いて空でない／売り切れの行ではない／文字（`\w` に当たる字）を1字以上含む／行全体が「【…】」だけではない。
   - 3件目以降も、条件2・4・5は「同じ価格の行を持つ受理済みの件の全部」と比べる（[1,3]・[2,3]・[2,3] の3件目は、行2が2件目に入っているので落ちる）。
   - 受理した件には、ほかの件と同じキーだけを付ける（新しいキーは足さない）。
   - 条件4・5の判定は小さな関数1つにまとめ、試験から直接呼べるようにする。
2. 同じファイルの価格の行の辞書4か所を「先に来た件を残す」にする（重なりが無いときの中身は今と同じ）。
   - `:602` `by_price_line`、`:1212` `by_price_line`、`:1474` `owners`、`:1571` `owners`
   - 書き方は、内包表記を `for` と `setdefault` に替える。行番号は実装の時点の origin/main で読み直す。
3. 触らないもの: `_unpriced_line`（:189-196）、規則13（`line_analysis_v102_svc.py:1135-1165`）、価格の行を集合で使う所（recon §3）、`gemini_raw_copy_v10.py`、`backend/app/tools/prompt_ab.py`（item_count は参考の数で、K2・K3 の判定には使わない）、DB、migrations/、deploy.yml、scripts/、指示書の定数。

### 3-2. 便1 の試験（新しく足す。既存の試験は書き換えない）
- T1: 3行「型番A／型番B／〆」に、Gemini が [1,3] と [2,3] の価格 none の2件を返す → 2件とも受理、price_line は2件とも3、rejected なし。
- T2: T1 を v102 の抽出まで通す → 2件とも status が sold_out、名前は型番A・型番B。
- T3: 価格のある2件が同じ行を取り合う → 今までどおり duplicate_price_line（既存の :820-870 と同じ形を、価格 none の件と混ぜても変わらないこと）。
- T4: 価格 none の2件だが、重なった行が売り切れの行ではない（例「残り2」）→ duplicate_price_line。
- T5: 価格 none の2件で、2件目の lines が1件目と同じ（自分の行が無い）→ duplicate_price_line。
- T6: keep_rejected=False（v101）では T1 と同じ入力でも今までどおり落とす。
- T7: 4か所の辞書は、重なりがあるとき先の件を返す（`:1474` の owners で、〆の行から作る名前が1件目と2件目で同じになる）。
- T8: 4行「型番A／型番B／型番C／〆」に [1,4]・[2,4]・[2,4] が返る → 1件目と2件目は受理、3件目は duplicate_price_line（3件目の行2は2件目に入っている）。[1,4]・[2,4]・[3,4] なら3件とも受理。
- T9: 「型番A／（空行）／〆」に [1,3]・[2,3] が返る → 2件目は自分の名前の行が空行だけなので duplicate_price_line。行2が「＝＝＝」や「【〇〇】」だけの行でも同じく落とす。
- T10: 解析の作り直しの経路（`line_analysis_v102_svc.py:1238` `_fixed_products`、`:1587-1591` `_prepare_v102`）に T1 の保存済みの件を通す → 2件とも残り、2件とも Sold out。

- T12: 「型番A／型番B／〆」に [2,3]・[1,2,3] が返る → 2件目は行2も重なるので duplicate_price_line（条件4）。

### 3-3. 便2 新しい指示書の行を足す（本番 DB への書き込み。PO が `!` で流す）
- 本文: f_dm の本文（sha256 84afd2e4…ac8b0c）の手順1の「完売の投稿」の行（pdm_decoded.txt:13）のすぐ下に、次の1項目を足す。ほかの行は1文字も変えない。

```
- まとめて〆る投稿：「〆」「〆切」「〆切り」「完売」だけの行のすぐ上に、価格も数量も売り切れの言葉も無い商品名の行が、空行やほかの行をはさまずに続けて並び、その行の一つ一つが別の商品の名前（型番や商品名）であるときは、並んだ商品名の行ごとに1件を作る。各件の lines は [その商品名の行, 〆の行]、price・quantity は none。並びは、空行・価格や数量のある行・区切りの行（「【〇〇】」「＝＝＝」のように記号で囲んだ見出し）で止まる。下の行が上の商品の補足（弾やシリーズの名前・付属の有無・未開封などの状態）のときは別の商品ではないので、今までどおり全部で1件である。商品名の行が1行だけなら、今までどおり1件である。
例:
[L0001] 型番AA-01
[L0002] 型番BB-02
[L0003] 〆
出力例（2件。どちらも 〆 の行 L0003 を持つ）:
{"lines":[1,3],"price":"none","quantity":"none"}
{"lines":[2,3],"price":"none","quantity":"none"}
補足の行の例（1件のまま）:
[L0001] サンプルBOX
[L0002] 未開封
[L0003] 完売
出力例（1件）:
{"lines":[1,2,3],"price":"none","quantity":"none"}
```

- 補足の行の決まりを入れる理由: 直近30日の候補34投稿のうち27投稿は「商品名の行＋補足の行＋完売」で、1商品である（recon §7）。並んだ行を全部割ると、この27投稿で余計な件ができる。K2 (b) で見る。

- 書き込み台本: 前例の write_fct 一式（社外秘の作業記録 prompts/write_fct/）と同じ4段（precheck → dryrun → commit → verify）。key・本文ファイル・sha256 の3つの値だけ替える。新しい key の行を1行足すだけで、既存の行は触らない。
- 台本を作る人: 本文は社外秘の作業記録の中にしか置けないので、クラウドには渡さない。手元で Sonnet を1回だけ起動して社外秘の作業記録の中で作らせ、Opus が前例との差分を読んで確かめる。手元での起動は見張りで止められているので、便2の前に PO に1回限りの許可（permit-danger の "local agent"）を頼む（§9）。
- この行を足しても、定数が f_dm のあいだは本番の解析は変わらない（試験の道具だけが使える）。

### 3-4. 便3 試験と切り替え（定数の PR。GO 記録が要る）

## 4. 影響範囲
- 便1: 5つの条件が全部当てはまる「価格 none の件どうしが売り切れの行を取り合う」形だけで結果が変わる。今の f_dm でこの形が出たときは、2件目が要確認から外れて Sold out になる（K0 で数える）。
- 便3: 指示書が少し長くなる（1項目と例1つ）。前例の失敗の見張り（F1〜F3）で、指示書が原因の失敗が増えていないかを見る。
- 呼び出し元: `parse_v101_response` は v101・v102 と prompt_ab から呼ばれる。v101 は条件1で変わらない。

## 5. リスクと対処
- まとめ〆でない投稿で、Gemini が記号で囲んだ見出しの行まで1件にしてしまう → 指示書で「区切りの行で止まる」と書き、K3 と K4 の「消しすぎ」で見る。消しすぎが1件でも出たら、便3を戻す（定数を f_dm に戻す PR）。
- 先に来た件を残す辞書で、迷う行の付け直し（:602）が1件目にだけ寄る → 重なりは「価格 none・売り切れの行」に限るので、付け直す行は〆の行の前後の空行か区切りだけ。T7 で確かめる。
- 便2の書き込みは本番の DB を変える。新しい行を1行足すだけで、precheck で同じ key があれば止まる。戻すときは、その行を使わなければよい（消さない）。
- 新しい指示書で、補足の行まで別の商品として割ってしまう → 指示書に補足の決まりと例を入れ、K2 (b) の27投稿で確かめる。外したら便3に進まない。
- 2件を受理したとき、Gemini が「迷う」に〆の行を挙げていると、2件とも要確認になる（`line_analysis_v102_svc.py:264`）。閉じ漏れよりは安全側なので、この設計では変えない。K4 の点検で要確認の件として数えられる。

## 6. 進め方と GO
- 順番: 設計審査（クラウドの architect）→ 便1の実装カード → クラウドの Sonnet が実装 → CI・reviewer(opus) → GO（ADR-1003 の委任発行）→ マージ・反映 → 便2（PO が `!`）→ 便3の試験 → 結果を PO に報告 → 切り替え PR → GO → マージ・反映 → K4・K5 を見る。
- 便1・便3の GO は、ADR-1003 の3条件（必須 CI 緑、新しく起動した reviewer opus の APPROVE、PO への3行のまとめ）が揃ってから、Opus が委任に基づいて出す。
- 便3（本番の解析の指示書を替える）は前例 `docs/handoff/v102-prompt-fdm/design.md` §6 と同じ手順にする。
  1. 試験の結果を PO に報告し、PO の「切り替える」の返事を別にもらう。返事は PR 本文の GO 記録に原文のまま写す（POの言葉を作らない）。GO 原文は `GO #<この PR の番号>` の形で、発行者・日時・HEAD を残す。
  2. GO の直前に、前例 §6 と同じ確かめをする: 読み取り鍵で f_bc と f_dm の行の is_active と sha256／前例の q_pre_go.sql と同じ形の失敗の一覧（直近24時間・一番新しい失敗が6時間以上前）／RemoteTrigger list と agent-console の routines.json・reservations.json で、反映のあとに動く予約が試験の道具を呼ばないか／前払い残高。
  3. GO 記録の「バックアップ確認」は、DB を変えないこと・戻し先の f_dm の行が残っていることを書く。
- 便1は指示書を替えないので、ADR-1003 の3条件だけで GO を出す（PO への3行のまとめに「直近30日の結果は変わらない（N0=0）」を書く）。

## 7. 維持の仕組み
- 毎朝の〆の点検（agent-console の定期実行、手順2c）が「まとめ〆の閉じ漏れ」を毎日数える。K4 はこれで見る。
- 便1の T1〜T12 が、受け取り側の条件が崩れたら CI で止める。
- K0 の後の測定（便1の反映から14日目）は、Opus が読み取り鍵で recon §7 の SQL を流して数える。結果は社外秘の作業記録と、この設計の台帳に書く。
