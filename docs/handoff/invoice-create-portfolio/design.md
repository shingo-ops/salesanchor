# design: 請求書作成画面をポートフォリオの形に作り直す（住所・税・関税・支払方法を記録の表から）

状態: 設計案（Opus 作成 2026-11-13）。審査前。PO 承認前。
根拠: 同じ場所の recon.md（§番号で指す）。対象 ADR: ADR-101（§7 関税・実装上の注意）、ADR-095 付録1-4、ADR-125 D5、ADR-1061（振込先・税率・発行元の表）、ADR-027（i18n）、ADR-144（UI の金型）、ADR-072（commit 後の reset）、ADR-135/136（危険な PR）。あるべき姿: docs/specs/quote-invoice/（KGI Q1〜Q15）。

## 1. 目的（PO の言葉から）

- 請求書の作成画面を、PO のポートフォリオ（https://shingo-portfolio.github.io/invoice-tool/）と同じ並びにする（recon §0・§8）。
- 画面に数字や選択肢を直書きしない。住所・税率・関税の決まり・支払方法・通貨は記録の表から読む（PO 2026-11-13「ハードコードはなくしてDBから該当する部分を取得するSSOTを採用」）。
- 関税の決まりは新しい表に持ち、自動で計算する（PO の選択「2」）。
- 奥の目的: 海外のお客さんへの請求書を、人が金額を打たずに、選ぶだけで正しく出せるようにする（quote-invoice/to-be.md:10）。

## 2. 対象と対象外

対象:
- 関税の決まりの表2つ（新）と、その設定画面。
- 請求書の表に4列（使った振込先・税率・送料の会社・送料のサービス）。
- 作成画面の材料を返す道1つ（新）、合計を試算する道1つ（新）、作る道（直す）。
- 請求書作成画面の並びの作り直し。

対象外:
- 見積の作成画面（QuoteCreatePage）。見積から請求書を作る道は今の金額の写しのまま（recon §3 :211）。
- 顧客別の関税（quote-invoice/kgi.md:13・:28 で対象外と決まっている）。
- 見本の「カテゴリ」列（商品の候補にその値が無い。recon §7）。
- PDF の見た目の変更。作成後は今の詳細画面（PDF のボタンあり）へ移る。
- 振込先を登録する画面（ADR-1061 の残りの便で作る。recon §5）。
- 決済手数料を合計に入れること（ADR-101:171）。payment_fee_settings の値と支払方法の結び付けが決まっていないため、別の設計で扱う。§7 の未決に載せる。
- 関税・税率・振込先の値を入れること。AI は値を入れない（ADR-095 付録1-4。PO が根拠付きで画面から入れる）。

### 3-3. 関税の決まりの表（新。会社ごとのスキーマ）

置き場と作り方は前例 migrations/20261112_160000_create_tenant_issuer_and_payment_tables.sql と同じ（全テナントのスキーマを回す・RLS は tenant_id で分ける・ポリシー名は `<表名>_tenant_isolation`・新しいテナント用に backend/app/services/tenant.py にも同じ表を足す）。

**tenant_duty_rules**（どの国・どの送料の会社のときに、どの条件で関税を請求するか）
- id、tenant_id（NOT NULL）
- destination_country_code（CHAR(2) NOT NULL。届け先の国）
- carrier（VARCHAR(50) NULL。NULL は「どの送料の会社でも」。値は /shipping/calculate の結果の carrier と同じ文字）
- incoterm（VARCHAR(3) NOT NULL。CHECK で DAP・DDU・DDP。ADR-101:153）
- label（TEXT NOT NULL。請求書の関税の行に出す名前）
- effective_from（DATE NOT NULL）、effective_to（DATE NULL）
- source_url（TEXT NOT NULL。値の根拠。空は不可。ADR-095 付録1-4「エビデンス確立」）
- note、is_active、created_at、updated_at
- 同じ国・同じ送料の会社で有効期間が重なる行は作れない（書く道で 409 duty_rule_overlap）。

**tenant_duty_rule_components**（関税の中身。1つの決まりに複数）
- id、rule_id（外部キー。決まりを消すと一緒に消える）、tenant_id（NOT NULL）
- sort_order（計算の順）
- label（TEXT NOT NULL。例: 関税・DDP 手数料・MPF）
- base（VARCHAR(30) NOT NULL。CHECK で次の3つ）
  - `subtotal`: 小計
  - `subtotal_shipping`: 小計＋送料
  - `subtotal_shipping_prior`: 小計＋送料＋この行より前の中身の合計
- rate_pct（NUMERIC(8,4) NOT NULL・0以上）
- min_amount・max_amount（NUMERIC(14,2) NULL）、amount_currency（CHAR(3)。min か max があるときは必須。CHECK）

計算（サーバーの1か所だけ。§3-4 の invoice_totals）:
1. 届け先の国＝発送先の写しの国。発送先の住所が無いときは請求先の国。
2. その国・その日に有効な決まりを探す。送料の会社が一致する行を先に、無ければ carrier が NULL の行を使う。
3. 決まりが無い、または incoterm が DAP・DDU のときは関税の行を出さない（買い手が着いてから払う条件のため。ADR-101:157「Duty 行は課税判定時のみ表示」）。
4. DDP のときは中身を sort_order 順に、金額＝基準×rate_pct/100。min があれば下限、max があれば上限で挟む。min・max の通貨が請求書の通貨と違うときは為替の表の最新の値で換算する。
5. 中身の合計を請求書の duty_amount に入れる。決まりと中身と換算に使った値を duty_policy_snapshot に写す（列は今ある。recon §4）。
6. その国に有効な決まりが「送料の会社つきの行だけ」あり、送料の会社が選ばれていないときは、関税を決められない。試算は関税を「未計算」で返し、作成は 409 duty_needs_carrier で止める（少なく請求してしまうのを防ぐ）。

### 3-4. サーバーの道

| 道 | 中身 | 権限 |
|---|---|---|
| GET /invoices/draft-context?company_id= （新） | 発送先・請求先（作る道が写しに使う関数と同じ）、発行元の地域、発送元の国（発行元の表の country_code。無ければ null）、通貨の一覧と最新の為替（通貨・値・取得日時）、支払方法の一覧（id・display_name・method_type。PayPal は method_type 'paypal'・id null）、今日有効な税率（無ければ null） | 請求書を作る権限（今の POST /invoices と同じ） |
| POST /invoices/preview （新・書かない） | 受ける: company_id・currency・items（数量・単価）・shipping（carrier・service_type・fee・currency。任意）。返す: 小計・送料・消費税（率と額）・関税（ラベル・中身ごとの額）・合計、「未計算」の印と理由のキー | 同上 |
| POST /invoices （直す） | 受ける値に payment_method_ref（method_type と id）と shipping（carrier・service_type・fee・currency）を足す。tax_amount は受けない（送られたら 422）。消費税・関税・合計は preview と同じ関数で計算し直して保存する。payment_method_ref は draft-context と同じ選び方の中にあるか確かめ、無ければ 422 payment_method。payment_method の文字の列には display_name（PayPal は今の道と同じ 'paypal'。invoices.py:672）を入れる | 同上 |

- 計算は backend/app/services/invoice_totals.py（新）の1つの関数だけで行う。preview と作成が同じ関数を呼ぶので、画面に出た額と保存される額は同じになる。
- 消費税をかける条件: 届け先の国（§3-3 の1と同じ決め方）が JP で、今日有効な税率の行があるとき。基準は小計＋送料（見本 js_app.js:117 と同じ。国税庁 No.6301「課税標準は対価の額」）。届け先が外国のときはかけない（輸出免税。国税庁 No.6551）。税率の行が無い日本宛は、試算で消費税を「未計算」で返し、作成は 409 tax_rate で止める。
- 為替の値が無い通貨の換算が要るときは 409 fx_rate。
- 秘書チャットの作る道（SecretaryDraftInvoice.tsx:92）も同じ POST /invoices を通るので、同じ計算が効く。秘書チャットは tax_amount を送っていない（recon §3）ので壊れない。支払方法は今と同じく任意（秘書チャットは送らない。後から詳細画面で直せる。invoices.py:120 の _UPDATABLE_COLUMNS）。作成画面では必須にする。
- 書いた後は reset_tenant_context()（ADR-072）。

### 3-5. 請求書の表に足す列（tenant_NNN.invoices。全テナント）

- payment_method_id（INTEGER NULL。同じスキーマの tenant_invoice_payment_methods(id) への外部キー、消されたら NULL）
- tax_rate_percent（NUMERIC(5,2) NULL。使った税率）
- shipping_carrier（VARCHAR(50) NULL）、shipping_service（VARCHAR(100) NULL）

### 3-6. 関税の決まりの設定画面

- 置き場: 管理センターの「ビジネス設定」の中に「関税の決まり」を1つ足す（会社情報のページと同じ並び。ADR-1061 design.md:242 の入口の作り）。新しい大きなメニューは作らない。
- 一覧（国・送料の会社・条件・有効期間・根拠）と、足す・直す・消す。中身の行は足せる。根拠の URL は必須。
- 権限: 会社情報のページと同じ tenant.profile.view／edit。
- 足す・直す・消すたびに会社ごとの audit_logs に1行（ADR-1061 design.md:269 と同じ record_audit_log）。
- 道: GET・POST・PUT・DELETE /admin/duty-rules（会社ごとのスキーマ。commit 後に reset）。

## 5. 代替案と選んだ理由

- 画面で合計を計算する（今の形）→ 取りやめ。関税の式を画面とサーバーの2か所に持つことになる。画面の値をそのまま保存すると、誤った額が通る。
- 関税の式を「率1つ」だけにする → 取りやめ。ADR-101:159 の FedEx の例は率・下限つき手数料・上下限つき MPF の3つの形を持つ。中身の行（率・下限・上限・基準）なら3つとも表せる。
- 関税の式を計算式の文字で持つ → 取りやめ。文字の式を実行する仕組みは誤りや危険が入りやすい。決まった形（基準×率を下限と上限で挟む）なら検査できる。
- 消費税をテナントごとの表に持つ → 取りやめ。税率は国の決まりで全社同じ。ADR-1061 で public.tax_rates を作ってある。
- 支払方法に B2B 専用の表を作る → 取りやめ。振込先の表がすでにある。2か所に持つと SSOT が崩れる（ADR-1061 design.md:417 の宿題をこの形で閉じる）。
- 住所を作成画面で直せるようにする → 取りやめ。PO が選択肢1・2で「取引先の記録を読むだけ」を選んだ。

## 6. リスクと対処

| リスク | 対処 |
|---|---|
| 関税の値が誤っていて請求額がずれる | 根拠の URL を必須にする。試算で中身ごとの額を出す。作成時の決まりと値を duty_policy_snapshot に残す |
| 送料の額は画面が選んだ値をそのまま受ける（見積は時間で変わるため、サーバーで取り直さない） | 送料の会社・サービス・source を保存し、PDF と詳細で確かめられる。今の道も送料は画面の値を受けている（invoices.py:342 付近） |
| 秘書チャットで作った米国宛の請求書が、送料の会社なしで 409 duty_needs_carrier になる | 関税の決まりが入るまでは起きない（本番の関税の表は作った直後は0行）。起きたら秘書チャットの画面に理由の文が出る（今の誤りの出し方と同じ） |
| 振込先が0件のあいだ作成画面で作れない | 選択肢が0件のときは会社情報のページへの案内を出す。PayPal 連携があれば PayPal を選べる |
| 発行元の表が0行のあいだ FedEx の見積が取れない | 送料は「未計算」で出し、会社情報のページへの案内を出す。暗黙に "JP" を使わない（ADR-125 D5 と同じ考え） |
| tax_amount を送る今の画面と、新しい道の食い違い | 便 C の実装カードで、C と D を同じマージにするか、移行の期間を置くかを決める（§4） |

## 7. 未決（PO に決めてもらうこと）

1. 端数の処理（消費税と関税の中身の1つずつ）: 切り捨て・四捨五入・切り上げのどれにするか。通貨の最小単位（円は1円、ドルは1セント）で処理する。

## 9. PO の確かめ方（本番）

- 便 D の後、請求書作成画面を開き、見本と同じ並びになっていることを見る。
- 関税の決まりを入れた後、米国の取引先で商品を1つ入れ、関税の行と額が出ることを見る（作成は押さなくてよい。試算だけで出る）。

## 10. 外部・過去事例の参照と我々への応用

- 画面の手本は PO 本人のポートフォリオ（recon §8）。並びと「国によって税の行が出たり消えたりする」動きをそのまま使う。数字の直書きだけを表に置き換える。
- 消費税の扱いは国税庁の頁（recon §9）に合わせた。
- 関税の値の外部事例（運送会社の公開の料金）は使わない。理由: 値は PO が根拠の URL 付きで入れる仕組みにし、AI が値を持ち込まないため（ADR-095 付録1-4 が未決）。ADR-101:159 の FedEx の例は、表の形が足りるかの確かめにだけ使った（§5）。

## 維持の仕組み

- 関税の値の正本は tenant_duty_rules と中身の表だけ。画面・PDF・試算はすべて invoice_totals を通す。
- 税率の正本は public.tax_rates だけ（最高管理者の画面で足す）。
- 支払方法の正本は振込先の表と public.tenant_paypal_config だけ。
- K2 の grep を画面の試験に入れ、直書きの選択肢が戻ったら試験が落ちるようにする（実装カードで書く）。
