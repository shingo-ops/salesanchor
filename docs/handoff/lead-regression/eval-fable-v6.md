## 総合の理由（要約）

計算の仕組み（§3-2・§4-1・§4-2・K3）は模擬計算でも崩れず、審査の APPROVE を覆す技術の誤りは見つからなかった。直してから進めるとした理由は、PO が「網羅性のある分析にしたい」と言っているのに、DB にもカルテの画面にもある固定の選択肢の項目3つ（想定規模・顧客タイプ・相見積もり）が、入れない理由も記録されずに分析から落ちていること（項目1）。入れるなら件数の決まり（§4-2 の 1項目 10件）との取り合いになり、テスト用リードの件数を増やすか項目を絞るかは PO の判断なので、§8 に1問足してから実装カードへ進むのがよい。あわせて、本物のデータに切り替えたときに結果を変える読み方の決まり2つ（論理削除の除外・店舗の形の複数選択の読み方）が設計に無い（項目5）。どれも設計文書への書き足しで済み、骨組みの作り直しは要らない。

## 項目2 統計の確かさ

### 2-1. 項目の数・分け方・判定の基準

- 1項目 10件の決まり（design.md:155）: 120 ÷ 11 ≒ 10.9 で、慣例（先行の設計 docs/handoff/accuracy-measurement/design-regression.md 78行の Peduzzi 1996）の下限ぎりぎり。項目を足すなら件数を増やす必要がある（項目1 1-2）。
- 2値の分け方（design.md:108）: 1時間・6時間の区切りは「仕込む側」と「読む側」で同じ値を使うので、計算の確かめとしては閉じている。ただし既存のカルテの「返信の速さ」は 24時間以内／3日以内／3日超（backend/app/schemas/lead.py:64〜67）で、ADR-015 §2（docs/adr/ADR-015.md 79行）も「問い合わせ〜返信の時間」としか決めていない。1時間・6時間は設計が置いた値で、本物で使う区切りは PO の判断（項目4 #3）。
- 幅の方法（design.md:153、ワルド）と K3 の合否の幅（design.md:46、二項分布とボンフェローニ）: 計算の筋は正しい。模擬計算でも 11項目の当たる回数は 183〜194回（仕込みあり）・186〜195回（成約の印を並べ替え）で、どちらも 180〜198 に入った。
- 成約をちょうど 120件にする引き直し（design.md:111）: 模擬計算の引き直しは平均 22.1回で、設計の「平均で 20回ほど」と合う。引き直しが項目の推定を歪めるかは、模擬計算では推定の幾何平均が仕込んだ値の 1.00〜1.05倍（仕込んだ5項目）で K3b の 0.90〜1.11 に入った。設計の「K3a〜K3c で実際に確かめる」で足りる。
- K3b の幅 0.90〜1.11（design.md:36）は緩い: 200回の平均の散らばりは 1項目あたり ±0.04倍ほど（模擬計算の標準誤差から）なので、この幅は「5%ほどの上振れ」を通す。少ない件数のロジスティック回帰は推定が大きめに出る性質があり（模擬計算でも 1.02〜1.05倍）、K3b はそれを「偏りなし」と数える。仕組みの誤りを見つける目的なら今の幅でよいが、「偏りが無い」と報告書に書くときは「5%ほどの上振れは許した幅」と添える（項目5 #8）。

### 2-2. 作り方が結果を決めてしまっていないか

- 決めてしまっている部分: §3-2 は「各項目は互いに無関係に割り振る」（design.md:92）。項目どうしの重なりが無く、成約の確率はロジスティック回帰と同じ式で作る（design.md:111）。つまり「計算の式」と「データを作る式」が同じで、K3 は「同じ式で作ったデータから同じ式で値を取り戻せるか」を確かめている。これは「計算と画面が正しく動くか」（design.md:114）の確認としては正しい設計で、設計自身もそう書いている。
- 決めていない部分（評価としてよい点）: 乱数で成約を決めるので、1回のデータでは仕込んだ値どおりには出ない。模擬計算の 200回で「差があると言える」（幅が 1 を含まない）と出た回数は、仕込み 2.5（卸）190回・2.0（相手から来た）170回・1.8（最初の返信）152回・1.6（相手の返信）111回・1.5（WhatsApp）65回。仕込まない6項目は 8〜13回（5% 前後で正しい）。つまり 1回の 400件では、相手の返信（1.6）は半分ほど、WhatsApp（1.5）は3回に1回しか「差あり」と出ない。設計は design.md:113 で一般に断っているが、どの項目がそうなるかは書いていない（項目5 #8）。
- 本物の傾向は何も言えない: 仕込みは設計者が決めた仮の値（design.md:96〜100 の 2.0・2.5・1.8・1.6・1.5）で、事業の実績に基づかない。テナント001の報告書に「本物の傾向ではない」と書く決まり（design.md:114・185）は必要十分。
- 本物のデータで崩れ得る前提（作り方には入っていない）: 項目どうしの重なり（例: 卸の相手は相手から来ることが多い）、こちらの返信の速さの逆向きの影響（recon.md:119、design.md:162 の注意書き）、放置されたまま状態 lead のリードを外すことによる偏り（項目3）。テストでは起きない。

## 項目3 得られる成果と効果

### 3-1. テスト用データで PO が知ること・決められること

- 知ること: ①画面に「11項目の名前・何倍か・95%の幅・差があると言えるか・入れた件数・外した件数」が出る形（design.md:162）②その数が正しく計算されていること（K3a〜K3d）③幅の読み方（幅が 1 をまたぐ項目は「分からない」と読む）。
- 決められること: 画面の置き場・出し分け（§8 #5 ③④）、本物に切り替える条件（design.md:227「成約 120件を超えたら」は目安で PO 判断）、どの項目を本物で入力させるか（項目1 A〜C を本物で効かせるには、カルテに入れる運用が要る。今は 0件 recon.md:67）。
- 決められないこと: 「どの相手を優先するか」「返信を何時間以内にするか」などの事業の判断。テスト用の結果は設計者の仕込みが返ってくるだけ（項目2 2-2）。画面に仕込んだ値を出さない決まり（design.md:163）は、この誤解を防ぐ向き。

### 3-2. 本物のデータに切り替えたときに言えること・限界

- 言えること: 成約した相手と失注した相手の間で、項目ごとに「何倍成約しやすい目印か」（原因ではない。design.md:162・recon.md:119）。回帰なので、ほかの項目の影響を差し引いた値になる（既存の「属性ごとの成約率」は1項目ずつ analytics.py:985〜991 で、差し引きが無い。recon.md:46）。
- 件数の限界: 本物は成約 0件（recon.md:64）。§4-2 の決まり（min(成約, 失注) ≧ 110）を満たすまで画面は「件数が足りない」（design.md:155）。いつ満たすかは未確認で、ここでは見積もらない。
- 読み方の限界（本物に切り替える前に決め直す点）:
  1. アプリの外からの送信が meta_messages に無い（design.md:74・233）。こちらから営業した Instagram・Facebook のリードは最初の返信が長く・回数が少なく出る。
  2. こちらから営業した Instagram のリードは channel_type が messenger になる（design.md:235）。経路の項目が本物では崩れる。
  3. 状態が lead のまま放置されたリードを外す（design.md:151）。本物のテナント004は 56件すべてが lead（recon.md:63）。外すと「返事が無かった相手」が分析に入らず、残った相手だけで比べることになる。これは生存者の偏りで、PO が「いつまで返事が無ければ失注とするか」を決めないと直らない（項目4 #2）。
  4. 成約済みは「入金の確認で自動」（docs/specs/db-ssot/classification-master/design.md 48行）と決まっているが、本物で誰が・いつ existing_customer に切り替えているかは未確認。切り替えの運用が揺れると「成約」の意味が揺れる。
  5. こちらの返信の速さには逆向きの影響（見込みの高い相手ほど急いで返す）が混ざる（recon.md:119）。画面の注意書き（design.md:162）で足りるが、「返信を速くすれば成約が増える」とは読めない。
  6. 店舗の形は本物では複数選択できる（migrations/20260614_100000_create_sales_form_tables.sql 63行の UNIQUE(lead_id, option_id)、frontend/src/pages/inbox/InboxKartePanel.tsx:590〜595 の SalesFormMultiSelect）。「卸か」の読み方が未定（項目5 #2）。
- 効果の見積もりは書かない: 本物の成約率・件数の伸びは本番の事実で、ここでは未確認。数を作らない。

## 項目5 実装カードに書くべき点（審査の補足3件のほか）

1. **論理削除の除外**: meta_messages と conversation_logs には deleted_at がある（migrations/20260622_010000_add_meta_messages_master_history_columns.sql 41行、migrations/20260611_120000_add_conv_log_manual_columns.sql 21〜22行）。既存の読み手は deleted_at IS NULL で絞る（backend/app/routers/conv_logs.py:355、backend/app/services/lang_judge.py:73）。§4-1（design.md:142〜147）に除外の決まりが無い。本物で消したメッセージを数えると、回数と返信の時間が狂う。実装カードで「deleted_at が空の行だけ読む」と固定し、試験に消した行を1つ入れる。
2. **店舗の形の複数選択の読み方**: テストは1つ（design.md:63）だが本物は複数（項目3 3-2 ⑥）。「卸を含めば卸」とするか「卸だけなら卸」とするかを実装カードで決め（既定は「含めば」が自然。PO に一言確認）、other_text は読まない、と書く。選択が1つも無いリードは空欄として外し、外した件数に数える。
3. **区切りちょうどの試験**: テスト用データは 60分・6時間ちょうどを作らない（design.md:108 の 1〜59分・61分〜）。「以内」が ≦ か ＜ かの取り違えを K2・K3 は見つけられない。試験に 60分ちょうど・6時間ちょうどの作り物を入れ、どちらに入るかを固定する。同じ時刻の受信と送信（並べ替えの引き分け）の順も id の順で固定する。
4. **本文の中身**: 受信は infer_original_language で言語を決める（design.md:66）ので本文が要る。本文は実在の人名・会社名・仕入元・投稿の文を含めない定型文にし、翻訳の見張りや Gemini を呼ぶ道（design.md:129）に触れないことを実装カードに書く。
5. **作り方の正本と id の取り方**: 仕込みの正本は作り方のコード1か所（design.md:163）。本番に流す SQL ファイルも K3 の 200通りのデータも、同じコードから種を変えて作ることを明記する。失注理由（テナント001の15個 recon.md:71）と店舗の形の選択肢の id は本番で決まるので、SQL は id を直書きせず、sort_order や value で引く（RETURNING で受ける）。
6. **「返信の速さ」が画面に2種類出ること**: 既存の「属性ごとの成約率」と優先リストは手入力の response_speed と leads.sales_form を読む（analytics.py:990・988、1844〜1851）。新しい欄はやり取りの表から計算した値と lead_sales_form_selections を読む。§10 に返信の速さの二重も記録し、画面の注意書きか報告書に「既存の成約率とは測り方が違う」と書く。
7. **収束しないとき・分離するとき**: 本物のデータでは、ある項目の値がすべて成約（または失注）になる組（完全分離）が起き得る。反復が収束しないときは例外で落とさず「この項目は計算できない」と返す決まりと、反復の上限・収束の判定の値を固定する。K3d の小数4桁一致（design.md:38）のため、行の順（id 順）と同じ関数を本番と本番の外で使うことも書く。
8. **報告書の雛形に、1回のデータで「差あり」と出にくい項目を先に書く**: 項目2 2-2 のとおり、相手の返信（1.6）と WhatsApp（1.5）は 1回の 400件では「差あり」と出ないことが多い。報告書の雛形に「出なくても仕組みの誤りではない。K3 の 200回で確かめる」と項目名を挙げて書く。K3b の幅が 5% ほどの上振れを許す点も添える。
9. **K5①(a) の点検の道具**: 「書き込み先がすべて tenant_001. で始まる」「public.・tenant_004・tenant_006・search_path の切り替えが 0件」を機械で見る（design.md:40）。実装カードで、点検を pytest の中の静的な検査にして CI で毎回流す（ADR-1049 の守り方 docs/adr/ADR-1049-lead-merge-all-tables-and-fill-blanks.md 38行と同じ型）。
10. **外した件数の内訳**: 画面に出す「外した件数」（design.md:147・151）を、状態で外した数と、受信だけ・送信だけで空欄になった数に分けて返す。本物で「件数が足りない」と出たとき、どちらが原因かを PO が読めるようにする。
11. **本物に切り替える前の点検表**: 項目3 3-2 の①〜⑥と項目4 #2〜#4 を、§9 の「切り替える前に決め直す」（design.md:227）の点検表として実装カード（または別の設計）に写す。
