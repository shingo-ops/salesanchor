# 設計（草案 第1版）— アプリ内のチャット秘書

この文書は、右下のチャットで AI に請求書・予定の下書きを作らせ、利用者の「作る」で今の機能を呼ぶ仕組みの設計の草案です。

## 1. 目的
- 利用者が、チャットに普通の言葉で頼むだけで、請求書と予定を作れるようにする（PO 2026-11-01）。
- 004 の AI は 004 以外、001 の AI は 001 以外の情報に触れない（PO 決定）。

## 2. 方針の芯（一番大事な決め）
**AI には書き込む力を持たせない。AI は下書きを返すだけ。書き込みは、利用者が「作る」を押したときに、画面が今の口（POST /invoices・POST /calendar/events）を利用者本人のログインで呼ぶ。**

- 理由1: 会社の判定は今の `get_current_tenant`（backend/app/auth/dependencies.py:263。recon §1）がそのまま効く。AI が会社を選ぶ余地が無い。
- 理由2: 請求書の権限確認 `require_permission`（recon §1 の表）・監査ログ・変わった合図（ADR-1016）が、今のまま全部効く。新しい書き込みの道を作らないので、SSOT も守れる。
- 理由3: AI が頼みの文に紛れた命令に従っても、書き込みは起きない（ADR-1052 Why と同じ考え）。

## 3. 変更前と変更後

| | 変更前 | 変更後 |
|---|---|---|
| 画面 | 右下の印・チャットの窓は無い | 001・004 の PO にだけ右下の印。押すと Drawer（横から出る窓）でチャット |
| AI | 本番サーバーに AI の道具は無い（recon §6） | 本番サーバーに専用の容器 1 つ。中で Claude Code を月額契約で動かす |
| 書き込み | 利用者が各画面で入力 | 同じ口を、下書きを確かめた利用者が「作る」で呼ぶ |

## 4. 仕組みの流れ
1. 画面: 利用者がチャットに書く → backend の新しい口 `POST /assistant/messages`。
   - 守り: `get_current_tenant` ＋ `require_feature("secretary_chat")`（dependencies.py:652。今は未使用。recon §4）＋ 第1段は PO 本人だけを通す確認。
2. backend: その場限りの「読む札」を作る。札には会社と利用者が固定で入り、読むことしかできず、5 分で切れる。札と頼みの文を専用の容器に渡す。
3. 専用の容器（新設・名前は仮に secretary-agent）: Claude Code を動かす。使える道具は「読む道具」だけ。
   - 読む道具: 会社を探す・担当者を探す・品物を探す・予定を見る。どれも backend の中の読む口を札付きで呼ぶ。会社は札で決まり、AI は指定できない。
   - 書く道具・ファイル・コマンド・ネットの検索は持たせない。
4. 容器は、決まった形の下書き（請求書なら company_id・contact_id・items。予定なら title・start_datetime・end_datetime。recon §1・§2 の必須項目）を返す。
5. 画面: 下書きを窓に表で出す。「作る」を押すと、画面が今の口を利用者本人のログインで呼ぶ。押さなければ何も起きない。
6. 使用量: 1 回ごとに使用量台帳（ADR-1004 の llm_usage_events）へ 1 行書く。purpose に `secretary_chat` を足す（llm_budget.py:159-166 は今 6 種で固定。recon §6）。

## 5. 容器の囲い
- データベースへの道を持たせない。容器は backnet（docker-compose.yml:567-569）の postgres に届かない別のネットワークに置き、backend の読む口だけに届くようにする。
- メモリの上限を 512MiB にする。同時に動かすのは 1 本（第1段は PO だけ）。AI 1 回分は約 0.25〜0.29GB（クラウドで測った参考値。recon §8）。本番のすぐ使える空きは約 0.8GB（2026-11-01 10:47 実測）。
- 月額契約のログイン情報は秘密の値として PO が入れる（AI は値を見ない・書かない）。

## 6. 代替案と選んだ理由

| 案 | 採らない理由 |
|---|---|
| AI に書き込みの道具を持たせ、自分で作らせる | 「作る前に下書きを見せる」（PO 決定）に合わない。紛れた命令で書き込まれるおそれ |
| AI にデータベースを直接読ませる | 会社の判定を AI 側に新しく作ることになり、SSOT と分離が崩れる |
| AI をクラウドに置く | PO 決定「サーバーの中に置く」 |
| 3 社の AI を同時に入れる | 変更は一度に 1 つ。測る前に基準値を取る |

## 7. リスクと対処

| リスク | 対処 |
|---|---|
| 月額契約の約束に反していて、契約を止められる（調査は PO 禁止） | 止められたらチャットが使えなくなるだけで、請求書・予定の機能は今のまま動く作りにする。見つからないように使い方をごまかす作りはしない（PO 決定） |
| 予定の表 calendar_events に、行ごとの守り（RLS）の記述が見つからない（recon §3。本番は未確認） | 本件は書き込みを今の口に任せるため、新しい穴は作らない。ただし第2段で広げる前に本番の状態を確かめ、無ければ別の作業で足す |
| 予定を作る口に権限の確認が無い（recon §2） | 第1段は PO だけなので影響なし。使う人を広げる前に決める |
| メモリが足りなくなる（予備の場所を 552Mi 使用中） | 上限 512MiB・同時 1 本。K6 で測る |
| 右下の印・吹き出しの金型が無い（recon §5） | PO の許可を得て金型を先に登録する（CC_UI_GOVERNANCE.md:17-19） |

## 9. 受入条件と検証方法

| 基準 | 検証方法 |
