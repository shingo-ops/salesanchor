## 4. 成功と失敗を分けた点（上の一次・二次から）
1. 項目が決まったデータ（在庫・顧客・注文）は元の表を直接探す。写しを作らない（S1・V2）。
2. 自由な文（手引き・書き起こし・過去の会話）だけを意味の検索（ベクトル）に入れる（V1・V2）。
3. 答えを出す前に、根拠と照らす点検を置く（V1。F1・F5 の反対側）。
4. 正解つきの試験で採点してから広げる（S2。F2 の反対側）。
5. 分からないときは「見つかりません」と答え、人へ引き継ぐ（F3）。
6. 効果は本番で時間や件数で測る（S1。F4 の反対側）。

## 5. 秘書チャットへの当てはめ（設計担当の見立て。PO 決定ではない）
- 今の秘書は会社のデータを AI に渡さず、名前は backend が今の表から部分一致で探す
  （`backend/app/services/secretary_resolve.py`・ADR-1056）。上の 1 と合う。
- 在庫の確認を足すときも、在庫・商品の表を直接探す形が 1 に合う。ベクトル DB は写しを持つため、
  「データを分散させない」決まり（ideal-state.md）とぶつかる。
- ベクトル DB を検討するのは、自由な文（LINE の会話・手引き）を探す要件が出て、
  名前で探して外れた件数を測った後。
- 要望（データに無いことは「見つかりません」・見たデータを1行添える）は、上の 3・5 と同じ向き。
  この要望の PO 承認は会話の中のもので、リポジトリに記録が無い【未確認】。要件に使う前に PO に確かめる。
- 試験（上の 4）は、ChatGPT 切替の目標（[../secretary-chatgpt/kgi.md](../secretary-chatgpt/kgi.md) の K1
  「決まった頼み文10本」）と同じ形で作れる。秘書チャットの kgi.md の K1 とは別のもの。
