# 設計：デッキビルドBOX 3商品のマスタ整備（2026-10-04）

状態：設計案作成済み／Opus 自己審査 APPROVE（§7）／PO 承認済み（2026-10-04）／本番適用済み（2026-10-04 23:11:34Z）。README.md の「実行記録」を参照。

## 1. 目的（PO に見える変化）
- LINE 解析の新方式（v7 の判定）では、「ステラミラクル」「[SV7]」のような通常版の投稿が、通常版 SV7 とデッキビルドBOX SVK の2候補で決めきれていなかった（ambiguous）。これを通常版1つに決まるようにする。
- 「デッキビルド」を含む投稿は、デッキビルドBOX に決まるようにする。

## 2. 現在地（recon.md の要約）
- デッキビルドBOX 3商品（SVN・SVK・SVF）の記号が、通常版と同じ（SV9・SV7・SV3）だった。商品名も通常版と同じだった。
- v7 の照合は、記号で候補に入る（extraction_judgement_svc.py:140 `_code_candidate_basis`）。そのため検索の語に当たらなくても、デッキビルド版が候補に入っていた（recon.md §2）。
- v9 の試験（T2、100投稿・3,066件）では、56件がこの原因で ambiguous だった。

## 3. 既存の ADR との関係
- ADR-155（商品マスタの SSOT は CSV とアプリ画面）
  - 今回は PO の判断（2026-10-04「はい」）で、例外として SQL で直接直した。
  - アプリの保存（tcg_product_detail_svc.update_product_detail）と同じ手順を SQL で再現した。行のロック、旧値の照合、キーワードの削除と再作成（position 1..n）、audit_log の1行がそれにあたる。
- ADR-025（本番の直接の INSERT・UPDATE）：開発の段階のため、PO の合意のもとで実施した。

## 5. 代替案と選んだ理由
- アプリ画面で PO が直す案：ADR-155 の正規の経路だが、PO が「あなたと sonnet が実行」と決めた。Claude はアプリにログインできないため、SQL を採用した。
- コードで記号の一致を弱める案：v7 の照合全体に影響する。今回の原因はマスタの登録の誤りなので、マスタを直した。

## 9. 維持の仕組み
- 守り手：設計担当（Opus）が、似た商品の洗い出し（product-check/similar_products.md、社外秘・手元）を元に、別版の登録の方針を守らせる。登録時の検査として仕組みにするかは、PO が判断する。
