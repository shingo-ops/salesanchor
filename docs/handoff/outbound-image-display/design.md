# 設計 — 送信画像の表示とプレビュー消去

> この文書は何か（専門用語なしの1行）:
> 送った画像を受信箱に映し、送信後に入力欄を空にするための作り方。

対象ADR: ADR-091
recon: docs/handoff/outbound-image-display/recon.md
親テーマ: docs/specs/attachment-storage/README.md

## 1. あるべき姿

顧客が送った画像やファイルが、いつ見返しても受信箱に残っている。
こちらから送った画像も同じように残り、同じように見える。

## 2. recon（実測）

docs/handoff/outbound-image-display/recon.md を参照。要点は次の2つ。

- 送信画像は保存されているが、配信URLが設定されていない。
- プレビューの状態が2つの場所に分かれており、片方しか消えない。

## 3. design（技術How）

課題1は、保存の直後に配信URLを設定する。
lead_attachments から採番された id を引き、
受信時と同じ形式のパスを meta_messages に書き込む。

課題2は、attachedFile が null になったことを画面側で検知し、
previewUrl も消す。state を1箇所にまとめる案もあるが、
影響範囲が広くなるため追従の形を採る。

frontend/src/pages/inbox/useInboxState.ts は変更しない。

## 4. 外部・過去事例の参照と我々への応用

同じ意味を持つ状態を複数の場所に分けて保持すると、
片方だけが更新されて食い違う。これは状態の二重管理と呼ばれる。

本件では添付ファイルの有無が
useInboxState の attachedFile と
InboxMessageThread の previewUrl の2箇所に存在した。

送信後に片方だけを消したため、画面には残り続けた。

根本の解決は state を1箇所にまとめることだが、
propsの受け渡しを含む広い変更になる。
本設計は追従の形を採り、二重管理そのものは残す。

我々への応用: 同じ意味の状態を2箇所に持つときは、
片方を変えたらもう片方も追従する仕組みを必ず置く。

## 5. 弊害・トレードオフ

- 弊害: 状態の二重管理が残る。
  追従の処理を1つ足すだけで、根本は解決しない。
- 弊害: 既に送信済みの2件は attachment_url が null のまま残る。
  それらは引き続き表示されない。
- トレードオフ: 保存の直後に SELECT を1回追加する。
  採番された id を得るためであり、送信ごとに1回だけ増える。

## 6. 受入基準

| 基準 | 検証方法 |
|---|---|
| 配信URLを設定する処理がある | grep で 送信画像の配信URL設定 が1件 |
| meta_messages を更新する | grep で UPDATE の記述が1件以上 |
| プレビューの追従処理がある | grep で attachedFile が null の判定が1件 |
| useInboxState を変更していない | git diff に当該ファイルが現れない |
| 既存テストを壊していない | pytest が全 pass |
| 実環境で表示される | 受信箱から画像を送り、送信済みの吹き出しに画像が出ることを確認する |
| プレビューが消える | 送信後に入力欄の添付が消えることを確認する |

## 7. 維持の仕組み

- 守り手: 人手で守る
- 理由: Discord への実送信と実ブラウザでの描画を伴うため、
  現在のテスト基盤では再現できない。
- 対象: 送信画像が表示されなくなること。
  送信後にプレビューが残ること。
- 検知方法: PO による実機確認。受信箱から画像を送り、画面を見る。
