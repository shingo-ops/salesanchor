# 設計: 開発の知らせ 4 種を Sales Anchor の「🛠開発の知らせ」へ移す

- 状態: PO 承認済み・実行済み（下の §8）
- 調べ: `docs/handoff/discord-dev-notices/recon.md`
- 関係する ADR: `docs/adr/ADR-1039-discord-pdca-agent-console.md`、`docs/adr/ADR-035-external-state-verification.md`、`docs/adr/ADR-1012-ai-ops-247.md`

## 1. 目的
PR・自動の点検・計画の審査・レビューのメールの知らせを、別のサーバーから Sales Anchor のサーバーへ集める。知らせを 1 つのサーバーで読めるようにする。

PO の決定:
- 2026-11-22 PO「1」: Sales Anchor に「🛠開発の知らせ」を 1 つ作り、4 種類をそこへ届ける。急ぎと定期の報告には混ぜない。
- 2026-11-22 PO「1」: 同意票の操作（チャンネルと送り口 4 つを作る・鍵 4 つの入れ替え・この記録の合流と本番反映）を実行する。

## 2. 対象と対象外
- 対象: Discord のチャンネル 1 つと送り口 4 つを作る。GitHub secret 4 つの値を入れ替える。手順書 `docs/runbooks/alerts.md` の届け先の節。
- 対象外: コードの変更（0 行）。別のサーバーにある古い送り口とチャンネル（Bot が入っておらず消せない。消すかは PO が決める）。外部の状態の写しの失敗（別件）。

## 3. 変更前と変更後
| 鍵 | 前の届け先 | 後の届け先 |
|---|---|---|
| `DISCORD_WEBHOOK_PR` | 別のサーバー | 🛠開発の知らせ（送り口「PR」） |
| `DISCORD_WEBHOOK_CI` | 別のサーバー | 🛠開発の知らせ（送り口「自動の点検」） |
| `DISCORD_WEBHOOK_PLAN_REVIEW` | 別のサーバー | 🛠開発の知らせ（送り口「計画の審査」） |
| `REVIEW_MAIL_DISCORD_WEBHOOK` | 別のサーバー | 🛠開発の知らせ（送り口「レビューのメール」）。本番反映の後に切り替わる |

## 4. 選んだやり方と、選ばなかったやり方
- 選んだ: 鍵の値だけを替える。コードも名前も変えないので、使う場所（recon §2）は 1 か所も触らずに済む。
- 選ばなかった: 「定期の報告」へ混ぜる。PR の知らせが 1 か月に 1,000 件を超え、週次の報告が埋もれる（PO が 1 を選んだ理由）。
- 選ばなかった: 鍵の名前を変える。使う場所 10 か所以上の書き換えが要り、得るものが無い。

## 5. 危ないことと対処
- GitHub の鍵は前の値を読み出せない。→ 戻すときは、別のサーバーで送り口を作り直してもらい、値を入れ直す。
- 本番の値の控え: 入れ替えの前に、本番サーバーの 本番サーバーの控えの置き場（backups の discord-dev-notice） に権限 600 で保存した。
- 日曜の外部の状態の写しで、送り口の id の差分が 1 回出る。予定どおりの変化として扱う。

## 6. 受入の基準
|基準|検証方法|
|---|---|
|K1 チャンネル「🛠開発の知らせ」が「アラート」の中にあり、送り口が 4 つある|Bot で Sales Anchor のチャンネルと送り口の一覧を読む|
|K2 GitHub secret 4 つの更新時刻が 2026-11-22 の入れ替えの時刻になっている|GitHub の鍵の一覧の更新時刻|
|K3 この記録の PR を作ると、PR の知らせと自動の点検の知らせが「🛠開発の知らせ」に届く|Bot でそのチャンネルの投稿を読む（送り口の id で照合）|
|K4 本番反映の後、本番の `REVIEW_MAIL_DISCORD_WEBHOOK` の送り口 id が「レビューのメール」の id と同じ|本番サーバーで id の部分だけを読む（値は出さない）|
|K5 計画の審査の鍵が「計画の審査」の送り口を指している|失敗時だけ送るので、K2 の時刻と、作った送り口の id の記録で照合する|
