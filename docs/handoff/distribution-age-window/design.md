# design: 配信の「48時間以内」を1か所の定義にし、設定が無い時は配信を止める（便AGE）

参照: docs/handoff/distribution-age-window/recon.md、ADR-158、docs/handoff/distribution-age-window/card-AGE.md。

## 1. 目的（PO の言葉、2026-10-11）
- 「システム解析後に最終的に集計したリストに残るのはLINEでの投稿日時が48時間以内の商品、それ以外は集計リストから外してログにする」
- 「解析したリストは全てログになってDBに残る認識で48時間以内の投稿のデータのみ印が付き配信される」
- 設計者の確認: 解析結果は全て analysis_results に残り（ログ）、配信は48時間以内だけを出している（recon）。ずれは (1) プレビューの除外内訳が48時間より前も数える、(2) 設定が無いと全期間を配信する、の2点。

## 2. 変更前後
| 場所 | 変更前 | 変更後 |
|---|---|---|
| 48時間の条件 | fetch_output_rows と fetch_preview_data に同文で複製 | `_age_window()` 1つ。配信・件数・除外内訳の3か所が使う |
| 除外内訳 | 48時間より前の現行行も数える | 48時間以内の現行行だけ数える |
| 設定の読み方 | `int(settings.get(..., "0"))` を2か所 | `_max_age_hours()` 1つ。無い・整数でない・負 → None |
| 設定が無い時 | 0 として扱い、全期間を配信 | 配信しない（errors と logger.error）。プレビューは 409 |
| 値 0 | 無制限 | 無制限のまま（画面の説明「0で無制限」に合わせる） |
- is_current の意味（ADR-158）は変えない。時間で変わる条件は読み取り時に当てる。
- 対象外: 在庫一覧 viewer の24時間（別リポジトリ）、他の画面。

## 3. 受入条件
| 基準 | 検証方法 |
|---|---|
| A1 配信の行・件数は変更前と同じ | 生成 SQL の比較（配信本体・件数は差0）、デプロイ後の配信件数 |
| A2 除外内訳も48時間以内だけ | PG テスト |
| A3 設定が無い・不正・負なら配信しない／プレビュー 409 | 単体テスト |
| A4 0 は無制限のまま | PG テスト |
| A5 値 48 をコードに書かない | grep |

## 4. 代替案
- is_current を「最新かつ48時間以内」に変える: 時間が経つたびに印を付け直す仕組みが要り、ADR-158 の意味も変わるので不採用。
- 設定が無い時にコードの既定値 48 を使う: 値が2か所になる（SSOT 違反）ので不採用。

## 5. リスクと対処・戻し方
- 設定の行が消えると配信が止まる → errors とログで分かる。設定画面（DistributionSettingsDrawer）で値を入れ直せば戻る。
- 戻し方: PR を revert。

## 外部・過去事例の参照と我々への応用
- 外部事例: 使わない（社内の配信設定の扱いで、比べられる公開の実測が無いため）。
- 過去事例: 便ER（#4129）で「配信しない状態」を状態の表の effect 列1か所で決めた。同じく、配信の時間窓も設定の表の1か所を唯一の値にし、コードに既定値を持たない。

## 維持の仕組み
- 単体テスト・PG テスト（3か所が同じ条件・設定なしで配信しない）が CI で毎回走る。
- 守り手: CI（backend/tests/test_tcg_distribution.py、backend/tests/test_tcg_condition_review.py）
