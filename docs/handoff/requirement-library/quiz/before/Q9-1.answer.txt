# 計画: チャット秘書に「会社データの検索」と「予定の直接作成」を足す

調べたのはリポジトリ内の文書とコードだけです。ファイル変更・commit・push はしていません。本番の実機は確かめていません。

## 1. 先に決める必要があること（既存の PO 決定とぶつかる点）

今の設計は、この依頼と正反対の約束で作られています。

| 今の約束（ADR-1056・設計第3版 §2・KGI） | 今回の依頼 |
|---|---|
| AI に会社のデータも道具も渡さない。名前探しは backend が行う（`backend/app/services/secretary_resolve.py`） | AI が会社データを検索する道具を持つ |
| AI は下書きを作るだけで、「作る」を押したときに画面が本人のログインで書く（PO 決定 2026-11-01「1」） | AI が直接予定を作る |
| K4: 他社の情報に触れた件数 0。K5: AI が自分で書き込んだ件数 0 | 道具経由の読み取りと書き込みが生まれる |

そのため、実装の前に次の手順を踏みます。

- **ADR を新しく起案します。** ADR-1056 の「方針の芯」を一部置き換える内容です。会社のデータが AI 会社へ送られること（ADR-1056 の「リスク」欄で送らないと明記）の変更を、PO の判断事項として明示します。
- **KGI の K4・K5 を文言変更します。** KGI は PO 承認済みなので、改める案を PO に見せて承認をもらいます。`ideal-state.md` は PO の言葉の正本なので触りません。
- **「直接作成」は PO の再決定が必要です。** 2026-11-01 に「作る前に下書きを見せる」を選んだのは PO です。

PO に聞くことは次の 3 点です。

1. 検索で AI に見せてよい項目はどこまでか（例: 会社名・担当者名・予定だけ。メール・電話・金額は不可）。
2. 直接作成は、自分だけに見える予定（`calendar_type=personal`）に限るか。
3. 直接作成を残すなら、取り消しボタンを付ける条件でよいか。

## 2. 方針（推奨）

**AI の容器は DB に届かないままにします。** 道具は「backend が持つ口」を呼ぶだけの形にします。会社の判定、権限確認、監査ログ、ADR-1016 の変わった合図は、今のものを使い回します。

### 段階 A: 読み取りの道具（検索）

- backend に、読み取りだけの口を新設します（例: `/assistant/tools/search_companies`・`search_contacts`・`search_events`）。
  - 検索条件は `backend/app/routers/companies.py:291-319` と `contacts.py:258-283` の列・条件を再利用します（`secretary_resolve.py` が既にこれを使っています）。
  - 返す項目は、PO が許可した項目だけの許可リストにします。件数の上限（最大 5〜10 件）と、1 回の頼みあたりの呼び出し回数の上限も付けます。
- AI の容器が口を呼ぶための鍵は、**1 回の頼みごとに backend が発行する使い捨ての短命トークン**にします。
  - トークンに、会社 ID・利用者 ID・使える道具の範囲・有効期限（容器の打ち切り 80 秒＋余白）を結び付けます。
  - AI に会社を選ばせません。口の側でトークンから会社を決め、`get_current_tenant` と同じ `SET`＋`reset_tenant_context`（ADR-072）を通します。
- 道具の渡し方は、`secretary-agent/server.mjs` の CLI 起動を変えます。
  - 今は `--tools "" --disallowedTools "mcp__*" --strict-mcp-config` で全部切っています。
  - これを「許可した道具だけを持つ小さな MCP サーバー（容器内）」に変えます。MCP サーバーは backend の口を HTTP で呼ぶだけです。
  - Claude CLI のこの組み合わせ（道具の許可リスト＋`--json-schema`＋stdin）が実際に動くかは**未確認**です。最初に使い捨ての試作で確かめ、動かなければ止めて報告します。
- 容器の囲い（frontnet のみ・read_only・cap_drop・mem 512m）は変えません。
- 検索結果は AI から見て「信頼できない外部の文章」です。会社名などに命令文が紛れても従わないよう、`secretary-agent/prompt.txt` に明記します。AI が使える道具は検索と予定の提案だけにするので、被害が広がらない作りにします。

### 段階 B: 予定の直接作成

- 道具 `create_event` は、**backend の口を通して**今の作成処理（`calendar_service`、`POST /calendar/events` と同じ経路）を呼びます。AI が DB に書く道は作りません。
- 作成の安全策は次のとおりです。
  - **必須の欄がそろったときだけ作ります。** ADR-1078（予定のカルテ）の欄の聞き返しをそのまま使い、足りなければ作らずに聞き返します。
  - **初期は `personal` のみにします。** `shared` や、Google 同期・Meet の付与は段階 B の対象外にします。
  - 二重作成を防ぐために、1 回の頼みごとに 1 件・冪等キー付きにします。
  - **作成者は利用者本人とし、「秘書経由」という印を監査ログに残します。** K5 を「AI が自分の判断で書いた件数 0」から「秘書経由の作成は全件が記録され、取り消せる」へ置き換える案を PO に出します。
  - 作った直後に、チャット上に「作りました（取り消す）」を出します。取り消しは今の予定削除の口を使います。
  - 利用者ごとの切り替え（`tenant_features` に新しいキー）で、直接作成と従来の「下書き→作る」を選べるようにします。初期値は従来のままにします。
- 請求書は今回の対象外です（請求書は従来どおり下書き→「作る」）。

## 3. 触る場所（代表）

- `backend/app/routers/assistant.py`: 頼みの処理。道具用トークンの発行と、道具の口の追加。
- `backend/app/services/secretary_resolve.py`: 検索の共通化。許可項目の絞り込み。
- `backend/app/services/calendar_service.py`: 作成処理を再利用します（`:196` の commit 後に `reset_tenant_context` が無い件は、設計 §8 に既出です。直接作成の前に直します）。
- `backend/app/schemas/assistant.py`: 道具の入出力の型。
- `secretary-agent/server.mjs`・`prompt.txt`・`schema.json` と、容器内の MCP サーバー（新規）。
- `frontend/src/features/secretary/`: 「作りました（取り消す）」の表示。使う部品は `components/` の金型とデザイントークン、文言は i18n の ja/en 同一キーを使います。
- `secretary-codex/` にも同じ道具が要るかは、まだ読んでいないので**未確認**です。
- migration（追加のみ）: `tenant_features` の新キー、必要なら監査ログの「秘書経由」列。`deploy.yml` の登録も要ります。
- 文書: 新 ADR、`docs/specs/secretary-chat/` と `docs/handoff/secretary-chat/design.md`（第4版）。

## 4. 進め方（運用ルール）

1. `bash scripts/new-worktree.sh release/secretary-tools --claude` で作業場所を作ります。作業前に `./scripts/dev/executor-preflight.sh` と `docs/ai-agents/executor-checklist.md` を確認します。
2. 設計の文書だけの PR を先に出し、PO の承認を得ます（上の 3 つの質問を含みます）。
3. 段階 A を、検索の口・トークン・容器の MCP の順に、小さな PR に分けて実装します。
4. 段階 B は、A が本番で合格したあとに別の PR で行います。変更は一度に 1 つにします。
5. `migrations/` と `deploy.yml` を含む PR は、PO の「GO #PR番号」までマージしません。トークンやログイン情報の値は表示しません。
6. コードの PR は `shingo-cc` 名義で作り、push の前に `check-before-submit.sh` を流します。認証・トークンに触れるので `/security-review` も流します。

## 5. 検証

- **段階 A（K4 の再定義）:** テナント 004 で「001 の会社を検索して」など 10 問、逆方向も 10 問を試し、他社の値が 1 つも出ないことを確かめます。
  - トークンの会社 ID を差し替えた口の直接呼び出しが 403 になることも確かめます。期限切れと別利用者のトークンも同様です。
  - 容器から postgres・redis に届かないことは、既存の `probe.mjs` で再確認します。
  - 許可リスト以外の項目が検索結果に出ないことは、pytest（使い捨ての PostgreSQL）で確かめます。
- **段階 B:**
  - 必須の欄が欠けたら作らずに聞き返すことを、5 回の試しで確かめます。
  - 作成された予定は、作成者が本人で「秘書経由」の印があることを、予定の画面と監査ログで前後を照合します。
  - 「取り消す」で消えること、同じ頼みを 2 回送っても 1 件であることも確かめます。
- **共通:**
  - 検索結果に命令文を仕込んだテストデータで、AI が従わないことを確かめます。
  - 容器の空きメモリが 0.4GB を下回らないこと（K6）も、10 秒ごとの記録で確かめます。
  - `frontend` の試験（vitest）と `backend` の pytest を流します。
