# 修正計画: 顧客情報管理の「新規登録」でエラーになる

ファイルの変更・commit・push はしていません。コードを読んだだけです。実機では再現していません。

## 原因（読んだ範囲で確実なことと、未確認のこと）

**確実なこと（コードの突合）**
- 「顧客情報管理」画面は `frontend/src/pages/companies/CompaniesPage.tsx` です。「新規登録」ボタンは 376 行目、送信処理は `handleCreateSubmit`（227〜322 行目）です。
- 送信する本文（`payload`、281〜298 行目）に **`lead_id` がありません**。`api.post("/companies", payload)` は 309 行目です。
- 一方、サーバー側の `backend/app/schemas/company.py:116` では `lead_id: int = Field(ge=1)` が**必須**です。`backend/app/routers/companies.py:391` の `create_company` も、リードの存在を確認してから登録します。
- この必須化は、便1a「背骨の必須化」の設計で入りました（`docs/handoff/txn-flow-asis-recon/design.md` の 42〜43 行目）。画面側がその変更に追従していないと考えられます。
- 画面の型 `Company` には `lead_id` があります（67 行目）。しかし作成フォームにはリードを選ぶ欄がありません。

**未確認のこと**
- 実際に出ているエラーの画面表示と HTTP ステータスです。コード上は 422（`lead_id` が欠けている）と推測します。
- 権限不足（`customers.create`）や、会社コードの重複（409）が原因ではない、という確認もまだです。

## 修正方針（PO への確認が必要）

便1a の設計は「会社は必ずリードの子」です。ADR を優先する決まりなので、`lead_id` の必須化は外さず、画面側を設計に寄せます。リードの決め方に 2 案あります。

- **案A（推奨）: フォームに「元のリード」を選ぶ欄を足す。**
  - 既存の金型（検索付きの選択部品）を使い、選んだ `lead_id` を `payload` に入れます。
  - 未選択なら送信前に画面で止めて、メッセージを出します。
  - 商談から作る流れ用に、`deal_id`（任意）も渡せるようにします。
- **案B: 画面で会社名からリードを自動で1件作る。**
  - 画面が `POST /leads` を先に呼び、続けて `/companies` を呼びます。
  - 途中で失敗すると孤立リードが残ります。
  - 設計の「名寄せはしない」方針に反するため、非推奨です。

どちらにするかは未確定です。「不明を残したまま実行しない」の決まりに従い、着手前に PO（しんごさん）へ確認します。
