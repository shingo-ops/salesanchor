# 計画: 「40パックセット ¥24,000」を1パック600円で保存する

調査だけで、ファイルの変更・commit・push はしていません。

## 先に決めてほしいこと

「1パック600円として保存」は、今の決まりと正反対です。

- ADR-1027 の決定は「まとめ売りは値段を割らずに保存する」です（`docs/adr/ADR-1027-bundle-sale-reading.md` の見出しと What 3）。
- 2026-10-17 の PO の言葉も「値段はまとめ1つの値段。割らない」です（`docs/specs/bundle-sale/ideal-state.md`）。
- ADR-1027 は、ADR-1021 便2 の「1枚単価に割る」を意図して置き換えた決定です。
- `AGENTS.md` では、ADR と実装が食い違うときは ADR を優先し、コードを ADR に寄せます。逆はしません。

そのため、方針を2つに分けます。どちらにするか PO の判断が要ります。

| 案 | 内容 | ADR との関係 |
|---|---|---|
| **A（推奨）** | 保存は今のまま（price=24,000、bundle_size=40）にして、在庫表の表示だけ「1パック ¥600」と出す | ADR 変更なし。割り算は表示のときだけ |
| B | 保存する値段そのものを 600 にする | ADR-1027 の決定を覆すので、追記と PO の合意が先に要る |

## 案A（推奨）の計画

1. **事前確認（読み取りだけ）**
   - 在庫表の列の出し方を確かめます。配信行は `backend/app/services/tcg_distribution_svc.py:265` 付近で、商品名に「N単位セット」を足しています。
   - アプリ側は `frontend/src` の在庫表の部品です。`frontend/AGENTS.md` と `docs/CC_UI_GOVERNANCE.md` を先に読みます。
   - GAS 在庫一覧と閲覧ページ（ADR-1019）にも同じ列があるか確かめます。
2. **作業場所**
   - `bash scripts/new-worktree.sh release/bundle-unit-price-display --claude` で作ります。
   - 着手前に `./scripts/dev/executor-preflight.sh` を流します。
3. **実装**
   - 配信の SQL に「1単位あたりの値段 = price ÷ bundle_size」を足します。bundle_size が NULL の行は今までと同じです。
   - 割り切れない場合の丸めを決めます。円なので四捨五入か切り捨てを選び、`docs/specs/bundle-sale/` に1行書きます。
   - 画面は「¥24,000（1パック ¥600）」のように、まとめの値段を主にし、単価を添える形を想定します。i18n は ADR-027 に従い、英語は「per Pack」にします。
   - 保存値と migration は触りません。
4. **ADR・文書**
   - 表示を足すだけなら決定の変更ではないので、ADR-1027 に短い追記（表示の追加）だけ入れます。
   - その後 `node scripts/generate-adr-index.js` を実行します。
5. **テスト**
   - `backend/tests/test_inventory_distribution_rows.py` に追加します。24,000÷40=600 の行、bundle_size が NULL の行、割り切れない行の3つです。
   - 実機の PostgreSQL で確かめます。
6. **PR**
   - `gh auth status` で `shingo-cc` 名義を確認します。
   - 本文に「### 標準ワークフロー確認」を入れます。

## 案B（保存値を600にする場合）の計画

先に ADR-1027 を直す必要があり、影響が広いので重く、不可逆に近い作業になります。

1. **ADR の追記**
   - ADR-1027 に追記（または新しい ADR で置き換え）します。PO の合意を取ります。`docs/ai-agents/adr-template.md` の型に従います。
   - 設計審査（Opus reviewer）も受けます。
2. **コード**
   - `_apply_bundle`（`line_analysis_v102_svc.py:1080`）で、決まった行の `price_normalized` を `÷ bundle_size` にします。
   - 数量は「まとめの数」のままか、「パックの総数」に掛けるかを決めます。
   - `bundle_size` を数量や値段の意味とどう整合させるかも決めます。
3. **影響を受ける処理の見直し**
   - 次の4つは、どれも「まとめの値段＝割らない」前提で作られています。
     - 単価の確かめ（`v102_unit_price_check_svc.py:64`、まとめ売りの行を相場から外している）
     - 価格の引き継ぎ
     - 買取単位の判定（`v102_buyback_unit_svc.py:200`）
     - 同じ行をまとめる鍵（`tcg_distribution_svc.py:352`）
   - 割った後も外すか、含めるかを決め直します。
4. **既存データ**
   - 既存の bundle_size の約157行（2026-10-21 時点）を `reanalyze_v102_job` で再解析します（Gemini は呼びません）。
   - 実行前に前の値を全列保存し、書き戻しの SQL を先に用意します。
   - 本番データを書き換える作業なので、同意票で PO に確認します（ADR-1033）。
   - 本番の読み取りは ADR-1024 の道（SELECT のみ）で行います。
5. **安全面**
   - 割り切れない値段（例: ¥25,000÷40=625、¥24,990÷40=624.75）は、丸めると元の値段に戻せなくなります。
   - 追加の列（例: `bundle_total_price`）に元の値段を残す案を検討します。migration は additive-only で、ADR-136 の GO が要ります。
6. **テストと PR**
   - `test_v102_bundle.py`、`test_v102_bulk_price.py`、`test_line_analysis_v102_pg.py` を更新します。
   - `bundle_replay.py` で全行に当て直し、変わる行の数を PR 本文に書きます。
   - `migrations/` を含む PR は、PO の「GO #PR番号」が出るまでマージしません。

## 推奨

案Aです。画面に「1パック600円」が出れば目的は果たせ、保存値と ADR を動かさずに済みます。案Bは、割った値段を保存したい理由が別にあるとき（例: 外部連携や相場比較が保存値を直接読む）だけ検討すれば足ります。

PO が決めること（回答をお願いします）:
- 案A・案B のどちらにするか。
- 丸め方（四捨五入か切り捨てか）。
- 単価は在庫表だけに出すか、GAS 在庫一覧と閲覧ページにも出すか。
