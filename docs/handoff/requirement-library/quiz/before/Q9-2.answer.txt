# チャット秘書に検索の道具を渡し、AI が直接予定を作れるようにする計画

調査エージェントの報告をもとにしています。ADR の本文は ADR-1056 の冒頭と ADR-1077 の抜粋しか読んでおらず、ADR-1072 は未読です。実装に入る前に確認が要ります。ファイルの変更・commit・push は行っていません。

## 1. 現状

- チャット秘書は実装済みです。AI は文を「請求書・予定・聞き返し」の下書きに直すだけで、道具もデータも持ちません。
- 作成は、利用者が「作る」を押したときに、本人のログインで既存の `POST /calendar/events`（`backend/app/routers/calendar.py:431`）を呼ぶ形です。
- LLM は Claude Code CLI または Codex CLI を専用容器で動かしています。tool/function calling は禁止されていて、ツール定義の仕組みもありません。
- 会社データの検索は、`secretary_resolve.resolve_names`（会社と担当者を最大 5 件）だけです。
- ADR-1056 の中核方針は「AI に書き込みの道を持たせない」です。今回の要望はこの方針と正面からぶつかります。

## 2. 最大の論点：ADR との衝突

「AI が直接予定を作る」は、ADR-1056 を改める内容です。AGENTS.md に「ADR と実装が食い違うときは ADR を優先する」とあるため、先に新しい ADR を起案し、PO（しんごさん）が承認する必要があります。コードを先に書くのは禁止です。

## 3. 進め方（段階）

**段階 0：決まりの確認と ADR 起案（コードなし）**
- `docs/INDEX.md` の該当手順書（`STANDARD-WORKFLOW.md`、`ai-agents/adr-template.md`、`specs/README.md`）、`adr/FEATURE-INDEX.md`、ADR-1056・1072・1077 を全文読みます。
- 新しい ADR には次を書きます。
  - AI に渡す道具の範囲：検索は読み取り専用、書き込みは「予定の作成」だけ。
  - 本人の権限とテナントの範囲内で動かすこと。
  - 監査ログを残すこと。
  - 取り消し（削除）の道を用意すること。
  - 削除・更新・請求書作成は対象外にすること。
- 利用者が「作る」を押す今の方式のまま、承認を省くのか残すのかを PO に決めてもらいます。

**段階 1：検索の道具（読み取りだけ、リスク低）**
- `secretary_resolve` を土台に、読み取り専用の検索サービス関数を足します。対象は会社・担当者・商談・商品・既存の予定など。
- 道具はサーバー側の許可リストで定義します。引数は検証し、件数に上限を付けます。
- 検索は必ずログイン中の利用者のテナントに絞ります。`tenant_id` 絞りと RLS の扱いは `backend/AGENTS.md` に従い、共通の依存関数を使います。
- 秘密の値や暗号化済みトークンの列は返しません。

**段階 2：AI 呼び出し側を道具対応にする**
- 今の CLI 方式で「道具を呼ぶ→結果を返す→最終回答」のループを回せるか、先に確認します。
- 無理な場合は、tool use に対応した API 呼び出しへの切り替えを選択肢にします。これは別の大きな設計判断なので PO に諮ります。
- ループ回数と時間の上限、道具の引数の検証、失敗時の聞き返しも決めます。

**段階 3：予定の直接作成**
- 既存の `POST /calendar/events` のロジックを、ルーターとサービス関数の共通部品に切り出して再利用します。AI 専用の別実装は作りません。
- AI の呼び出しは、本人の資格情報とテナントの文脈のまま実行します。作成元（`created_by_ai` など）と元の発話を監査に残します。
- 暴走を防ぐため、1 回の会話での作成件数に上限を置きます。
- 重複防止（冪等キー）、日時のあいまいさ（相対日時・タイムゾーン）、参加者の解決に失敗したときの聞き返しも入れます。
- 作成後は画面に「AI が作成した」と表示し、「取り消し」を出します。
- 既存 API に権限の Depends が無く、`calendar_events` の RLS も未確認です。ここは先に確認し、足りなければ安全な追加マイグレーションで補います。マイグレーションを含む PR は PO の「GO #PR番号」まで main にマージしません。

**段階 4：画面（`frontend/`）**
- `frontend/AGENTS.md` と `CC_UI_GOVERNANCE.md` に従います。
- 「AI が検索した・作成した」の表示と、取り消しボタンを足します。

## 4. 検証

- backend の pytest：
  - 検索がテナントをまたがないこと。
  - 道具の許可リスト外の呼び出しが拒否されること。
  - 作成件数の上限と冪等性。
  - 権限のない利用者が作成できないこと。
  - 監査ログが残ること。
- AI の挙動を固定する試験：モックの LLM で「検索→作成」の流れを確認します。
- フロントの試験と手元での実機確認（`run` で画面を動かす）。
- 本番 DB への直接の書き込み・確認は行いません。SQL を流すのは、使い捨ての localhost の PostgreSQL 上の pytest だけです。

## 5. 作業の進め方（リポジトリの決まり）

- 作業前に `bash scripts/new-worktree.sh release/<topic>` を実行し、`./scripts/dev/executor-preflight.sh` を通します。
- コード変更を含む枝は push までです。PR は手元で `shingo-cc` 名義で作り、本文に「### 標準ワークフロー確認」の節を入れます。docs だけの ADR 起案 PR は、クラウドで作ってよい扱いです。
- マージはクラウドでは行いません。

## 6. 未確認事項（着手前に潰す）

- `calendar_events` の RLS の有無。
- ADR-1072 の内容。
- 商談・タスク・アポ専用の API があるか。
- 今の CLI 方式で道具ループを回せるか。
- 作成を「承認なし」にするのか、「確認つき」にするのか。

最後の点が最大の決めどころです。リスクを抑えるなら、まず検索だけ（段階 1〜2）を出し、直接作成（段階 3）は ADR 承認後に別 PR にすることを勧めます。
