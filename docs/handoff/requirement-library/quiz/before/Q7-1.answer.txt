# 計画: 再解析しても古い投稿の行が現行に戻るようにする

ファイルの変更・commit・push はしていません。調べたのはコードと ADR の読み取りだけです。

## 1. 分かっていること

- 現行（`is_current`）を決めるのは `backend/app/services/tcg_analyzer_svc.py:1981` の `_merge_supplier_products` です。
  - 同じ仕入元の投稿を、商品×状態の組ごとに `received_at` で比べます。
  - 組ごとに最新の投稿を 1 つ決め、その投稿の行を TRUE、ほかを FALSE にします。
- 再解析の呼び出し元は `line_analysis_v102_svc.py:1640` です。`prior_current_pairs=after.prior_current` を渡しています。
- ADR-1032 の「復活止め」が `tcg_analyzer_svc.py:2122-2139` にあります。
  - 組の最新投稿の行でも、前から現行でなく、かつ同じ仕入元のより新しい投稿に同じ商品の行（仮の行を含む）があれば FALSE にします。
- `was_current` は (投稿, 商品, 状態) の組で判定します（`tcg_analyzer_svc.py:2070-2075`）。
  - 再解析で商品や状態が変わると、付け替え後の組は「前から現行」と見なされません。
  - そのうえ、より新しい投稿に同じ商品の行があると FALSE になります。
- ADR-1032 の 2026-10-23 追記は、これを承知の上の挙動として記録しています。
  - PO 2026-10-22「1」で、同じ仕入元のより新しい投稿に同じ商品の行がある古い値段は、付け替え後に現行にしないと決めています。
  - 実例は 2 行（TRUE→FALSE）で、配信への影響は 0 でした。

## 2. 最初に決めること（実装の前）

今回の依頼は、ADR-1032 のこの決定と食い違う可能性があります。AGENTS.md は「ADR と実装が食い違うときは ADR を優先する」としています。

- 依頼の意図が「より新しい投稿に同じ商品の行がある古い投稿でも、再解析後は現行に戻す」なら、PO の決定を変えることになります。
  - ADR-1032 の追記（または新しい ADR）の起案と、PO の確認が先に必要です。
- 依頼の意図が「同じ商品・同じ状態のまま再解析しただけなのに消える」不具合の修正なら、決定は守ったままバグだけ直せます。
  - ただし、これがバグかどうかは未確認です。

→ 実装前に PO へ「どちらの意図か」を 1 問だけ確認します。

## 3. 原因の特定（読み取りと試し実行だけ）

次の点を確認します。いずれも未確認です。

1. `after.prior_current` の作り方（`line_analysis_v102_svc.py` 内）を読みます。
   - 再解析で行を作り直す前に、現行だった組を正しく控えているかを見ます。
   - 控えが空だったり、削除と再作成で `is_current` が初期値に戻っていないかも見ます。
2. `_write_results` が行を作り直す際の `is_current` の初期値を確認します。
3. 再解析のたびに、`extra_pairs=after.previous_pairs`（前の組）が必ず渡っているかを確認します。
4. 本番相当の再現確認は、使い捨ての PostgreSQL（localhost）の pytest の中だけで行います。本番 DB へは書きません。
5. 次の 3 ケースを再現して、どれで消えるかを切り分けます。
   - (a) 商品も状態も変わらない再解析
   - (b) 商品が変わる再解析
   - (c) 状態が変わる再解析

## 4. 修正方針（原因が確定したあと。有力案）

- **推奨:** 再解析する投稿について、「前から現行だった行」を行単位で保持します。
  - 再解析の前に、その job の現行行の (商品, 状態) を控えます。
  - 付け替え後の組は、付け替え前の組と対応づけます。付け替え前に現行だった行は、付け替え後も「前から現行」とみなします。
  - 実装箇所は `_merge_supplier_products` の `was_current` 判定と、呼び出し側の `prior_current` の作り方です。
  - 追加の安全なマイグレーションは不要の見込みです。SQL の変更だけで済みます。
- 復活止め本来の目的は、古い投稿の行を新しく現行に戻さないことです。この目的は崩しません。
  - 再解析でも、現行ではなかった行まで現行にはしません。
- 削除・取り消し（`revival_guard=False`）の呼び出し（`v102_transcription_svc.py:382`、`reextract_v6_with_v102.py:764`）の挙動は変えません。

## 5. テスト

- `backend/tests/test_adr1032_revival_guard.py`（12 件）に、次の回帰テストを足します。
  - 古い投稿を同じ商品で再解析しても、現行のままになる。
  - 古い投稿を商品付け替えで再解析すると、付け替え後の行も現行になる（§2 で PO が「戻す」と決めた場合）。
  - もとから現行でなかった古い行は、再解析しても現行にならない（復活止めが生きている）。
  - 削除・取り消し（`revival_guard=False`）の既存挙動が変わらない。
- 既存の ADR-158 系のテストも通します。`make check` を流します。

## 6. 進め方・運用

1. `docs/ai-agents/executor-checklist.md` と `docs/STANDARD-WORKFLOW.md` を読み、`./scripts/dev/executor-preflight.sh` を実行します。
2. `bash scripts/new-worktree.sh release/<topic> --claude` で作業場所を作り、そこで変更します。
3. ADR-1032 に追記するか、新しい ADR を起案します。起案後は `node scripts/generate-adr-index.js` を流します。
4. `make check` が通ったら、枝を push します。
   - クラウドでは push までです。コード変更の PR は手元で `shingo-cc` 名義で作ります。
   - PR 本文には「### 標準ワークフロー確認」の節を入れます。
5. すでに本番で消えてしまった行の戻し（データ補正）は別作業にします。
   - 本番 DB への書き込みは PO の GO が必要で、クラウドでは行いません。
   - 手元で試し実行し、TRUE に戻る行数を数えてから PO に確認します。ADR-1032 の運用手順と同じです。

- 影響の見積もりは、試し実行の行数で出します。
