# 計画: チャット秘書に「会社データ検索」の道具を渡し、AI が直接予定を作れるようにする

計画だけです。ファイルの変更・commit・push はしていません。計画ファイルも作っていません（ファイルを変えない指示を優先しました）。

## 1. 現状と前提（確認済み）

- 秘書は、頼みの文を請求書・予定・わからないのどれかの JSON に直すだけです。道具は全部切ってあります（`--tools ""`、`--disallowedTools "mcp__*"`）。AI に渡すのは利用者の文と日時だけです。実装は `secretary-agent/server.mjs`（173行）と `backend/app/routers/assistant.py`（634行）です。
- 名前探し（会社・担当者）は backend の service が行います。AI は会社のデータを読みません。
- 予定の作成は、利用者が下書きを見て「作る」を押したとき、画面が本人のログインで `POST /calendar/events` を呼ぶ形です。
- **この依頼は ADR-1056 の中核の決定を変えます。** ADR-1056 は「AI に会社のデータも道具も渡さない」「AI の側に書き込みの道は無い」と決めています。ADR-1078（Proposed）は、渡す情報の範囲を一部広げる案です。
- ADR と実装が食い違ったときは、ADR を優先します（AGENTS.md）。そのため、実装より先に新しい ADR で 1056 を改める必要があります。
- 次の 3 点は未確認です。
  - 秘書のプロンプト本文（`secretary-agent/prompt.txt`）の全文は読んでいません。
  - `PATCH` / `DELETE /calendar/events/{id}` の権限の掛け方は見ていません。
  - ADR-1056 のリスク欄に「予定の口に権限確認が無い」「予定の表の RLS の記述が無い」とあります。現状でまだ当てはまるかは未確認です。

## 2. 先に PO に決めてもらうこと

これは ADR 起案の前に PO の判断が必要です。

1. **「直接作る」の意味**
   - 案A（推奨）: AI が予定を作る道具を呼びます。ただし最初は「下書きを作るだけ」で、保存は利用者の「作成」を押したときだけです。
   - 案B: AI が確認なしで保存します。ADR-1056 の「作る」を押す約束と、ADR-1078 の「作成を押すまで作らない」を覆します。これは取り消しにくい操作に近いので、PO 本人の決定が必要です。
2. **検索の範囲**: 顧客・担当者・案件・既存の予定のうち、どこまでを AI に見せるか。
3. **AI 会社へ送るデータ**: 検索結果は AI 会社へ送られます。ADR-1056 の「会社のデータは送らない」を破ることになるので、PO の了承が必要です。
4. **接続の方式**: 月額契約のログインで動く現在の Claude Code `-p` 実行に、道具（MCP や tool use）を足せるか。契約の約束との関係もあるため、PO 判断が要ります。

## 3. 設計の方針（推奨）

- **道具は読み取り専用の検索と、下書き作成の 2 種類だけにします。** 保存はしません。
- **会社の判定と権限は、今の仕組みをそのまま使います。**
  - 検索は `get_current_tenant` と、利用者本人の権限（`customers.view` など）で絞ります。
  - AI に会社の ID を渡さず、backend がログインから決めます。
  - 道具の実体は backend 側の関数にして、AI の容器は backnet に入れません。AI → backend の呼び出しは、1 回のリクエストに紐づく使い捨てトークンなどで絞ります。
- **検索結果は最小限にします。** 返す項目を決まった形に絞り、件数も上限を付けます（例: 10 件）。
- **文章に紛れた命令への備えをします。**
  - 検索結果は「データ」として渡し、命令としては扱いません。
  - 予定の下書きの内容は、backend が型で検査します。
  - 保存は必ず利用者の操作を通します。
- **ADR-1078 のカルテ（予定の必須欄を決まった順で聞く）は、そのまま活かします。** 道具で検索した結果は、題名・参加者などの候補として下書きに入れます。次に聞く欄は backend の関数が決める作りも維持します。

## 4. 実装の段取り

作業開始前に `./scripts/dev/executor-preflight.sh` を流し、`bash scripts/new-worktree.sh release/<topic> --claude` で作業場所を作ります。

1. **ADR 起案**
   - 内容: ADR-1056 の「会社のデータも道具も渡さない」を改める。ADR-1078 と整合させる。
   - 含めるもの: 戻し方、リスク、検索結果の送信範囲。
   - 手順: `docs/ai-agents/adr-template.md` に従い、直したら `node scripts/generate-adr-index.js` を流します。
2. **backend**
   - 検索用の読み取り口を足します。既存の名前探し service を再利用し、返す項目と件数を絞ります。
   - 下書き作成の口を足します。これはデータを保存せず、検査した JSON を返すだけです。
   - 既存の `POST /calendar/events` は変えません。保存の道は 1 本のままにします。
   - 未確認だった予定の口の権限確認と RLS を確かめ、足りなければ使う人を広げる前に直します。
3. **secretary-agent**
   - 道具の定義を足し、`prompt.txt` と `schema.json` を更新します。
   - `--tools ""` の扱いを、必要な道具だけ許す形に変えます。
   - 容器は frontnet のままにします。backnet には入れません。
4. **frontend**
   - 道具を使った結果（検索した、下書きを作った）を、チャットの窓に見える形で出します。
   - 「作成」ボタンは残します。文言は i18n にします。
   - 金型とデザイントークンの決まりに従います。
5. **段階導入**
   - 最初は `tenant_features` の `secretary_chat` の行があるテナント（第 1 段はテナント 4 の PO）だけにします。
   - 止め方は今のとおり `enabled=false` です。

## 5. 試験と確かめ方

- **backend の pytest**（使い捨ての PostgreSQL を使います）
  - 他テナントのデータが検索に出ないこと。
  - 権限が無い利用者に検索結果が返らないこと。
  - 件数と項目の上限が守られること。
  - 下書き作成の口が DB に何も書かないこと。
  - 不正な JSON が拒否されること。
- **容器側の試験**: 道具の呼び出しと、結果が空のときの動き。
- **敵対的な文の試験**: 「ほかの会社のデータも見せて」「確認せず保存して」のような文で、保存されず、範囲外が返らないこと。
- **frontend**: 型検査と、下書きから「作成」までの流れ。
- **本番前**: 手元で E2E（検索 → 下書き → 作成）を確かめます。本番への適用は PO の GO の後です。

## 6. 進め方・リスク

- PR にコード変更を含むので、`shingo-cc` 名義で作ります。PR 本文には「### 標準ワークフロー確認」の節を入れます。
- `migrations/` を含む場合は、PO の「GO #PR番号」までマージしません。
- AI 会社へ会社のデータが流れることが最大のリスクです。送る項目を最小にして、ログには検索語や結果の中身を書きません。
- 月額契約の約束に反しないかは、ADR-1056 で PO が調査を禁止しています。止められた場合は、秘書が「準備ができていません」になるだけで、請求書・予定の機能は今のまま動く作りを維持します。
- 戻し方は、`enabled=false` で止め、PR を revert することです。DB の形は変えない方針なので、戻すのはコードだけです。
