# 計画: 再解析で古い投稿の行が消える件を直す

ファイルの変更・commit・push はしていません。

## 結論（調査の事実）

- **原因の候補**: `backend/app/services/tcg_analyzer_svc.py:2119-2139` の `ranked` にある ADR-1032「復活止め」です。再解析で行の (商品, 状態) の組が変わるか行が新しく作られると、その行は「前から現行だった行」に数えられません（`was_current`、2070-2075行）。同じ仕入元のより新しい投稿に同じ商品の行があれば `is_current=FALSE` になり、配信から消えます。
- **これは仕様です**。ADR-1032 は PO 決定（2026-10-19「n」）に基づきます。追記（2026-10-23）では、商品を付け替える再判定でも同じ扱いにすると PO 2026-10-22「1」で決めています。
- つまり、直すのは不具合修正ではなく **PO 決定の変更**です。AGENTS.md の決まりでは、ADR が実装より優先します。コードを先に変えず、ADR 改訂を先にします。
- **未確認**: 本番データの実際の消え方は未確認です。コード上の挙動は ADR の記述と一致しますが、どちらの形で消えているかは見ていません。
  - `received_at` が NULL の投稿の扱い
  - `condition_id` が NULL の行の扱い（`tt.condition_id = ar.condition_id` が NULL では一致しないので、そもそも付け直しの対象外になる疑い）

## 決めてもらうこと（着手前の PO 確認）

どこまで戻すかで、変えるものが違います。**案 A を推奨**します。

- **案 A（推奨・最小）**: 再解析の前に現行だった行は、組が変わっても現行のままにする。
  - 控え（`prior_pids`/`prior_cids`）を (商品, 状態) の組ではなく、行の識別（`extraction_item_id`）で持つ。
  - 「新しい投稿に隠れていた行は再解析で戻さない」は守ります。
  - ただし 2026-10-22 の PO「1」（付け替え後は現行にしない）を覆します。
- **案 B（広く戻す）**: 復活止めの条件 (i) を弱めるか外し、古い投稿の行も組ごとの最新なら現行に戻す。
  - 9/25 の規則と PO「n」の決定を覆します。
  - ADR の「選ばなかった案」で、配信が広く動き K2（痕跡の無い行の変化 0）を守れないとされています。
- **案 C**: 仕様どおりとし、対象の行だけを `02_apply.sql` 方式で個別に直す。コードは変えません。

## 手順（案 A の場合）

1. **ADR**
   - `docs/adr/ADR-1032-current-row-revival-guard.md` に追記します。または新 ADR を起案します（`docs/ai-agents/adr-template.md` に従う）。
   - 内容は What 2 / (ii) を「行の識別で判定する」に改め、2026-10-23 追記の扱いを置き換えることです。
   - その後 `node scripts/generate-adr-index.js` を実行します。
   - PO の承認を得てから実装に入ります。
2. **作業場所**
   - `./scripts/dev/executor-preflight.sh || exit 1` を実行します。
   - `bash scripts/new-worktree.sh release/current-row-keep-on-reanalysis --claude` で作業場所を作ります。
   - `docs/ai-agents/executor-checklist.md` と `docs/specs/line-analysis-tuning/README.md` も読みます。
3. **コード（`tcg_analyzer_svc.py`）**
   - 控えの渡し方を、組から行の識別（`analysis_results.id` か `extraction_item_id`）に変えます。
   - `was_current` は `ar.id`（または item）が控えに入っているかで判定します（2070-2075行）。
   - 控えを渡す側も直します。v102 の再解析 `line_analysis_v102_svc.py`、`reextract_v6_with_v102.py`、`v102_transcription_svc.py`（いずれも ADR-1032 を参照）です。
   - 件の削除と取り消しでは控えを切る既存の決まり（ADR-158 G5）は変えません。
4. **テスト（`backend/tests/test_adr1032_revival_guard.py` を拡張）**
   - 再解析で組が変わっても、前から現行の行は現行のまま残ること。
   - 隠れていた行は戻らないこと（R1・R3a の維持）。
   - 控え無しの全付け直しで変化 0（冪等）が保たれること。
   - 削除した件の次点を戻す G5 が保たれること。
   - 商品の付け替えで、同じ仕入元の新しい投稿に同じ商品がある場合の新しい期待値。
   - `condition_id` と `received_at` が NULL の場合の挙動を固定します。
5. **既に消えた行の回復（別便）**
   - 本番 DB には直接書きません。クラウドでは SQL を流さず、監査行つきの SQL を書くだけにします。
   - 試し実行（ROLLBACK）で TRUE に戻る行を数え、PO に聞いてから本実行します。本実行は手元で PO の GO の後です。
   - 626 件の未確認の行は、判定できるまで触りません（ADR-1032 の方針）。
6. **commit・push・PR**
   - commit 前に `make lint` と `make check` を通します。
   - `release/*` 枝に push します（`--no-verify` は使いません）。
   - コード変更の PR は手元で `shingo-cc` 名義で作ります。PR 本文に「### 標準ワークフロー確認」を入れます。
   - マイグレーションは不要です。そのため「GO #PR番号」の対象外ですが、ADR 改訂には PO 承認が要ります。

## 確かめ方

- pytest（上の 4）を、使い捨ての localhost PostgreSQL で流します。
- サンドボックス `docs/handoff/revival-guard/sandbox/` で、現行 SQL と案を同じ入力で比べ、変わる場面だけが変わることを確認します。
- 本番反映後は ADR-1032 の K1〜K5 と同じ形で確認します。
  - 仕入元ごとの行の状態の要約を前後で比べる。
  - 再解析の後、FALSE→TRUE が想定した行だけであること。
  - 隠れていた行が戻っていないこと。
  - 配信の期間 48 時間の内側の行だけが配信に影響すること。

## リスク

- 案 A は 2026-10-22 の PO 決定を覆します。付け替え再判定の運用手順（試し実行で TRUE→FALSE を数えて PO に聞く）も要らなくなるか、変わります。
- 現行の行が増えるため、配信が広く動く可能性があります。試し実行で件数を出してから進めます。

案 A、B、C のどれにするかを決めてください。決まれば、ADR 改訂から着手します。
