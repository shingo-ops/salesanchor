# 計画: Discord 連携失敗時の画面文を例外メッセージそのままにする

## 先に確認したいこと（ADR との衝突）

調査では、この依頼は `docs/adr/ADR-1071-plain-language-error-messages.md` と食い違う可能性があります。調査担当は、例外の中身を応答に入れる箇所を ADR-1071 違反としていました。私は ADR 本文をまだ直接読んでいません。

`AGENTS.md` では ADR と実装が食い違ったら ADR を優先します。実装前に次の2点を決める必要があります。

- ADR-1071 の本文を読み、例外の露出が禁じられているかを確かめる。
- 禁じられているなら、「そのまま出す」案は ADR の改訂が先になります。ADR の起案は PO（しんごさん）の判断です。

  - 依頼の方向に近いのは、この2箇所だけです。

## 推奨案: 例外をそのまま出さず、原因を分かりやすく出す

「原因が分かりやすい」ことが目的なら、生の例外文は向いていません。

- Discord API やライブラリの例外文には、URL、ヘッダ、トークンの断片が混ざることがあります。画面に出すと秘密の漏えいになります。
- 英語の技術文が顧客に見えます。ADR-027 の i18n 方針にも反します。

そこで次の形を推奨します。

1. **サーバー側**
   - 例外の種類を理由コードに分類します。例は、権限不足、ボットが未参加、レート制限、接続断、トークン無効です。
   - `discord_oauth.py` の理由コード方式を、未移行のルーターにも広げます。
   - 例外の生の文は、秘密をマスクしてサーバーログに残します。
   - 応答には短い問い合わせ用の ID を付けます。
2. **画面側**
   - 理由コードごとに `discordConnect.error.*` の i18n キーを足します（ja/en）。
   - 未知のコードでは、汎用文に問い合わせ用 ID を添えます。
3. **既存の漏えい箇所の修正**
   - `discord_auto_setup.py:166` と `:718-727` から `{exc}` を外し、理由コードに置き換えます。

## 「そのまま出す」を貫く場合（PO が選んだとき）

- ADR-1071 を改訂します（PO 起案）。
- 出す前に、秘密のマスク処理を必ず通します。調査では共通のマスク関数を確認できなかったので、新設が必要かもしれません。
- 例外の文を出すのは管理者向けの画面に限ります。
- `error_detail_baseline.json` と ADR 検査を、改訂に合わせて更新します。

## 実装の手順（承認後）

1. `docs/INDEX.md` の手順に従い、`executor-checklist.md` を読み、`bash scripts/new-worktree.sh release/discord-error-messages --claude` で作業場所を作る。
2. ADR-1071 と `backend/AGENTS.md`、`frontend/AGENTS.md` を読み直す。
3. 例外から理由コードへの分類関数を足す。
4. 対象ルーターを順に移行する。まず `discord_auto_setup.py` の2箇所、その後 `discord_own_server.py` などを移す。
5. ja/en の文言とフロントの対応表を足す。
6. テストを足す。
   - バックエンドでは、例外の中身（秘密を模した文字列）が応答に出ないことを確かめます。
   - フロントでは、各理由コードの表示を確かめます。
   - あわせて `error_detail_baseline.json` を更新します。
7. `pre-push` の検査を通してから push する。PR は手元で `shingo-cc` 名義で作る。

## 確認方法

- backend と frontend のテストを実行し、例外を起こした応答に秘密を模した文字列が含まれないことを確認する。
- 開発環境で、権限不足やボット未参加などの失敗を起こし、画面の文を目で確認する。

## PO に決めてほしいこと

- 方針は、理由コードで分かりやすく出す案（推奨）と、例外文をそのまま出す案（ADR 改訂が必要）のどちらにしますか。
- 移行の範囲は、`discord_auto_setup.py` の2箇所だけにするか、未移行のルーター全部にするか。
