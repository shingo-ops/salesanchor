# 計画: チャット秘書に「会社データの検索」と「予定の直接作成」を持たせる

## 1. 現状（調べて分かったこと）

- 秘書は、容器 `secretary-agent` で Claude Code を `-p` 実行する作りです。道具は全部切ってあります（`--tools ""`・`--disallowedTools "mcp__*"`）。
- AI に渡すのは、利用者の文、日時、決まり帳（ADR-1077）、予定の途中の状態（ADR-1078）だけです。会社のデータは渡していません。
- 名前の検索は backend の `resolve_names`（`backend/app/services/secretary_resolve.py`）が行っています。検索は AI の返答の後です。AI は検索の結果を見ません。
- 予定の作成は、画面が下書きを見せます。利用者が「作る」を押すと、画面が `POST /calendar/events` を利用者本人のログインで呼びます。AI に書き込みの道はありません。
- 道具を使った合図が出たら答えを捨てる検査もあります（`tool_used`）。
- この作りは ADR-1056 の決定そのものです。K4（他社に触れない）は「AI にデータも道具も渡さない」ことで成り立っています。今回の依頼は、この決定を 2 点とも変えます。

  | 変える点 | 今の決定 |
  |---|---|
  | データを渡す | 渡さない |
  | AI が直接作る | 「作る」を押すまで作らない |

- そのため、先に ADR で PO の決定を取る必要があります。ADR-1056 と ADR-1078 の「Amended by」の形になります。

## 2. 方針（推奨案）

AI に DB 接続や書き込みの鍵は渡しません。代わりに、backend が持つ「検索」と「作成」の 2 つの口を、AI からの呼び出し（tool call）として公開します。権限と会社の範囲は、これまで通り backend が利用者本人のログインで判定します。

- **経路**: 容器は frontnet のままにして、backnet には入れません。
  - 容器から backend の内部専用の口へ、1 回限りの短寿命の許可証を付けて呼びます。
  - 許可証には、会社・利用者・許される操作を入れます。
  - 容器が保持する権限は、これだけです。
- **検索の道具** `search_company_data`
  - 対象は、最初は会社・担当者・予定の読み取りだけにします。
  - 範囲は今のログインの会社だけです。RLS と `get_current_tenant` をそのまま使います。
  - 結果は件数上限（5 件）と項目の絞り込みをかけます。メモなどの自由記述は返しません。
- **予定作成の道具** `create_calendar_event`
  - backend が今の `POST /calendar/events` と同じ関数を呼びます。呼ぶのは本人の権限でです。権限確認・監査ログ・変わった合図が今のまま効きます。
  - Google Meet は `can_add_meet` の判定 1 か所のままです。

## 3. 「勝手に作る」ことへの安全策（PO の決定が要る点）

AI が直接作れるようにすると、頼みの文に紛れた命令でも作られるおそれが出ます。次の 2 段階を提案します。

- **既定**: AI は「作成案」を返すだけです。backend が下書きとして保持し、画面で「作る」を押すと作成します。今の ADR-1056 の安全性に近い形です。
- **自動作成（オプション）**: 次の条件をすべて満たすときだけ、押さずに作ります。
  - 自分だけに見える予定
  - 会社名・担当者名の確認が不要
  - 1 回の頼みで 1 件まで
  - 作成後すぐに「取り消し」ボタンを出し、その予定だけを削除できる

どちらを既定にするかは PO に聞きます。私の推奨は、最初は既定の「下書き → 作る」だけにして、自動作成は本番の観察後に足す、です。

## 4. 手順（段階）

1. **ADR 起案（docs のみ）**
   - ADR-1056 と ADR-1078 を改める新しい ADR を書きます。次の点を含めます。
     - 渡すデータの範囲
     - 道具 2 つ
     - 許可証の仕様
     - K4（他社に触れない）の代わりの検証
     - 戻し方
   - PO の承認を待ちます。承認が出るまで実装はしません。
2. **backend の内部の口と許可証**
   - 追加先は `backend/app/routers/assistant.py` の隣に新しい router です。
   - 許可証の発行と検証は新しい service にします。
   - 検索は `secretary_resolve.py` の読み取りの作りを広げて再利用します。
   - 作成は `calendar` router の作成関数を共通化して呼びます。
3. **容器 `secretary-agent`**
   - `server.mjs` と `compose.mjs` で、道具を「許可した 2 つだけ」に絞ります。
   - `prompt.txt` と `schema.json` を更新します。
   - 既存の `tool_used` 検査は、許可した道具だけを通すように変えます。
   - その他の道具・`mcp__*` は引き続き切ります。
4. **画面**（`frontend/src/features/secretary/`）
   - 検索結果の根拠の表示を出します。
   - 作成した予定の取り消しの表示を出します。
   - 文言は i18n（ADR-027）に入れます。金型は `frontend/AGENTS.md` と `CC_UI_GOVERNANCE.md` に従います。
5. **台帳と上限**
   - 道具の呼び出しを `llm_usage_events` と秘書のログに記録します。
   - 1 回の頼みあたりの道具の呼び出し回数と時間に上限を設けます。
6. **使える人**
   - 今のまま、`secretary_chat` の行があるテナント 4 の PO だけにします。広げるのは別の判断です。

## 5. 確認方法

- **pytest**: 許可証の期限切れ・別テナント・操作外のはすべて拒否されること。検索は他テナントを返さないこと。作成は権限のない人では 403 になること。
- **容器の試験**: 許可していない道具は呼べず、`tool_used` 相当で捨てられること。容器から DB への接続は引き続き失敗すること。
- **K4 の再検証**: 004 で「001 の予定を見せて」などを 10 問、逆も 10 問試し、他社の値が 1 つも出ないこと。
- **本番相当の通し確認**
  - 「明日 10 時に〇〇社と打ち合わせを入れて」で、検索の結果が下書きに入ること。
  - 「作る」で予定が 1 件だけ増えること。
  - 押さなければ 0 件であること。
  - 取り消しで消えること。
- **品質チェック**: `make check`、frontend のテストを通します。

## 6. リスクと戻し方

- **リスク**
  - 利用者の文に紛れた命令で、検索結果が AI に渡ります。AI 会社へ送られるデータの範囲が広がります。
  - 月額契約の使い方の問題が、今より重くなります。
  - 予定の口には権限確認が無く、予定の表の RLS の記述も無い点は、ADR-1056 に既知のリスクとして書かれています（予定の作成のあとの会社の文脈の張り直し漏れも）。道具を足す前に確かめて直します。
- **戻し方**
  - `tenant_features` の `secretary_chat` を無効にするか、新しい機能フラグを切ります。
  - 道具の許可リストを空にすれば、今の動きに戻ります。
  - 新しい表を作らない設計なら、データの戻しはありません。

## 7. 進め方のルール（このリポジトリの決まり）

- 作業前に `bash scripts/new-worktree.sh release/<topic>` で作業場所を作ります。
- `executor-preflight.sh` を流します。
- migration を足す場合は `deploy.yml` への登録が必須です。
- migration を含む PR は PO の「GO #PR番号」が出るまで main にマージしません。
- コード変更の PR は `shingo-cc` 名義で作ります。ただしクラウドでは push までです。
- PR 本文に「### 標準ワークフロー確認」の節を入れます。
