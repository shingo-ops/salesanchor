# 計画: 再解析で古い投稿の行を現行に戻す

調査は読み取りだけで行い、ファイルの変更・commit・push はしていません。

## 結論

今の動きは不具合ではなく、PO が決めた方針どおりです（ADR-1032「復活止め」）。そのため、コードを直す前に ADR の改訂が要ります。AGENTS.md の「ADR と実装が食い違うときは ADR を優先」に従い、ADR を先に直してからコードを合わせます。

## 原因（確認済み）

- 再解析の最後で `_merge_supplier_products` を呼んでいます（`backend/app/services/line_analysis_v102_svc.py:1640`）。このとき `revival_guard` は既定の True です。
- True の場合、次の行は FALSE のままになります（`backend/app/services/tcg_analyzer_svc.py:2122` 付近）。
  - 組（商品×状態）で最新の投稿の行である。
  - 同じ仕入元のより新しい投稿に、同じ商品の行がある。
  - 再解析の前から現行ではなかった。
- つまり、新しい投稿に隠れていた古い投稿の行は、再解析しても現行に戻りません。画面から消えたように見える行は、削除されたのではなく `is_current=FALSE` になっています。
- 件の削除と取り消しは、すでに `revival_guard=False` で動いています（`v102_transcription_svc.py:383`、`reextract_v6_with_v102.py:764`）。

## 手順

1. **PO に決めてもらうこと（コードを書く前）**
   - 「古い投稿の行も現行に戻す」とは、どこまでを指しますか。
     - (a) 組ごとに最新の投稿の行なら戻す。ADR-158 の規則は保ち、復活止めだけやめる。
     - (b) 同じ商品に新しい投稿があっても、古い投稿の行を現行にする。ADR-158 の規則そのものを変えるため、2026-10-19 の PO の決定（「n」）を覆すことになります。
   - 戻す範囲は、再解析全般ですか。それとも `reanalyze_v102_job` など一部の経路だけですか。
   - 推奨は (a) を再解析全般に適用することです。最小変更で済み、ADR-158 の規則も保てます。
2. **作業場所を作る。** `bash scripts/new-worktree.sh release/reanalysis-restore-current --claude` を実行し、`./scripts/dev/executor-preflight.sh` を通します。
3. **ADR を改訂する。** ADR-1032 に追記するか、新しい ADR を起案します。起案は PO の担当です。
   - 変える点と、変えない点（ADR-158 の「組ごとに最新」）を書きます。
   - 「承知の上の性質」の節と、K5 の確認項目を直します。
   - 直したら `node scripts/generate-adr-index.js` を実行します。
4. **コードを直す（案 a の場合）。**
   - `line_analysis_v102_svc.py:1640` を `revival_guard=False` にします。
   - `reextract_v6_with_v102.py` の再抽出で同じ経路を通るか確認し、そろえます。
   - `revival_guard` の引数自体は消しません。削除経路が使っています。
5. **テストを直す。** `backend/tests/test_adr1032_revival_guard.py` に、復活止めを前提にしたケースがあります（R1・R3a など）。これを「再解析で戻る」期待に書き換え、削除経路が従来どおりであることを確かめるテストは残します。
6. **本番にある既存データの扱いを PO に確認する。**
   - ADR-1032 の運用で、確認済みの 2 行（349eaef0・f61f1ea7）を SQL で FALSE にしています。
   - 方針を変えると、再解析のたびにこの 2 行が TRUE に戻ります。戻ってよいか、戻さないための措置が要るかを確認します。
   - 未確認の 626 件は、再解析した分だけ現行に戻ります。配信への影響を試し実行で数えます。

## 確かめ方

- `make check` を実行します（ruff・bandit・mypy・pytest）。
- 使い捨ての PostgreSQL 上の pytest で、次の 3 点を確認します。
  - 新しい投稿に隠れた古い投稿の行を再解析すると、案 a の範囲で現行に戻る。
  - 件の削除は従来どおり動く（ADR-158 の G5）。
  - すでに現行の行は変わらない（冪等）。
- 本番での確認は、PO の GO のあとに手元で行います。クラウドでは本番に書き込みません。

## 進め方の注意

- クラウドではコード変更を `release/*` の枝に push するところまでにします。PR は手元で `shingo-cc` 名義で作ります。
- PR 本文には「### 標準ワークフロー確認」の節を入れます。
- 配信の期間は 48 時間（`tcg_distribution_svc.py:217-227`）です。古い投稿の行が戻っても、その期間より前の投稿なら配信には出ません。この点は影響の見積もりに使えます。
