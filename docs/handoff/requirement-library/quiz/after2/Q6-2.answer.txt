# migration のロック待ちを 30 秒にする計画

結論から言うと、現状のまま「30 秒に延ばす」のは勧めません。ADR-1037 の決定と正面からぶつかるためです。実際に変えるなら、先に PO が ADR を改訂する必要があります。

## 1. 現状（確認済み）

- ロック待ちの値は `scripts/run_all_migrations.sh:223` の `SQL_LOCK_TIMEOUT="${SQL_LOCK_TIMEOUT:-1s}"` が正本です。
  - SQL の migration（`run_sql`）は `PGOPTIONS=-c lock_timeout=…` で反映されます（295 行目）。
  - Python の migration（`run_py`）は `MIGRATION_LOCK_TIMEOUT` 経由で `scripts/migration_py_entry.py` が反映します。
- ロックで落ちたファイルは、3 秒あけて流し直します。再試行は全体で合計 40 回までです。
- 設計の根拠は `docs/adr/ADR-1037-migration-lock-timeout.md` です。

## 2. 30 秒にする場合の問題点

1. **ADR-1037 と矛盾します。**
   - ADR は、待ちを最大 1 秒にすることで、入れ替え中の在庫表を止めない（成功条件 K1・K7）と決めています。
   - 無制限に待たせたとき、後から来た読み取りが 8912ms 待たされたと記録されています。
   - 本番では 10/19 に在庫表の平均が最大 13.5 秒になりました。
   - AGENTS.md の「ADR と実装が食い違ったら ADR を優先する」に従うと、まず ADR を直すことになります。ADR 起案は PO の役割です。
2. **打ち切り時間を超えます。**
   - 現在の 40 回 ×（待ち 1 秒＋間隔 3 秒）＝160 秒は、10 分の打ち切りに収まっています。
   - 30 秒にすると 40 ×（30＋3）＝1320 秒になり、`deploy.yml` の `command_timeout: 10m` を超えます。
   - 超えた場合は、ロック競合が続いた末に打ち切られ、失敗の仕方が悪くなります。
3. **失敗の原因は待ち時間とは限りません。**
   - 直近の記録では、`082_extend_products_box_attributes.sql` が約 38 秒、products の鍵を離さない接続に当たって失敗しています。
   - 鍵を持ち続ける接続が原因なら、30 秒に延ばしても通りにくく、待っている間の読み取り停止だけが増えます。
   - 今回の失敗が「どのファイルが、誰の鍵で、何回目の再試行で落ちたか」は未確認です。

## 3. 推奨する進め方

**手順 0: 原因の特定（先にやる）**
- 失敗した Deploy to VPS のログで、次の点を確認します。
  - `lock conflict; retry` と `retry limit reached` の回数
  - `lock holders` の出力（鍵を持っていた接続）
  - 落ちたファイルが `SET LOCAL lock_timeout = '5s'` を持つ 8 ファイルのどれかか（ADR で対象外のもの）
- 次のどれに当たるかで対策が変わります。
  - **A. 一時的な競合が多いだけの場合:** 再試行の間隔か回数を調整すれば足ります。ロック待ちは 1 秒のままで済みます。
  - **B. 長い鍵の持ち主がいる場合:** 持ち主（`ai_reader` や celery など）側を直します。
  - **C. 本当に 30 秒待たないと通らない場合:** 手順 1 以降に進みます。

**手順 1: PO の承認と ADR 改訂（C の場合のみ）**
- ADR-1037 の What 1・3 と成功条件を、追記または改訂します。
  - 次の 2 点を PO が判断します。
    - 読み取りの待ちを最大 30 秒まで許すか
    - 全体を 30 秒にするか、「最初は 1 秒、失敗が続いたら延ばす」段階方式にするか
  - 段階方式なら K1・K7 を守れます。私の推奨は段階方式です。
- 改訂後は `node scripts/generate-adr-index.js` で索引を更新します。

**手順 2: 実装（承認後）**
- `scripts/run_all_migrations.sh` の `SQL_LOCK_TIMEOUT` を `30s` にします。
  - 1 行の変更で `run_sql` と `run_py` の両方に効きます。
- 打ち切り時間と整合させます。次のどちらかを選びます。
  - `SQL_RETRY_BUDGET` を減らす（例: 全体の上限を 10 回程度にして最悪でも約 330 秒に収める）
  - `deploy.yml` の該当 `command_timeout` を延ばす
- `log_lock_holders` の「xact > 1s」は、30 秒運用では見る範囲が狭すぎる可能性があります。必要なら閾値を見直します。

**手順 3: 試験の更新**
- `tests/sandbox/migration-run-sql-retry.sh`（K1 は「1.5 秒以内」を前提にしています）
- `tests/sandbox/migration-read-probe.sh`
- `.github/workflows/migration-test.yml` の P1 などで 1 秒前提の判定
  - これらは新しい値に合わせて直します。

## 4. 必要な手続き

- 作業場所は `bash scripts/new-worktree.sh release/<topic> --claude` で作ります（AGENTS.md「ブランチと作業場所」）。
- 作業前に `./scripts/dev/executor-preflight.sh` を実行します。
- PR は `shingo-cc` 名義で作ります。
- `scripts/` や `deploy.yml` を含む PR は、PO の「GO #PR番号」が出るまで main にマージしません（ADR-135・136）。
- `SET LOCAL lock_timeout='5s'` の 8 ファイルのうち DROP を含む 2 本は、変更する場合に PO 本人の GO が必要です（ADR-1003）。今回の計画では触りません。

## 5. 検証

- sandbox 試験（`migration-run-sql-retry.sh`）と `migration-test.yml` の S1〜S3・P1〜P3 が通ること。
- 入れ替え後、次の 3 点をログで確認します。
  - 失敗が 0 回であること
  - `retry limit reached` が 0 回であること
  - `read probe` の `slow=0` が維持されていること。slow が出たら、延ばした 30 秒が読み取りを止めているので、1 秒に戻すか段階方式にします。

## 6. PO への確認事項

1. 失敗のログから、手順 0 の A・B・C のどれに当たるかを確認してよいか。
2. C の場合、ADR-1037 の「最大 1 秒」を緩めることを承認するか。
3. 30 秒を一律にするか、段階方式にするか。
