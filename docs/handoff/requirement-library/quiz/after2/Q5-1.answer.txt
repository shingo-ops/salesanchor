# backend Python 3.12 → 3.13 への版上げ計画

ファイルの変更・commit・push はしていません。このあとの実装は、別の枝で行う前提です。計画ファイルも作っていません（ファイルを作らない指示を優先しました）。

## 先に PO 確認が要る点（最重要）
- **ADR-1022 と食い違います。** ADR-1022（Proposed）は「3.12 のまま作り続け、2027 年 10 月までに本番・CI・手元を一度に 3.14 へ上げる」と決めています。手元だけ・本番だけを先に上げることも禁じています。設計の開始は 2027 年 7 月が目安です。
- 3.13 へ上げるのは、この決定の変更にあたります。AGENTS.md の「ADR 優先」により、実装前に ADR-1022 の改訂（または新しい ADR）が必要です。起案と承認は PO（しんごさん）の判断です。
- 次の 3 つの選択肢があり、PO に決めてもらいます。
  - **A**: ADR を改訂して 3.13 を挟む。3.14 への期限（2027 年 10 月）は残します。
  - **B**: 3.13 を飛ばして、ADR どおり 3.14 を目指す。
  - **C**: 期限を前倒しして、3.14 に一本化する。
- 私の推奨は B か C です。版上げを 2 回やる手間が省けます。3.13 の公式のサポート終了は 2029 年 10 月ごろで、3.12 の 2028 年 10 月まで余裕があります（日付は私の知識によるもので、**未確認**。ADR-1022 は devguide の値を 2026-10-16 に取得したと書いています）。
- 以降の手順は、PO が A を選んだ場合の計画です。

## 現状（調べた事実）
- 3.12 の固定箇所は次のとおりです。
  - `backend/Dockerfile:1` の `FROM python:3.12-slim`
  - `backend/pyproject.toml` の ruff `target-version = "py312"`（4 行目）と mypy `python_version = "3.12"`（31 行目）
  - `.github/workflows/` の約 20 本（`test.yml`、`migration-test.yml`、`schema-check.yml` など）の `python-version: '3.12'`
  - `migration-test.yml:2345` の `docker run ... python:3.12-slim`
  - `pmg-cutover-probe.yml:30` の `python3.12`
  - `monitoring/*/Dockerfile` の 2 つ、`scripts/rehearsal_phase2.sh:205`、`scripts/test_rollback_simulation.sh:135`
  - `scripts/dev/check-before-submit.sh:458` の表示文
  - 手元の見張り（`python_version_guard.py`、`cloud/test.sh` の B4/B4b、`rules.yml:919`、`docs/ai-agents/dev-commands.md`、`docs/handoff/py312-guard/`）
- 依存は `backend/requirements.txt` と `requirements-dev.txt` にあります。
- 3.13 で動くかを確かめる必要がある依存は、`asyncpg`、`psycopg2-binary`、`Pillow`、`lxml`、`bcrypt`、`cryptography`、`argon2-cffi`、`maxminddb`、`pydantic` 2.10.6、`sqlalchemy` 2.0.38、`uvicorn[standard]` 0.34.0、`hiredis`、`discord.py` 2.4.0 です。
- `discord.py` と `google-generativeai` は古い系統です。3.13 での対応は**未確認**です。
- 3.13 の影響点も未確認です。
  - 3.13 では標準ライブラリの `cgi`、`crypt`、`telnetlib` など「dead batteries」が削除されました。
  - `audioop` も削除されました。`discord.py` 2.4.0 が `audioop` を使うため、これが影響する可能性があります。後継の `audioop-lts` などで対応できるか調べます。

## 手順
1. **決定**: PO が A/B/C を選び、ADR を改訂します（`ai-agents/adr-template.md` に従う）。ADR を直したら `node scripts/generate-adr-index.js` を流します。
2. **作業場所**: `bash scripts/new-worktree.sh release/python-3-13 --claude` で作ります。作業前に `./scripts/dev/executor-preflight.sh` を流します。
3. **recon（調査のみ、変更なし）**
   - 3.13 の使い捨て venv に `requirements.txt` と `requirements-dev.txt` を入れ、ビルドが通らない依存を洗い出します。
   - その環境で `make lint-ci` を流します。
   - 非推奨や削除された標準ライブラリを `grep` で探します（`cgi`、`audioop`、`imp`、`distutils`、`asyncore` など）。
   - 通らない依存は、版を上げるか代替を使うかを決めます。
4. **依存の更新**: 3.13 に対応する版へ上げます。`pip-audit` も流します。上げる版は recon の結果で決めます。
5. **設定の更新**
   - `backend/Dockerfile` を `python:3.13-slim` にします。
   - `pyproject.toml` の `py313` と `3.13` を直します。
   - 全 workflow の `python-version` を直します。ただし `.github/workflows/workflow-lint.yml` は不可逆操作の一覧に入っているため、触れません。
   - 手元の見張りの許可を 3.13 にします。ADR-1022 の「許可を設計で変える」の手続き（design.md §6 R2）に従います。
   - `docs/ai-agents/dev-commands.md` や `check-before-submit.sh` の表示文も直します。
6. **検証**: 下の「検証」を実施します。
7. **PR と配備**: PR 作成は `shingo-cc` 名義にします。本文に「### 標準ワークフロー確認」を入れます。`deploy.yml` や `scripts/` を含む場合は、PO の「GO #PR番号」までマージしません。

## 検証
- `make lint-ci`（ruff / bandit / mypy）を 3.13 で通します。
- `make check`（pytest、カバレッジ 60% 以上）を、Docker の postgres と redis を立てて通します。
- `test.yml`、`migration-test.yml`、`schema-check.yml` などの CI が全部緑になることを確認します。
- 3.13 の Docker イメージをビルドして起動し、`/api/health` と `/metrics` を確認します。
- Celery worker と Discord Gateway worker（`app.discord_gateway.main`）の起動を確認します。
- 発注書 PDF（reportlab）と画像処理（Pillow）の出力を、3.12 と見比べます。
- 本番の前に、リハーサル環境（`docs/handoff/rehearsal-env/`、`scripts/rehearsal_phase2.sh`）で通しで動かします。

## リスクと戻し方
- ADR-1022 は 3 つ（本番・CI・手元）を一度に上げると決めています。そのため、一つの PR にまとめます。CI と手元の見張りも同時に切り替えます。
- 戻し方は、PR を revert して `Dockerfile` を 3.12 に戻すことです。DB の migration は伴わないので、データへの影響はありません。
- 本番への配備は PO の GO の後に限ります。VPS の直作業はしません。
- 未確認の点（依存の 3.13 対応、`audioop` の影響、3.13 のサポート終了日）は、recon で事実を確かめてから手順 4 以降に進みます。
