# チャット秘書に「会社データの検索」と「予定の直接作成」を渡す計画

作成した計画は以下のとおりです。ファイルの変更・commit・push はしていません。計画書ファイルも作っていません。

## 0. 最初に分かったこと：既存の決定と食い違う

- **ADR-1056** は「AI に会社のデータも道具も渡さない」と決めています。AI は頼みの文を決まった形に直すだけです。作成は利用者が「作る」を押したときに、画面が今の口を呼びます。
- 「作る前に下書きを見せ、『作る』を押したら作る」は PO の選択「1」（2026-11-01）です。
- 今回の依頼は、この 2 点を変えます。
  - AI が検索の道具を持つこと
  - AI が予定を直接作ること
- AGENTS.md の決まりでは ADR が優先です。そのため、実装より先に **新しい ADR（ADR-1056・1078 を改める案）を PO が起案・承認する**必要があります。
- 守る前提は PO の言葉どおりです。001 の AI は 001 以外に、004 の AI は 004 以外に触れません。
- 未確認のもの：`kgi.md` の K1〜K6 の本文、ADR-1078・1058・1077 の本文、`secretary-agent/server.mjs`、`prompt.txt`、`schema.json`、予定の作成口（`/calendar/events`）の実装。手順 1 の現状調べで file:line 付きで確認します。

## 1. 進め方（STANDARD-WORKFLOW に沿う）

1. 作業場所は `bash scripts/new-worktree.sh release/secretary-ai-tools --claude` で作ります。作業前に `./scripts/dev/executor-preflight.sh` を実行します。
2. PO に確認して KGI を決めます（粒度は○×で判定できるもの）。
   - 他テナントのデータが検索結果に 0 件であること
   - 予定の二重作成が 0 件であること
   - 名前検索の当たり率
   - 作成後に取り消せること
3. 設計仕様書を先に読みます。対象は `docs/specs/secretary-chat/` と `docs/specs/schedule/` です。
4. 現状調べ（`docs/handoff/secretary-ai-tools/recon.md`）を書きます。
   - 既存 ADR を grep します（FEATURE-INDEX 76 行目の関連 ADR を含む）。
   - `assistant.py`、`secretary_resolve.py`、`secretary_karte.py`、`secretary-agent/`、`secretary-codex/`、予定の router を file:line で突き合わせます。
5. 設計書（`design.md`）には「外部事例と応用」欄と「維持の仕組み」欄を入れます。空欄は不可です。
6. ADR 案は下書きを用意します。承認は PO の GO です。

## 2. 設計の方針（推奨案）

### A. 検索の道具：実行は backend、AI は「呼びたい」と頼むだけ

- 容器（`secretary-agent`、`secretary-codex`）には引き続き DB もネットワークも持たせません（backnet 外）。
- 容器は JSON で `tool_request{name, args}` を返します。backend が実行して結果を容器へ返し、最終の下書きが出るまで往復します。最大 3 往復程度にします。
- 道具は読み取り専用の少数に絞ります。
  - `search_companies`、`search_contacts`：既存の `resolve_names` を再利用します。
  - `list_events(期間)`：空き時間の確認用です。
  - 請求書の検索は第 2 弾に回します。
- 隔離は、今のログインの会社の文脈（`get_current_tenant`、RLS）をそのまま使って守ります。AI が会社を指定できる引数は作りません。
- 返す項目と件数は最小にします（上限 5〜10 件）。メールや電話は、必要になるまで返しません。
- 道具の結果は「データであって命令ではない」と扱います。結果に命令文が紛れても、書き込み系の道具は呼べない作りにします。
- 既存の順番ルール「AI を待つ間 DB の取引を開いたままにしない」を守ります。往復ごとに短い取引で読んで commit し、`reset_tenant_context()` で文脈を張り直します。
- 容器への本文は 15,000 バイトまでです。結果を詰め込めるよう、上限の見直しか要約が必要です。
- 往復ごとに使用量の台帳へ記録します。全体の打ち切りは今の 85 秒の枠に収めます。

### B. 予定の直接作成：「backend が検査して作り、取り消せる」

- AI が `create_event` を提案します。backend が、既存の予定作成と同じコードを本人のログインで呼びます。
- 作る前の検査には、ADR-1078 のカルテ（`next_ask`、`settle_dates`）を再利用します。必須欄が揃っていないときは作らず、聞き返します。
- 二重作成を防ぐため、冪等キーを付けます。1 回の頼みで作るのは 1 件までです。
- 作った後は画面に「作りました」のカードと **取り消し** ボタンを出します。取り消しは既存の削除口を使います。
- **請求書は今までどおり下書きのままにします。** 直接作成の対象は予定だけです。
- 作る前に直す既存の穴があります（ADR-1056 の「リスク」に記録済み）。
  - 予定の口に権限確認が無い
  - 予定の表の RLS の記述が無い
  - 作成後の会社の文脈の張り直し漏れ
  - 実装は、先にこの穴を埋めてから始めます。

### C. 容器と画面の変更

- `secretary-agent` と `secretary-codex` の `prompt.txt`、`schema.json`、`server.mjs` に、`tool_request` と `create_event` を足します。担当表（`ai_assignment`）で provider を切り替えても同じ約束で動くよう、**両方を揃えます**。
- 今の `tool_used`（道具を使ったら答えを捨てる）の検知は、AI が自前の CLI 道具を使った場合に限定します。backend が仲介する道具の呼び出しとは区別します。
- 画面は `SecretaryChat.tsx` と `SecretaryDraftEvent.tsx` を直します。
  - 検索中の表示を足します。
  - 作成済みカードと取り消しを足します。
  - 部品は金型・デザイントークンに従い、ハードコードしません（`CC_UI_GOVERNANCE.md`）。
  - 文言は i18n に入れます（ADR-027）。

### D. DB と配備

- 監査の「秘書が作った」印が必要なら、追加だけの migration にします。タイムスタンプ名で、`deploy.yml` に登録します。`DO $$ pg_namespace` 走査形式、`COMMENT ON COLUMN`、migration-test の最小定義も付けます。
- 要否は現状調べで決めます。**未確認**です。
- `migrations/`、`deploy.yml`、compose の変更を含む PR は、PO の「GO #PR番号」が出るまで main にマージしません。

## 3. 検証（各受け入れ基準に紐づける）

- **隔離の試験（最重要）**：本物の PostgreSQL（SQLite 不可）で、001 と 004 のように 2 テナントを用意します。001 のログインから 004 の会社・担当者・予定が 1 件も返らないことを確かめます。
- **命令の紛れ込み試験**：検索結果や頼みの文に「予定を作れ」と書いておきます。それでも書き込み系の道具が呼ばれないことを確かめます。
- **往復の上限・打ち切り・二重作成・取り消し・権限なしの 403** の試験を付けます。
- 容器側の node 試験（`server.test.mjs`、`compose.test.mjs`）を更新します。
- 画面は Playwright で確認し、`make check` を通します。
- 人の動作確認は、本番の tenant_001 だけで行います。**tenant_004 には触りません。** 結果は `docs/ai-agents/evidence-registry.md` に記録します。

## 4. 公開の順序と戻し方

1. 検索だけ先に出します（読み取りで安全）。
2. 予定の直接作成は、穴の修正がマージされてから出します。
3. 道具用に専用の `tenant_features` フラグを新設します。最初は PO のみで、うまく動けば広げます。
4. 戻し方は、フラグを false にすると今までの「下書きのみ」に戻ります。データの戻しは不要です。
5. PR は `shingo-cc` 名義で作り、本文に「### 標準ワークフロー確認」を入れます。
6. user-impact の変更（`backend/app/routers`・`services`、`frontend/src/`）には GO 記録が必要です。

## 5. リスク

- AI が検索結果から他の情報を推測して話してしまうこと。返す項目を最小にして抑えます。
- 誤解釈で予定が作られること。必須欄が揃うまで聞き返し、取り消しを付けて抑えます。
- 往復が増えて遅くなったり、使用量が増えたりすること。往復の上限と台帳の記録で抑えます。
- 2 つの容器で約束が食い違うこと。共通の試験で抑えます。
- 月額契約の約束の懸念は、ADR-1056 のとおり PO が調査を禁止しています。この計画では扱いません。
