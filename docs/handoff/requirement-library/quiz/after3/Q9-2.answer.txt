# 計画: チャット秘書に検索の道具を渡し、AI が直接予定を作れるようにする

調査は探索エージェントの報告に基づきます。私自身はファイルを開いて確認していないので、着手時に ADR-1056 と `assistant.py` を読んで裏取りします。ファイルの変更・commit・push はしていません。

## 背景と最大の壁

- 秘書は `backend/app/routers/assistant.py` から別の容器 `secretary-agent`（Claude Code CLI）または `secretary-codex` に HTTP で渡す作りです。backend からは LLM を直接呼びません。
- 今は tool use を使っていません。予定も「下書きを返す → 利用者が『作る』を押す → 本人のログインで `POST /calendar/events` を呼ぶ」という流れです。
- ADR-1056 は AI に道具もデータも渡さないと決めています。AGENTS.md には ADR と実装が食い違ったら ADR を優先するとあります。
- そのため、今回の依頼は ADR-1056 を Amend する新規 ADR と、PO（しんごさん）の承認が先に必要です。実装はその後です。

## 方針

- 設計の中心は、AI に権限を渡さず、既存の本人権限の API を道具として包むことです。
- 道具の呼び出しは backend が仲介します。AI は「この道具をこの引数で」と要求するだけで、実行は常に本人の認証とテナント文脈（`tenant_NNN` スキーマ、`reset_tenant_context`）の中で行います。
- AI が直接予定を作る範囲は段階的に広げます。最初は下書き確認つき、次に低リスクなものだけ確認なし、と進めます。

## フェーズ

### フェーズ 0: 決める（コードは書かない）

1. 新規 ADR を起案します（`docs/ai-agents/adr-template.md` に従う）。
   - ADR-1056 の Amend として、道具を渡す範囲を決めます。
   - 渡すデータの境界を決めます（顧客の個人情報や仕入元の投稿原文は渡さない、など）。
   - 「直接作る」の条件を決めます。
2. PO に承認を取ります。
3. 次の点を先に確認します。
   - 容器側（Claude Code CLI）で道具をどう渡すか。選択肢は、MCP 経由、HTTP で backend に戻る形、backend 側でループを回す形の三つです。容器は同時 1 本で `busy` を返すので、往復が増えると詰まります。
   - `docs/specs/secretary-chat/` の仕様と、ADR-1056 から 1082 までの関連 ADR。

### フェーズ 1: 検索の道具（読み取りだけ）

- 道具の定義を 1 か所にまとめ、名前・引数スキーマ・説明・必要な権限を持たせます。
- 再利用する既存部品は次の二つです。
  - `secretary_resolve.resolve_names`
  - `inventory_search.search_inventory`
- 商品・顧客・案件の検索は、既存のサービス関数を薄く包みます。新しい SQL は書かない方針です。
- 守ること:
  - 返す件数と項目に上限をつける。
  - 本人の権限で見えない物は返さない。
  - 結果は「データ」として AI に渡し、命令として扱わせない（プロンプトインジェクション対策）。

### フェーズ 2: 予定作成の道具（書き込み）

- 既存の `services/calendar_service.py:391` と `routers/calendar.py:431` を呼びます。
- 流れは二段階にします。
  1. 提案: 日時・参加者・件名を検証し、衝突も確認して画面に出す。
  2. 確定: 本人の承認（ボタン）で実行する。
- 「確認なしで直接作る」を認めるなら、次をすべて満たす場合に限ります。
  - 本人の予定だけである。
  - 通知を他人に飛ばさない。
  - 1 回の会話あたりの作成件数に上限がある。
  - 取り消し手段がある。
- 本人のログインで呼ぶので、既存の権限判定がそのまま効きます。
- 削除・変更は今回の範囲に入れません。

### フェーズ 3: 安全装置

- **監査ログ**: `audit.record_audit_log` はあるものの calendar では呼ばれていないため、道具の呼び出しごとに「誰が・どの道具を・どの引数で・結果は」を記録します。ここは新規追加です。
- **レート制限**: 全体の 300 回/分とは別に、秘書専用の上限（会話あたりの道具呼び出し回数、予定作成回数）を設けます。
- **失敗時**: 容器の `busy` やタイムアウトでは、道具が途中で止まっても二重作成しないよう、冪等キーを使います。

### フェーズ 4: 画面（`frontend/src/features/secretary/`）

- 道具の実行状況を表示します（「検索中」「予定を提案しました」）。
- 承認ボタンを出し、直接作成した場合は取り消しボタンを付けます。
- 触る前に `frontend/AGENTS.md` と `CC_UI_GOVERNANCE.md` を読みます。

## テスト（`backend/tests/test_assistant_*.py`、`test_secretary_*.py` のパターンに合わせる）

- 道具ごとの単体テストを書きます。
- テナント越境が起きないこと、権限が無い人に結果が出ないことを確かめます。
- 引数が不正な場合と、結果に命令文が混ざる場合のテストも書きます。
- PostgreSQL 専用のテストは `RLS_TEST_DATABASE_URL` が無いと skip されます。skip を成功と数えないようにします。
- 監査ログとレート制限のテストも書きます。

## 作業の進め方（AGENTS.md の決まり）

- 作業前に `bash scripts/new-worktree.sh release/secretary-tools --claude` で作業場所を作り、`./scripts/dev/executor-preflight.sh` を流します。
- ADR のみの PR は docs-only として出せます。コード変更の PR は `shingo-cc` 名義で作ります。
- `migrations/` を含む場合は PO の「GO #PR番号」までマージしません。監査ログ用のテーブルを足すなら、これに当たります。
- PR 本文には「### 標準ワークフロー確認」の節を入れます。

## 未確認・要判断

- 容器側で道具をどう受け渡すか（MCP か HTTP か）。これが一番大きな設計判断です。
- 「直接作る」をどこまで確認なしにするか。私の推奨は、最初は常に確認ありで出し、運用して様子を見てから本人のみの予定に限って確認なしにすることです。
- 渡してよいデータの範囲。これは PO の判断です。

まずフェーズ 0 の ADR 起案から始めるのがよいと考えます。
