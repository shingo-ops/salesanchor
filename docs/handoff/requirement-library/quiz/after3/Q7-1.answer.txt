# 計画: 再解析で古い投稿の行が現行から消えないようにする

## 先に確認したいこと（実装前に必要）
この計画は、コードと ADR を読んだ範囲で作りました。本番 DB は見ていないので、実際の行が下の原因に当てはまるかは未確認です。

`_merge_supplier_products`（`backend/app/services/tcg_analyzer_svc.py:1981`）は、再解析のたびに古い投稿の行を現行（`is_current`）から外すことがあります。外れるのは、次の 3 条件がそろったときです（同 2117-2140 行）。

- 同じ仕入元に、より新しい投稿があり、同じ商品の行を持っている。
- その行は、付け直しの前は現行ではなかった。
- `revival_guard=True` である（再解析の既定）。

この動きは、ADR-1032 で PO が決めた仕様です（2026-10-19「n」）。商品を付け替える再判定で行が消える場合も、2026-10-22「1」で受け入れ済みです（ADR-1032 の追記）。AGENTS.md には「ADR と実装が食い違うときは ADR を優先する」とあります。このため、そのままコードだけ直すことはできません。

PO に聞くことは次の 3 点です。

1. 消えて困っている行は、次のどちらですか。
   - (A) 新しい投稿に同じ商品があって隠れる行。ADR-1032 の意図どおりの動きです。
   - (B) 商品や状態が変わって、前は現行だったのに消える行。ADR-1032 の 2026-10-23 の追記の動きです。
2. ADR-1032 の方針を変えてよいですか。変えるなら、新しい ADR で置き換えます。
3. 変える場合、(A) と (B) のどちらを戻しますか。

## 進め方（PO が変更を承認した場合）
1. **現状確認（読み取りだけ）**
   - reader 鍵の道（`docs/handoff/ai-readonly-db-path/usage.md`）で、消えた行の仕入元・投稿・商品を調べ、(A) と (B) のどちらかを特定します。
   - 同じ手順を、使い捨ての PostgreSQL 上の pytest で再現します。
2. **ADR を先に起案**
   - 新しい ADR（ADR-1032 を置き換える形）を起案します。PO の承認後に `node scripts/generate-adr-index.js` を実行します。
3. **コード変更**（`release/<topic>` の作業場所を `scripts/new-worktree.sh` で作ってから始めます）
   - **(B) を戻す場合**
     - 「前から現行だった」の判定を、`(商品, 状態)` の組ではなく、行（`extraction_item_id`）単位に変えます。
     - 控えを渡す側（`line_analysis_v102_svc.py:1640` 付近の `after.prior_current`、`reextract_v6_with_v102.py:370`）に、行単位の控えを足します。
     - SQL の `was_current`（同 2053-2058 行）が、その行単位の控えを見るようにします。
   - **(A) も戻す場合**
     - 「より新しい投稿に同じ商品がある」という条件（`NOT EXISTS`）を弱めるか外します。
     - ただし、この条件は 9/25 の「商品×状態ごとに最新が現行」という規則と配信（`tcg_distribution_svc.py:217-227`）に影響します。
     - その影響を ADR に書き、PO の判断を得ます。
   - **削除・取り消しは今のまま**
     - 呼び出し側は `revival_guard=False`（`v102_transcription_svc.py:383`、`reextract_v6_with_v102.py:764`）なので、動きを変えません。
4. **テスト**
   - `backend/tests/test_adr1032_revival_guard.py` を直します。ADR-1032 の旧挙動を固定している箇所（R1・R3a・R3c・R5）は、新しい決定に合わせて直します。
   - 次の場面を足します。
     - 商品を付け替える再判定で、古い投稿の行が現行のまま残る。
     - 全投稿を付け直しても変化が 0 になる（冪等）。
     - 件の削除では ADR-158 の G5 が保たれる。
4. **本番への反映**
   - 既存の行の修正は、監査行つきの SQL で行います。
   - 実行前に、試し実行（ROLLBACK）で FALSE→TRUE になる行数を数え、PO に承認を求めます。
   - コード変更の PR は手元で `shingo-cc` 名義で作ります（クラウドは push まで）。
   - 本番反映は PO の GO と確認が必要です。ADR-1032 の K1〜K5 と同じ形で、反映の前後を比べます。

## 確かめ方
- pytest（使い捨ての PostgreSQL）で、上のテスト場面が通ること。
- 反映の前後を比べ、変わるのは対象の組だけで、ほかの組の差が 0 であること。
- 古い投稿の行を再解析しても現行のままで、2 回目の付け直しで変化が 0 であること。

## 推奨
まず (A) と (B) のどちらかを特定して、PO に 3 点を確認するのが先です。ADR を変えずにコードだけ直すと、PO の決定を黙って覆すことになります。
