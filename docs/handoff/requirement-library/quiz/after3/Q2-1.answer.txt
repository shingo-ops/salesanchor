# 会社の「休眠」状態を足す計画（計画のみ・ファイル変更なし）

調べただけで、ファイルの変更・commit・push はしていません。プランモード用のプランファイルも、「ファイルを変えない」というご指示を優先して作っていません。

## 1. 先に分かったこと：列は足さず「状態の表に1行足す」形になる

`companies` 表にはすでに `status` 列があります。ADR-1076 で、`public.customer_statuses` が正本になり、`companies.status` はその `code` を指す外部キーになっています（`migrations/20261112_140000_customer_status_fk.sql`）。この表は会社と連絡先で共用です。

現在の値は `active` / `inactive` / `archived` / `pending_dedup_review` の4つで、名前・並び順・選択肢の出し分けは表の列にあります。

そのため、列を足すと正本が2つになり、ADR-1076 と食い違います。「ADR を優先する」という決まりにも反するので、**新しい状態 `dormant`（休眠）を表の1行として足す**ことを推奨します。

## 2. 決めたい点（PO に確認）

- **`inactive`（無効）との違い**：この違いが分かる文を、ADR か design に1〜2行で書いておく必要があります。`inactive` は今は「無効」としか定義されていません。これが決まらないと、使い分けがぶれて分析も混乱します。案は次のとおりです。
  - 休眠 = 取引が止まっているが、復活の見込みはある
  - 無効 = 取引関係を終了した
- **連絡先にも出るか**：表が共用なので、行を足すと連絡先の画面の選択肢にも出てしまいます。会社だけに出すか、連絡先にも出すかを決めます。会社だけに出す場合は、連絡先側の選択肢で `dormant` を除く工夫か、別設計が必要です。
- **自動で休眠にするか**：今回は手で選ぶだけにして、「最終取引から◯か月で自動休眠」は別の依頼に分けるのを推奨します。
- **正本の文書の扱い**：ADR-1076 は Proposed のままです。値の追加を ADR の追記で済ませるか、新しい ADR にするかを PO に確認します。
- **作業の区分**：新規テーマではなく「既存の延長」にあたります。`docs/specs/customer-management/` と `docs/handoff/status-ssot-contact-company/` に追記します。
