# ロック待ちを30秒に延ばす計画（計画のみ・ファイルは変更していません）

## 先に確認したいこと

- **今の値は 1 秒で、PO が決めた成功条件に基づいています。** ADR-1037 は「入れ替え中の作り替えが、ほかの読み取りを待たせるのは最大 1 秒まで」を PO 承認済みの条件にしています。30 秒にするとこの条件と食い違います。
- AGENTS.md の方針では ADR が優先です。そのため、実装の前に PO が ADR-1037 の改訂を承認する必要があります。
- 失敗の原因も未確認です。ADR の記録では、`082` が 38 秒 10 回続けて lock timeout になり、握り手が誰かは「未確認」のままです。握り手が長く鍵を持っている場合、30 秒に延ばしても通らない可能性があります。

## 変更の中身

1. **値の変更（1 行）**
   - `scripts/run_all_migrations.sh:223` の `SQL_LOCK_TIMEOUT` の既定値を `1s` から `30s` にします。
   - 値の正本はこの 1 行だけです。`deploy.yml` と `.env` には書きません。
   - `run_sql` は `PGOPTIONS` から、`run_py` は `MIGRATION_LOCK_TIMEOUT` から同じ値を受け取るので、SQL と Python の両方に効きます。
2. **再試行の上限を見直す（必須）**
   - 今は最大 40 回 ×（待ち 1 秒 + 間隔 3 秒）で、最悪でも約 300 秒に収まっています。
   - 30 秒にすると最悪 40 × 33 秒 = 1320 秒になり、移行ステップの打ち切り 10 分（ssh-action v1 の既定）を超えます。
   - 次のどちらかが必要です。
     - **A（推奨）**: `SQL_RETRY_BUDGET` を 10 回前後に下げて、最悪を約 330 秒に収めます。
     - **B**: `deploy.yml` の打ち切りを延ばします。`deploy.yml` を含む PR は PO の GO が必要です。
3. **コメントと文書を合わせる**
   - `run_all_migrations.sh` 内の「1 秒で諦める」「約 300 秒」というコメントを直します。
   - ADR-1037 の What 1・3、Why の計算、成功条件を更新します。
   - 更新後に `node scripts/generate-adr-index.js` を流します。
   - `docs/handoff/migration-lock-timeout/design.md` に追記します。
4. **試験を合わせる**
   - `tests/sandbox/migration-run-sql-retry.sh` の既定値の確認と、時間に依存する T 系の期待値を直します。
   - 本物の `run_sql` を抜き出して使い捨て DB で試すので、この試験は必ず流します。
   - `.github/workflows/migration-test.yml` の S1〜S3・P1〜P3 の見張りが、新しい値でも通るか確認します。ただし `workflow-lint.yml` は触りません。

## 副作用（PO に伝えておく点）

- 鍵待ちの間、後から来た在庫表などの読み取りも最大 30 秒止まります。ADR の元々の問題（読み取りが 8.9 秒止まる）より悪化します。
- `migration-test.yml` の試験に含まれる `read probe` の判定（`slow=0`）が、鍵待ちで落ちやすくなります。

## 代わりの案（先に検討する価値あり）

- 全体を 30 秒にせず、失敗しているファイルだけ `SET LOCAL lock_timeout` で個別に延ばします。
- 握り手を特定します。`deploy-db-precheck.sh` と lock holders のログで、誰が鍵を持っているかを見ます。
- 失敗した実行のログを `gh run view` で読み、失敗の原因を確かめてから決めます。

## 進め方

1. 直近の失敗した deploy のログを読み、実際の原因（lock timeout の上限到達か、deadlock か）を確かめます。
2. PO に「30 秒に延ばす（成功条件の緩和）」を確認します。
3. 承認後に `release/migration-lock-timeout-30s` の作業場所を `new-worktree.sh --claude` で作ります。
4. 1〜4 を変更し、`executor-preflight.sh`・sandbox 試験・`migration-test.yml` を流します。
5. 枝を push します。PR は手元で shingo-cc 名義で作ります。

## 検証

- sandbox 試験が全件通ること。
- 使い捨て DB で、別の接続が鍵を握っている間に migration を流し、最大 30 秒待ってから通ることを確かめます。
- 同じ条件で、読み取りが最大何秒止まるかを記録します。
- 次回 deploy のログで、"lock conflict; retry" と "retry limit reached" の回数を確認します。

この計画は以上です。実行前に、1 秒から 30 秒に変えてよいかをご判断ください。
