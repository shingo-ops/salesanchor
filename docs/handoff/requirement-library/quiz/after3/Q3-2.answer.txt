# 計画: 期限切れの札も接続元の回数止めに数える

調査担当の報告に基づく計画です。私自身は該当コードを直接読んでいないので、行番号は報告のままで、着手前に再確認が必要です。ファイルの変更・commit・push は一切していません。

## 現状（調査の報告より）
- 接続元ごとの回数止めは `backend/app/cache.py:311` の `check_auth_rate_limit` と `:328` の `record_auth_failure` です。Redis キーは `auth_fail_ip:{sha256(ip)[:16]}`、上限 10 回、期間 900 秒です。
- 期限切れの札は `backend/app/auth/dependencies.py:63` で `ExpiredSignatureError` を捕まえ、401 を返します。ここでは**意図的に回数を数えていません**（ADR-1083、コミット `640a42fe`）。ほかの検証失敗は数えます。
- IP がすでにロック中なら、期限切れの札でも先に 429 になります。
- テストは `backend/tests/test_self_auth.py:457-523`（`AsyncMock` と `await_count`）と、実 Redis を使う `backend/tests/test_real_redis_lockout.py` にあります。
- 未確認なのは、`RateLimitMiddleware` の中身と nginx 層の制限です。

## 最大の注意点: ADR との食い違い
今回の変更は、ADR-1083（Proposed）が決めた「期限切れは数えない」を覆します。AGENTS.md の決まりでは、ADR と実装が食い違うときは ADR が優先されます。コードだけ先に変えることはできません。

「ログインで」という表現が、`dependencies.py` の札の検証経路を指すのか、ログイン処理そのものを指すのかも、確認が必要です。

## 手順
1. **前提確認**
   - ADR-1083 を全文読み、「数えない」理由を把握します。たぶん、正規ユーザーが期限切れの札を送り続けて自分の IP をロックしてしまう事故の防止です（これは推測）。
   - PO（しんごさん）に、方針を変えてよいか確認します。ADR の起案は PO の役割です。
   - 数える対象は、ログイン処理だけか、札を使う全経路かを決めます。
2. **ADR の更新**
   - ADR-1083 を直すか、後継の ADR を起案し、`node scripts/generate-adr-index.js` で目次を作り直します。
3. **作業場所の用意**
   - `bash scripts/new-worktree.sh release/<topic>` を使います。クラウドなので、先に `./scripts/dev/executor-preflight.sh` を流します。
4. **実装**
   - `dependencies.py:63` の `ExpiredSignatureError` の分岐で、他の検証失敗と同じように `record_auth_failure` を呼びます。
   - 回数の数え方は共通の関数に寄せ、分岐ごとの重複は作りません。
   - 誤ロック対策として、次のどちらかを ADR で決めます。
     - 期限切れは通常の失敗と同じ 1 回として数える。
     - 軽い重みで数える。
   - 画面側が札を自動更新する仕組みがあるかも確認します。更新前の期限切れが連発して自分で IP ロックにならないようにするためです。
5. **テスト**
   - `test_self_auth.py` に次を足します。
     - 期限切れで `record_auth_failure` が呼ばれる。
     - 上限に達すると 429 になる。
     - ロック中の IP は引き続き先に 429 になる。
   - 現在の「期限切れは数えない」を確かめているテストは、新しい仕様に合わせて直します。
   - `test_real_redis_lockout.py` に、実 Redis での通しの確認を 1 件足します。

## 検証
- `docs/ai-agents/dev-commands.md` の手順で、バックエンドの該当テストを流します。
- 全体の検査と pre-push の入口を通してから、枝を push します。
- コード変更を含むため、PR は手元で `shingo-cc` 名義で作ります。クラウドでは push までです。

## リスク
- 正規ユーザーが誤ってロックされること。札の自動更新の挙動と、上限・重みの設計で抑えます。
- `RateLimitMiddleware` や nginx 側に別の数え方がある可能性があり、未確認です。実装前に確認が必要です。

## 確認したい点
1. 方針転換の了承を、PO から得られているか。
2. 数える対象の範囲（ログインだけか、札を使う全経路か）。
3. 期限切れ 1 回の重み（通常の失敗と同じか、軽くするか）。
