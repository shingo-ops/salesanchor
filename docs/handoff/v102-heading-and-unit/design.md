## 決め方（変更後）

### T. 区分ごとに取れる単位の表

1. 表は設定 `public.tcg_distribution_settings` の key `v102_kubun_allowed_units` に JSON で持つ（列 `value` は TEXT。`migrations/20260921_110000_pipeline_tables_public.sql:354-359`）。値は次のとおり（単位の名前は `line_units.canonical`）。

   ```json
   {"箱系": ["Box", "Case", "Pack", "MasterCarton"], "プロモパック系": ["Booklet", "Pack"], "ブックレット系": ["Booklet"]}
   ```

   - 表に無い区分（シングル系・サプライ系・セット系・バルク系など）は調べない。今と同じ。
   - 単位の名前は本番の `line_units` で確かめた（MasterCarton は区分「箱系大」、recon 8）。
2. 読み込みで検査する。次のどれかなら、警告を出して表全体を使わない（今と同じ動き）。
   - key が無い。
   - JSON として読めない。区分名 → 文字列の配列の形でない。
   - 区分名が `tcg_product_categories.kubun_type`（有効な行）に無い。
   - 単位の名前が `line_units.canonical`（有効な行）に無い。
3. 判定は、状態から単位を決め直した後（`_resolve_unit_from_state` の後）に 1 回だけ行う。
   - 単位が無い、または表にある単位なら、何もしない。
   - 表に無い単位なら:
     - (a) 状態の単位（`masters.condition_unit[状態]`）が表にあれば、その単位に置き換える。`unit_basis` に `kubun_unit_fix: "a"` と `kubun_unit_from: <元の単位>` を残す。
     - (b) なければ単位はそのまま、要確認の理由「単位不明」（`unit_unknown`。既にある理由。recon 4）を足す。`unit_basis` に `kubun_unit_fix: "b"` を残す。
   - `unit_basis` は DB に保存されない（v102 の保存の SQL `_UPSERT_SQL` に列が無い。`backend/app/services/line_analysis_v102_svc.py:755-766`。本番の現行行も空、recon 8）。保存の SQL は変えない（変更は一度に 1 つ）。代わりに、(a)・(b) のたびに INFO のログを 1 行出す。中身は印 `kubun_unit_fix`・区分・元の単位・後の単位・商品 id。投稿の原文は出さない。毎朝の点検（K9）はこのログで行を見つける。
   - 状態・商品は変えない。
4. 値段で単位を決める処理（ADR-1036）は、この後に保存処理の中で動く。決める単位は Box／Case／Pack だけで、箱系の表に入っている。ただし Box／Case は箱系以外の区分にも付き得る（Pack だけが箱系に限られる。`backend/app/services/v102_buyback_unit_svc.py:379-380`、:202）。プロモパック系で状態が `R4:単位既定` の行などに、表に無い単位が値段の処理で付く経路が理屈の上では残る。もう 1 つ、まとめ売りの処理も後から単位を中身の単位にそろえる（`backend/app/services/line_analysis_v102_svc.py:1028-1043`）。この 2 つの組み合わせは K2 の置き換え（保存処理まで通す）と K4 で見つける。K4 で 0 行にならないときは、その行がどの処理で単位を得たか（表・値段の処理・まとめ売り）を切り分けて、設計に戻す。

### M. 3 商品の区分直し

- `public.products` の 3 行の `product_category_id` を 4（セット系）→ 1（箱系）にする。`tenant_id IS NULL` と今の値 4 を条件にし、変わる行がちょうど 3 行でなければ取り消す。
- 区分の変更は Opus に任されている（PO 2026-10-16）。本番の書き込みは制限なしの鍵が要るので、PO が `!` で実行する（同意票）。
- 試しの実行（dryrun）→ 本実行の順。台本は社外秘フォルダ `set-to-box/` にある。
- 入れる順は **便1（T）の後**（便1b）。理由: 本番の単位「Set」の区分は「複合」（recon 8）で、箱系の再判定の区分（`BOX_RECHECK_UNIT_KUBUNS`、`backend/app/services/gemini_raw_copy_v102_product_first.py:65-67`）に入る。区分が箱系になると、この 3 商品の行は値段で単位を決める処理の対象になる（`backend/app/services/v102_buyback_unit_svc.py:181`・`:184-189`・`:201`。今はセット系なので :201 で除かれている）。買取の物差しがあれば Box／Case／Pack が値段で決まり、無ければ単位は Set のまま残る。T を先に入れておけば、物差しが無いときも Set は表で Box に直る。
- 今の 3 商品の現行の行は 4 行で、どれも単位 Set・状態 Sealed box・`R4:単位既定`（recon 8）。状態が語で決まった行（R1〜R3）は無いので、:712 の経路で単位が変わる行は今は無い。
- 区分を変えても保存済みの行は変わらない。新しい投稿か再解析で変わる。→ K2 の置き換えに M を含め、K7 は再解析した行で測る。

### D2. 状態の見出し（便2。審査 3 回目の 2 点を直すまで実装しない）

1. 品目の選択行（block）で状態の語が当たらないときだけ働く。当たれば今まで通り。
2. 品目の最初の行から上へ、見出しの行を探す。見出しは次をすべて満たす行。
   - 形が見出し（設定 `condition_heading_line_regex`。例: 記号で始まる行）。
   - 見出しでない印を含まない（設定 `condition_heading_not_regex`。例: @・在庫・円・4 桁以上の数）。
   - 状態の語を含む。状態の語は状態マスタの各行の検索の形で判定する（`_entry_hit`。recon 5）。**コードに語を書かない。**
3. 注意書きとの区別: 見出しの直後に品目の塊（次の空行までに値段がある行。値段の形は設定 `condition_heading_price_regex`）が来るときだけ見出しにする。見出しと品目のあいだは、説明の行 1 つ（値段なし・設定 `condition_heading_desc_max_len` 文字以内・単位の別名 `line_unit_aliases` を含む）と空行 1 つまで越えてよい。
4. 見出しが効く範囲: 見出しの次の行から、次の見出しの形の行・空行 2 連続・空行の次が品目でない行の、どれかの手前まで。
5. 見つかったら、見出しの行を block に足して状態を決め直す。変えるのは状態だけで、`condition_basis` を `R11:見出し:<語>` で始める（`R9:` はブックレット既定・`R10:` はサプライ既定で使用済み。`backend/app/services/gemini_raw_copy_v102_product_first.py:98-99`）。
   - `R11:` は「語で決まった」と扱われる（`condition_decided_by_word`、`backend/app/services/gemini_raw_copy_v102_soldout_ref.py:41-52` の `^R\d+:`）。見出しの語も原文の語なので、この扱いを意図どおりとする。影響する先は、値段で単位を決める処理の対象判定（`backend/app/services/v102_buyback_unit_svc.py:169`）、値段の行き先を状態の札で決める `_current_kind`（:312）、適用の `apply_buyback_units`（:379-394。行き先の札が箱・ケースの群に無ければ値段で単位を決めない :382-384）、〆の規則 11b。この 2 つまで通した確かめは、便2 の実装の受入条件 K5b にする（K5a の再試算の道具は状態を決め直すだけで、根拠の接頭辞を出さないため）。
6. 設定のどれかが無い・正規表現として読めないときは、警告を出して D2 全体を使わない。
7. 語を DB から読む形の再試算（K5a）で、31 行はすべて状態マスタの語で当たった（傷ありの見出しは語「状態A-」、未サーチ品の見出しは語「未サーチ」）。状態マスタに語を足す必要は無い。「傷あり」だけの見出しは当たらず、今と同じ動き（変化なし）になる。
