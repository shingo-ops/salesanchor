## 目的（PO の言葉からの読み）

- PO の言葉: 「チャンネルごとの通知別にプロンプトの指示を変えて保守運用にも使う」「Discord は人間が状況把握をするための見る専用」。
- 奥の目的（推測・承認で確定）: 通知が来ても PO が手を動かさずに片付き、PO は Discord を見て様子が分かるだけで済む。

## ゴール案（○×で判定）

## 要件

### やること（機能の要件）

| # | 要件 | ○ の確かめ方 | 関係するゴール |
|---|---|---|---|
| R1 | 保守の通知は、送り手が何であっても、まず保守 API を通り、保守の記録に 1 件ずつ入る | 直接送りの送り手 0（コードの検索）・送った通知と記録の件数が一致 | G1 |
| R2 | Discord の部屋分けと見え方は今と同じに保つ。Discord は記録の写しを表示するだけ | 付け替えの前後で、同じ通知が同じ部屋に出る（目で確かめる） | G1・G5 |
| R3 | 通知の種類ごとに AI への指示書を 1 つ置く。中身は「調べる範囲」「してよいこと」「止まって PO に聞く条件」。置き場は既存の正本 `docs/ai-agents/ops-incident-agent.md` §3（今は空） | 指示書の一覧と記録の種類の照合 | G2 |
| R4 | 指示書のある種類だけ、記録 1 件につき 1 回 AI を起こす。起こすのはサーバー側（PO の Mac が閉じていても動く） | Mac を閉じた状態の試験で 5 分以内に着手 | G3 |

| R6 | 全停止スイッチ（既存の `/ops/control/halt`）が入っていると、AI を 1 回も起こさない | スイッチを入れた試験で起動 0 | G3・G4 |
| R7 | AI は本番に直接書かない。結果は記録への書き込み（注記）、修理は PR だけ | AI の操作の記録と PR の一覧 | （親 KGI 4） |
| R8 | 起きた件ごとに「対応が要ったか」を記録に付ける | 記録の要否の欄の空き 0 | G4 |

### 守ること（安全と正本の要件）

- 保守の記録が唯一の正本。書けるのは保守 API だけ（ADR-1012 決定 2）。Discord・画面に値を別に持たせない。
- 不可逆操作は AI が止まり PO に聞く。危険な変更の GO は ADR-136 のまま。
- 個人情報は既存の相談係 AI（ADR-1052）の伏せ方と道具の絞り方（使える道具 4 つ・コネクタ 0）に合わせる。新しい伏せ方を作らない。
- 費用はサブスクの枠の中。枠が切れたら人に戻る（Discord で知らせる）。

### やらないこと

- Discord への書き込みで AI を起こすこと（不具合報告の部屋は今のまま・ADR-1039/1052）。
- AI が本番のサーバーや DB に直接手を入れること。
- 成績表の画面（親設計の段階6 で作る）。

### 今ある部品で使えるもの（事実）

- 保守 API の口 9 つと全停止スイッチ: `backend/app/routers/ops.py:230`〜`:718`。
- 記録の AI 用の欄: `ai_started_at`・注記の種類 `ai`（`backend/app/routers/ops.py:414`）。
- クラウドの相談係 AI（ADR-1052）: 段1・段2 は合流済み（台帳 `release/cloud-case-ai-stage1`・`-stage2`）。ただし起こす役は PO の Mac の agent-console（`docs/handoff/cloud-case-ai/design.md` §4-5）。段階4 はサーバー側から起こす点が違う。段3 以降の進み具合はまだ確かめていない。

## PO にお願いすること（順番）

1. この要件定義とロードマップの承認。
2. 見張りからの常時起動がサブスクの使い方の範囲に入るかの判断（ADR-1012 :42）。週 1 の設計の前。
3. その場で直す係を本番に出す GO（週 2）。
4. GitHub の自動作業用の鍵の登録（週 3・PO の操作）。
5. routine を作り、起こす鍵を本番の secrets に入れる（週 4・PO の操作。ADR-1012 :45）。
