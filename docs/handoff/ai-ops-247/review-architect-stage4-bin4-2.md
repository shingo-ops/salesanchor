## 直さないと作れない・壊れる物

### R1 報告（proposal）が無い件で、実行係へ送る文の作り方が決まっていない

場所: カード §2 4b（１）⑦（:144）・⑥a（:135）、分岐表（:187-197）、§4 V3（:203）、試験（２）（:148-159）。

事実:
- ⑦ は、送る文に「報告の proposal（種類 `investigation` の行）」を入れる、としか書いていない。行が無いとき・proposal が空のときの振る舞いが無い。分岐表にも無いので、カードの決まり（:185「ここに無い分岐は止まって報告」）で実装役は止まる。
- 報告の proposal は任意の欄で、空でも報告は通る（`backend/app/routers/ops_case.py:198` の `proposal: Any = None`）。表の列は jsonb（`migrations/20261031_210000_create_ops_case.sql:29`）で、文字ではない。文にするときの書き方（JSON の書き出し方）も決まっていない。8000 字の判定（⑥a）は書き出した後の長さで決まる。
- この便では調べ係を起こさない（カード :90）ので、報告ができるのは相談係を人が動かしたときだけ。本番の報告の表は 2b の確かめの時点で 0 行（`docs/handoff/ai-ops-247/stage4-design.md:228-229` の rows 0）。その後の行数は未確認。
- V3（カード :203）は試しの件 OpsPipelineTest に approve を書くだけで、報告を作る段が無い。今の書き方では V3 で ⑦ が報告の無い件に当たり、V3 と、それで測る K2 を判定できない。

直し方（カードに書く。4a の Literal に値を足すかどうかに関わるので、4a の依頼の前に決める）:
1. ⑦ に「その件に種類 `investigation` の報告が無い、または proposal が空なら」の振る舞いを 1 つ決めて書く。例:
   - 案 x: 起こさず、`wake_skipped` を書く。reason は新しい値（例 `no_report`）を 4a（１）の Literal に足すか、今ある値を使うなら、どの値をどの意味で使うかを書く（今の `not_ready` は Discord 発の回の値で、意味が違う。`backend/app/routers/ops.py:443`）。T1 に足した値を入れる。
   - 案 y: proposal 無しで、approve の note（PO の言葉）だけを設計として送る。その場合、実行係の指示文（:167）に「proposal が無いときは note を設計として読み、分からなければ PR を作らず止まる」を足す。
2. proposal を文にする書き方を決める（例: `json.dumps(..., ensure_ascii=False, indent=2)`。8000 字はこの後の長さで数える）。
3. 試験を足す: W12 報告が無い件の approve で、1 で決めた振る舞いになる（案 x なら /fire を呼ばず、wake の行を書かない）。W13 proposal が日本語を含む JSON で、書き出した文が 8000 字を超えるなら full。
4. V3 の前提を書く: 案 x なら、試しの件に種類 `investigation` の報告を先に作る段（誰が・どの鍵で・PO の同意票）を V3 に足す。案 y なら、V3 は報告なしのまま approve の note だけで行う、と書く。
