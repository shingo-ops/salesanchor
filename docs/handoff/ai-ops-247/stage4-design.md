## 2. U3 調べた結果を記録に書く道

### 決めること

試しでは、記録を書く窓（api.salesanchor.jp・保守の鍵）と読む窓（同じホスト・読む鍵）が同じホストで、1 つの環境に両方は登録できなかった（試し §3-1）。

### 選んだ案: 相談係の入口（case-api）をそのまま使う

- 読むのも書くのも case-api の 1 ホスト・1 本の鍵（相談係の鍵）で足りる（読む窓・報告の口・値の口が同じ鍵を受ける: `docs/handoff/cloud-case-ai/design.md:187`）。1 ホスト 1 つの secret の制約に当たらない（E1・E2）。
- 読む窓は伏せた窓なので、要件の「相談係の伏せ方に合わせる」（E13）のうち伏せ方を満たす。道具の絞り方は、コネクタ 0 を守る。使える道具は試しで 5 つ（Bash・Read・Glob・Grep に、Sonnet に任せるための Agent を足したもの。試し `:68`・`:111`）で、要件の 4 つより 1 つ多い。R4（調べは Sonnet に任せる）から来る差として、PO の承認を得る（§8）。試しで使った読む窓（api.salesanchor.jp の読むだけの窓）は伏せていないので、本番の調べ係では使わない。
- 流れ:
  （１）サーバーが記録 1 件ごとに札を作る（E4 の作り方をサーバーの中で呼ぶ。管理者の操作は要らない）。
  （２）サーバーが routine を /fire で起こす。文に、記録の id・札・アラートの名前（E5 で伏せてあるため）を入れる。
  （３）調べ係は伏せた窓で読み、まとめ役が報告 1 通に「調べた結果」と「F4 の設計」を入れる（設計は proposal に入れる）。
- 値を見たい申請は v1 では使わない。申請の判定役は PO の Mac の上で動くため、夜中は止まる。値が要るときは needs_decision に書いて止まり、PO の承認待ちにする（O6）。

### 実装カードで足すこと（この設計では作らない）

- C3-0（正本は 1 か所・写しを持たない。PO 決定 D1・D4）: 報告の中身（status・summary・cause・evidence・proposal・risk・needs_decision）の正本は `ops_case.reports` の 1 行だけ（列は `migrations/20261031_210000_create_ops_case.sql:22-33`）。PO 決定 D1 で、この表を障害記録の一部として扱う。報告を受けたら、サーバーが同じ処理の中で出来事の表（`ops_incident_events`）に「報告が届いた」という出来事を 1 行書く。detail に入れるのは報告の id（参照）だけで、status・summary などの値は写さない（PO 決定 D4「データを分散させることは禁止」）。中身を見る側（手元の Opus・将来の画面）は id で `ops_case.reports` を読む。値を写さないので、detail の上限 8192 バイト（`ops_incident_events_detail_size_check`）の切り詰めは起きない。
  - 注記の口（`POST /ops/incidents/{id}/events`）が受ける kind は `annotated`・`first_aid`・`ai` の 3 つ（`backend/app/routers/ops.py:414`）。出来事の表の決まりが許す kind は 6 つ（notified・resolved・annotated・first_aid・ai・halt。`migrations/20261016_100000_create_ops_incident_tables.sql:54-55`）。kind を足すなら、口と表の決まりの両方の変更が要る（表は migration と GO #番号が要る）。`ai` は今、Discord 発の件の「回」の記録（round）にも使われている（`backend/app/routers/ops.py:366-427`）。報告が届いた出来事と U1 の「許可」の出来事をどう見分けるか（kind を足すか、detail の形で分けるか）は実装カードで決め、カードに見分け方の試験を入れる。
  - 出来事の表の actor は alertmanager / ops_token / super_admin に限られる（`migrations/20261016_100000_create_ops_incident_tables.sql:56-57`）。報告の口から書くときの actor の値（新しい値なら表の変更が要る）は実装カードで決める。
  - Discord について（事実の訂正）: 前の版では「Discord は出来事の表の写しを出す」と書いたが、事実と違った。今の障害通知は Alertmanager が Discord と保守 API（ops-api）に別々に送っている（`monitoring/alertmanager/alertmanager.yml:13-24`）。出来事の表から Discord を作る道は今は無い。AI の報告を Discord に出すかどうか・出し方は、この設計では決めない。要件 R2・G1・K1（送り手を記録経由に付け替える仕事）で、記録を正本にして表示だけする形で設計する（§8）。
- C3-1: 報告を 1 件に複数通にする。kind（investigation / verification / effect）を足し、一意を（incident_id, kind）にする。F7（直ったかの確かめ）と F9（効果確認）でも書けるようにするため。今は 2 通目が 409（E3）。表の変更なので migration と GO #番号が要る。
- C3-2（PO 決定 D3）: alertname と severity を伏せる対象から外す。値は自分たちの見張りの規則から来るので、自由入力ではない。外すまでは（２）のとおりサーバーが文で渡す。

### 選ばなかった案

| 案 | 選ばない理由 |
|---|---|
| api.salesanchor.jp の保守の鍵を書く窓に使い、読む窓を別ホストに移す | 新しい読む道を作ることになり、伏せ方も新しく作ることになる（E13 に反する） |
| 書く窓と読む窓を別の環境に分け、2 つの会話にする | 起こす回数が倍になり、B3（1 日 20 回）を早く使い切る。会話をまたいで結果を渡す道も要る |

### 弊害

- 相談係の鍵を相談係の環境と共有する。片方だけ取り消せない。対処: 鍵を分けるのは後回し（PO 2026-11-12「2」）。取り消すときは両方止まると運用手順に書く。
- 環境を作り直して case-api の secret を入れる必要がある。secret はアカウントごと（試し §3-7）。値を PO が持っているかは X4（§6 の P4）。持っていない場合は鍵を作り直すことになり、動いている相談係の環境の secret も入れ直す（相談係が止まる時間が出る）。その場合は進める前に PO に影響を示して聞く。
- グラフの Loki（ログ）は伏せていない。ログに個人情報が入りうる。対処: v1 の指示書ではグラフは Prometheus（数）だけに限る。Loki を使うかは新しい宿題 U6 として別に設計する。

## 3. U1 許可のあと実行係を誰が起こすか

### 選んだ案: 起こすのはサーバーだけ

- サーバーだけが AI を起こす。回数の数え（R5・B2・B3）と全停止（R6）が 1 か所で済む。クラウドの Opus は別の routine を起こせない（E9）。
- 流れ:
  （１）PO が許可を出す。v1 はチャットで手元の Opus に出す。
  （２）手元の Opus が記録に「許可」の注記を書く。E6 の round の step に「許可」を表す値を足す（C1-1。detail の中なので表の変更は要らない。コードの変更だけ）。
  （３）サーバーが「許可」の注記を見つけ、実行係の routine（置き場あり）を /fire で起こす。文に許可された設計を入れる。
  （４）実行係のまとめ役（Opus）が Sonnet に実装を任せ、PR を出す。merge は手元で行う（E8）。
- 許可された設計が /fire の文に入りきらないとき（X1）: 実行係が case-api から自分の記録の報告を読む GET の窓を足す（C1-2・予備）。

### 実装カードで足すこと

- C1-1: round の step に「許可」を足す。誰が許可したか（PO の言葉の写し）を detail に残す。
- C1-2（予備）: 報告を読む GET の窓。X1 の試しで入りきらないと分かったときだけ。札は有効 24 時間で、作り直すと上書きされる（E4）。PO の許可が 24 時間より後になると札が切れるので、実行係を起こすときにサーバーが札を作り直して文で渡す形をカードで決める。

### 選ばなかった案

| 案 | 選ばない理由 |
|---|---|
| 調べ係と実行係を 1 つの置き場ありの会話に入れる | 調べ係にも GitHub の書く道具が約 50 個付く（E11）。試しで「置き場ありは実行係だけ」と決めた（試し `:102`） |
| クラウドの Opus が実行係を直接起こす | 道具が無い（E9） |
| 手元の Opus が直接 routine を起こす | Mac が閉じていると動かない（R4）。回数の数えが 2 か所になる |
