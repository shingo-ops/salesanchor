## 1. 目的と、PO から見て変わること

- 目的（PO の言葉から）: Mac の負担を下げる。スマホから保守運用の担当に話しかけ、結果を受け取る。
- 変わること（§6 の試しに通った場合）: Mac を閉じていても、スマホの Discord で保守運用の担当とやりとりできる。

### 4-2. ADR-1012 と外れる点（D3）

- ADR-1012:35 は、指示は防壁にならないことを理由に「鍵は VM の外の network secrets」と決めている。AI の処理から鍵の値を読めない形である。
- 案 B では、§5「置くもの」の 3 つの鍵を、AI が動くサーバーの上に置く。AI の処理から鍵の値が読める形になり、ADR-1012:35 から外れる。
- 外れを避ける形は、まだ確かめていない（例: 鍵を別の利用者の権限で持つ中継を挟む）。
- D3: この外れを受け入れて ADR-1012 を改訂するか、外れない形を探す試しを先にするか。どちらも PO の判断。決まるまで実装カードは出さない。
- R5（1 日の回数の上限）の扱いも同じく PO の判断に含める。§5 の案は「PO が書くたびに起きる道は R5 の外」。stage4-design.md:82 の「起こすのはサーバーだけ」は自動で起こす道の決まりと読んだが、PO の確認はまだ。

### 4-3. PO の判断（2026-11-25）

- PO の言葉（原文）: 「サブスクで使用したい、現状の4GBではメモリが不足するか？小さくテストしてみたいと考えており、監視系統と同じサーバーに入れることで常駐うする保守運用社員として常駐させたいと考えている、メモリが不足したタイミングでサーバーを拡張させたらどうか？」
- 設計担当の返事: メモリは測るまで分からない。守り方（メモリの上限・置く鍵を絞る・7 日測る）を付けて prod2 で小さく試す案を出した。サブスクの 24 時間の常駐が規約に合うかは公式に書かれていない（U-c）と伝えた。
- PO の選択（原文）: 「1」（この守り方で小さく試す）。
- 決まったこと: D1 はサブスク。試しの置き場は prod2（§3 の案 A を、試しに限って守り方付きで使う）。メモリが足りなければ、その時点でスケールアップを PO に諮る（§12-5）。
- D3 の試しでの扱い: 試しでは本番に届く鍵を 1 つも置かない（§12-2）。置くのは担当自身のログインと Discord のボットの鍵の 2 つだけ。ADR-1012:35 が塞ぐ「本番への道」は試しには無い。本運用で case-api の札と GitHub の鍵を足すかは、試しのあとに D3 として PO が決める。
- 本運用の置き場を prod2 のままにするかは、試しの数字（§12-4）を見て PO が決める。

## 5. 案 B の形（本運用の形・置き場の決定は §4-3）

- 担当: 公式の Discord の道具（F5）で起動した Claude Code 1 つ。PO の書き込みだけを受ける（PO の Discord のユーザー ID だけを許す。道具の設定のしかたは T1 で確かめる）。
- 異常の知らせは今までどおり段階4 の仕組み（F11）が受ける。この担当は知らせの投稿を読まない（公式の道具はボットの投稿を捨てる・F6）。そのため自前で手直しした道具（F7・起動のたびに確認画面）は使わない。
- 担当にさせること（試しに通った場合）: 調べる（本番は相談係の入口 case-api の伏せた窓から読むだけ）・PR を作る。マージと本番反映は今の GO の決まり（ADR-136・ADR-1003）のまま。
- 本番の読み方は段階4 の調べ係と同じ（`docs/handoff/ai-ops-247/stage4-design.md:46-48`）。ADR-1012:35 の「DB 直結なし・SSH なし」を守るため、reader の SSH 鍵や DB の鍵は置かない。
- 置くもの: case-api の札（相談係の鍵）・Discord のボットの鍵・GitHub の鍵（shingo-cc 名義、salesanchor の「中身の書き込み」と「PR」だけ、期限付き）。
- 置かないもの: SSH の鍵すべて（無制限の鍵・reader の鍵・prod1 へのトンネルの鍵）・本番のデータベースの鍵すべて。
- 全停止: PO の指示を受けるたび、作業の前に全停止スイッチ（`backend/app/routers/ops.py:691`・stage4-requirements.md:114 の R6）を読み、入っていれば作業せずにそう返す。読む道が case-api の札で足りるかは T4 で確かめる。札は有効 24 時間で、作り直すと上書きされる（stage4-design.md:17 の E4・:93）。切れたときの作り直し方も T4 で決める。
- 回数の上限（R5）【案・PO 判断待ち】: この担当を起こすのは PO の書き込みだけで、サーバーが自動で起こす道ではない。そのため R5 の数えの対象外とする案。そのかわり K5 で PO 以外は起こせないことを確かめる。
- 許可の出し方: 担当の許可確認は Discord に中継されないことがある（ADR-1009:18 の実測）。そのため、使ってよい道具を一覧に書き、一覧に無い道具は聞かずに断る設定で起動する。全部の許可を開ける設定は使わない（K4 が破れるため）。設定の名前と書き方は T1 で公式資料と照らす（未確認）。
- 見張り: 生存を prod2 の Uptime Kuma で見る（K3）。止まったら今の Discord の知らせに出す。
- 正本: 担当の決まりは `docs/ai-agents/ops-incident-agent.md` 1 か所を読む（ADR-1012 Decision 5 と同じ）。新しい記録の置き場は作らない。

## 7. リスクと対処

- 担当が間違った変更をする → 本番に届く道は PR だけ。GO の決まりは変えない（K4）。
- 規約（D1 の 1 を選んだとき）→ 使い方が変わったら、すぐ API の鍵に切り替えられるよう、手順を実装カードに書く。
- 研究プレビューの道具が変わる → 止まったら K3 の見張りで気づく。そのあいだは今の受付をそのまま使う。この担当は ADR-1012 Decision 5 の予備 C を置き換えない（予備 C は ADR-1039 で置き換える決まり・ADR-1012:51）。担当の決まりは同じ共用ファイル 1 つを読む（§5）。
- 許可確認で止まる、または許可を開けすぎる → 一覧に無い道具は聞かずに断る設定にする（§5・T1）。
- 第二の起動の道になる → PO だけが起こせる（K5）。全停止は毎回読む（§5・T4）。自動で起こす道は段階4 のサーバーだけのまま。
- 秘密の置き場が増える → サーバーには §5「置くもの」の 3 つだけを置く。値は文書に書かない。サーバーを解約するときは 3 つとも取り消す。

### 12-3. 段取り（サーバーに入れる直前に PO の確認を得る）

1. 基準を取る（読むだけ）: prod2 の `free -m`・`docker stats --no-stream`・各コンテナの `RestartCount` と `OOMKilled`・runner の有無（`systemctl list-units` で actions.runner を探す）と、あれば直近の実行時のメモリの山・`systemctl cat monitoring-tunnel.service` で転送の鍵の場所と権限・監視の compose の `.env` の場所・名前を引く番地（G7）・`ip -6 addr`（G7）。残りが 500MB を切る見込みなら、ここで止めて PO に報告する。
   - 読む鍵: 監視用の読み取り鍵（`claude-monitor@`）は決まった表示（docker stats・free・df・uptime）しか返さず、送った命令を流さない（`docs/runbooks/claude-monitor-access.md:38`）。このため、段取り 1 と毎日の確認は、PO の許可した管理用の鍵で、この節に書いた読むだけの命令に限って流す。PO は導入直前の確認で、この鍵の使い方（7 日間・毎日 1 回・読むだけ）を承知するかを決める。
2. 管理者として（PO の許可した管理用の鍵で）: `ops-agent` を作る（G1）。担当の unit ファイル（G2・G7・G8 の値・`User=ops-agent`・`Restart=always`・`RestartSec=30`・`StartLimitIntervalSec=600`・`StartLimitBurst=5`）を先に置く。`Restart=on-failure` にしない理由: tmux の形では、担当が終わると tmux も 0 で終わるため、systemd から見て「正常に終わった」になり立ち上げ直さない（審査 2026-11-26 の指摘）。10 分に 5 回止まったら立ち上げ直しをやめ、毎日の確認で見つける。まだ起動しない。道具の一覧（G4）の設定もこの段で `ops-agent` の家の場所に置く（段取り 4 のログインの間も Bash などが使えないようにするため）。
3. 管理者として: 導入も同じ上限の下で行う。`systemd-run --uid=ops-agent --pty` に G2 と G8 の値を `-p` で付けて、Claude Code を公式の方法で入れる（`curl -fsSL https://claude.ai/install.sh | bash`、空きが約 512MB 要る・公式）。公式の Discord の道具が使う Bun も同じ形で入れる。Discord の道具は、段取り 4 でログインしたあと、同じ窓のシェルで AI に頼まず命令で入れる: `claude plugin install discord --marketplace anthropics/claude-plugins-official -s user`（`claude plugin install --help` 2.1.332 で確認。担当の道具の許しの一覧を通らない。ログイン前に通るかは未確認のため、ログインの後に置く）。G7 はこの段も付けない（3・4 の段だけ。外の 443 番に出る必要があるため）。
4. PO の手で（鍵の値を AI が扱わないため）: Discord の Developer Portal でボットを作る（Public Bot は切る）。PO の Discord の利用者番号（Developer Mode の「Copy User ID」）を控える。同じ `systemd-run` の形（G2・G8 の上限付き）で `ops-agent` の `claude` を開き、サブスクでログインし、作業の場所を信頼する画面に答えて閉じる。ボットの鍵と利用者番号は、AI の入力欄ではなく、管理者の台本が出す見えない入力（`read -rs`）に PO が貼る。台本がそれを `~/.claude/channels/discord/.env`（`DISCORD_BOT_TOKEN=`・`DISCORD_ACCESS_MODE=static`）と `access.json`（`dmPolicy` は `allowlist`・`allowFrom` は PO の番号 1 つ・`groups` は空）に、持ち主 `ops-agent`・`600` で書く。`/discord:configure` と `/discord:access` は使わない。理由: この 2 つは中で Write の道具を使い（公式の道具の手順書 `skills/configure/SKILL.md`・`skills/access/SKILL.md` の `allowed-tools`、claude-plugins-official 668a0c65）、G4 の deny で止まる。また鍵を入力欄に打つと会話の記録に残る。`static` にすると名簿は起動時に読んだまま書き換わらない（道具の本体 `server.ts` 39-56 行と 183-200 行）。G7 はログインの通り道を塞ぐ恐れがあるため、この段だけ付けない（未確認）。そのかわり G4 の一覧は段取り 2 で入っているので、この段でも担当は Bash を使えず 19187 などへ届かない。PO はこの段で担当に仕事を頼まない。
5. 管理者として: G4 の一覧が効いていることを確かめ（一覧に無い命令を頼んで断られる）、G7・G8 の確かめを行う。確かめは「効いた」と「元から届かない」を分ける: 先に同じ上限で `true` が通ることを確かめる（上限の書き間違いで全部が失敗して○に見えるのを防ぐ）。G7 は守りを外した同じ命令で 19187 番に届くことを先に確かめ、届かなければ確かめにならないので止まる。G8 は `stat -c %a` で場所の権限を読み、守りの下では `0`（systemd が上にかぶせる中身の無い印。公式 systemd の CONTAINER_INTERFACE「all zero access mode」）、守りの外では `0` 以外になることで効きを示す。tmux の中で `claude --channels plugin:discord@claude-plugins-official` を動かす形で unit を起動する（U-a・T1 で確かめる）。
6. 試し T1（K1 を 3 回・K5・G4）と K2（再起動 1 回）を行う。
7. 7 日間動かし、毎日 1 回、次を記録する: G6・担当が動いているか（`systemctl is-active` と担当の unit の `NRestarts`）・担当のメモリの山（cgroup の `memory.peak`）・上限で止まった回数（`journalctl -u` の記録）。担当が止まっていたら、その日のうちに PO に報告する。

### 12-4. 合格と、止める条件

- 合格: K1（3 回とも 2 分以内）・K2・K5・G4・G7・G8 が ○。7 日間で、監視のコンテナの再起動と OOMKilled が基準からの差 0。担当が上限で止まった回数 0。担当が 7 日の毎日の確認で 7 回とも動いている。上限で 1 回でも止まったら不合格とし、§12-5 のとおり PO に諮る。
- 試しで測らないもの: K3（止まった時間）。生存の合図を送るには担当側に送る道が要り、G4・G7 と食い違うため。本運用の設計で決める。§6 T2 の「3GB 未満」は案 B（別のサーバー）での基準で、試しの基準はこの節が正。
- すぐ止める（`systemctl stop`）: prod2 の使えるメモリが 500MB を切る／監視のコンテナが 1 つでも再起動する／PO 以外の書き込みに担当が反応する／一覧に無い道具が動く。止めたら PO に報告する。
- 見る人と回数: 設計担当（Opus）が毎日 1 回、読むだけの命令で見る。そのあいだ（夜間を含む）の守りは G2 の上限だけ。自動で止める仕組みは作らない。PO は導入直前の確認で、これを承知のうえ始めるかを決める。

### 12-5. メモリが足りないとき（PO の案）

- 担当が 7 日で 1 回でもメモリの上限で止まったら、上限を上げる（監視の残りが 500MB 以上の場合だけ）か、スケールアップかを PO に諮る。
- さくらの VPS は管理画面から上のプランに変えられる。変える時はサーバーを一度止める。下のプランには戻せない（公式 https://manual.sakura.ad.jp/vps/server/scaleup.html・2026-11-25 に確認）。止めているあいだは監視も止まるので、時刻を PO と決める。

### 12-6. 戻し方

- `systemctl disable --now` で止める → `ops-agent` を家の場所ごと消す → Discord のボットの鍵を Developer Portal で作り直して無効にする → claude.ai の設定で、このサーバーのログインを外す。担当の unit を消す。監視の仕組みには手を入れていないので、戻すものは無い。

### 12-7. 未確認（試しで確かめる）

- U-a: systemd と tmux の形で、再起動のあと確認の画面が出ずに立ち上がるか。止まって見えたら、管理者が `tmux -S`（担当の tmux）の画面を読むだけで確かめ、PO に報告する。
- 道具の起動のたびに `bun install` が走る（道具の `package.json` の start）。外の 443 番に出るので G7 の下でも通る見込みだが未確認。T1 で確かめる。
- U-c: 24 時間の常駐がサブスクの規約に合うか。公式に明言なし。PO は承知のうえで「1」を選んだ（§4-3）。
- G4 の設定の書き方が CLI で効くか。
- G7 の下でログインと Discord の道具が動くか（loopback を使うか・名前を引く番地を開けるだけで足りるか）。`systemd-run` の `--uid`・`--pty` の書き方は導入時に公式の説明と照らす。
- 長く使う札（`claude setup-token`）は「モデルへの頼みだけ」に使える札で、claude.ai の接続などは使えないと公式にある（https://code.claude.com/docs/en/authentication）。channels が使えるかは書かれていないので、試しでは画面でのログインを使う。
