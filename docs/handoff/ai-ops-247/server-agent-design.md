## 1. 目的と、PO から見て変わること

- 目的（PO の言葉から）: Mac の負担を下げる。スマホから保守運用の担当に話しかけ、結果を受け取る。
- 変わること（§6 の試しに通った場合）: Mac を閉じていても、スマホの Discord で保守運用の担当とやりとりできる。

## 2. 成功条件（○×で判定する）

| # | 基準 | 検証方法 |
|---|---|---|
| K1 | Mac の電源を切った状態で、PO がスマホの Discord に書いた指示に、担当が 2 分以内に最初の返事（受け付けた旨の一言でよい）を書く | PO のスマホで 3 回試し、書いた時刻と最初の返事の時刻を Discord の表示で記録。3 回とも 2 分以内で ○ |

| K3 | 7 日間、担当が止まっていた時間の合計が 1 時間以下。止まっていた＝Uptime Kuma が DOWN と記録した時間 | 新しいサーバーが 5 分おきに「claude の処理が動いている」ときだけ prod2 の Uptime Kuma へ生存の合図（push 型）を送る。10 分届かなければ DOWN。7 日分の DOWN の合計を Uptime Kuma の記録で数える。Discord に返事できるかは K1 で見る |
| K4 | 担当が本番を変えられる道は PR を作ることだけ。マージと本番反映は今の GO の決まりのまま | サーバーに置く鍵の一覧を読み、SSH の鍵（本番・監視のどちらも）と本番 DB の鍵（読み取り・書き込みのどちらも）が 0 件、本番を読む鍵は相談係の入口（case-api）の札 1 つだけ、GitHub の鍵は salesanchor の「中身の書き込み」と「PR」だけで ○。main への直接 push は既存の Branch Protection で止まることを 1 回試す |
| K5 | Discord で担当に届くのは PO の書き込みだけ（PO の Discord のユーザー ID で絞る） | 別のアカウントから、同じ部屋と DM の両方で 1 回ずつ書き込み、どちらにも担当が反応しなければ ○ |

## 3. 置き場の案（D2）

| 案 | 中身 | 判断 |
|---|---|---|
| A 監視サーバー（prod2）に入れる | 費用は増えない | 選ばない。メモリが公式の条件（4GB 以上・F4）に届かない（全部で 3,915MB・F1）。スワップも無い。prod1 へ常時つなぐ仕組みと同じ機械に同居する（F3）。監視が止まると、異常に気づく仕組みごと止まる |
| B 保守運用だけの小さなサーバーを別に借りる | さくらの VPS 4G（メモリ 4GB）。月額はおよそ 3,200〜3,800 円（U-d・未確認） | おすすめ。条件を満たし、監視と本番から切り離せる |
| C サーバーを置かない | スマホの Claude アプリから、今のクラウドの仕組み（claude.ai/code）を使う。Discord ではなく Claude アプリでやりとりする | 費用は増えない。Discord ではない。Remote Control（F9）は機械が動いたままの必要があるので、Mac の負担は減らない |

## 4. ログインのしかた（D1）

| 案 | 中身 | 判断 |
|---|---|---|
| 1 今のサブスクでログインする | 追加の費用なし | 24 時間の常駐が「ordinary, individual usage」に入るか公式に書いていない（F8・U-c）。ADR-1012:42 の未決と同じ問題。PO の事業判断 |
| 2 API の鍵で動かす | 使った分だけの別料金 | 公式は製品やサービスを作る人に API の鍵を勧めている（F8）。Discord の道具は API の鍵でも動く（F12）。費用は使い方で変わり、まだ測っていない |

設計担当はどちらとも決めない。D1 は事業の判断なので PO が決める。

## 5. 案 B の形（D2 が B のとき）

- 担当: 公式の Discord の道具（F5）で起動した Claude Code 1 つ。PO の書き込みだけを受ける（PO の Discord のユーザー ID だけを許す。道具の設定のしかたは T1 で確かめる）。
- 異常の知らせは今までどおり段階4 の仕組み（F11）が受ける。この担当は知らせの投稿を読まない（公式の道具はボットの投稿を捨てる・F6）。そのため自前で手直しした道具（F7・起動のたびに確認画面）は使わない。
- 担当にさせること（試しに通った場合）: 調べる（本番は相談係の入口 case-api の伏せた窓から読むだけ）・PR を作る。マージと本番反映は今の GO の決まり（ADR-136・ADR-1003）のまま。
- 本番の読み方は段階4 の調べ係と同じ（`docs/handoff/ai-ops-247/stage4-design.md:46-48`）。ADR-1012:35 の「DB 直結なし・SSH なし」を守るため、reader の SSH 鍵や DB の鍵は置かない。
- 置くもの: case-api の札（相談係の鍵）・Discord のボットの鍵・GitHub の鍵（shingo-cc 名義、salesanchor の「中身の書き込み」と「PR」だけ、期限付き）。
- 置かないもの: SSH の鍵すべて（無制限の鍵・reader の鍵・prod1 へのトンネルの鍵）・本番のデータベースの鍵すべて。
- 全停止: PO の指示を受けるたび、作業の前に全停止スイッチ（`backend/app/routers/ops.py:691`・stage4-requirements.md:114 の R6）を読み、入っていれば作業せずにそう返す。読む道が case-api の札で足りるかは T4 で確かめる。
- 回数の上限（R5）: この担当を起こすのは PO の書き込みだけで、サーバーが自動で起こす道ではない。そのため R5 の数えの対象外とする。そのかわり K5 で PO 以外は起こせないことを確かめる。
- 許可の出し方: 担当の許可確認は Discord に中継されないことがある（ADR-1009:18 の実測）。そのため、使ってよい道具を一覧に書き、一覧に無い道具は聞かずに断る設定で起動する。全部の許可を開ける設定は使わない（K4 が破れるため）。設定の名前と書き方は T1 で公式資料と照らす（未確認）。
- 見張り: 生存を prod2 の Uptime Kuma で見る（K3）。止まったら今の Discord の知らせに出す。
- 正本: 担当の決まりは `docs/ai-agents/ops-incident-agent.md` 1 か所を読む（ADR-1012 Decision 5 と同じ）。新しい記録の置き場は作らない。

## 6. 試し（実装カードの前）

| # | 試すこと | 合格 |
|---|---|---|
| T1 | 新しいサーバーで公式の Discord の道具を起動し、再起動のあと人の操作なしで立ち上がるか（U-a） | 確認画面が出ずに K1 の試しに返事。一覧に無い命令を 1 つ頼み、止まらずに断ったと返事が来る |

## 7. リスクと対処

- 担当が間違った変更をする → 本番に届く道は PR だけ。GO の決まりは変えない（K4）。
- 規約（D1 の 1 を選んだとき）→ 使い方が変わったら、すぐ API の鍵に切り替えられるよう、手順を実装カードに書く。
- 研究プレビューの道具が変わる → 止まったら K3 の見張りで気づく。そのあいだは今の受付をそのまま使う。この担当は ADR-1012 Decision 5 の予備 C を置き換えない（予備 C は ADR-1039 で置き換える決まり・ADR-1012:51）。担当の決まりは同じ共用ファイル 1 つを読む（§5）。
- 許可確認で止まる、または許可を開けすぎる → 一覧に無い道具は聞かずに断る設定にする（§5・T1）。
- 第二の起動の道になる → PO だけが起こせる（K5）。全停止は毎回読む（§5・T4）。自動で起こす道は段階4 のサーバーだけのまま。
- 秘密の置き場が増える → サーバーには §5「置くもの」の 3 つだけを置く。値は文書に書かない。サーバーを解約するときは 3 つとも取り消す。
