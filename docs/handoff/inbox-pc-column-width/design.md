# design: PC受信箱の3列の幅を「比率＋最大の幅」にする

> この文書は何か: PC の受信箱で、会話一覧を細く・会話欄を広くするために、3列の幅の決め方を作り直す設計書。

親（設計仕様書）: [docs/specs/inbox/README.md](../../specs/inbox/README.md) ／ 調査: [docs/handoff/inbox-pc-column-width/recon.md](./recon.md) ／ 決定: [ADR-1086](../../adr/ADR-1086-inbox-pc-column-width.md)

- 起案: 2026-11-23 Claude Opus（設計担当）
- 区分: 既存テーマ（受信箱）の延長（STANDARD-WORKFLOW §1.8）。記録は `docs/specs/inbox/track-record.md` に追記する。

## 1. 目的と PO の言葉（2026-11-23 チャット原文）

- 「1カラム目の顧客一覧の幅を狭めて2カラム目の会話欄を幅を大きく取りたい」
- 「1280px（小さめのノートPC）　左：顧客一覧→330pxに変更　真ん中：会話欄→463　右：カルテ→420pxに変更　あまりは真ん中に割り当て」
- 「この比率でPCは全画面対応できるようにレスポンシブさせられる？pxでなく比率で調整することは出来る？」
- 「一覧とカルテの最大幅は決めておいて最大値に達したらそれ以上は広げずに会話欄に割り当てることは出来る？」
- 「一覧は最大 330px、カルテは最大480」

## 2. KGI（PO 決定の数値。○×で判定）

PC 帯（窓の幅 1280px 以上）で、一覧とカルテは比率で広がり、最大の幅で止まる。残りはすべて会話欄に回る。

比率は PO 提示の 1280px の数字（330:463:420 ≒ 27%:38%:35%）から作る。測り方は recon.md §3-2 と同じ（縦スクロールバー 15px がある状態）。許す差は ±1px。

| # | 窓の幅 | 一覧 | 会話欄 | カルテ | 今の会話欄 |
|---|---|---|---|---|---|
| K1 | 1280 | 320 | 450 | 415 | 346 |
| K2 | 1366 | 330 | 496 | 445 | 432 |
| K3 | 1440 | 330 | 545 | 470 | 506 |
| K4 | 1536 | 330 | 631 | 480 | 602 |
| K5 | 1920 | 330 | 1015 | 480 | 986 |

- K6: どの窓の幅でも、一覧は 330px を、カルテは 480px を超えない（1280〜2560px を 1px 刻みで計算した結果と、上の5幅の実測で確かめる）。
- K6b: カルテを隠したとき、一覧は全 PC 幅で 330px。
- K7: 窓の幅 1279px 以下（タブレット帯・スマホ帯）の見た目は変わらない。768px・1024px・390px で、変更前と変更後の一覧とカルテの幅が同じ。
- K8: `frontend/src/pages/inbox/InboxPage.css` に、幅の生の数字（px・%）を新しく書かない。値はすべて `frontend/src/tokens.css` に名前を付けて登録する。

## 3. 技術の方法

### 3-1. 比率の基準を画面の作りに合わせる

- CSS の `%` は、親の箱の幅を基準に数える。一覧とカルテは親の箱が違う（recon.md §2）。
  - カルテの親: `.inbox-wrapper`（中身の幅 W ＝ body幅 − 54 − 12）。
  - 一覧の親: `.inbox-columns`（幅 C ＝ W − 14 − カルテ）。
- PO の比率（3列に使える幅 U ＝ W − 14 に対して 一覧 27%・カルテ 35%）を、それぞれの親に合わせて置き換える。
  - カルテ: 35% × U ÷ W ≒ **34.6%**（W に対して）。
  - 一覧: 27% ÷ (100% − 35%) ≒ **41.6%**（C に対して）。
- 置き換えたあとの計算（W ＝ body幅 − 66）:

| 窓 | W | カルテ min(34.6%W, 480) | C | 一覧 min(41.6%C, 330) | 会話欄 C − 一覧 |
|---|---|---|---|---|---|
| 1280 | 1199 | 414.9 | 770.1 | 320.4 | 449.8 |
| 1366 | 1285 | 444.6 | 826.4 | 330 | 496.4 |
| 1440 | 1359 | 470.2 | 874.8 | 330 | 544.8 |
| 1536 | 1455 | 480 | 961 | 330 | 631 |
| 1920 | 1839 | 480 | 1345 | 330 | 1015 |

- カルテを設定で隠したとき（recon.md §2）: 一覧の基準が W 全体になり、41.6% × W は 1280px の窓でも 499px なので、一覧は全 PC 幅で 330px。残りは会話欄に回る（今は 443px 固定）。
- 比率で広がるのは、一覧が窓の幅 約1316px まで、カルテが約1469px まで（上の式で 1280〜2560px を 1px 刻みに計算した結果:最大を超える幅 0 件・会話欄の最小 449.8px）。そこから先は最大の幅で止まり、増えた分は会話欄に回る。

### 3-2. 「比率と最大の幅の小さいほう」を使う

- CSS の `min()` を使う（recon.md §4。書き出し先 Chrome 87・Safari 14 で使える）。
- コンテナ単位（`cqw`）は Safari 14 で使えないので使わない。

### 3-4. 触らない範囲

- `frontend/src/pages/inbox/InboxPage.css:902-1013`（タブレット帯）: `:904` の一覧 `35%` と `:922` のカルテ `var(--karte-panel-width) !important` は変えない。`:922` が `!important` で PC の指定を上書きするので、タブレット帯のカルテは 396px のまま。
- `frontend/src/pages/inbox/InboxPage.css:1014` 以降（スマホ帯。Android 側の担当）: 変えない。`:1042` と `:1249` が `width: 100%` で上書きする。
- `.inbox-wrapper` の左余白 12px・すき間 14px・メニュー 54px: 変えない。
- ページが縦に 31px はみ出す件（recon.md §3-1）: 本件では直さない（別件として PO に確認する）。
- 画面の部品（.tsx）・API・DB: 触らない。幅は見た目だけの話で、データの置き場所と配線は変わらない。

## 4. 代わりの案と選ばなかった理由

| 案 | 内容 | 選ばなかった理由 |
|---|---|---|
| A | 一覧 330px・カルテ 420px の固定 | PO が「比率で全画面対応」を希望 |
| C | 3列とも比率（最大なし） | 1536px 以上で会話欄が今より細くなる（1920px で 694px。今は 986px）。PO の目的と逆 |
| cqw | 受信箱の外枠を基準にした単位で 27%・35% をそのまま書く | 書き出し先の Safari 14 で使えない（`frontend/vite.config.ts:18`） |
| JS で幅を計算 | 画面の大きさを読んで幅を入れる | CSS だけで出せるのに部品が増える。描き直しのたびに計算が走る |

## 5. 弊害・トレードオフと対処

| 弊害 | 対処 |
|---|---|
| 一覧が 443→320〜330px に細くなり、名前と最後のメッセージが早く「…」で切れる | タブレット帯（1024px）では今も一覧が約335pxで出ている。実装後の画面確認（§6 E3）で切れ方を PO に見てもらう |
| 1280〜1467px ではカルテが 396px より広くなり、見本（ADR-108 の karte_reference.html の 396px）と違う幅になる | PO 決定（最大 480px）を優先する。見本の 396px はタブレット帯の引き出しで使い続ける。ADR-1086 に記録する |
| `41.6%`・`34.6%` は PO の言った 27%・35% と見た目の数字が違う | トークンの説明に「3列の幅の27%（35%）相当」と書く。§3-1 の表で一致を示す |
| `--width-inbox-panel` を消す | 使う場所は `InboxPage.css:83` の1か所だけ（recon.md §2）。消さないと未使用トークンになる |

## 6. 受け入れ基準と検証方法

| 基準 | 検証方法 |
|---|---|
| K1〜K5 の幅（±1px） | 評価係（evaluator）が本番（tenant_001）の受信箱で、recon.md §3-2 と同じ body 幅の方法で5幅を測り、生の値を PR に貼る |
| K6b カルテを隠したとき | 評価係が 1280px・1920px でカルテを隠し、一覧が 330px であることを測る |
| K6 最大の幅を超えない | 評価係が 1280〜2560px を 1px 刻みで計算した一覧表（式は §3-1）と、K1〜K5 の実測の一致を示す |
| K7 タブレット・スマホは不変 | 評価係が 768・1024・390px で変更前（本番）と変更後の一覧・カルテの幅を測って並べる。加えて既存の画面検査（Playwright・GitHub 上）が緑 |
| K8 生の数字を書かない | `npm run check:all`（`check-css-hardcoded-values.js` を含む）が GitHub の CI で緑。差分に InboxPage.css の生の px・% が無いことを審査役が目で確かめる |
| E3 見た目 | 本番反映後、PO が 1台の PC で受信箱を開き、一覧の名前が読めること・会話欄が広がったことを○×で答える |

## 7. 外部・過去事例の参照と我々への応用

- MDN `min()`（Context7 `/mdn/content` web/css/reference/values/min、2026-11-23 取得）: `width: min(40%, 400px)` で「比率で縮み、最大の幅を超えない」形が公式の使い方として示されている。本件はこの形をそのまま一覧とカルテに当てる。
- 事業の数字の事例は該当なし。理由: 列の幅の決め方は見た目の調整で、効果は本件の K1〜K5 の実測で直接確かめられるため。

## 維持の仕組み

- 守り手: frontend/scripts/check-css-hardcoded-values.js
- 対象: 受信箱の CSS に幅の生の px が書かれて、トークンを通らない値が増えること。
- 関所なしの部分: 幅の数字そのもの（330・480・比率）を勝手に変えられること、と `%` の直書き。今の検査は `%` を見ないので、人手で守る（審査役がトークン以外の値を差分で確かめる）。幅を変えるときは ADR-1086 を更新する。
