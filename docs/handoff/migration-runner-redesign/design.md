## 0. 一言でいうと（PO 向け）

- いま：DB を変える手順 317 件を、デプロイのたびに全部やり直している。記録が無いので「やり直しても壊れない」ことを人が毎回確かめる必要があり、見落としが障害になってきた（recon §2 の 4 件）。
- 目標：「どの手順を実行したか」を DB に記録し、まだの手順だけを 1 回実行する（Flyway などで一般的な方式。recon §5）。
- ただし先に直す穴がある：新テナントの「ひな形」が手順より約 40 列遅れていて、今は全件やり直しがその穴を埋めている（recon §3）。順番を守らずに切り替えると、新テナントに列が永久に足りなくなる。
- そこで 3 段階に分けて進める。各段階の実装前に PO の GO をいただく。

## 外部・過去事例の参照と我々への応用

- 事例1: Flyway 公式資料（Context7 /flyway/flyway：Validate error codes、Baseline On Migrate Setting、FAQ）→ 我々への応用: 実行済み記録の表（ファイル名・チェックサム・成否・実行時刻）、既存 DB は「baseline（今の全手順を実行済みとして記録）」、毎回実行が必要なものは別種類として明示、実行済みファイルの書き換えは検出して止める。テナントごとのスキーマは「1テナントずつ適用」の公式パターンに倣う。
- 事例2: Alembic 公式資料（stamp による既存 DB の記録）→ 我々への応用: baseline の手順を「何も実行せずに記録だけ入れる」操作として独立させる。
- 事例3: PostgreSQL 16 公式（limits.html：削除した列も 1600 列の上限に数える）→ 我々への応用: 「後で消す列を前の手順で足す」形を CI で禁止する（段階0）。
- 事例4（社内の過去事例）: ADR-045（登録漏れで本番 500）→ 全件やり直しを選んだ理由。新方式でも「登録漏れ」を防ぐ既存の CI（migration-guard.yml の登録チェック）は残す。
- 外部ツール（Flyway 等）そのものを導入するかは段階2で比較する。現時点の推奨は「既存の実行スクリプトに記録の仕組みを足す」（理由：手順ファイル 317 件の改名が不要、Java 等の追加実行環境が不要）。ただし Flyway の Community 版の baseline/validate/repair の提供区分は【未確認】で、比較時に確かめる。

## 2. 段階0：安全網（小さく、すぐ効く）

- ① CI チェック（新規スクリプト、例：scripts/check-migration-column-churn.js。名前は実装時に確定）
  - 登録順に全手順を読み、「表 T に列 C を足す」手順と、それより後の「表 T の列 C を削除する」手順の組を見つけたら PR を止める。
  - 既知の組（2026-10-03 の対処で無効化・ガード済みのもの）は、ガードの有無を確かめたうえで許可リストに載せる。
  - 文字の照合で見つけられる根拠：登録された SQL 290 件の列の追加・削除は、テナント全体に繰り返す形（EXECUTE format の中）でも、列名がそのまま文字で書かれている（列名を変数で組み立てている例は 0 件。Architect 審査で確認）。
  - 対象範囲：run_sql の SQL ファイルに加え、run_py の Python 26 本も対象にする。26 本のうち 9 本は本文に列の追加・削除の文字を含む（設計担当が数えた）。Python が別の SQL ファイルを読み込んで実行する形（例：migrations/041_extend_meta_messages.sql）は、読み込まれる SQL ファイルも対象にする。
  - 組み込み先：`.github/workflows/migration-guard.yml`（既存の登録チェックと同じ場所）。`.github/workflows/workflow-lint.yml` は触らない。
- ② 二重登録の削除：`scripts/run_all_migrations.sh:536` の行を消す（530 行の 1 回目は残す）。同じファイルの 2 回目は、何もしない再実行なので、消しても結果は変わらない。
- ③ 全件ドライランの対象範囲（`.github/workflows/migration-test.yml:1660`）：2026-06-30 以降が対象外になっている理由を履歴で確かめ、更新漏れなら範囲を広げる。広げて落ちる手順が出た場合は、その手順ごとに直すか、理由を書いて除外する（黙って除外しない）。

## 3. 段階1：テナントの正本を1つに

- 問題：テナントの表の定義が、ひな形（`backend/app/services/tenant.py:184` 以降）と、テナント全体に繰り返す手順（約 140 件）の 2 か所にある。
- 推奨案（1B）：本番の「標準形」のテナント（recon §4 で同じ形の 003・005・006）から表の作りを機械的に書き出し、それを新テナント作成の唯一の定義にする。以後のテナント向けの変更は「テナントごとに実行済みを記録する手順」として段階2の仕組みで全テナント（新規を含む）に適用する。Flyway 公式 FAQ の「テナントごとにループで適用」パターンに当たる。
- 代替案（1A）：ひな形に足りない列を足し、「ひな形で作ったテナント」と「手順で作ったテナント」の列を CI で比べて一致を保証する。定義は 2 か所のまま（SSOT ではない）が、変更は小さい。
- 書き出しの方法（1B の場合）：PostgreSQL の構造だけの書き出し（pg_dump の schema-only。読み取りのみ）で、表・列・既定値・制約・索引・連番・トリガ・行単位の権限（RLS のポリシー）・権限付与を含めて書き出す。表の中のデータ（そのテナントの役割・スタッフ・設定の行など）は一切含めない。テナント名の部分は {schema} の置き換えにする。具体的な書き出し手順と、書き出した結果に何が含まれたかの一覧は、段階1の前調査で実物を見て確定する。
- 初期データ（役割・権限・テナント設定など）：今は create_tenant_schema が表を作った後に入れている（`backend/app/services/tenant.py:1620` 以降の処理）。初期データは構造の書き出しに含めず、今の入れ方を残す。今の入れ方が正しいかは段階1の前調査で確かめる。
- 先に確かめること：001・004 の多い表の正体（recon 不明点1）、ひな形と本番の差分の全件（不明点2）、書き出しに含まれるもの（RLS・トリガ・権限・連番）の一覧。この結果で 1A／1B を確定し、PO に確認する。

## 4. 段階2：実行済み記録

- 記録の表（案）：public の 1 表に「対象（public かテナント名）・ファイル名・チェックサム・実行時刻・成否・所要時間」。名前と列は段階2の着手時に確定。
- 最初の 1 回（baseline）：本番で全件の実行が成功した直後の状態を「全手順実行済み」として記録だけ入れる（実行はしない）。根拠：2026-10-03 17:33Z と 17:49Z の 2 回連続で全件成功し、商品の表の削除済み列数が 1543 のまま変わらなかった（設計担当が本番で確認）。
- 以後の実行：未記録の手順だけを登録順に実行し、成功したら記録する。毎回実行が必要な手順（recon §1 の C のうち、段階1で正本に取り込めなかったもの）は、名前の付いた別リストとして毎回実行する。
- 実行済みファイルの書き換え：チェックサムの違いを検出し、デプロイ前（CI）で止める。直したいときは新しい手順を足す。
- 戻し方：実行スクリプトに「全件やり直しモード」を残す。既存の手順は今も冪等なので、記録を無視して全件やり直しに戻せる。

## 技術 How・KPI

- KPI1：毎デプロイで再実行される古い手順の数 317 件 → 段階2後 0 件（＋毎回実行リストの件数）。
- KPI2：「古い手順と今の状態のぶつかり」による migration 失敗 → 0 件（2026-09-15 以降 4 件発生）。
- KPI3：新テナントと標準形テナントの列の差 → 0。
- KPI4：デプロイ中の手順実行時間 66〜67 秒 → 段階2後に実測（目標は数秒。見込みであり確定ではない）。
- 技術選択：段階2は既存の実行スクリプト（`scripts/run_all_migrations.sh`）に記録の仕組みを足す案を推奨。理由：手順ファイルの改名不要、新しい実行環境が不要、戻し方が単純。Flyway 等の導入は段階2の着手時に比較表で再判断する。

## 弊害・トレードオフ

- 登録漏れ（ADR-045 の事故の型）が戻るおそれ → 対策：既存の登録チェック（migration-guard.yml）を残す。加えて「repo にあるが未登録・未記録」の手順を CI で一覧化する。
- 記録と実態のずれ（手作業の SQL で DB を変えた場合など）→ 対策：手作業の DB 変更の原則禁止は ADR-025 で「本番運用フェーズ移行後」に有効（現在は開発フェーズ。CLAUDE.md の ADR-025 の項）。段階2で「記録の一覧」と「本番の表・列」を照合する点検を用意する。
- テナント間で表が違う（001・004）→ 対策：段階1の前に正体を確かめ、標準形との差を一つずつ判断する（PO に確認が要るものは確認する）。
- デプロイの順番（新しいコードが先に動き、手順はその後に実行される。`.github/workflows/deploy.yml` の「Deploy to VPS」が先、「Run database migrations」が後）→ 対策：今と同じく、新しい表や列を使うコードは、表や列を作る手順の後の便で出す（2 段階で出す）。記録方式では「手順の実行が途中で止まったとき、どこまで記録されたか」を決める必要がある。1 手順ごとに実行と記録を同じトランザクションで行う案を段階2の設計で検討し、確定する（未決）。
- 1 手順の途中失敗 → 対策：PostgreSQL では 1 手順を 1 トランザクションで包めば巻き戻せる（Flyway FAQ）。ただし自分で BEGIN・COMMIT を書いている既存手順が 13 件あるため（設計担当が数えた）、包めるかは手順ごとに確認する。
- 実装量が大きい → 対策：段階ごとに PR を分け、各段階で効果を測ってから次へ進む（一度に1つ）。

### 5-6. 会社のひな形を1つにする（5-2）

**前提の事実**: 今の CI は、本物の作り方で会社を作っていない。手書きの最小の表から始め、run_sql だけを流し、run_py は2本しか流さない（§5-1）。そのため「CI で全部流した会社の形」は、そのままでは本番の69表にならない。

**どの案でも入れる仕組み（CI）**: 次の検査を CI に入れる。
1. ひな形で使い捨て DB に会社を作る。
2. 登録全件（run_py を含む）を、本体と同じ流し方で流す（P10）。
3. 流す前と後で、その会社の形（表・列・型・既定値・索引・制約・トリガ・RLS・権限）を比べる。差が0なら合格。

この検査が守るのは片方の向きだけ。「手順が作る物は、全部ひな形にもある（足し忘れが無い）」は守れる。会社向けの手順を足した PR は、同じ PR でひな形も直さないと CI で止まる。
逆の向き「ひな形にだけ余計な物がある」は、この検査では見つからない（手順が触らない物は流しても変わらないため）。そこで次の2つで守る。
- 最初: P1（ひな形と本番 003 の差の全件）で、余計な物を0にする。
- その後: ひな形を変える PR は、同じ PR に migrations/ の新しい手順（今ある会社に同じ物を足す）が無ければ CI で止める。

流す前の DB の作り方（public の前提の表をどう用意するか）と、run_py 26本が全部通るかは P10 で決める。

**決めること（PO の確認）**: ひな形を何で持つか。P1・P8 の結果を見てから聞く。

| 案 | ひな形の持ち方 | 正本 | 長所 | 短所 |
|---|---|---|---|---|
| 1A | 今の直書き（_TENANT_TABLES_SQL）に、足りない列・表を足す | 手順。ひな形は上の検査で手順と一致させる | 変更が小さい | 手順を足すたびに、ひな形の SQL を人が書き足す |
| 1B | 本番 003 の構造だけの書き出し（pg_dump の schema-only）をファイルにし、新しい会社はそのファイルから作る（ADR-1005 :28 の推奨）。以後は上の検査が出す「流した後の形」から書き出し直す | 手順。ファイルは書き出しの写し | ひな形を人が書かない。差は機械で出る | 003 の癖（P2・P3 の差）を写す。最初にどの差を正すかを決める必要がある |

推奨は P1・P8 の後に決める。第1版の 1B'（CI の会社から書き出す）は取り下げた。理由は上の前提の事実のとおり、今の CI の会社が本番の形にならないため。
どちらの案でも、データ（役割・権限・会社の設定）はひな形に含めない。今の入れ方（tenant.py の seed_system_roles など）を残す。
ひな形を直接使う5か所（setup の3本、backend/tests/rls_bootstrap.py、backend/tests/test_roles_system_key_ddl.py :29）も同じ PR で新しいひな形に揃え、古い直書きは消す（残すなら理由を書く）。

### 5-7. 実行済みの記録（5-3）

- 置き場所: 新しいスキーマ ops の1表（#4020 の案を引き継ぐ）。public に置かない理由: public には salesanchor_app に読み書きの権限が自動で付く（`migrations/20260605_030000_create_salesanchor_app_role.sql` :21-24）。アプリから記録を書き換えられないようにする。
- 列（案）: ファイル名・チェックサム・流した時刻・所要秒数・結果・流した本番反映の番号。会社ごとの列は持たない（§5-3 の理由で、会社ごとの差はひな形で埋める）。
- 「流し終えた」の正本: 本番の ops の表の1か所だけ。別の一覧ファイルは作らない。起点のタグ（下）は人が起点の本番反映を見つけるための印で、検査も本体も読まない。
- 記録の対象と記録の外: 登録済みとは、`scripts/run_all_migrations.sh` の `^run_(sql|py)[[:space:]]` の行にあること。そのうち、0 の外す手順（:219 の 20261017_125900）と 2 の毎回の一覧（P4）を「記録の外」とし、残りを「記録の対象」とする。3 の作り直し（:226 の AI_RO_CREATE_SQL）は `^run_` の行ではないので、もともと登録済みに入らない（:225）。記録の外の一覧は本体の中の1か所に書き、CI の検査もそこを読む。
- run_py の台本が読む SQL: 台本（例: `scripts/migrate_inventory_sprint1.py`）は、中の配列（:51-59 と :61-63）にある SQL（056〜063）を読んで流す。10/29 の入口の 056 もこの形で、`^run_sql` の行には無い。そこで、run_py の行の記録のチェックサムは「台本の本文と、台本が読む SQL の本文を、本文に現れる順（P13）につないだもの」で取る。台本が読む SQL の一覧の正本は台本の本文の1か所で、本体と CI はそこを機械で読む（別の一覧ファイルは作らない。取り出し方は P13）。チェックサムには、登録の行の引数（例: `scripts/run_all_migrations.sh` :300 の `-e TENANT_CODE=…`）も含める。引数を変えると (b) で止まる。
- 言葉の書き分け: 「記録の行」は登録の行ごとに1行（run_py は台本名で1行）。台本が読む SQL は自分の行を持たず、台本の行のチェックサムに入る。(a)・(c)・K5-4・起点の定義は、記録の行で数える。CI の書き換え禁止の対象（「凍らせるファイル」）は、記録の行のファイルと、台本が読む SQL の両方。
- ops のスキーマと表を作る文の置き場所: `scripts/run_all_migrations.sh` の中の1か所。migrations/ には置かない。記録の表そのものを、記録で管理することはできないため。記録の外で、毎回「無ければ作る」で流す。
- 書き換えを止める CI の決まり: PR が変える・消すファイルのうち、PR の base ブランチ（`.github/workflows/migration-guard.yml` :5 で main・develop。比べる元は pull_request.base.sha）で「記録の対象」だった物は、書き換えも削除も止める。直したいときは新しい手順を足す。この決まりは起点の後に足した手順も守る。
  - 例外の道（1つだけ）: 本番で記録される前に失敗した手順は、新しい手順を足しても届かない（登録順に流し、`set -e` で同じ所で止まるため）。そこで `scripts/migration-guard/` に「書き換えを許す一覧」（ファイル名・PR 番号・理由・失敗した本番反映の番号）を1つ置き、一覧にあるファイルだけ CI が書き換え・削除を通す。一覧への追加は同じ PR で行い、審査役が理由と、そのファイルが本番の記録に無いこと（移行の段のログ）を確かめる。既存の許可一覧（value-write-allowlist.tsv・dryrun-exclusions.tsv）と同じ置き場所と形にする。行は、直した手順が本番で記録された次の PR で消す（value-write-allowlist.tsv の規則 (3) と同じ考え方）。行を消す PR は、移行の段のログでその手順が記録されたことを審査役が確かめる。CI は、一覧のファイルが PR の base で凍らせるファイルに無い（登録から消えた）ときに失敗させる（dryrun-exclusions.tsv の規則と同じ）。
  - CI と本番で止める範囲が違う理由: CI は本番の記録を読めないので、広めに止める。本番の (a)・(b) は記録そのものを見るので、記録済みのファイルを間違えて一覧に入れて書き換えても、本番で必ず止まる。記録の外の物（0・2・3）は毎回流れて記録とずれないので止めない（ただし次の「毎回の一覧の書き換えの検査」の文は除く。実物でも 20261017_130100 は一度直している。`git log -- migrations/20261017_130100_create_ai_ro_views.sql`）。今の CI に、登録済みの既存ファイルの変更を止める検査は無い（同 yml の変更検出は :81・:294 の `--diff-filter=A` で新しいファイルだけ）ので、新しく作る。
- 毎回の一覧の書き換えの検査: 記録の外でも、毎回の一覧（P4）のファイルに、ビューが依存する物を変える文（DROP COLUMN・ALTER COLUMN の型の変更・DROP TABLE）を足す PR は CI で止める。0本の回は ai_ro を外さずに流すため（流れの 0 の前提）。
- 本番側の突き合わせ（ADR-1005 :34）: 本番反映のたびに、流す前に次を確かめる。(a) か (b) が0でなければ、移行の段を何も流さずに止める。
  - (a) 記録にあるのに、今の「記録の対象」に無いファイルの数。0 であること。
  - (b) 記録にあるファイルのうち、チェックサムが今のファイルと違う数。0 であること。
  - (c) 「記録の対象」から記録を引いた残り。これがこの回に 1 で流す手順になる。本数をログに出す。
  記録が0件の初回は、(a)・(b) が自然に0になり、(c) が「記録の対象」の全部になる。特別な扱いは要らない。

- 起点（最初の記録）: 別の「記録だけ入れる」作業は作らない。5-3 の本体が初めて本番に出る本番反映（PO 本人の GO）で、記録は0件なので、本体は「記録の対象」の全部を今と同じく流し、1本成功するごとに記録する。この回が起点になる。流す中身は今の毎回の全件と同じなので、本番の動きは今と変わらない。ops のスキーマと表は、本体が 1 の前に作る（無ければ作る）。GO はこの本番反映の1回だけ。

- 1回の本番反映の流れ（この順番を守る）:
  0. 前処理: 記録に無い手順が1本以上あるときだけ、ai_ro のビューを外す（`scripts/run_all_migrations.sh` :219 の 20261017_125900）。外す理由は、ビューが依存していると後の手順の列の削除・型の変更が止まるため（同 :217-218）。0本の回は外さない。これは、毎回の一覧がビューの依存する物を変えないこと（P4 の合否の線）が前提。

  2. 毎回の一覧（P4 で確定）を流す。

### 5-8. 控えのムラをなくす（5-4）
