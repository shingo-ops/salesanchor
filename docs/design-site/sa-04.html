SA-04 ④ 実装中 (35%)

チャネルリンクテンプレ SSOT＋guild_id

多チャネル名寄せ — チャネル ID だけ保存し、リンクはテンプレ表から自動生成。手入力 URL を0にする。

① 一言でいうと

「連絡先タブには "ID" だけ保存する。リンクは1か所のテンプレ表から自動生成する。手入力 URL 欄をゼロにすることで、腐ったリンクが構造的に生まれない。」

現在の連絡先タブには「手入力した URL」が保存されており、Discord の旧 username 形式（廃止済）や 開けないリンクが混入しています。SA-04 では「ID だけ保存してリンクは都度生成」に変えることで、 チャネルの URL 形式が変わっても テンプレ表を 1 行直すだけで全顧客に一斉反映します。

③ 仕組みの図解 — ID 保存 → テンプレ → リンク生成

ID だけ保存し、リンクはリクエストごとにテンプレ表から生成します。 担当者に URL を手入力させる画面は存在しません。

④ 4原則との対応表
原則 SA-04での実現方法
SSOT リンクの「URL の組み立て方」は link_templates テーブル（1か所） だけが持つ。 型の変更は 1 行の修正で全顧客に一斉反映。顧客マスタには ID のみを保存（URL は二重保存しない）。
2本背骨 チャネル情報は背骨①（顧客マスタ）に紐づく属性。 複数チャネルから来た顧客でも「1顧客 1 カルテ」に統合される。
派生値 クリック要素（リンク）は ID + テンプレートから都度計算して表示。 URL 文字列を DB に保存しないため、テンプレ変更で全顧客のリンクが自動で最新になる。
ポカヨケ 担当者が URL を手入力する欄がない（腐ったリンクが入れない）。 重複 ID は保存前に警告・統合への導線を表示。 Meta 非公式 URL は link_templates の 1 行に隔離（壊れてもそこだけ修正可能）。
⑤ 用語ミニ辞典
チャネル ID
各プラットフォームでの識別子。WhatsApp = 電話番号（国際形式）、Telegram = username、Discord = guild_id / channel_id。保存するのはこれだけ。URL は保存しない。
テンプレ表（link_templates）
1 チャネル = 1 行。「ID をどう URL に変換するか」だけを持つ SSOT。変更は 1 行の修正で全顧客に反映される。
名寄せ
複数チャネルから来た発言を 1 人の顧客に束ねること。完全自動の同一人物判定はせず、担当者が UI から明示的に「これは同一人物」と決定する。
guild_id / channel_id（Discord）
Discord のサーバー（guild_id）とチャンネル（channel_id）の固定 ID。username より安定しており、リンク discord.com/channels/{guild_id}/{channel_id} は永続する。
Meta 内部 URL（Messenger / Instagram）
Meta が非公式の内部 URL 形式を使うチャネル。壊れる可能性があるため link_templates の 1 行に隔離し、壊れたときはその 1 行だけを修正する。

# ゴール（KGI）— 本番で観測できたら成功 種別
G1 連絡先のチャネル情報は ID（WhatsApp = 電話番号、Discord = サーバー/チャンネル ID 等）で保存。手入力の URL 欄が 0 個 = 腐ったリンクが構造的に発生しない データ構造（SSOT）
G2 リンクの「URL の組み立て方」は テンプレ表 1 か所だけが持つ。型の変更は 1 行の修正で全顧客に一斉反映 SSOT
G3 連絡先タブで クリック 1 回で顧客スレッドを開ける。チャネルの追加・編集は同タブから ID 単位（URL 文字列は見せない・編集させない）。重複 ID は保存前に警告し、統合への導線を出す UI/UX＋ポカヨケ
G4 複数チャネルから来ても 1 顧客 1 カルテ。自動の同一人物判定は しない（誤マージ 0）。統合は人が UI から明示的に実行 名寄せ
