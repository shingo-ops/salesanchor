## 2. 承認済みKGI（2026-06-11 Shingo承認）

| # | KGI |
|---|-----|
| G1a | 連携済みチャネルの受信メッセージ100%が自動で会話ログに保存・contactに紐づく。取りこぼしは自動検知 |
| G1b | 未連携チャネルはスレッド欄のチャット風入力で手動記録でき、自動と同じログ・集計・翻訳/解析・スレッド表示に乗る |
| G2 | 会話数・最終会話日時・会話要約は自動計算のみ。手入力箇所0 |
| G3 | 会社を開くと連絡先粒度の会話が1画面に集約、3クリック以内で原文＋訳文に到達 |
| G4 | 会話の同じ事実を手入力で二重に持つ場所0 |

確定済み要件（手動記録の仕様・1チャネル＝1入口の排他ルール・AI分割v2延期など）は `SA-02-plan.md` §2 を正とする。

## 4. 調査観点（SA-02-plan.md §3 の表に対応）

1. **会話ログの保存先と構造** — 原文・原文言語・翻訳文・商談解析の各列があるか。手がかり: `meta_messages`、`message_translations`（migration 094、ADR-088/110）、テナントスキーマ内テーブル。
2. **チャネル→会話ログの取り込み経路** — チャネル別（Messenger/Instagram/WhatsApp/Discord/Telegram/Email）の網羅率。Meta webhook・Discord Bot（ADR-091）の現状。
3. **派生値の算出方法** — 会話数・最終会話日時・会話要約が「書き込み可能カラム」か「ビュー/集計/トリガ」か。
4. **派生値への手入力経路** — UI・API・DB権限のどこかに手で上書きできる穴がないか。
5. **会社（companies）⇔連絡先（contact/lead）の紐づけ構造** — ADR-089（customers→companies統一）後の実態。会社粒度で会話を集約できる結合キーがあるか。
6. **カルテUI・スレッド欄の現状** — ADR-108/110準拠の実装状態。スレッド描画コンポーネントが「手動メッセージの混在表示・手動バッジ・入力ボックス常設・チャネル選択」に対応できる構造か。
7. **既知関連実装の被覆率** — 翻訳基盤（ADR-088/110/ADR-SA-17: 即時翻訳発火・sweeper・glossary）、lead_channels（ADR-119）。流用できる部分／不足部分を分ける。
8. **編集履歴（監査ログ）の既存パターン** — 手動記録の「編集可＋履歴」に流用できる土台があるか。
9. **手動メッセージを翻訳・解析パイプラインに乗せる経路** — 即時翻訳の発火点を手動保存時にも呼べるか。
10. **チャネル定義の構造** — 「電話」「対面」等の手動チャネルをマスタ追加できるか（enum固定か、テーブル管理か）。
11. **連携チャネルのアプリ外送信分** — スタッフが公式アプリ等から送った送信メッセージをwebhookで自動取得できる範囲（チャネル別）。
12. **取りこぼし検知の現状** — 受信の欠落を検知・通知する仕組み（sweeper等）の有無と適用範囲。
