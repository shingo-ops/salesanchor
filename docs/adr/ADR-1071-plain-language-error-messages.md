# ADR-1071: 失敗したときの文は「何が起きたか＋次にすること」を誰でも分かる言葉で出す

## What（何を決めたか）

1. 利用者の画面に出る失敗の文は、すべて次の2つを含む。
   - 何が起きたか（利用者に見える出来事の言葉。仕組みの名前は使わない）
   - 次にすること（もう一度試す・別のものを選ぶ・入力を直す・誰に何を頼む、のどれか）
2. 例（PO 原文）:「時間切れにより連携できませんでした。もう一度お試しください。」
3. 画面に出してはいけないもの: 英語の識別子・理由コードの生の値・権限名・仕組みの名前（Redis・token・state・HTTP の番号など）・例外の中身。
4. 文はサーバーで作らない。サーバーは安定した理由コードを返し、画面が「理由コード → 文言キー＋次にすること」の対応表から文を選ぶ（前例 `frontend/src/pages/inbox/discordSendError.ts`）。文言は ja/en 同じキー（ADR-027）。
5. 対応表に無い理由は「うまくいきませんでした。もう一度お試しください。続く場合はサポートにお問い合わせください。」の型の文に落とす（生の値は出さない）。
6. 表示は既存の部品（帯・お知らせ・Toast・Callout）だけを使う。新しい部品は作らない（ADR-144）。
7. 新しい違反は機械で止める。今ある違反の数を基準値として記録し、CI で「基準値より増えたら落とす」。直すたびに基準値を下げ、最後は 0 にする。
8. 直す順番は便に分ける。便1 は Discord 連携の失敗（KGI 承認済み）。

## Why（なぜ）

- 今の画面は、失敗しても理由が分からない文が多い。例: Discord 連携は 12 種類の失敗がすべて同じ1文になる（recon §3-3）。始めるときの失敗では「権限が不足しています: tenant.profile.edit」「（Redis 接続失敗）」が画面に出る（recon §3-2）。
- サーバーの文がそのまま画面に出る仕組みになっている（`frontend/src/lib/api.ts:162-171`）。サーバーに日本語の文の直書きが 662 か所、英語の文が 62 か所ある（recon §4）。サーバーで文を作る限り、言葉の決まりは守れない。
- PO は同じ要件を Discord 送信の失敗で既に出している（ADR-159:23）。範囲を限ると、同じ指摘が画面ごとに繰り返される。
- 外部の指針も同じことを言う（design.md の外部事例）。

## 却下した案

- サーバーの日本語の文を言い換えるだけ: 英語画面で日本語が出たまま。文がサーバーと画面の2か所に分かれる。
- 画面ごとに文を足すだけ（機械の見張りなし）: 新しい画面で同じ欠けが入る。PO の恒久ルール（同じ種類のミスは二度と通さない）に反する。
- 全件を一度に直す: 1056 か所。変更が大きすぎて確かめられない。

## 維持の仕組み

- CI の見張り（design.md §5）: サーバーの文の直書きの数・次の行動が無い文言の数が、記録した基準値を超えたら落ちる。
- 便ごとに基準値を下げ、基準値のファイルの変更履歴で減り方が見える。
