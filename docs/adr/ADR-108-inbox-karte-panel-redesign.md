# ADR-108: 受信箱カルテの表示再編（商談／顧客／連絡先の再編・段階出し分け）

**Status**: Proposed
**日付**: 2026-06-04
**配置先**: `docs/adr/`
**関連**: ADR-109（status の SSOT化）/ ADR-012（What/How 分離）/ ADR-025 / デザイントークン
**UIリファレンス**: [`docs/adr/karte_reference.html`](./karte_reference.html)（見た目の正本）

> このADRは What／Why／Scope のみを記す。実装手順（How）は Generator に委ねる。
> 再現性は「画面別 受け入れ条件（観測可能な挙動）」で担保する。

> **正本性**: 本ADRが当該領域（受信箱カルテ）の正本。既存実装と矛盾する点は本ADRに寄せる。
> conform は通常パイプライン（`deploy.yml`）で、手動VPS作業はしない。

---

## Why

- `InboxKartePanel` の「商談情報」タブが SFA（商談の状態）と CRM（顧客の不変ファクト）を1タブに混在。成約後も同じ長大フォームが出て、引き継ぎ時に要点が掴めない。
- 連絡先タブは手入力URL欄・旧式 DISCORD ID 形式で属人的。
- 全項目は `leads` テーブルに存在し、見せ方の問題は DB構造を変えずに解消できる。
- 段階の先頭値が CRM語彙「リード」と乖離（実値 "新規"）。本ADRは表示で「リード」ラベルを用い、値の正常化は ADR-109（status の SSOT化）で行う。

---

## What

**表示の再編のみ。データ構造（テーブル／カラム配置・`status` 値）は変更しない。**
値の正常化・新規項目・担当者列・登録フォーム送付は別ADR。

1. カルテ3タブを再編：**商談**（SFA・編集）／**顧客**（CRM・要点＋実績要約）／**連絡先**（リンク・読み取り）。タブ内部ID（`deal`／`contact`／`company`）は維持し、表示ラベルと中身を再編。

2. 既存 `leads` 項目を各タブに振り分け直す（移動でなく表示位置の変更）:
   - **商談タブ**: `next_action`（＋`next_action_date`）／`response_speed`／`temperature`／`challenge`／`competitor_check`／`estimated_scale`／`monthly_forecast`／`per_order_amount`／`monthly_frequency`／`meeting_memo`
   - **顧客タブ**: `nickname`／`country`／`customer_type`／`target_titles`／`sales_form`／`cs_memo` ＋ 実績サマリー（読み取り）
   - **連絡先タブ**: `email`／`phone`／各チャネルの「開く」リンク

3. 顧客タブは段階によらず同一レイアウト（フルスペック）。段階で変えるのは「既定で開くタブ」のみ（成約前＝商談タブ／成約後＝顧客タブ）。未取得項目は「未入力」、取引実績が無ければ取引額累計に「取引実績なし」。

4. 実績サマリー（取引額・会話数・最終会話）を顧客タブに読み取り専用で表示。取引額＝`invoices` の `paid_at` 非NULL かつ `voided_at` NULL の合計。判定は `status` ではなく invoice データ。

5. 連絡先タブで Discord は既存の自動ID（`discord_user_id`／`discord_guild_channel_id`）から「開く」リンクを表示。

6. 連絡先タブの手入力URL欄は廃止し、IDからのリンクに統一。Discord は即時。Messenger／Instagram は Meta連携WS が相手ID・検証状態を供給次第（それまで「未連携」を明示）。

7. 固定アクションバー：段階で主アクションを出し分け（残りはオーバーフロー）。起動先は既存機能に接続。

8. 文言は i18n（`ja.json`／`en.json`）にキー追加で管理。直書きしない。先頭段階の表示ラベル「リード」は i18n のラベルとして与える（内部値は現状の "新規"。値の不変コード化は ADR-109）。

9. 失注・対象外・アーカイブに対し、カルテは専用挙動を持たない（一覧側で扱う）。

## Scope外（別ADRへ）

- `leads` → `deals`／`companies`／`contacts` の DB正規化
- `status` の SSOT化（不変コード＋i18nラベル）→ ADR-109
- 新規メッセージ→自動リード化／自動昇格・降格
- `leads.assigned_to`（担当者表示・割当UI）＋歴代担当
- 登録フォーム／登録リンク送付機能の新設
- Messenger／Instagram の ID→リンク生成・未検証バッジ（Meta連携WS）
- 新規項目（言語・TZ／決済・通貨・支払条件／注意事項アラート）

---

## 事業上の制約

- マルチテナント：他テナントのデータを描画しない。
- 取引額は `invoices` に依存。`paid_at`／`voided_at` の整合を実装時に確認。

## 段階（status）の扱い（実値・確認済み）

| 表示ラベル | 内部値（現状） | 備考 |
|---|---|---|
| リード | `新規` | 先頭段階。内部値の正常化は ADR-109 |
| 商談中 | `商談中` | |
| 既存顧客 | `既存顧客` | 成約後 |
| 追客（短期） | `追客（短期）` | 成約後 |
| 追客（長期） | `追客（長期）` | 成約後 |
| 失注 | `失注` | カルテ専用挙動なし |
| 対象外 | `対象外` | カルテ専用挙動なし |

- UIの「リード」フィルタ＝`status` "新規"。「追客」フィルタ＝"追客（短期）"＋"追客（長期）" を集約。
- 既定タブ：成約前（リード・商談中）＝商談タブ／成約後（既存顧客・追客短期・追客長期）＝顧客タブ。
- アーカイブ＝受信箱「アーカイブ」タブ＝`status` IN ("失注", "対象外")。カルテ設計には非依存。

## 画面別 受け入れ条件（観測可能な挙動）

対象: `InboxKartePanel`

**実装後のカルテUIは、添付の高忠実度リファレンス（[`docs/adr/karte_reference.html`](./karte_reference.html)）に一致すること**を本ADRの受け入れ基準とする。
一致の対象は「タブ構成・項目の並びとグルーピング・編集／読み取り（派生）の別・段階による既定タブと主アクション・固定アクションバー」。
色・フォント・余白の最終トーンは Sales Anchor 既存のデザインシステム（Tailwind＋トークン）に従い、ピクセル一致は求めない。
リファレンス上の「追加予定」タグの項目は本ADRのスコープ外。

### 個別チェックリスト

- [ ] 商談タブには SFA の10項目のみが表示・編集できる。`nickname`／`country`／`customer_type`／`target_titles`／`sales_form` は商談タブに表示されない。
- [ ] 顧客タブには `nickname`／`country`／`customer_type`／`target_titles`／`sales_form`／`cs_memo` と実績サマリー（取引額・会話数・最終会話）が表示される。実績サマリーは編集不可。
- [ ] 顧客タブは段階によらず同一レイアウト。成約前に未取得の項目は「未入力」と表示され、項目自体は消えない。
- [ ] `status` が "既存顧客"／"追客（短期）"／"追客（長期）" のとき既定で顧客タブが開く。"新規"（表示「リード」）／"商談中" のとき商談タブが開く。
- [ ] 成約後でも商談タブは開けるが、進行中の商談が無ければ「進行中の商談なし」を表示する。
- [ ] 取引額累計は、`invoices` の `paid_at` 非NULL かつ `voided_at` NULL の合計に一致する。該当が1件も無いとき「取引実績なし」と表示する（`status` で判定しない）。
- [ ] 連絡先タブで `discord_guild_channel_id` がある場合は「Discordで開く」リンクが表示され、押すと該当チャンネルが開く。
- [ ] 連絡先タブに、手入力URL欄（`messenger_link`／`instagram_link`／`whatsapp_link`）と旧式 DISCORD ID（username#0000 形式）の入力欄は表示されない。Meta系チャネルは相手ID・検証状態が供給されるまで「未連携」を明示する。
- [ ] 固定アクションバー：リード＝「商談化（営業へ引き渡し）」（既存の変換機能で起動）。既存顧客＝見積・請求書作成。残りはオーバーフロー。起動先が未実装のアクション（登録リンク送付等）は表示しない。
- [ ] 失注・対象外・アーカイブの状態でも、カルテは専用挙動を取らず通常どおり描画される。
- [ ] 新規ラベルは `ja.json`／`en.json` にキーがあり、ハードコード日本語がない（ESLint `local/no-japanese-literal` を通る）。
- [ ] どの段階でも他テナントのデータは描画されない。
- [ ] Evaluator（Layer 1: Playwright）で、リード／既存顧客 の各段階・3タブ（商談／顧客／連絡先）の画面が、添付リファレンスの構成・項目の並び・編集/読み取りの別・段階別の主アクションと一致することを確認する（色・フォント・余白は既存DS準拠で可、ピクセル一致は不問）。
