## Context（なぜ必要か）

- 今は、不具合を見つけた PO がチャットで AI に伝え、PO が作業を開いて直させている。PO の願いは「不具合用の Discord チャンネルに書くと、agent-console が Opus の作業を自動で開き、調べて直し、効果を測り、合格まで回す」こと。
- 前の受付（ADR-1009）は Claude Code の常駐の受付で、公式のプラグインはボットや webhook の投稿を捨てる。自前版は起動のたびに対話の確認が要り、無人で起こし直せない。
- 解析の誤り報告（ADR-1025）は、agent-console が Discord のチャンネルを読む形で本番に入っている。同じ受け口を使える。
- 同じ Mac の同じ利用者で動かすため、件の作業は利用者の権限を持つ。指示（プロンプト）は防壁にならない（ADR-1012 Why）。

## Decision（何を決めたか）

1. 受け口は agent-console の1つの部品で、不具合受付と誤り報告の2つのチャンネルを 30 秒ごとに Discord の REST で読む（外へ出る通信だけ。受け付けのポートを開けない）。返る順は新しい順なので、id を BigInt で小さい順に並べ直し、最後に処理した id より大きいものだけを受ける。100 件返ったら after で古い方から続きを読む（最大5回）。受ける種類は通常の投稿と返信だけにする（第0段 0-3）。
2. 許可するサーバー・チャンネル・投稿者を決め、それ以外は捨てる。投稿者は最初は PO だけ（§14-1）。投稿の id で重複を防ぐ。投稿の本文はデータとして囲んで渡す。
3. ボットの権限は、読む2つのチャンネルの「見る」「履歴を読む」だけにする（第0段 0-7 で本番のサーバーに適用済み）。
4. 種類ごとに1件ずつ同時に動かせる。数の上限を設ける。1時間の関門は「開始の差が60分未満」で、PO が画面から作る予約には関門をかけず、確認の欄で重なりを見せる（§14-2）。
5. 全停止は既存の `halt_all` を見る。誤り報告の側にも効かせる。再開は super admin のログインだけ（§14-7）。
6. Discord 発の作業は、起動の引数で道具を絞った役割 `discord-case`・`discord-measure` で動かす。引数は再開のたびに付け直す（第0段 0-4: 再開では引き継がれない）。名前の形の拒否（`Bash(curl *)` など）は絶対パス・`bash -c` で抜けられるため（0-4）、外への通信と秘密の置き場は、サンドボックスの行き先の許可と `filesystem.denyRead` で塞ぐ（0-15・0-21・0-5）。
7. 秘密を環境変数に置かない。ボットの鍵と報告の webhook は Keychain に置き、件の作業からは読めない設定にする（0-5: 設計の設定では試験用の項目・置き場は全部読めなかった）。例外: shingo-cc の GH_TOKEN だけは、起動の関数が囲いの外で取り、件の作業の環境に渡す（PR を出すため。設計 §4-5・K11。件の作業から `env` で見えるのは避けられない）。値は依頼文・記録・画面に出さない。
8. 件の作業に PR のマージを任せない（§14-5）。修理は PR として既存の審査・CI・GO（ADR-136）を通す。
9. 修正のあと効果測定の予約をサーバーが作る。合格で終わり、不合格なら次の回を予約し、3回続けて不合格なら止めて PO に報告する。
10. Discord 発の不具合の行は、段階6 より前から ADR-1012 の障害記録の表に入れ、`labels.source='discord'` で分ける（§14-9）。
11. ADR-1009 は全部置き換える（§14-4）。前の受付はやめる。
12. 件の作業に渡す指示書と、ADR-1012 Decision 5 の共用の担当定義は `docs/ai-agents/ops-incident-agent.md` の1ファイルにする（正本は1か所。まだ無い。本件の便2 で先に作る）。
13. 件の worktree の作成と作業前の確かめは、件の作業を開く前に囲いの外で行う。囲いの外で件の worktree に向けて動かす git には `-c core.fsmonitor=false -c core.hooksPath=/dev/null` を付け、`status`・`diff` には `--ignore-submodules=all` も付ける。フックが動く命令（commit・checkout・merge・push・rebase など）は囲いの外から件の worktree に向けて動かさない。件の作業から `.git/hooks`・`.git/config`・件の worktree の `.git` ファイル・`.git/worktrees/<名>/commondir`・`gitdir` は書けない設定にする（第0段 0-19 で `.git/hooks`・`.git/config` の拒否と commit の両立を確かめた。本物のリポジトリでは便2 で確かめる）。

## Why（なぜこの形か）

- 読みに行く形は、Mac に受付口が増えず、常駐の Claude Code が要らない。眠っていた間の投稿も「最後に処理した id より後」を読めば取りこぼさない（第0段 0-3: after でページを送ると古い方から取りこぼし無く読めた）。この形は ADR-1025 と同じ。
- 指示書だけでは止められない（ADR-1012 Why）。第0段 0-4・0-5 で、名前の形の拒否は抜けられ、python などの子プロセスでは権限の拒否だけでは秘密が読めると分かった。サンドボックスを足すと、試した道はすべて止まった。
- ボットの権限を2つのチャンネルに絞ると、ボットの鍵が漏れても読めるのはその2つだけになる。

## Consequences（結果）

- 同じ利用者のまま受け入れる弱さが残る（§14-8。PO 2026-10-21「まず3で進め穴を塞ぐ、変えるなら2」）:
  - 拒否の一覧に入れていないファイルは読める。
  - 読んだ秘密を、許可した行き先（GitHub・保守 API）へは出せる。shingo-cc の名義のまま `gh api` で書く道は塞げない。
  - 誤り報告の作業や普通の作業が名乗れる。切り離されたプロセスの見張りは作れない（0-14）。
  - 知らせと監査で見張る。作りを変えるときは別の macOS 利用者で動かす案にする。
- R8（自動の起動とサブスクの関係）は、契約の文面を確かめずに、本件の形（PO の投稿1件ごと・1日10件まで）で進める（§14-3。PO の事業判断）。契約に合わない使い方だった場合に気づけない。
- 保守 API にはステージングの環境が無い。API 側は backend の試験（実 PostgreSQL）で確かめ、本番での確かめは時刻を PO に確かめて行う（第0段 0-9）。
- agent-console は別リポジトリで、本リポジトリの CI が届かない。agent-console 側の試験で守る。
- REST で分類（カテゴリ）の権限を変えると、同期している子チャンネルにも同じ上書きが移る（第0段 0-7 の観測事実）。権限を変えるときは子を書き直して確かめる。

## Exceptions

- 監視アラートの webhook 投稿を受けることは本 ADR の範囲外（ADR-1012）。
- 誤り報告の件の中身（指示書・専用の鍵・照合・再解析）は ADR-1025 の決まりのまま変えない（同時1・1時間6・同じ番号1回・5分以内に開く・決まった指示文）。
- 件の作業場所（PO 2026-10-26 チャット「1」。件ごとに本店から切り離した写しにする案への回答。設計第18〜20版 §4-5「件ごとの写し」）: Discord の件のセッションの作業場所は、`scripts/new-worktree.sh` の linked worktree ではなく、agent-console の常駐サーバーが囲いの外で作る、本店から切り離した丸ごとの写し（`git clone --no-hardlinks --local`。置き場 `~/worktrees/discord-cases/<セッション id>`・枝 `release/discord-case-<id の先頭8字>`・origin/main 起点）とする。linked worktree では、囲いの中の命令が本店の共有の `.git` に書けてしまうため。
  - 台帳への登録は `scripts/new-worktree.sh` と同じ書式で、agent-console が写しの中の `.claude-pipeline/active-work.d/` に書く（push の前の検査 `scripts/validate-pr-ownership.sh` が写しの中の台帳を読むため）。この台帳のファイルは件の PR に入ってよい。
  - 件のセッションは `--no-verify` を使わない（commit・push の前の検査を飛ばさない）。
  - 上限・自動回収（ADR-114 の worktree の上限・自動回収）は件の写しに当たらない。終わった件の写しの片付けは agent-console の便2b-4 で決める。
