## What（何を決めたか）

1. 会社（companies）と連絡先（contacts）の status に入る4つの記号（active・inactive・archived・pending_dedup_review）・日英の名前・並び順の正本を、共用の表 `public.customer_statuses` の行にする。会社ごとの独自の状態は持たない（tenant_id 列なし）。
2. 行は運営の手作業（PO の `!`・ADR-1007）で入れる。表の読みは誰でも全行、書きは運営（`app.is_operator`）だけ。
3. 会社・連絡先の status 列は、この表の code を指す外部キーにする（今の CHECK 制約を置き換える・便2）。
4. 画面の選択肢・札の名前・統合の小窓の文は、API からこの表を読む（便3）。作る画面の選択肢には `selectable_on_create = TRUE` の行だけを出し、直す画面にはすべての有効な行を出す。
5. 色の種類は今のまま `statusPresentation.ts`（ADR-120）に残す。名前の出所だけが DB になる。
6. サーバー側の記号の列挙は、試験で表の行と一致することを確かめる。

## Why（なぜ）

- 今は同じ4つの値が、DB の CHECK・サーバーのコード・画面の辞書と分岐など複数の場所に書かれ、ずれても気づけない（recon §1）。分析で状態を数えるとき、正本が1つでないと数の意味が揃わない。
- 共用の表にすると、名前や並びを変えるのは行の書き換え1回で済み、外部キーで知らない値が入るのを DB が止める。
- 前例のチャネル名簿（public.channel_masters・PR #5206）と同じ型で、作る→1回だけ入れる→付け替える、の順が本番で通っている（design §12-3）。
- 外部キーは NOT VALID で付けて別の回に確かめる。鍵待ちで後ろの読み書きを止めないため（design §12-1・§12-2、ADR-1037）。

## 受け入れたリスク

- 見込み客（leads）の状態は今回変えない。正本が2系統残る（ADR-109・PO 判断待ち）。
- 表を消す・行を消す操作は外部キーで止まる。行を外したいときは is_active を FALSE にする。

## 戻し方

- 便1: 表は残してプログラムが使わない（表を消すのは別便・PO GO）。
- 便2: 外部キーを外して元の CHECK を付け直す migration を流す。
- 便3: 画面と API の PR を戻す。
