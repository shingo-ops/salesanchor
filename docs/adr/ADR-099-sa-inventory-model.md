# ADR-099: 在庫モデル（商品/在庫マスタ分離・在庫ソースA/B・集計フィルタ・在庫イベント）（ADR-SA-05）

## Status
Accepted（A+B混合時の価格採用ルールは未決＝ADR-095付録1）

## Date
2026-06-04（起案: Hikky-dev / PO: shingo-ops）

## Context（背景）

事業者ごとに運用が違う（A専業／B専業／A+B混在）。単価は変動し、同一商品が提供元ごとに別価格・別在庫で存在する。

実データ例：ニンジャスピナーM4 → 島田50@¥11,900／イセキ30@¥11,800／イセキ24@¥10,800

---

## Decision（What / Why / Scope）

### 確定した設計

#### 1. 商品マスタ（カタログ）と在庫マスタ（在庫レコード）の分離

**商品マスタ＝商品の identity（価格・数量を持たない）**

| カラム群 |
|---|
| Category / Mark / 和英タイトル / 梱包 / 重量 / Release Date / Keywords / カテゴリ分類 / MOQ / 品目 / HSコード / 素材 （19列＋ID） |

**在庫マスタ＝商品×提供元ごとのレコード（単価は在庫レコード側の変動値）**

| カラム |
|---|
| 商品ID / 提供元ID / Quantity / Unit Price / Condition / Status / 提供元種別（A/B） |

#### 2. 在庫ソース A/B

在庫レコードの属性（提供元種別）として持つ。売る側（注文/見積/請求）は出どころを気にせず「在庫数」を見る。

| ソース | 真実の場所 | 数量管理 | 発注 |
|---|---|---|---|
| A（自社在庫） | アプリ内 | 売れたら減算 | 不要 |
| B（仕入元フィード） | 仕入元 | **触らない** | 取り寄せが走る |

#### 3. 生オファー（SCM出力同期）＝SSOT

全提供元の全オファー。同一商品が提供元ごとに複数行。

#### 4. 集計同期＝動的ビュー（実テーブルに保存しない）

生オファーに集計フィルタを当てた結果。コピーを手管理しない。

#### 5. 集計フィルタ（採用ポリシー・テナント設定）

| 設定 | 内容 |
|---|---|
| ① フィルタなし | 全提供元表示（**既定**） |
| ② 最安値優先 | しきい値なし |
| ③ バランス | 「価格差¥X以内かつ在庫差Y以上なら高在庫を優先」。X・Yはカスタム設定、初期値0（0のとき上書きが起きず②と同挙動） |

#### 6. A在庫の増減＝2段階管理

```
引当時: 「引当済み（確保）」として利用可能から除く（物理は減らさない）
発送時: 物理を実減算

利用可能 ＝ 物理 − 引当済み

引当キャンセル: 確保を戻すだけ
```

**増えるイベント:**
- 自社仕入れ（古物台帳に取得記録）
- 返品の在庫戻し（→ADR-105）

**Bは引当の概念なし。** フィード数をそのまま「利用可能」とする。

### 仕組み（意図）

A/B分離は「表示の便利」ではなく**納期の約束＝信頼**の機能（A即日／B取り寄せを正確に提示）。A専業/B専業/混在を**同一コード**で吸収。二重売り（オーバーセル）を構造で防止。

---

## 実装上の注意（誤実装防止）

- **集計同期を実テーブルに保存して手/バッチ更新しない。** 生オファー＋フィルタからの**動的ビュー**にする（コピーを持つと食い違う）。
- **Bの数量をアプリが減算しない**（「2つ目の嘘の在庫」を作らない）。Bは日次スナップショットなので売り切れの取りこぼしは残る前提で「取り寄せ」と明示。
- A在庫は**物理在庫数・引当済み数・利用可能数**を持つ。在庫マスタに**提供元種別(A/B)**を必ず持たせ、A/Bで挙動分岐。
- 単価は商品マスタに持たせない（在庫レコード側の変動値）。
- Bフィードは外部連携＝**ADR-025の3点セット（取り込み本体＋状態検証＋失敗通知）必須**。止まると古い在庫＝オーバーセル＝信頼崩壊に直結。
