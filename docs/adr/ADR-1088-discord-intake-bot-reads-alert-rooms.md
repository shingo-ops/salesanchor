## Context（なぜ必要か）

- AI が Discord の知らせ（🚨急ぎ・📋定期の報告・🛠開発の知らせ）を読む道は、本番サーバーの Bot「Sales Anchor」の鍵だけだった。この Bot は部屋・役割・送り口の管理まで持つ。読むたびに manual-only の鍵と PO の許可が要った（recon F1・F2）。
- ADR-1039 の受付の Bot（SA Bug Intake）は、読むだけの Bot として作られている（ADR-1039 Decision 3）。
- 2026-11-24 に、この Bot に3部屋の「見る」「履歴を読む」を足し、鍵の写しを ADR-079 の置き場に置いて、AI が Mac から読めるようにした（design §5）。これが ADR-1039 Decision 3 の「読む2つのチャンネル」と食い違うと、マージ前の審査で分かった（review-opus.md）。

## Decision（何を決めたか）

1. ADR-1039 Decision 3 を次のとおり改める。「ボットの権限は、読むチャンネルの『見る』『履歴を読む』だけにする。読むチャンネルは、受付が読む2つ（不具合受付・誤り報告）と、AI が読むだけの知らせの3つ（🚨急ぎ・📋定期の報告・🛠開発の知らせ）とする」。
2. 知らせの3部屋では、この Bot の「送る」「反応」「投稿の管理」「リンクの埋め込み」「添付」「スレッドを作る」「スレッドで送る」を止める（部屋ごとの上書きの deny。design §3）。
3. agent-console の受付は、今までどおり受付の2部屋だけを読む。知らせの3部屋は受付の対象にしない。
4. AI が読むための鍵の写しは `~/.claude-access.env`（ADR-079 の置き場）の1行だけにする。この置き場は、ADR-1039 Decision 7 の「件の作業から読めない」置き場に、もともと入っている（agent-console v0.55.3 の server/case-sandbox.ts 99 行の CASE_DENY_READ。315〜319 行で囲いの読み取りの拒否に使う。このリポジトリの外）。Decision 7 の目的（件の作業から鍵を読めない）は守れる。置き場が Keychain だけでなくなる点は Exceptions に書く。
5. 読めない（401・403）ときに、AI は強い Bot の鍵に切り替えない。止めて PO に知らせる。

## Why（なぜこの形か）

- 読むたびに強い鍵と PO の許可を使う回数を 0 にできる。新しい Bot を作る案（PO の画面の作業が5つ）より、PO の作業が少ない（design §4）。
- 鍵が漏れたときに読まれる部屋は、2つから5つに増える。増える3部屋は、見張りの仕組み（webhook）が障害・点検の知らせを流す部屋である。チケットの部屋（お客様との会話）など、ほかの20部屋は今までどおり読めない（design §6 G3。2026-11-24 に全25部屋で確かめた）。
- 書く権限は増やしていない。3部屋への投稿・部屋の変更・送り口の一覧はどれも 403 だった（design §6 G2）。

## Consequences（結果）

- 同じ鍵が2か所（Keychain と ADR-079 の置き場）にある。受付の Bot の鍵を作り直したら、PO が写しの台本をもう一度 ! で流す。AI は 401 で気付く。
- 部屋の権限をまとめて書き直すときは、知らせの3部屋の上書きを消さないこと。消すと AI が知らせを読めなくなる。
- 戻し方: 3部屋の上書きを allow 67584・deny 1024 に戻し、置き場の1行を消す（design §7）。戻したら本 ADR を Superseded にする。

## Exceptions

- ADR-1039 Decision 7 の「ボットの鍵は Keychain に置く」の例外として、SA Bug Intake の鍵の写しを ADR-079 の置き場 `~/.claude-access.env` に1行だけ置く。写しは PO が ! で行う（2026-11-24 PO「1」で選んだ案 A'。design §4）。AI が Keychain を開く道は作らない（go-identity-guard はゆるめない）。
