## What（何を決めたか）

1. 管理者は役割を選んで招待リンクを作る。リンクは手で送り、アプリはメールを送らない。リンクは 72 時間、1 回限り。作り直すと古いリンクは開けなくなる。
2. 招待は新しい表 public.staff_join_invites に置く。この表は FORCE RLS とする。鍵と番号は sha256 だけを保存し、人の名前やメールは置かない。
3. 申込で作る人は、今の新規作成と同じ1つの関数で作る（public.users・staff・user_roles）。staff の状態は「登録待ち」にする。users は無効（is_active=false）で作り、Discord の照合で有効にする。既存の users は使い回さず、同じメールがあれば断る。役割の付与者は、招待を作った人で、申込の時点で停止・権限の有無を検査し直す。
4. 申込の完了画面に、登録番号（16 文字）と、自社サーバーの「スタッフ受付」への招待リンクを出す。
5. 自社サーバーの受付で番号が合うと、次を行う。
   - 本人、Bot、アプリで staff.create を持つ役割の Discord ロールだけが見える個室を作る。
   - Discord ID を staff に入れる。
   - 仮パスワードを個室に出し、変えるまで止める。
   - ロール合わせを予約する。
   - お客様のチケットの道には入らない。
6. 「変えるまで止める」は、public.users.password_must_change と get_current_user の 403 password_change_required で行う。止めない道は1か所の一覧に置く。
7. 生体認証と認証アプリを登録するまで止める仕組みと、「有効」への自動切り替えは、認証アプリが本番に入った後に別の設計で決める。

## Why（なぜ）

- 管理者が人ごとに全項目を書く手間と、Discord ID を手で入れるときの誤りをなくす（PO の願い）。
- 閲覧者の申込で同じ形がすでに本番で動いているため、新しい仕組みを作らずに写せば危険が少ない。
- 招待を別の表にするのは、人の正本（public.users・staff）に招待の状態を混ぜないため（ADR-1008）。
- 申込の時点で無効にしておくのは、パスワード再設定の道から Discord を通らずに入れてしまうのをコードで止めるため（設計審査 R1）。
- パスワードは Discord の個室に出す。PO がメールを使わない形を選んだため。閲覧者と同じ形でもある。
