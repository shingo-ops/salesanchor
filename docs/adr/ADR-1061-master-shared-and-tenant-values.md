## What（何を決めたか）

1. 選択肢の表（マスタ）は、public の表 1 つに置く。会社の区画に写しを作らない。
2. 行の持ち主は `tenant_id` で表す。空（NULL）は全社共用、数字は会社独自。
3. 全社共用の値は、運営側の管理画面と LINE 解析から書く。書くときは `set_operator_context` で運営の印（`app.is_operator='true'`）を立て、commit の後に `reset_operator_context` で戻す。
4. 会社独自の値は、その会社の管理センターから書く。その会社の中でだけ見え、使われる。
5. 各社は、全社共用の値を見られるが、直せない・消せない。窓口は 403 で断り、画面は「共用」の印を付けて編集のボタンを出さない。
6. 3〜5 は、表の守り（FORCE ROW LEVEL SECURITY と 4 つの決まり。文は suppliers と同じ）で DB が強制する。
7. LINE 解析は、全社共用の値だけを使う。読む文に `tenant_id IS NULL` を書く。
8. 業務データ（リード・商談・注文・顧客）は、この決まりの外。各社の区画のまま。業務データは選択肢のコードか番号だけを持ち、表示名を写さない。
9. 新しい選択肢の表を作るときは、1〜7 の型に合わせる。
10. 例外: 役割（ロール）。初期の役割と権限は、運営だけが書く共用のひな形の表（public.role_templates・public.role_template_permissions）に置き、コードの定数に書かない。会社の役割・役割の権限・人と役割は、会社の区画に残す。会社は写した役割の名前・権限を直せ、足せ、消せる。オーナーは直せない・消せない。システム管理者は会社を作るときに写さず、運営の会社だけに置く。設計 §13。

## Why（なぜ）

- PO の要件定義（2026-11-05）: 共用は運営が足す初期値、会社独自は社長が足して自社だけで使う値。共用は見られるが直せない。会社の値は LINE 解析で使わない。
- 本番で、6 つの選択肢の表に表の守りが無く、LINE 解析は会社の行も読む作りだった。会社が 1 行足すと、全社の解析に入る。
- 連絡ツールは会社ごとに写しを持ち、5 社×6 行が同じ値だった。共用の値を直すと全社の写しを直す必要がある。値の置き場所が分散する。
- 同じ型（products・suppliers・translation_glossary）が本番で動いている。型を 1 つにすると、作る人も審査する人も迷わない。
- 役割を例外にする理由: 本番で営業・CS の権限は会社ごとに既に違い、役割は人の付け方（user_roles）と結び付いた会社の業務データだった。共用にすべきなのは初期値だけ。全部を public に移すと役割の表を読む 24 ファイルと 5 社分のデータを移す必要があり、戻すのも重い（設計 §13-3）。PO（2026-11-05）「ロールもロール権限もカスタマイズできるようにしたい」。

## 受け入れた点

- 運営専用で会社の列を持たない表（形式・種類・ライン・数量の単位・重さの区分など）は、会社の層を作らず共用だけのまま。LINE 解析専用で、会社の値は解析で使わないため。
- 失注・成約理由、会社の画面からの商品追加、発送地域・送料は、この ADR の採用時点では型に揃えていない（残件。設計 §9）。

## 戻し方

- 表の守り: 各表で `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` と `DISABLE ROW LEVEL SECURITY` を流す（決まりは残してよい）。
- 解析の読む文: 便1 の PR を revert する。
- 連絡ツール・流入元: 新しい表を読む所の切り替えを revert する。古い区画の表は、便6 で消すまで残す。

## 見直す条件

- 会社が自社の値を LINE 解析でも使いたいと PO が決めたとき。
- 運営専用の表に、会社ごとの値が要るとき。
