## What（何を決めるか）

1. 解析の保存 public.analysis_results に「まとめの数」bundle_size（整数・NULL＝まとめ売りでない）を持つ。「40パックセット」の文字は保存しない。
2. まとめ売りの読み取りは区分を問わず全ての行に当てる。形は「数 N＋単位の語＋まとめの語」（N は 2 以上・括弧の中と直後が「入」の当たりは使わない）。単位の語は単位の別名マスタ（line_unit_aliases）から作り、コードに持たない。canonical が Set の別名（セット・set）は単位の語に使わない。
3. まとめ売りと決まった行は、値段・数量を割らない・掛けない。単位は中身の単位にそろえる。状態は今の決め方のまま。
4. 本文だけでは決まらない行（値段が無い、数量がまとめの数で割り切れて「セット」と書かれていない、単位の語が別名マスタに無い、違う大きさのまとめが2つ以上）は、値を変えずに理由 bundle_unverified を付けて要確認にし、配信しない。この理由は人の「このままで良い」で外せる（NON_ACKABLE に入れない）。
5. 商品名の欄は配信 SQL の 1 か所で「商品名 N＋単位の呼び名＋セット」（英語は「name N unit Set」）にする。単位の呼び名は単位マスタ public.line_units の name_ja・name_en に置き、無いときは canonical を使う。
6. まとめ売りの行は、単価の確かめの相場・価格の引き継ぎ・買取単位の判定から外す。同じ行をまとめる鍵に bundle_size を入れる。
7. ADR-1021 便2 の set の換算（値段÷N・数量×N・単位 Piece・備考「N枚セット単位」・price_basis `V102:bulk:set:N`）はやめる。便2 の piece と review はそのまま。

## 現行かどうかの決め方（2026-10-18 追記）

- 現行（is_current）を決めるキーは (supplier_channel_id, product_id, condition_id) のままにし、bundle_size を入れない。
- 理由: 新しい投稿＝その仕入元の今の在庫を表すため。
- 影響: 同じ仕入元が後で同じ商品をバラや別のまとめ数で出すと、古いまとめの行は現行から外れる。2026-10-18 時点では観測 0 件。
- 根拠: backend/app/services/tcg_analyzer_svc.py の `_merge_supplier_products`（1951 行〜）の UPDATE（2076 行〜。組は product_id・condition_id で、同じ仕入元 sm.supplier_channel_id の中で最新の投稿を 1 つ決める。2031〜2073 行）。
- PO 決定: 2026-10-18、チャットでの回答は「y」。

## Why

- PO の指定が「値段はまとめ1つの値段・割らない」「数量はまとめの数」で、ADR-1021 便2 の決定と逆。
- 本番の現行 4,804 行の試しで、まとめ売りの当たり 152 行のうちバルク系は 19 行だけ。区分で入口を絞ると 133 行に効かない。
- 本番の別名マスタで規則を当てると、決まる 82 種 144 行・決まらない 5 種 5 行・当たらない 4,655 行。「N＋別名に無い語＋まとめの語」の 135 行は全て品名や中身の説明で、単位のまとめ売りの取りこぼしは 0（design.md §5-2）。
- 当たった単位の語（パック・個・枚）は全て単位の別名マスタにある。マスタから語を作れば、新しい単位の登録がそのまま読み取りに効き、語の表が 2 か所にならない。
- 商品名の欄を配信 SQL の 1 か所で作ると、アプリ在庫表・閲覧ページ・GAS は同じ欄を読むだけなので、画面ごとに作らずに済む。
- まとめの値段を 1 個の相場と比べると「単位と値段が合わない」になる（例の行が今そうなって配信に出ていない）。

## 戻し方

コードの PR を revert → まとめ売りで保存した行を reanalyze_v102_job でやり直す（Gemini は呼ばない）→ 単位の呼び名と理由コードは rollback の SQL で消す。列（bundle_size・name_ja・name_en）は NULL 許可で残してよい（読む処理が無くなるため）。

## 維持の仕組み

- 単体テスト（形・括弧・入・N=1・複数・値段なし・割り切れ・セット付き・別名に無い語・バルク系で割らない・相場と引き継ぎと買取から外す・商品名と鍵の作り方・単位の語をコードに書かない）が CI で毎回走る。
- 規則を変える便は、PR の前に scripts/dev/bundle_replay.py で本番の全行（リポジトリの外のデータ）に当て直し、決まる・決まらない・当たらないの数を PR 本文に書く。
- 決まらない行は要確認の欄に理由 bundle_unverified で出て、人が見る。
- 理由コードの定数・記録した SQL・ja/en・ラベル JSON のずれは、既存の整合テスト（backend/tests/test_review_reason_codes_consistency.py・test_review_reason_labels_ja_sync.py）が CI で赤にする。
- bundle_replay.py は「N＋別名に無い語＋まとめの語」の語を数えて出す。新しい語が出たら規則かマスタを見直す（自動の通知は無い）。
