## What（何を決めるか）

1. 新しい表 `public.product_packagings` を作る。1行は「ある商品の、ある単位 1 つ分」。中に入る単位とその数、その単位 1 つの重さを持つ。
   - 例: 商品X｜CASE｜中は BOX｜12｜5.5 kg、商品X｜BOX｜中は PACK｜30｜0.300 kg、商品X｜PACK｜中は CARD｜5｜（重さ空）
2. 単位は `public.quantity_units` の id で指す（販売単位の名簿。今は CASE/BOX/PACK）。1 パックの枚数のために CARD を名簿に足す。`product_lines`（商品の系統: BOX・SINGLE など）は「商品の行が何か」を分ける別の名簿なので、変えない。
3. 入数と重さそれぞれに、出典の種類と出典の URL を持たせる。出典の種類は 5 つ:
   - `official` 公式サイト／`official_store` 公式通販（例: ポケモンセンターオンライン）／`retailer` 販売サイト／`measured` 実測／`legacy` 古い列から写した値（出典が残っていない）
   - 採用の決まり（PO 2026-10-17）: 公式と公式通販は出典 1 つで採用。販売サイトは 2 つ以上の一致で採用（表の制約で URL 2 つ以上を強制）。カートンとパックの重さは実測。
4. 入数・重さの正本はこの表だけにする。products の `boxes_per_case`・`packs_per_box`・`box_weight_kg`・`case_weight_kg` の値はこの表へ写し、読む所を全部この表に切り替えた後に列を消す。使われていない `products.quantity_unit_id`・`products.weight_class_id`・表 `product_quantity_units`・`quantity_units.value` も同時に消す。

## Why（なぜ）

- products は列番号が上限 1600 に達していて、新しい項目（パックの枚数・出典など）を足せない（ADR-1026）。
- 入数は商品ごとに違う。同じ「ボックスのブースターパック」でも 1 箱のパック数は 30・24・20・10・4・12・15 の 7 種（/tmp/CC報告ファイル/product-qty-weight/recon/ q5a, q6b）。細分類や系統に 1 つの値を持たせると値を失う。
- 単位ごとの値を列で持つと、単位が増えるたびに列が要る（今は CASE と BOX の分しか無く、PACK→CARD を書く場所が無い）。
- 単位の表は作りかけのまま止まっていて（quantity_units の value は全て空、product_quantity_units 0 件）、同じ意味の入れ物が列と表の 2 か所にある。PO の決まり「配線と DB の SSOT を守り、データを分散させない」（2026-10-17）に合わせ、1 か所にする。
- 外部から取った値は出典で信頼度が違う（recon.md §5: 輸出店の重さは公式通販と 4 商品で食い違った）。値と一緒に出典を残さないと、後で正しい値か判断できない。

## 選ばなかった案

- **product_quantity_units を使い続ける**: 列が value 1 つで、重さ・中の単位・出典を持てない。作り直すのと同じ手間で、名前も中身と合わない。
- **product_lines の CASE/BOX/PACK を単位に使う**: product_lines は商品の行の分類で、BOX が 1247 行に使われている。単位の名簿と混ぜると「この商品は何か」と「何個入りか」の 2 つの意味を 1 つの id に持たせることになる。
- **細分類や系統ごとに入数を 1 つ持つ**: 同じ細分類で 7 種に分かれるため値を失う。
- **列のまま残す**: 足せない・単位を増やせない・出典を持てない。

## 守ること・危ないこと

- 値は migration で書かない（ADR-155・ADR-1007）。古い列からの写しと CARD の追加は「1回だけのデータ変更」（DRY-RUN→COMMIT、docs/handoff/product-packaging/ に SQL と記録）。
- 読む所を切り替える前に列を消すと、見積・請求の重さと在庫検索が空になる。だから「表を作る→写す→読む所を切り替える→消す」の順を守り、消す段は最後にする。
- 古い列を消す段は DROP COLUMN/TABLE を含むので、PO 本人の「GO #PR番号」を受けてから入れる。products の列は消すと二度と足せない（列番号の上限）ので、消す直前に値を CSV に退避する。
- `moq`（最小発注数）・`weight`・`volume_weight` は荷姿ではない（注文の条件・単品の重さ・容積の重さ）ので、この ADR では変えない。
