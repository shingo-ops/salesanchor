## What（何を決めたか）

1. 管理者（`users.is_super_admin` が true の人と、ロールが owner か admin の人）は、パスワードだけでは全権のトークンを受け取れない。判定は既存の正本（`is_tenant_admin`・`get_user_system_keys`）を使い、新しい管理者の列や名簿は作らない。判定に失敗したときは管理者として扱う。
2. 管理者が全権で入れるのは、パスキー（指紋・顔）か、パスワードと認証アプリの6桁の数字のどちらか。どちらでも全部の画面を使える。トークンの amr は ["webauthn"] か ["pwd","otp"]。トークンに scope（full か enroll）を持たせる。refresh で強さを失わないよう、refresh の組に amr を記録して引き継ぎ、refresh のたびに判定をやり直す。トークンを出す口（ログイン・6桁・承認待ち・パスキー・refresh）はすべて1つの共通の判定を通る。自社のトークンは認証のキャッシュに入れず、毎回 scope と amr を確かめる。
3. 「パスワード＋6桁」で初めての機器から入るときは、いつもの機器の画面で、初めての機器に出た2けたの番号を3つの候補から選ぶ承認を必須にする。承認の画面には依頼した機器のブラウザ名と時刻を出す。違う番号を選ぶか「心当たりがない」を押すと依頼を取り消す。パスキーで入るときは承認は要らない。
4. 承認の知らせは、開いている画面（ADR-1016 の SSE 1本に人単位の範囲と宛先 `rt:u:{user_id}` を足す）とメールで送る。承認そのものは、いつもの機器の画面の中でだけ行う。メールに承認のボタンやリンクは置かない。
5. 6桁の秘密は子表 `public.user_totp` に既存の暗号部品（`encryption.encrypt`）で暗号化して置く。いつもの機器は子表 `public.user_trusted_devices` に cookie の値のハッシュだけを置く。承認の依頼と、パスワードと6桁の間の券は Redis に5分・1回限りで置く。6桁の外れは既存の `failed_login_count` と IP の失敗の数に数え、2段階を設定済みの人はパスワードが合っても数を戻さない。券は1人1枚で、止められている人は6桁の口でも拒む。
6. 2段階を設定していない管理者は、パスワードで入ると設定だけができる短いトークン（scope=enroll・15分）を受け取る。
7. 2段階を設定済みの管理者には、設定 `ADMIN_2FA_ENFORCED` の値に関係なく2段階と承認を求める。この設定が決めるのは、未設定の管理者に設定だけのトークンを出すかと、管理者の Firebase のトークンを拒むかの2つ。必須化は `ADMIN_2FA_ENFORCED`（既定 false）で入れ、全員の設定が済んだことを数え、管理者の今の refresh の組を失効させてから PO の GO で true にする。true の間は、管理者の Firebase のトークンを拒む（キャッシュに当たった場合も）。
8. 管理者でない人は、今のまま（ADR-1013 Decision 7: 6桁は任意）。

## Why（なぜ）

- 管理者の権限は全社のデータに届くため、パスワードが漏れただけで入られる状態をなくす。2026-10-27 の本番の読み取りで、有効な管理者3人とも2段階の確認が無い（パスキー0件・6桁の仕組みなし）。
- 6桁の数字は偽のログイン画面に打ち込まされると盗まれる。NIST SP 800-63B-4 3.2.5 は手で打つ数字を「フィッシングに強い」と見なしてはならないとする。PO は「どちらでも全部使える」を選んだので、弱い方の入口にだけ、いつもの機器での承認を足して弱さを小さくする。Google のログイン確認と同じ形。ただし、偽の画面が本物の番号を中継し本人が承認してしまう危険は残る。完全に防げるのはパスキーだけで、この残る危険は設計書 §7 に記録する。
- 押すだけの承認は、通知を何度も送られて押してしまう手口に弱い（2022年の Uber の件の記事。Uber の公式発表は未確認）。番号を選ぶ形にし、依頼の数に上限を付ける。
- 今の refresh は amr を引き継がず、Firebase のトークンは発行元の設定に関係なく受け付けられる（設計書 §3-2 に行番号）。この2つの抜け道をふさがないと、2段階を通らない全権が残る。
- 置き場所を子表と既存の SSE・暗号部品・メール部品にするのは、データと配線を分散させないため（ADR-1013 Decision 2、ADR-1016）。

## 守り方

- 発行の判定（login・refresh）と、`require_super_admin`・`require_tenant_admin` の amr 確認を、backend の自動試験で守る（パスワードだけ・6桁の使い回し・違う番号・承認なしの初めての機器がすべて拒否されること）。
- 発行のたびに backend ログに `admin_token_issued`（scope・amr・機器・依頼の id）を1行出し、管理者に scope=full かつ amr=pwd 単独で出た件数が0であることを数える。承認の依頼・承認・取り消しも1行ずつ出し、承認なしで初めての機器に全権が出た件数が0であることを数える。
- refresh での引き継ぎ、scope=enroll の制限、管理者の Firebase トークンの拒否を自動試験で守る。
- QR の金型 `QrCode` は var() のみで、カタログ（Storybook）に載せる。UI ガバナンスの CI で守る。
- 毎週、2段階の確認が無い有効な管理者の人数を本番の読み取りで数え、0 でなければ設計パートナーが対応する。
