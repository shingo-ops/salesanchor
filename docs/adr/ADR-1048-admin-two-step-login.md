## What（何を決めたか）

1. 管理者（`users.is_super_admin` が true の人と、ロールが owner か admin の人）は、パスワードだけでは全権のトークンを受け取れない。判定は既存の正本（`is_tenant_admin`・`get_user_system_keys`）を使い、新しい管理者の列や名簿は作らない。
2. 管理者が全権で入れるのは、パスキー（指紋・顔）か、パスワードと認証アプリの6桁の数字のどちらか。どちらでも全部の画面を使える。トークンの amr は ["webauthn"] か ["pwd","otp"]。
3. 「パスワード＋6桁」で初めての機器から入るときは、いつもの機器の画面で、初めての機器に出た2けたの番号を3つの候補から選ぶ承認を必須にする。違う番号を選ぶか「心当たりがない」を押すと依頼を取り消す。パスキーで入るときは承認は要らない。
4. 承認の知らせは、開いている画面（ADR-1016 の SSE 1本に人単位の宛先を足す）とメールで送る。承認そのものは、いつもの機器の画面の中でだけ行う。メールに承認のボタンやリンクは置かない。
5. 6桁の秘密は子表 `public.user_totp` に既存の暗号部品（`encryption.encrypt`）で暗号化して置く。いつもの機器は子表 `public.user_trusted_devices` に cookie の値のハッシュだけを置く。承認の依頼は Redis に5分・1回限りで置く。
6. 2段階を設定していない管理者は、パスワードで入ると設定だけができる短いトークン（15分）を受け取る。
7. 必須化は設定 `ADMIN_2FA_ENFORCED`（既定 false）で入れ、全員の設定が済んだことを数えてから PO の GO で true にする。
8. 管理者でない人は、今のまま（ADR-1013 Decision 7: 6桁は任意）。

## Why（なぜ）

- 管理者の権限は全社のデータに届くため、パスワードが漏れただけで入られる状態をなくす。2026-10-27 の本番の読み取りで、有効な管理者3人とも2段階の確認が無い（パスキー0件・6桁の仕組みなし）。
- 6桁の数字は偽のログイン画面に打ち込まされると盗まれる。NIST SP 800-63B-4 3.2.5 は手で打つ数字を「フィッシングに強い」と見なしてはならないとする。PO は「どちらでも全部使える」を選んだので、弱い方の入口にだけ、いつもの機器での承認を足して埋める。Google のログイン確認と同じ形。
- 押すだけの承認は、通知を何度も送られて押してしまう手口に弱い（2022年の Uber の件の記事。Uber の公式発表は未確認）。番号を選ぶ形にし、依頼の数に上限を付ける。
- 置き場所を子表と既存の SSE・暗号部品・メール部品にするのは、データと配線を分散させないため（ADR-1013 Decision 2、ADR-1016）。

## 守り方

- 発行の判定（login・refresh）と、`require_super_admin`・`require_tenant_admin` の amr 確認を、backend の自動試験で守る（パスワードだけ・6桁の使い回し・違う番号・承認なしの初めての機器がすべて拒否されること）。
- 発行のたびに backend ログに `admin_token_issued` を1行出し、管理者に amr=pwd 単独で出た件数が0であることを数える。
- QR の金型 `QrCode` は var() のみで、カタログ（Storybook）に載せる。UI ガバナンスの CI で守る。
- 毎週、2段階の確認が無い有効な管理者の人数を本番の読み取りで数え、0 でなければ設計パートナーが対応する。
