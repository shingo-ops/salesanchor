# ADR-1034: Opus が権限を足し引きし、理由を台帳に残して毎週点検する

| 項目 | 内容 |
|------|------|
| ステータス | Proposed（便1のマージ・例外の文の登録・初回点検の後に昇格） |
| 備考 | PO 2026-10-19「日々の業務中にopusが必要と感じたら権限を追加しても良い権限委譲する、代わりに定期実行で追加した許可や削除した許可、意図や理由を確認していまの権限が適切かどうかを確認する仕組みを設けて管理しながらPDCAを回して」 |
| 起案日 | 2026-10-19 |
| 方針の決定者 | Shingo（PO）。範囲は同日の選択肢「1」（保留4項目を残し、ほかは Opus が足し引きする） |
| 関連 | ADR-1011（範囲外の一部を改める。What 6）、ADR-1033（週次点検の定期実行を共有）、ADR-1003（GO 発行の委譲） |

---

## What（何を決めたか）

1. Opus は仕事の途中で、必要と判断した許可の文（~/.claude/settings.json の permissions.allow と、本店の .claude/settings.local.json の permissions.allow）を PO の確認なしに足し引きしてよい。autoMode.allow の文（`SM-` 以外）は外すことだけを Opus が行い、足すのは保留とする。
2. ただし次の4つ（保留4項目）は PO の確認を残す: R1 本番データの削除、R2 main への直接の書き込み、R3 秘密情報、R4 見張りを弱める変更。言い換えで素通りさせないよう、広い許可（R0）も保留にする。R0 は「決まった受け入れの形に当てはまらない文すべて」とし、受け入れの形は設計 §2-2 の (a)〜(e)（決まった読み取りの命令の一覧、リポジトリの一部の場所だけの書き換え、読み取り、名前を指定したサイト、読み取り専用の外部道具）に限る。受け入れの形を広げる変更は PO の確認に残す。hooks・deny/ask・確認を省く設定・danger_ops・フック本体は、今までどおり AI は変えない（R4）。
3. 足し引きは新しい道具 `perm-change.py` だけで行い、道具が「台帳（~/.claude/logs/permission-changes.jsonl）への記録」と「反映」を1回で行う。記録には意図・理由・期待する効果・見直し日を書く。保留は道具が見分けて反映せず、PO が `!` で実行する台本を出す。
4. 週次点検（`consent-audit.py`）の範囲を権限の全種類に広げ、台帳に無い変化・PO 記録（マージ済み PR、同意の台帳、または PO が `!` で走らせた台本の同意票と typed の「1」を会話の記録で照らしたもの）の無い保留の変化・台帳の書き換えを異常として PO に知らせる。
5. Claude Code の自動判定が道具の実行を止めないよう、PO が `!` で autoMode.allow に例外の文 PDL-1 を1つ足す。例外が効くのは ~/.salesanchor-tools から `python3 -I -B` で道具を走らせたときだけで、道具は起動時に、自分と点検の道具が GitHub の main（`git ls-remote` で取る）の版と同じで書き換えられていないことを確かめる。変更が無いのに版が古いときは、道具自身が Mac の自動作業と同じ形で GitHub の main に揃える。設定ファイルや道具を直接書き換えること、AI が自分で ~/.salesanchor-tools の git の設定や参照を変えることは引き続き止める。
6. ADR-1011 の「範囲外」のうち「`SM-` で始まらない allow の文」を、本 ADR の道具を通す場合に限って改める。ADR-1011 のほかの範囲外と `SM-` の手順は変えない。
7. 見直し日を過ぎた権限は、週次点検で効果を確かめて残す／外すを決め、台帳に書く（PDCA）。
8. 許可券の発行を記録に残す（permit_issued）。

## Why（なぜ）

- 権限不足で毎回 PO に頼むと、PO の判断の負荷が増え、仕事が止まる（PO 2026-10-19）。
- これまで AI が権限を変えた記録は `SM-` の文を除いて無く、何がいつ・なぜ変わったか後から分からなかった（設計の現在地 §1・§3）。
- 事前に毎回承認を求めるより、変える前に理由を書かせて事後に必ず照らすほうが、速さと見通しを両立できる。危険の大きい4種だけは事前の確認に残す。

## 受け入れたリスク

- 点検は事後なので、道具を通らない変化（自動判定が見逃した場合）は最長1週間見つからない。
- 目印は文字の照合なので、取りこぼしがありうる。止めすぎに倒し、4週ごとに見直す。
- リポジトリの .claude/settings.json の変更は、マージ済み PR の差分を記録の証にする。Opus は委任により PR をマージできるため、この項目は PR の審査とマージ前の確認に頼る。ほかの保留の項目は PO 本人の同意だけを証にする。
- 許可の文に `grep *` があると、秘密のファイルも読める。ファイルを読む許可とほぼ同じ広さとして受け入れる。読み取りの許可と、名前を指定したサイトへの接続の許可を組み合わせた場合も同じ扱いとし、週次点検で足した理由を確かめる。
- Bash の許可の文は、Claude Code が連結した命令を分けて照合する仕組み（公式の文書の Compound commands）を前提にする。公式の文書は、引数を絞る形の文は壊れやすく、守りの境目ではないと書いている。このため Opus が足せる Bash の文は、読み取りの命令の短い一覧だけに絞る。試験の命令などリポジトリのコードを走らせる文は PO の確認に回る。
- PO が `!` で走らせた台本の同意は、会話の記録（同意票と、その直後に人が打った「1」）が本物であることに頼って照らす。ADR-1033 の同意票と同じ水準として受け入れる。記録が見つからないときは異常として PO に知らせる。
- PO の `!` と AI の実行を区別できないため、許可券の発行元は「AI か PO」としか分からない。

## 戻し方

PO が `docs/handoff/permission-delegation/po-unregister-delegation.sh` を `!` で実行して例外の文を外し、便1 の PR を revert し、週次点検の手順を ADR-1033 の版に戻す。道具が足した文は台帳の新しい順に外す。

## 測り方

台帳に無い変化（毎週 0 件）、保留の PO 記録漏れ（毎週 0 件）、台帳の鎖の切れ（0 件）、見直し期限切れの2週連続の放置（0 件）、権限不足で止まる回数（導入前4週より8週後に減る）。詳細は設計 §5。

## 維持の仕組み

- 守り手: agent-console の定期実行「同意と権限の週次点検」（毎週月曜 09:30）と、その結果を読む Opus。
- 道具の動作は `scripts/dev/permission-delegation-tests.py` の試験で守る。
- 4週ごとに KPI を並べ、保留4項目の目印を見直す。見張りを弱める方向の見直しは PO 確認。
