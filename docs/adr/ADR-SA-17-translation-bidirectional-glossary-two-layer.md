# ADR-SA-17（改訂）翻訳サブシステム — 双方向自動判定・即時翻訳・辞書2層化＋管理UI

- 状態: 起案（Planner: Web Claude）
- 日付: 2026-06-05
- **本ADRは ADR-110（`docs/adr/ADR-110-translation-subsystem`）を改訂・上書きする**
- 関連: ADR-110（翻訳サブシステム 初版）, ADR-025（外部連携 3点セット）, ADR-072（テナントコンテキスト）, ADR-107（顧客優先度: RBAC パターン参照）

## PART 1 — ADR（What / Why / Scope）

### Why（背景）

- 初版 ADR-110 は「受信＝必ず和訳／送信＝英訳」の方向固定。だが実テストで、日本語の受信が日本語のまま表示され混乱した。実運用では「原文の言語を見て反対側へ訳す」方が自然。
- 受信→表示まで最大15分（定期バッチ）。即時性が欲しい。
- 固有名詞辞書を現場の誤訳から育てたい。ただしテナント機密は守る（テナントは互いに競合になり得る）。

### What（この改訂で変えること）

1. 双方向自動判定翻訳
2. 受信時の即時翻訳（Gemini）
3. 辞書の2層化（共有ベース＋テナント私有）
4. 辞書の昇格フロー（テナント→operator承認→共有）
5. 管理UI 2ページ（テナント辞書＝管理センター配下／共有辞書＝SaaS管理者配下）

#### 1. 双方向自動判定

- メッセージの言語を判定し、反対側へ訳す：**日本語→英語／日本語以外（英語・中国語等）→日本語**。
- 送受信の区別ではなく「原文の言語」で訳す向きを決める。
- 表示は従来どおり**原文＋訳の併記**。原文は不変。
- 言語判定で日本語/英語以外が来た場合の target は日本語（非日本語はすべて日本語へ）。

#### 2. 即時翻訳

- 受信 webhook でメッセージ保存後、**即座に翻訳タスクを発火**（非同期・数秒）。「翻訳中」表示はほぼ一瞬で解消。
- **受信 webhook 自体はブロックしない**（Meta へ即 200。翻訳完了を待たない）。
- 受信パスのモデルは **Gemini**（flash 系。モデル名は config）。
- 既存の定期バッチは「主役」から「**取りこぼし拾い（sweeper）**」へ降格。即時翻訳が失敗/未処理の分を後追いで翻訳し、通知する。

#### 3. 辞書2層

- **Layer1 共有ベース辞書**：operator（HIGH LIFE JPN）管理。**全テナント読み取り専用**。業界共通の固有名詞（カード名・セット略号・グレード・状態用語等）。
- **Layer2 テナント私有辞書**：各テナント **RLS 分離**。テナントが CRUD。商品名は商品マスタから自動 seed。誤訳補正もここ。
- **翻訳時の優先順位：テナント私有 → 共有ベース → モデル**（私有が勝つ）。
- glossary 登録語は「訳さない／登録訳を使う」をモデルより優先。

#### 4. 昇格フロー（誤訳→共有辞書の成長／漏洩・汚染なし）

- テナントが私有エントリに「**共有提案**」フラグ → operator のレビューキューへ。
- operator 承認で共有ベースへ **匿名コピー**（提供テナントは記録に残さない／表示しない）。
- **非破壊**：私有エントリは残す。**自動昇格は禁止**。

#### 5. 管理UI（2ページ）

- **テナント辞書ページ**：**管理センターのサブメニュー**。tenant_admin / tenant_staff のみ。Layer2 の CRUD。
- **共有辞書ページ**：**SaaS管理者のサブメニュー**。operator 専用。Layer1 の CRUD ＋ 昇格レビューキュー（承認／却下）。

### Scope外

- 送信側の英訳プレビュー＋確認ゲートは初版 ADR-110 のまま（本改訂で変更しない）。
- 逆翻訳プレビュー・対応言語の追加・辞書の自動増殖（AI による自動登録）は本改訂では扱わない（将来）。
- 商談解析（要約・意図・温度感）は引き続きスコープ外。

### 受け入れ条件（invariants — 守れているかで適合判定）

- **I-1** 原文の言語判定で 日本語→英語・非日本語→日本語 に訳され、原文も併記される。
- **I-2** 受信 webhook は翻訳完了を待たずに即 200 を返す（ブロッキングしない）。
- **I-3** 即時翻訳に失敗したメッセージは sweeper バッチが後追いで翻訳し、失敗/滞留は operator へ通知される。
- **I-4** 翻訳結果は message_translations に保存（言語・確信度・status 含む）。**冪等**（同一メッセージを二重に訳さない）。
- **I-5** 翻訳優先順位は テナント私有 → 共有 → モデル。
- **I-6** glossary 登録語はモデル訳より優先（固有名詞・型番・カード名を勝手に訳さない）。
- **I-7【最重要・機密保護】** 共有辞書ページ（Layer1 ＋ 昇格レビュー）は **SaaS管理者のみ到達可**。いかなるテナント権限でも到達不可。
- **I-8** テナント私有辞書（Layer2）は他テナントから RLS で不可視。
- **I-9** 昇格は operator 承認必須・匿名コピー（提供テナント非開示）・非破壊。自動昇格しない。
- **I-10** 確信度が閾値未満の訳はフラグ表示（受信/送信の閾値は初版踏襲・config）。

## PART 2 — 開発指示書（Generator 向け）

### §Codebase reconnaissance（実装前に実体 file:line で突合すること）

自然言語名のまま実装しない。以下の referent を実体で突き合わせてから着手：

- **管理センター**のナビ／ルート定義（テナント辞書サブメニューの追加先）
- **SaaS管理者**のナビ／ルート定義（共有辞書サブメニューの追加先）
- **translation_glossary** テーブル現行スキーマ（Layer 分離・昇格用カラム追加の起点）
- **message_translator** の glossary 参照箇所（2層解決へ差し替え）
- **Meta 受信 webhook ハンドラ**（即時翻訳タスクの発火点）
- **Celery 定義**（即時タスク追加・既存 translate-pending バッチの sweeper 降格）
- **権限キー（新規）**：テナント辞書 view/edit、共有辞書 manage/promote
- **i18n ラベル**（新メニュー・ページ）
- **受信パスのモデル config**（Gemini）

### 3点セット（ADR-025）

1. **本体**：双方向即時翻訳 ＋ 2層辞書 ＋ 昇格フロー ＋ 2UIページ
2. **状態検証**：即時翻訳の未処理/失敗/滞留を検出するスクリプト（既存 translation_monitor を拡張可）
3. **監視/通知**：即時翻訳失敗・sweeper 拾い・昇格キュー滞留 を Discord 通知

### 補足

- RBAC は ADR-107（顧客優先度ページ）の require_permission パターンに倣う。**I-7 は最優先で満たすこと**（共有辞書ページのテナント到達を構造的に不可能にする）。
- 既存の保護（原文不変・原文＋訳併記・確信度・テナント分離・送信プレビューゲート・冪等）は維持。
- DB スキーマ変更は migration を deploy.yml 経由で自動適用（**VPS 直接接続禁止**）。

## 実装後の適合監査（PO 運用メモ）

- 本体だけでなく **I-2（webhook 非ブロッキング）/ I-3（sweeper 拾い＋通知）/ I-7（共有ページ operator 限定）** が「実際に効くか」を実機で確認。
- 即時翻訳タスク・sweeper・通知が **登録 → 稼働 → 実際に発火** まで閉じているかを裏取り（"merged ≠ live"）。
- Generator が ADR と違う判断をした点は別表で報告させ、採否を PO が決定。
