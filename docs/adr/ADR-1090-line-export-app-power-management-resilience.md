## この ADR が扱う範囲（責任の境目）

端末（Android）で動くアプリ `jp.salesanchor.lineexport`（表示名 SA LINE Export）**だけ**を決める。トーク本文を受け取ったあとのサーバー側の取り込み・解析は ADR-100、さらに下流の在庫表の配信行は ADR-1014 が決める。本 ADR はそれらの決定を変えない。

全 ADR を機械的に走査した結果、端末自動化・ユーザー補助（AccessibilityService）・AlarmManager・電池最適化に触れる ADR は本 ADR の前には存在しなかった（2026-11-26 時点）。したがって既存 ADR との矛盾は無い。これまでこの領域の正本は `docs/handoff/line-auto-export-app/design.md` だけだったため、本 ADR で動作方針の芯を ADR 側に上げ、手順と実測値は引き続き design.md に置く。

## What（何を決めたか）

### 1. アプリの役目

LINE の通知を合図に、画面を起こし（必要なら施錠を解き）、対象のトークを端末内のファイルへ書き出し、Termux 側へ渡すところまでを行う。送信は行わない（`android.permission.INTERNET` を意図的に持たない）。トーク本文はアプリの記録（`/sdcard/Download/sa-line-notify/`）に残すが、PR・issue・push の本文へ書き写さない（ADR-1045 と同じ考え）。

### 2. 省電力による間引きは「起こりうる前提」として扱う

アプリの実行は AlarmManager の合図で始まる。この合図は Android の省電力の仕組みによって**遅らされたり束ねられたりすることがある**。アプリはこれを異常ではなく起こりうる前提として扱い、**間引かれたこと自体を記録に残す**。回数の具体値に依存した作りにはしない（下の「実測と一般仕様の区別」参照）。

### 3. 電池最適化の除外が外れたら記録する

`PowerManager#isIgnoringBatteryOptimizations`（API 23 で追加）で現在の除外状態を見る。状態が**変わったときだけ** `flow=scheduler` / `phase=battery_exemption_changed`（`ignoringBatteryOptimizations`）を1行記録する。毎回は記録しない（記録が膨らむため）。取得できないときは「不明」として扱い、前回値も変えず、何も記録しない。あわせて実行開始の記録に `batteryOptimizationIgnored` を載せる（不明なときは項目を出さない）。

### 4. 予約した合図が来なかったら記録する（空振りの可視化）

合図を予約するとき、引き金ごとに発火予定時刻を端末内に保存する。実際に発火を受けたら消す。スケジューラの公開入口を通るたびに、保存値が **120 秒**以上過去のまま残っていれば `flow=scheduler` / `phase=missed_fire`（`trigger`・`scheduledAt`・`lateByMs`）を1行記録して消す。意図したキャンセル（OFF 操作・再構成）では保存値も消し、空振りと誤判定しない。

**120 秒という値は省電力の割当の具体値から導いたものではない**。「予約した時刻を2分過ぎても来なければ、理由が何であれ人が知りたい遅れである」という運用上の線引きである。したがって端末・OS 版が変わっても意味が保たれる。

### 5. 利用者が自分で戻せるようにする

設定画面に除外状態の表示と、Android の除外設定（`Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）を開くボタンを置く。そのために `android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` を宣言する。画面が無い端末での失敗は捕まえて落ちない。設定画面から戻ると表示は更新される。復旧に ADB や開発者の介入を要しない状態を保つ。

### 6. 採らないもの

- **`USE_EXACT_ALARM` の宣言**: 本アプリの `targetSdkVersion` は 24 で、正確アラームは互換扱いで既に許可されている（実測で `window=0 exactAllowReason=compat`）。この宣言は API 33 以降向けであり、本アプリの間引きを解消しない。
- **`targetSdkVersion` の引き上げ**: 影響範囲が広く、本件の解決には不要。
- **自律クラフト免除（ADR-112）での素通し**: 本件は記録と画面を足す変更であり、バグ修正・CI 修復・リファクタのいずれでもない。免除は使わない。

### 7. 署名鍵

APK は**既存の `tools/line-auto-export-app/build/debug.keystore`（2026-09-17 作成）で署名する**。別の鍵で署名すると上書き更新ができず、消して入れ直す＝暗証番号・ユーザー補助・通知の権限を失い、自動化が止まる。更新前に `apksigner verify --print-certs` で実機の APK と証明書の SHA-256 が一致することを確かめる。この鍵はリポジトリに入れない（`sdk/` と同様に追跡対象外）。

## 実測した事実と、Android の一般仕様の区別（PO 条件2）

この区別を守ることを決定の一部とする。

### 実測した事実（1端末・1時点に限る）

端末 SC-51G・2026-11-26 に `adb shell dumpsys` で読んだ値。**この端末・この OS 版・この時点の設定値であり、ほかの端末や将来の OS 版での値を保証しない。**

- `dumpsys alarm` の設定値: `app_standby_window=+1h0m0s0ms`、`standby_quota_active=720`、`standby_quota_working=10`、`standby_quota_frequent=2`、`standby_quota_rare=1`、`standby_quota_restricted=1`、`min_window=+10m0s0ms`。
- `am get-standby-bucket jp.salesanchor.lineexport` = `40`。`dumpsys deviceidle whitelist` に本アプリは不在。
- 保留中の `*walarm*:jp.salesanchor.lineexport.SCHEDULED_RUN` 2 件が同一の `whenElapsed=2074665196` に束ねられ、`origWhen` は 18:39:06 と 18:53:59、`nowELAPSED=2073958167`（18:57:11）＝発火予定は約 19:09。
- 発火済みの履歴に `policyWhenElapsed: app_standby=-57m12s531ms`。
- アプリの記録では 18:09:08 の書き出し成功以降、新着通知4回に対し `scheduler/reserve` だけが残り、実行が0回（48分）。
- 除外に入れた直後（区分 `40` → `5`）に合図が発火し、18:57:51 開始・18:58:02 書き出し成功・18:58:11 送信受理（HTTP 200・32,119 バイト・基準 18:07）。

### Android の一般仕様として依拠する範囲

- App Standby のバケットに応じて、アプリのアラームの発火に上限が課されることがある。
- 電池最適化の除外に入ったアプリは、これらの制限の対象から外れる。
- **具体的な回数・時間窓・バケットの決め方は、OS 版・端末メーカー・利用状況によって異なる。**

### したがって断定しないこと

「除外が外れると最大1時間に1回になる」は**この端末で読み取った設定値から言えることに限り**、全端末共通の保証仕様として扱わない。本アプリの作りは回数の具体値に依存せず、「除外が外れている事実」と「予約した時刻に発火しなかった事実」の2つだけを根拠に記録する。

## 記録の保持期間と上限（PO 決定 2026-11-26）

### 実測した事実（本 ADR 起案時・1端末）

`/sdcard/Download/sa-line-notify` に 265 ファイル・合計 38.0 MB（2026-09-30〜11-26 の 58 日）。1日平均 0.65 MB、直近7日平均 0.77 MB、最大の日 1.35 MB。1年で約 280 MB の見込み。中身は `.jsonl`（214）と `.txt`（51）だけで、画面画像・音声・動画は 0 件（拡張子で機械的に確認）。アプリのコードにも画像・音声を保存する処理は無い。削除・世代管理・容量上限の仕組みも無い。

### 決めたこと

1. **画面画像・音声・動画は保存しない。** 記録は文字（JSON の行とテキスト）だけに限る。将来も常時保存はしない。
2. **日付ごとのファイルのうち、90 日より古いものは自動で削除する。** 容量ではなく日数で切る。Termux 側の台帳の `prune()` が既に 90 日で切っているため、同じ日数に揃えて考え方を1つにする。
3. 削除は記録の書き込みに合わせて **1日1回だけ**行う。毎回の書き込みでは走らせない。
4. **容量での上限と、種類ごとに日数を変える方式は今回は採らない。** 実測の増え方（1日 1 MB 未満）に対して日数で切るだけで足り、作りが単純なほど壊れにくい。1日あたりが大きく増えたとき、または本文を含む記録だけ短く保つ必要が出たときに再検討する。
5. **この削除の仕組みは本 ADR を起案した便では実装しない。** 別便で実装する。本 ADR は方針だけを決める。

### この ADR では決めず、宿題として記録すること

- Termux 側の `prune()`（90 日で台帳を削る）は `check()` からしか呼ばれず、その `check()` は 2026-10-17 に PO 判断で廃止済み。現時点の最古の記録は 2026-09-17 で 90 日未満のため実害は出ていないが、**2026-12-16 頃から台帳が消えなくなる**。呼び出し元を足す作業は別便とする。
- 書き出したトーク本文と通知の本文（`talk-*.txt`・`diag-*.jsonl`）は共有ストレージ（`/sdcard`）に平文で残り、保存権限を持つほかのアプリから読める。アプリ専用領域へ移すかどうかは容量とは別の論点として、別途 PO の判断を仰ぐ。

## Why（なぜ）

- 48分の取りこぼしが起きたとき、アプリは「予約した」としか記録せず、**黙って止まっていた**。原因の特定に ADB と `dumpsys` が必要だった。同じ事象が再発したとき、記録だけで気づける状態にしておく価値が、記録1行の重さを上回る。
- 除外はユーザー操作・端末メーカーのスリープ機能・アプリの再インストールで失われる。失われることを前提に、**気づく手段**と**開発者を介さない復旧手段**の両方を端末側に置く。
- 回数の具体値に依存しない設計にすれば、端末を買い替えても OS が上がっても同じ判断で動く。

## 範囲外（この ADR では変えない）

- サーバー側の取り込み・解析（ADR-100）と在庫表の配信行（ADR-1014）。
- 送信側 `line-import`（Termux の Python）の作り。端末通知の廃止は 2026-11-26 に PO が別途決定し、`client.py` の `NOTIFY_ENABLED = False` として実装済み。本 ADR はこれを変えない。
- ユーザー補助サービスが未接続のときに合図が黙って捨てられる事象（2026-10-13 記録）。本 ADR の対象は電池最適化側のみ。
- `termux-job-scheduler` の登録と、その呼び出しに残る「孫プロセスを止めない」書き方。
- 実機へのインストールの可否。PO の承認を都度得る（PO 条件6）。

## リスク・トレードオフ（記録）

- **記録が増える**: 変化時だけ・空振り時だけに限ったため、通常運転では増えない。
- **再起動の直後に空振りが1行出ることがある**: 端末の電源が切れていた間は実際に発火していないため記録として誤りではないが、読み手は再起動を考慮する必要がある。
- **不正確モードに落ちた回は、正当な遅れも空振りとして記録されうる**: 発火した引き金は受け取った時点で消えるため、記録されるのは他の引き金の入口を通ったときに限られる。これは検知したい症状そのものなので許容する。
- **除外は端末の設定であり、アプリから保証できない**: だから「気づく」と「戻せる」に倒した。アプリ側で除外を強制する道は無い。

## 外部・過去事例

- 省電力の割当の具体値は、当該端末の `dumpsys alarm` の `standby_quota_*` が唯一の確かな出所である。本件は公開記事や記憶ではなく、当該端末の実値で確認した。
- 「黙って止まる経路は記録を足して可視化する」は、本リポジトリの既往の対処（2026-10-13 のユーザー補助未接続の件）と同じ方針であり、同じ型を踏襲した。

## 維持の仕組み

- 除外の状態は設定画面でいつでも確認できる。外れた場合はアプリの記録に `battery_exemption_changed` が残る。
- 空振りが続く場合は `missed_fire` の `lateByMs` が証拠になる。原因の切り分けは design.md 追補 2026-11-26 の手順（`dumpsys alarm`・`am get-standby-bucket`・`dumpsys deviceidle whitelist`）に従う。
