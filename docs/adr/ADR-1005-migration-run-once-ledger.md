## Context

詳細な根拠は `docs/handoff/migration-runner-redesign/recon.md` を正とする。要点：

- `scripts/run_all_migrations.sh` は登録済みの全手順（run_sql 291 行・run_py 26 行、計 317 行。重複 1 件を含む）をデプロイのたびに最初から実行し、実行済みの記録を持たない（`docs/adr/ADR-1002-unify-product-id-and-fix-migration-compat.md:23` に既出）。
- この方式が原因または増幅要因になった障害が少なくとも 4 件ある。直近は 2026-10-03 の商品の表の列番号上限（1600）到達で、復旧に PR 5 本を要した。
- 事前テストの全件ドライランは 登録された SQL 290 件（重複を除く）のうち 162 件を対象外にしており、障害は本番で初めて見つかった。
- 新テナントの表は `backend/app/services/tenant.py` のひな形から作られるが、ひな形はテナント向けの手順より約 40 列遅れている。今は「次のデプロイでの全件やり直し」がその差を埋めている。したがって全件やり直しを先に止めると、新テナントに列が永久に足りなくなる。
- 外部の一般的な方式（Flyway・Alembic・golang-migrate の公式資料）は、実行済みの記録表を持ち、既存 DB は baseline／stamp で「ここまで実行済み」と記録し、未実行のものだけ実行する。

## Decision（提案）

`docs/handoff/migration-runner-redesign/design.md` の 3 段階で進める。各段階の実装前に PO に確認する。

1. 段階0（安全網）：「後で削除する列を前の手順で足す」組を CI で止める。二重登録を消す。全件ドライランの対象外の理由を明らかにし、戻せるものは戻す。
2. 段階1（テナントの正本を1つに）：新テナントの表の定義を単一にする（推奨：本番の標準形テナントから機械的に書き出した定義を唯一の正本にする）。1A／1B の確定は前調査の結果を見て PO に確認する。
3. 段階2（実行済み記録）：記録の表を作り、全件成功直後の状態を baseline として記録し、以後は未実行の手順だけを 1 回実行する。毎回実行が必要な手順は名前付きの別リストで明示する。実行済みファイルの書き換えは CI で止める。全件やり直しモードは戻し方として残す。

## Consequences

- 良くなること：古い手順と今の状態のぶつかりによる障害が構造的に起きなくなる。新テナントの列不足が無くなる。デプロイの手順実行時間が短くなる見込み（実測で確認）。
- 悪くなりうること：登録漏れの事故の型が戻るおそれ（既存の登録チェックを残して防ぐ）。記録と実態のずれ（照合の点検を用意する）。実装量が大きい（段階ごとに PR を分け、測ってから次へ進む）。
- 範囲外：商品の表の列番号は使い切ったまま。新しい列を足すには表の作り直しが必要で、旧表の削除を伴うため、PO 本人の判断と GO で別途扱う。
