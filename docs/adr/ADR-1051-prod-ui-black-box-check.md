## What（何を決めたか）

- 本番の画面点検は `.github/workflows/prod-ui-check.yml` が毎日 JST 07:00 と手動で行う。動かす機械は GitHub 提供の `ubuntu-24.04`。
- 点検は `https://app.salesanchor.jp/` に HTTPS で入り、画面が開く・ログイン・最初の画面・会社一覧・リード一覧・検索・会社詳細・誤ったログインが拒まれる・サインアウト、を確かめる。
- ログインする人は 1 名。tenant_001 のテスト用の人か、tenant_002 の使っていない人を使い、新しく作らない。管理者ではなく、見るだけの権限だけを持つ役割にする。役割の変更は画面で行う（ADR-025）。認証情報は GitHub secrets `SMOKE_E2E_EMAIL`・`SMOKE_E2E_PASSWORD` にだけ置く。
- 自社ログイン（ADR-1013）に切り替えるまでは、ログインしない点検（画面が開く・誤ったログインが断られる）だけを動かす。ログインが要る点検は secrets が無い間は飛ばす。
- 二段階の確認を飛ばす専用の入口は作らない。
- 点検は SQL・DB 接続を持たない。本番のデータを作らない・変えない・消さない。
- 不合格のときだけ `DISCORD_WEBHOOK_OWNER_PING` に知らせる。合格は知らせない。
- trace・スクリーンショット・html レポートは作らず、artifact に上げない。リポジトリは公開で、これらには入力したメールとパスワードが残るため。
- 配備（deploy.yml）が動いている間は 10 分待って 1 回だけ確かめ直し、まだ動いていれば見送る（不合格にしない）。
- ログインの手順は `tests/prod-check/login.ts` の 1 ファイルに閉じ込める。ADR-1013 のログイン切替では、このファイルだけを差し替える。
- 旧 qa-smoke（ADR-038）は自動実行を止めた（手動のみ）。新しい点検が 14 日続けて合格したら、qa-smoke.yml・scripts/qa・tests/qa-smoke・`QA_` で始まる secrets 13 件を削除する。

## Why（なぜ）

- 旧 qa-smoke は 2026-06-19 を最後に一度も完走していなかった。動かす機械（監視サーバー）に道具が無く、本番 DB にも届かなかった。さらに、動くたびに本番の会社のデータを消して入れ直す作りだった（design.md §2）。
- 利用者から見た壊れ方（入れない・一覧が開かない）は、外側から画面を触れば分かる。DB を直接数える必要は無い。DB に触らない点検なら、本番を壊す道がそもそも無い。
- 管理者は ADR-1048 で二段階ログインが必須になる。点検用の人を管理者にすると点検がログインできなくなるため、見るだけの役割にする。
- 今の Firebase のログインは全員に二段階の確認を求め、機械は通れない（`backend/app/auth/dependencies.py:39`、`:222-229`）。自社ログインの後は、見るだけの人はパスワードだけで入れる（ADR-1048）。
- 監視サーバー専用の入口は、二段階を飛ばす道を常設し、監視サーバーを狙われやすくする。新しい入口を作らない方が攻撃される場所が増えない（2026-10-30 Fable 相談）。
- 毎日失敗を重ねると締め出されるため、誤ったログインの点検は存在しないメールで行う。
- 合格を知らせると知らせに慣れて見なくなるため、不合格だけを知らせる。

## 守り方

- 点検のファイルに SQL・DB 接続の文字が無いことを、PR の審査で `grep` して確かめる。
- 点検用の人の権限は見るだけ。漏れても書き込みはできない（API が 403 を返す）。
- 「点検そのものが動いていない」ことは、GitHub の実行一覧で直近の成功を確かめる（design.md 「維持の仕組み」）。
- ログイン切替の当日は、login.ts を差し替えて手で 1 回動かし、合格を確かめる。
