## ひとことで

作業部屋（worktree）の「作る→使う→片付ける」を、**人の手作業ゼロ・記憶ゼロ・矛盾ゼロ**で回す。
鍵は「原則を1つに統一する」こと。判断の真実を1か所に集約し、完了の合図を1種類にし、各層の担当を1つずつに固定する。

---

## 唯一の原則（不変条件）

この4行が全体を支配する。すべてのスクリプト・ワークフロー・ドキュメントはこれに従う。

1. **真実は1つ** … 「作業中か／完了か」は、ノート（`active-work.md`）の **ステータス（IN_PROGRESS / DONE）だけ** が決める。他の手段（リモートブランチの有無・経過時間）で"完了"を判断しない。
2. **合図は1つ** … 「完了」の合図は、**feature PR が develop にマージされた事件だけ**。
3. **行はDONEで残す・フォルダは消す** … ノートの行は履歴として DONE で残す（削除しない）。部屋のフォルダ（実体）は消す。
4. **担当は1つずつ** … ノートの行を更新するのは GitHub 側、フォルダを消すのは各 Mac 側（自分の部屋だけ）。

---

## Context（なぜ今これか・現状の矛盾）

recon（実機確認）で、ルールが二重・三重に食い違っていることが確定した。

| 矛盾 | 実体（file:line） |
|------|------------------|
| ノートの行は「DONEで残す」が決まり | `active-work.md:12`「該当行を DONE に更新する（削除しない・ログとして残す）」 |
| なのに片付け道具は行を「削除」している | `cleanup-worktree.sh:65`（行を削除） |
| ゾンビ通知も「削除しろ」と案内 | `zombie-report.yml`（"active-work.md から削除"） |
| 完了判定が実データで機能しない | 162部屋中、リモート消滅は12だけ（マージ後にブランチ未削除のため） |
| 上限が実態に追従せず、逃げ道が「上限を上げる」 | `new-worktree.sh:45-52`（既定5・環境変数で上書き）／実数162 |
| 完了判定の流用元がない | `check-stale-worktrees.sh:23-97`（経過時間で判定。マージ判定は持たない） |
| マシン集中が未解消 | `claude-pipeline.yml:L62` は `[self-hosted, macOS]` のまま（`shingo-mac` 未付与）。Shingo-Mac-Temp は offline → 実行は Hikky-dev-Mac に集中 |

放置すると、片付かない部屋が積み上がり（現162）、新規作成が止まる（sa-18 がブロック）。

## Decision（完全自動・矛盾ゼロのモデル）

### 1. 真実の集約
「作業中か」を判断する唯一の場所を `active-work.md` のステータスに固定する。スクリプト類は、完了判定にリモート有無や経過時間を使わない（それらは"通知"用途に限定）。

### 2. 合図＝developマージ（イベント駆動）
feature PR が develop にマージされた瞬間を「完了」とする。squash マージでも、ブランチを消していなくても、**マージ事件そのもの**を見るので確実。

### 3. ノートの行を自動DONE（GitHub側・即時）— 専用ワークフローを新設
develop マージ時に、対象ブランチの行を自動で DONE に書き換える。**行は消さず残す**。
- **重要（recon で判明・前提を訂正）**：当初「登録と同じ経路を再利用」と書いたが、その経路は存在しなかった。`new-worktree.sh:105-142` は active-work.md を Python で書くだけで git commit/push を持たず、マージ起点で active-work.md を更新する仕組みも現存しない。→ **新規ワークフローを作る。**
- 設計要素：
  - 発火トリガー：`pull_request: types:[closed]` かつ `merged==true` かつ `base==develop`
  - 動作：該当ブランチの行を DONE に更新 → commit → develop に push
  - 権限：develop は保護下のため `PIPELINE_PAT`（既存・Issue #300 で rotation 管理）でコミット。Generator 着手前に `gh api .../actions/secrets` で存在を確認。
  - 制約：更新後も `active-work-lint.yml` の6列フォーマットを満たすこと。

### 4. フォルダを自動削除（各Mac側・掃除係＝reaper）
フォルダはその Mac の中にしかないので、削除は Mac 側でしか行えない。掃除係は次の条件を**すべて満たす**部屋だけ消す。
- ノートが DONE（または PR がマージ済み）
- かつ **未保存の作業がない**（未コミット・未pushがゼロ）

起動タイミング：
- (a) 新規作成時に先に1回（`new-worktree.sh` の上限判定の前。これはその Mac 上でローカル完結）
- (b) 各 Mac で定期実行：`schedule:` + `runs-on:[self-hosted, macOS, <各Macのラベル>]` のワークフロー（既存に同方式の実績あり）。reaper は冪等なので concurrency 制御は不要。
- **依存（recon で判明）**：(b) の「offline でも復帰時に追いつく（self-heal）」は、ランナーが自動起動して初めて成立する。現状ランナーは手動起動（`runner-start`）で、launchd 自動起動は ADR-029 の TODO のまま未実装。→ **launchd 自動起動の実装を本ADRの依存前提とし、Generator スコープに含める**（plist 実装）。

### 5. 安全条件（非交渉）
- **IN_PROGRESS の部屋は絶対に消さない。**
- **未保存の作業がある部屋は絶対に消さない**（現状162中16件該当）。これらは消さず、通知して人の判断に回す。
- 実削除の前に dry-run（消す予定一覧の表示）を経由。

### 6. 上限はセーフティネット化・エスケープ廃止
- 4 で自動的に減り続けるので、上限は「異常検知の網」に降格。
- 上限到達メッセージから「`WORKTREE_LIMIT` を上げる」案内を**削除**（バイパス禁止）。代わりに「掃除係を実行／未保存N件を確認」と表示。

### 7. マシン分離（集中の解消＝ADR-111の実効化）
- `claude-pipeline.yml` の全ジョブの `runs-on` を `[self-hosted, macOS, shingo-mac]` に変更（ADR-111の実装が未反映だったため、本ADRで実効化）。`shingo-mac` ラベルは現状0件＝新規導入。
- **順序制約（非交渉・recon で判明）**：`shingo-mac` 付与と Shingo-Mac-Temp のオンライン化は**同時に行う**。GitHub Actions はラベルを AND マッチするため、オンライン化の前にラベルを付けると**パイプライン全停止**になる（どのランナーも `shingo-mac` を持たないため）。
- 各 Mac は **自分の部屋だけ** を掃除する（中央集計はしない＝クラウドからフォルダは見えないため構造的に不可）。

### 8. 既存スクリプト・文書を原則に整合（矛盾の解消）

| 対象 | 変更 |
|------|------|
| `cleanup-worktree.sh:65` | 行「削除」→「DONE更新」に直す |
| `zombie-report.yml` | 案内を「削除」→「DONE」に直す（自動DONE導入後は実質バックアップ） |
| `PARALLEL_TERMINAL_GUIDE.md` / ADR-086 | 文言を「行はDONEで残す・フォルダは消す」に統一（"終了時は削除する"の曖昧表現を排除） |
| `check-stale-worktrees.sh` | 役割を「経過時間アラート（IN_PROGRESS放置の通知）」に明確化。完了判定には使わない |

## 一度きりの後始末（既存162の解消）

新モデルは将来の積み上がりを止めるが、既存162は一度だけ手当てが要る。
- 後始末reaper：162のうち **マージ済み（gh で PR 状態を確認）かつ未保存なし** を対象にフォルダ削除＋行DONE化。
- IN_PROGRESS と未保存あり（16件）は残し、通知で人に回す。
- これで実数が上限以下に戻り、**sa-18 の作成ブロックが解ける**。後始末reaper はそのまま 4 の本体になる。

---

## 「完全自動」でも意図的に人を残す2点（矛盾ではなく安全・統治）

1. **未保存の作業がある部屋** … 自動削除しない。失うと取り返せないため、通知して人が判断（安全）。
2. **develop → main のリリース** … PO が承認する既存ゲートは維持（統治）。

これ以外（作成・登録・完了判定・DONE化・フォルダ削除・上限管理）はすべて自動。

## architect recon 結果（2026-06-06・反映済み）

| 項目 | 判定 | 反映 |
|------|------|------|
| ①自動DONEの書き込み経路 | ❌ FAIL | 既存経路なし。専用ワークフロー新設に変更（§3 改訂） |
| ②定期reaper の置き場所 | △ PARTIAL | schedule+self-hosted 方式を採用。launchd 未実装が self-heal の前提欠落 → スコープに追加（§4） |
| ③マージ判定の正確さ | ✅ PASS | `gh pr list --state merged --base develop --head <branch>` で確定（squashでも機能）。下記の切り分けを採用 |
| 付帯：ADR-111実効化 | ✅ 条件付き | 同時適用の順序制約を §7 に明記 |

マージ判定の切り分け（③・採用）：
- `merged` かつ base=develop → 回収対象
- `closed`（未マージ）→ 消さない（安全側）
- PR が一度も無いブランチ → 消さない（確証なし）
- IN_PROGRESS かつ未マージ → 絶対に消さない
- 未コミット・未push あり → 絶対に消さない

## 順序制約・依存（実装時の必須事項）
1. `shingo-mac` ラベル付与は Shingo-Mac-Temp オンライン化と**同時**（先付与は全停止）。
2. reaper の self-heal は **launchd 自動起動**が前提（本ADRスコープに含める）。
3. 自動DONEワークフローは **PIPELINE_PAT** の存在確認後に着手。
