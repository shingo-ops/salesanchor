## What（何を決めたか）

1. 画面への即時反映は、通り道（SSE）1本 GET /api/v1/events/stream で行う。ページごとに通り道を作ることは禁止する。
2. 合図には「何が変わったか」の名前（topic）と、送った元のタブ（origin）だけを入れる。データの中身は送らない。画面は既存の API でデータを読み直す。
3. topic の正本は backend/app/realtime/topics.py の1か所に置く。中身は次の2つ。
   - ルートのテンプレートとメソッド → topic と範囲（tenant か global）
   - 合図を出さないルート → その理由
   - 画面側の topic 名は、ここから生成した定数を使う。
4. 書き込み API（POST/PUT/PATCH/DELETE）が 2xx で終わったら、middleware が自動で合図を送る。対応表との照合キーはルートのテンプレート（request.scope["route"].path）にする。各 router に手で publish を書くことは原則しない。
5. 裏の処理（Celery など）がデータを書き換えたときは、終わったところで publish_change を明示的に呼ぶ。
6. 合図のチャンネルは、会社ごとの rt:t:{tenant_id} と、会社をまたぐ共用データ用の rt:global に分ける。
   - global は super admin だけが受け取る。
   - 会社 ID が分からない書き込みでは、会社別の合図を送らない。
7. 画面は useRealtimeRefresh(topics, reload) で合図を受ける。
   - 合図はまとめてから1回だけ読み直し、表は残したまま差し替える。
   - 自分のタブが送った合図は無視する。
   - 裏にあるタブは、表に戻ってから読み直す。
8. CI で全ての書き込み API を列挙し、3 の対応表にも「出さない理由」の一覧にも無いものがあれば赤にする。
9. DB を直接 SQL で直したときは合図が出ない。これは対象外とする。

## 改訂 2026-10-18

在庫表を開いたまま、在庫が変わったら自動で最新にするため、決定6と決定7を次のとおり足す。本文の決定1〜9は書き換えない。PO 決定 2026-10-18「y」。

- 決定6への追加: 3つ目のチャンネル rt:shared を足す。会社共通データ（public スキーマにあり、どの会社のログイン利用者も同じものを見る在庫表など）が変わった合図だけを流し、全接続に届ける。合図は名前と origin だけでデータを含まず、データは既存 API が権限を見て返すので他社のデータは漏れない。rt:global は今までどおり super admin だけに届く。
- shared の合図は products.view の有無に関係なく全接続に届く。届くのは topic と届いた時刻だけ（Celery からは origin も空）で、在庫の中身は届かない。
- shared を使える topic は topics.py に shared と明記したものだけ（今は tcg.inventory）。書き込み API ではなく裏の処理だけが出す topic は、topics.py の TASK_TOPICS に置く。書き込みルートの表（WRITE_ROUTE_TOPICS）には shared を置かない。
- 決定7への追加: まとめる時間はページごとに変えられる（useRealtimeRefresh の debounceMs。在庫表は 5 秒にページごとの 0〜3 秒のずれを足す）。

## 改訂 2026-10-19

在庫表を、マスタや配信設定の編集、v6 の訂正、時間の枠からの脱落でも自動で最新にするため、決定3・4と決定6に次を足し、決定10を新しく置く（在庫表の行の定義は ADR-1014）。本文の決定1〜9と改訂 2026-10-18 は書き換えない。PO 決定 2026-10-18「y」（この3つの経路も自動で画面に反映するよう設計を始めるか）。

- 決定3・4への追加: topics.py に INVENTORY_SIGNAL_ROUTES を置く。これは「在庫表が読む共通の表（public）に書く書き込み経路」の集合である。2xx を返すと、middleware が tcg.inventory を出す。範囲は TASK_TOPICS の tcg.inventory の値（shared）から引く。そのため、改訂 2026-10-18 の「TASK_TOPICS は裏の処理だけが出す topic」は、「tcg.inventory は書き込み API からもこの集合を通して出る」と読み替える。WRITE_ROUTE_TOPICS と NO_SIGNAL_ROUTES のどちらに載るかとは別に持つ。WRITE_ROUTE_TOPICS には、これまでどおり shared を置かない。一覧の増減は設計の改訂を通し、試験で数を固定する。
- 決定6への追加: 一般の権限の口（共通の表に書くもの）からも shared を出す。この合図の origin は空にする。他社に届くのは「変わった」という名前と時刻だけで、中身も編集した人のタブの識別子も届かない。
- 新しい決定（決定10）: 時間だけで変わる表示（時間の枠から外れる行）は、書き込みの合図ではとらえられない。そこで在庫 API が「次に行が外れるまでの秒数」をサーバーの時計で返し、画面はその時刻に1回読み直す。間隔は最短 60 秒、上限 1 日で、隠れタブでは保留する。定期的に読みに行くポーリングではない。外れる行が無いときは何もしない。

## 改訂 2026-11-01（ADR-1055）

知らない機械からのログインの許可依頼を、その人のいつもの機械だけに知らせるため、範囲に人単位の `user`（宛先 `rt:u:{user_id}`）を足す。本文の決定と既存の改訂は書き換えない。中身はこれまでどおり話題の名前と origin だけで、データも依頼の id も入れない。人宛ての話題は topics.py の `USER_TOPICS` に置き、書き込みの口の自動の合図には使わない（口の中で直接送り、その口は NO_SIGNAL_ROUTES に理由付きで並べる）。接続は user_id を持ち、`rt:u:` は同じ人の接続だけに届く。設計: docs/handoff/auth-new-device-approval/design.md の A-2「知らせ」。

## 改訂 2026-11-02（ADR-1054 K4）

在庫表でも、ほかの人の変更が 5 秒以内に出るようにするため、改訂 2026-10-18 の決定7への追加のうち在庫表の秒を次に替える。本文の決定と既存の改訂のほかの部分は書き換えない。PO 決定 2026-11-02「1」（ほかの画面と同じ速さに縮める）。

- 在庫表の合図の待ちは、ほかの画面と同じ 1.5 秒（REALTIME_DEBOUNCE_MS）に、ページごとの 0〜1 秒のずれを足す。読み込みの最大 1.8 秒を足しても、変更が出るまで最大で約 4.3 秒。
- 行が外れる時刻の読み直しのずれ（改訂 2026-10-19 の決定10）は 0〜3 秒のまま。
- 根拠: 2026-10-27〜11-02 の記録で、在庫表の読み込みは 180 回・1 時間の最大 21 回・10 秒以内に同時に読んだ接続元は最大 2。合図のもとの解析の完了は 7 日で 682 回・1 時間の最大 20 回。数え方と生の数は docs/handoff/line-like-speed/design.md §3-4-16。
- 見張り: 縮めた後に同じ数え方で測り、1 時間の読み込みが 63 回（基準の最大の 3 倍）を超えたら PO に報告して秒を決め直す。

## 改訂 2026-11-03（アプリ内の鈴）

画面の右上の鈴の未読数を、ほかの人の知らせの作成から 1 分以内に増やすため、人宛ての話題に `notices`（範囲 `user`、宛先 `rt:u:{user_id}`）を足す。本文の決定と既存の改訂は書き換えない。中身はこれまでどおり話題の名前と origin だけで、知らせの中身・書き込みの本文・Discord の id は入れない。画面は合図を受けたら `GET /api/v1/notices` を読み直す。

- 人宛ての話題は topics.py の `USER_TOPICS` と frontend/src/lib/realtime/topics.ts の両方に置く（試験で照合）。
- 送り口は backend/app/services/user_notices.py の `signal_notices_changed` の 1 か所だけ。知らせの行を commit した後に、宛先 1 人ずつへ `publish_user_change` で出す。失敗は握る（知らせの作成は止めない）。
- 既読の口 `POST /api/v1/notices/{notice_id}/read` は合図を出さない（画面が返り値の未読数で更新する）。NO_SIGNAL_ROUTES に理由付きで並べる。
- 設計: docs/handoff/in-app-notice-bell/design.md §7-2。

## Why（なぜ）

- PO の願いは「読み込み速度を落とさず、変更があったら即時反映」を全ページの標準にすることである。
- 今の SSE は受信箱とリードの2本だけで、合図は "update" しかない。ページを増やすたびに、通り道とチャンネルが増える（`docs/handoff/realtime-standard/recon.md` §1）。
- 書き込み API は360件ある。手で publish を書くやり方では、書き忘れを機械で止められない（recon §3）。
- データの中身を合図で送ると、会社の分け方と権限を二重に守ることになり、データの正本が分散する。合図を名前だけにして、読み直しを既存の API に任せれば、正本は1か所のままになる。
- 速さの面では、読み込みの処理そのものは変えない。読み直しはまとめて1回にし、表も消さないので、体感の速さは落ちない（G3 で測る）。

## 追記: 流し続ける口は DB を持たない

流し続ける口（SSE）は、流している間 DB の接続と取引を持たない。認証・会社・権限は backend/app/realtime/stream_db.py の短いセッションで済ませ、流し始める前に閉じる。見張りは backend/tests/test_sse_no_db_hold.py。理由: yield 依存の後始末は応答を送り終えた後に走るので、流れ1本ごとに取引が開いたままになり、本番反映の前の点検（ADR-1037）を止めた（docs/handoff/app-idle-tx/recon.md）。
