## ひとことで

migration は DB の形（表・列・索引・制約）の変更だけに使い、1本は1回だけ流す。値の投入や上書きは migration から外す。テナントの作成は、作った時点で完全な状態にする。所有者と管理者の権限は、役割の表の新しい目印（system_key）からコードで計算する。

## 背景（2026-10-05 実測。根拠は docs/handoff/migration-hygiene/recon.md）

- scripts/run_all_migrations.sh は、デプロイのたびに登録済みの 317本を最初から流し直している。実行済みの記録は無い（ADR-1002 の背景、#3965 の recon）。
- 値を書く migration が 52本あり、毎回届くものが 28本ある（上書き型 8、補充型 20）。
  - 2026-10-05 02:38Z、seed_product_marks（migrations/20260604_010000_seed_product_marks.sql:23-25）が、00:33Z に M2a へ直した MEGAドリームex の mark を M3 に戻した。audit_log には残らなかった。
  - 上書き型の8本は、どれも本番の今の値と同じである（違う行は 0）。直した値を、次のデプロイで戻す状態にある。
- 毎回の流し直しに頼っている仕組みがある。
  - テナントの作成：tenant.py は phase を 'A' にしている（:1753）。システム管理者は is_system=False（:62）で、goals.* の付与も無い。migration 080・023・075 が、次のデプロイで直している。後から足した権限を所有者と管理者に配る役目は 025 が担っている。
  - 試験：countries の 190行、在庫の集計の決まりの 4行、type_master など、migration のファイルを流して使っている。
- 所有者と管理者を見分ける変わらない目印が無い。役割の表にあるのは、name（日本語の表示名）・priority・is_system だけである（tenant.py:485-496）。
- migration-guard の Check 7・8 は、追加されたファイル（--diff-filter=A）しか見ない。既存の migration の書き換えや、毎回の流し直しは検査の外にある。
- 全体の試し流し（migration-test.yml:1649-1720）の対象は、ファイル名の日付で 2026-06-29 までに限られていて、以降の 162本が入っていない。理由の記録は、2026-06-01〜03 の分にしか無い。

## 決定

1. **migration は構造の変更だけ（ADR-155 を全マスタに広げて確認する）**
   - INSERT・UPDATE・DELETE などの値の操作は、新しい migration に書かない。
   - 値の変更は、次のどれかで行う。
     - アプリ画面か CSV（ADR-155）
     - テナントの作成の処理（アプリのコード）
     - 1回だけのデータの変更：PO の合意、DRY-RUN → COMMIT、docs/handoff/<topic>/ に SQL と記録を残す
2. **既存の値を書く migration は無効にする**
   - #3544 と同じ形で、本文を NOTICE だけにする。
   - 構造と値が混ざったファイルは、値の部分だけを止める。
   - 頼っている試験は、試験の側でデータを用意するように直してから無効にする。
3. **テナントの作成は、作った時点で完全にする**
   - tenant.py で次を行う。
     - phase 'B'
     - システム管理者を is_system=True
     - goals.* の付与
     - system_key の書き込み
   - migration の流し直しで補うことをやめる。
4. **所有者と管理者の権限はコードで計算する**
   - 役割の表に system_key（'owner'・'admin'・NULL）を足す。
   - load_user_permissions で、所有者は public.permissions の全部、管理者はそこから system.manage を除いたものを、ほかの役割の付与と合わせて（union）返す。
   - 値と除く権限の名前は、backend/app/auth/system_roles.py の定数の1か所に置く。
5. **検査を強める**
   - migration-guard が、変更されたファイルと、登録済みのファイルの値の操作も見るようにする。
   - 全体の試し流しの対象から、理由なく外している分を外さないようにする。
6. **1回だけ流す（ADR-1005 の段階0〜2に従う。段階0は PR #3998）**
   - 実行済みの記録の表を作り、まだ流していないものだけを登録順に流す。
   - 流し終えたファイルの書き換えは、チェックサムで止める。
   - 2〜5 を終えてから入る。そうしないと、値を書く migration を無効にする書き換えが、できなくなるため。

## 理由

- 直したマスタの値が、デプロイで黙って戻る。これは SSOT（正本は1か所）に反する。
- migration の流し直しを、テナントの準備や試験の準備に使っていると、流し直しをやめた途端に壊れる。正本を、アプリのコードと試験の準備の側に移す必要がある。
- 日本語の表示名で役割を見分けると、名前が変わったときに権限が外れる。コードに表示名を直接書くことにもなる。

## 弊害・トレードオフ

| 弊害 | 対処 |
|---|---|
| 新しい権限を足したとき、所有者と管理者に届くまで最大 300秒かかる（cache.py:18 の TTL） | 許容する。急ぐ場合は invalidate_tenant_permissions（cache.py:208）を呼ぶ |
| 既存の所有者・管理者の role_permissions の行が残り、画面の一覧には出る | 計算では使わない。消すかどうかは別に判断する |
| 段階2の前に無効化を終える必要があり、作業の順番が固い | 実施順序を下に固定する |
| 権限の一覧の正本が DB だけで、コードの中に写しが複数ある（public.permissions 123件、migration に無い5件、試験の準備は 85件） | この ADR の範囲外とする。別の ADR で扱う |

## 外部・過去事例の参照と我々への応用

- 外部事例
  - 一般的な migration の道具（Alembic・Flyway・Rails）は、実行済みの記録の表を持ち、未実行のものだけを1回流す。流し終えたファイルは書き換えない。
  - 特定の数値には依存しないため、外部の事例は原則として挙げるにとどめる。
- 過去事例
  - #3544（2026-09-18）：seed 13本を無効にした。そのとき1本（seed_product_marks）が漏れ、2026-10-05 の書き戻しにつながった。
  - #3958〜#3963：列が増え続ける問題を止めた。原因は、毎回の流し直しで列を足して消す組が流れていたこと。
  - #3965（ADR-1005）：記録して1回だけ流す設計。main にマージ済み。この ADR は、その前提となる後始末と順番を補う。

## 維持の仕組み

- 守り手: 設計担当（Opus）。実施順序の各段で、本番の読み取りの確認を行う。
- 決定5の検査の強化で、値を書く migration が新しく入ることと、既存のものの書き換えを止める。
- 決定6の後は、チェックサムで実行済みのファイルの書き換えを止める。

## 実施順序

```
段1: PR-1a migration（roles.system_key と索引。tenant.py のテナント定義にも同じ列）
     → データの変更（既存の5社に system_key を入れる。DRY-RUN → COMMIT）
     → PR-1b コード（tenant.py の作成の完全化、load_user_permissions の計算、PG の試験）
段2: 試験の準備の側にデータを移す（countries・集計の決まり・type_master・権限など）
段3: 値を書く migration の無効化（seed_product_marks は #3978。事実：#4051 でファイルごと削除済み、PO 2026-10-09）
段4: migration-guard の強化、全体の試し流しの対象の修正
段5: ADR-1005 の段階0（PR #3998）→ 段階1 → 段階2（記録して1回だけ流す。段階2の記録の起点は、段3 の無効化がデプロイされた後に取る）
```

- migrations/ や本番に影響する PR のマージには、PO の「GO #番号」が要る（ADR-136）。
- 各段のあとに、本番で読み取りの確認をする。

## 受入条件

- [ ] 新しく作ったテナントが、デプロイ（migration の流し直し）を待たずに、phase 'B'、システム管理者 is_system=True、goals.* の付与、system_key を持つ。
- [ ] 所有者は全部の権限、管理者は system.manage 以外の全部の権限を持つ。新しく足した権限が、role_permissions の行なしで届く（PG の試験）。
- [ ] 毎回届く値を書く migration が 0本になる（一覧で確認）。
- [ ] 値を書く migration の追加と、既存の migration の書き換えが CI で止まる。
- [ ] 記録の表が入り、デプロイで流れるのが未実行の migration だけになる（段5）。
- [ ] 段ごとに pytest が全部通る。デプロイが成功し、smoke の試験が通る。
