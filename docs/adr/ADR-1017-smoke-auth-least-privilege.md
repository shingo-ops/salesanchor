# ADR-1017: smoke 認証経路は最小権限の専用ユーザーだけを許可し、全権ユーザーはコードで拒否する

## Context

- デプロイ後の FedEx ライブ見積もり確認（smoke）のため、サービス用トークンで Firebase 検証と MFA を省いて認証する経路が `backend/app/auth/dependencies.py` にある。
- この経路は、解決先ユーザーの権限がそのままトークン漏洩時の影響範囲になる。解決先が過大な権限（全テナントに及ぶ権限）だと、影響が全テナントに及ぶ。
- 解決先に対する制約がコードに無く、非ASCII 入力で 500 になる欠陥があり、使用の記録も残らない。
- ADR-1013 は Firebase 依存の smoke を便6 で置き換えるとし、`docs/handoff/auth-self-hosted-passkey/design.md` は SMOKE を据え置くと記す。この 2 つが食い違っている。

## Decision

1. smoke 認証経路は、最小権限の専用ユーザーだけを許可する。解決先が super admin なら、ユーザーを返さず 401 にする（fail-closed。設定ミスでもコードが拒否する）。
2. 非ASCII 入力は 500 ではなく 401 に倒す（エラー詳細は出さない）。
3. smoke 認証の成立を記録する（トークン値は記録しない）。
4. トークンはローテーション可能とし、運用でローテーションする。専用ユーザーの作成とシークレット更新は ADR-136 の GO 手順に従う。
5. ADR-1013 と据え置き設計の食い違いは、「当面は本 ADR の最小権限化で据え置き、恒久策の短命スコープ付き自社 JWT 化は別便」と整理する。ADR-1013 の便6 の対象に smoke を残す場合も、本 ADR の最小権限化は便6 まで有効とする。

## Consequences

- 漏洩時の被害上限が「全テナントの運営権限」から「1 テナントの送料計算のみ」へ縮む。
- 将来 SMOKE の向き先を誤って全権ユーザーにしても、コードが拒否する。
- 本番に専用ユーザーとシークレット更新が必要になる（GO 待ち）。適用順は、ユーザー作成、シークレット更新、コード反映の順。順序が前後しても smoke が赤くなるだけで安全側。戻し方は Revert とシークレットの戻し。
- 記録は当面アプリのログ。テナント文脈が揃う位置での監査表への記録は別便。

## 代替案

- 案 B（恒久）: 短命スコープ付きの自社 JWT（ADR-1013 の方式と整合）を smoke 専用に発行する。長寿命の共有トークンが無くなる。別便で起案する。
- 経路の廃止: FedEx 見積もりの自動確認を失うため不採用（PO 2026-10-15）。
- owner／admin ロールの判定を同時に入れる案: ロール表がテナントスキーマ内にあり、この位置では参照できず過剰設計になるため不採用。専用ユーザーに必要な権限だけを付ける運用で担保する。
