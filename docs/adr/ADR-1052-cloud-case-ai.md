## What（何を決めたか）

1. Discord の投稿は、保守を自動で始める合図としてだけ使う。相談係 AI から外へ情報を出すことは禁止する（PO 決定）。
2. 受付は agent-console。許可リストの人の投稿だけを受ける。本文の電話・メール・郵便番号の形を置き換え、添付は渡さない。backend に件を作り、件の札を受け取ってから、routine の /fire を呼ぶ。呼ぶ前に記録に「呼ぶ」と書き、同じ投稿では二度呼ばない。
3. 相談係 AI は Anthropic のクラウドで、専用の環境に 1 件 1 台で動く。ネットワークは None。届く先は network secret のホスト case-api.salesanchor.jp だけ。鍵は `Authorization: Bearer <CASE_AGENT_TOKEN>` の 1 つで、環境変数には置かない。
4. 相談係 AI が読むのは新しいスキーマ ai_cloud のビューだけ。型で判定し、決め打ちの型（数・真偽・日時・uuid・enum）だけをそのまま出す。それ以外の型は長さと文字の種類だけの形で出す。json は長さとキー数、配列は要素数だけ。秘密列はビューから外す。列ごとの例外は分類表 ai_cloud_meta.column_class に理由付きで書く。
5. 読む道は相談係専用の容器 ai-reader-cloud-http とロール ai_reader_cloud。ai_reader_cloud は ai_reader と同じ属性で、ai_cloud の USAGE と SELECT だけを持つ。今の窓口 ai-reader-http・ai_reader・ai_ro・Mac の AI は変えない。
6. 中身が要るときだけ、相談係 AI が列（最大 5）・行（最大 20）・理由（20〜1000 字）を申請する。backend の機械の上限（件ごと 2 回・拒否表と秘密列・15 分・読み 1 回）を通った申請だけを、道具も MCP も設定も持たない判断役 Opus が JSON で判断する。agent-console のコードが上限を確かめてから記録する。
7. 値を返す口は backend に置かず、専用容器 ai-unmask-http に置く。容器は DB 関数 ops_case.unmask_fetch を呼ぶ。関数は SECURITY DEFINER で、件の札・許可・期限・読みの回数・拒否の列と表を確かめ、読みの記録を同じ取引で書く。関数の持ち主 ai_unmask_owner は NOLOGIN。
8. 申請・許可・読み・報告・点検の記録は新しいスキーマ ops_case に置く。値そのものは記録しない。
9. 相談係 AI が届く道は case-api.salesanchor.jp の 3 つだけ（読む窓口・件の報告と申請・値を返す口）。ほかの道と管理の口は 404。今の 443 の server ブロック全部で、TLS の名前が case-api なら 421 を返す。
10. 専用の環境につなぐのは専用の非公開リポジトリ 1 つ。コネクタは 0 個にし、`.claude/settings.json` で WebSearch・WebFetch・Artifact・`mcp__*` を拒否する。リポジトリはアーカイブ（読み取り専用）にする。
11. 相談係 AI は型付きの報告を 1 回送って終わる。報告を受けた agent-console は、件のセッションを囲い（ADR-1039 Decision 6）の中で開く。修理は今までどおり PR と審査と GO を通す。
12. 毎週月曜 09:30 に、判断役とは別に起動する点検役 Opus が記録を点検する。おかしな所だけを PO に Discord で知らせ、知らせに値は書かない。
13. 始めは PO だけが投稿できる。合格の基準 K1〜K6 が全部 ○ になったら、Opus の判断で誰でも投稿できるように開く（PO 決定の範囲）。
14. 進め方は段0〜段5 を 1 段ずつ（反映→測定→次）。段0（試し）は 2026-10-30 に済んだ。段3（クラウドの本番の設定）に進む条件は、design.md §8 の U9・U10 を確かめること。1 つでも確かめられなければ段3に進まない。

## Why（なぜ）

- PO は、Discord に書けば保守が自動で始まることを求めた。同時に、外への情報の持ち出しを禁止した（PO 決定）。Mac の囲いで動かす案は、Mac が重くなること（PO）と、囲いの受入が 4 つ中 2 つしか合格しなかったことで採らない（design.md §6）。
- 個人の値は列名に当たらない所にもある（請求の宛先の写し・保管データ・監査の前後の値・会話の生データなど）。列名で伏せると漏れるため、型で伏せる側に倒す（design.md §2・§4-1）。
- 今の ai_ro を伏せると、Mac の見張りと正答率の測定が効かなくなる。今の窓口の接続を替えると、正答率の取得 3 本が ai_ro を読めなくなる。そのため相談係の道を別に作る（PO 決定「1」・design.md §6）。
- 「必要ない情報は取得しない、事前に申告してopusが許可する仕組み」（PO）を、AI の判断の前に機械の上限で絞る形にした。判断役に道具を持たせると、申請の文に紛れた命令で道具を使われるため、道具を 0 個にする（ADR-1039 Why と同じ考え）。
- 値を返す口を backend に置くと、書ける接続や復号鍵と同居する（ADR-1042・ADR-1024 の不採用の理由と同じ）。DB 関数で確かめれば、backend や容器の書き損じでも値は出ない。
- クラウドの network secret は、1 つのホストに 1 つ・ヘッダ 1 行だった（段0）。そのため 3 つの口が同じ CASE_AGENT_TOKEN を受ける形にした。
- api.salesanchor.jp には公開の書き込み口がある。パス分けでは相談係 AI から隠せないため、新しいサブドメイン case-api を使う。Host 見出しの付け替えでほかの口に届かないよう、TLS の名前で 421 を返す。
- 段0の試しは 3 回とも外への書き込みが 0 件だった。ただし、まだ塞いでいない道が見つかったため、最終合格とはしていない（中身は PO の非公開の記録）。

## 不採用の案

| 案 | 採らない理由 |
|---|---|
| 列名の正規表現で伏せる | 名前の合わない列から値が出る |
| 出力の列名で伏せる | 別名ですり抜ける（ADR-1024） |
| ai_ro そのものを伏せる | Mac の見張りと測定が効かなくなる（PO 決定「1」） |
| 今の読む窓口の接続を ai_reader_cloud に替える | 正答率の取得 3 本が ai_ro を読めなくなる |
| 値を返す口を backend に置く | 書ける接続・復号鍵と同居する（ADR-1042・ADR-1024） |
| 判断役に道具を持たせる | 申請の文に紛れた命令で道具を使われる（ADR-1039） |
| api.salesanchor.jp を丸ごと許可する | 公開の書き込み口に届く |
| Mac の囲いで相談係を動かす | Mac が重くなる（PO）。囲いの受入が 4 つ中 2 つ |
| 同じホストに secret を 2 つ、または 1 つにヘッダ 2 行 | 画面に無く、作れなかった（段0） |
| 無料の非公開リポジトリで ruleset を使う | 作れなかった（403。段0） |

## 戻し方

クラウドに個人の値が出ない順で行う。
1. routine を止める。
2. network secret を消す。
3. GitHub secret の CASE_AGENT_TOKEN を消してデプロイする（全部 401。サーバーの .env だけ空にしても次のデプロイで書き戻される。ADR-1042 と同じ）。
4. case-api の nginx の server ブロックを外す。
5. 段1の migration・ai-reader-cloud-http・deploy.yml の追加を戻す。

今の窓口は段1から変えていないので、戻しても Mac の AI に影響しない。

## 検証

- 合格の基準 K1〜K6（design.md §1。2026-10-30 PO 承認済み）。
  - K1: PO だけが投稿できる期間に 10 件連続で、報告が backend に届き、件のセッションが自動で開く。
  - K2: 投稿から報告までの中央値が基準値以下（基準値は段5の前に今の Mac 版で 3 件測る）。
  - K3: 許可なしで DB の個人の値が相談係 AI に渡った件数 0。投稿本文の形の置き換え漏れ 0。
  - K4: 相談係 AI の外への書き出し 0。
  - K5: 許可リスト外の人の投稿で /fire が呼ばれた件数 0。
  - K6: 解除の判断の全件に理由があり、週次点検の記録が毎週 1 本ある。
- 試験 T0〜T14（design.md §7）。段ごとの試験は design.md §9。

## 受け入れるリスク

- 投稿本文に書かれた人名・住所は、形で見分けられないため、置き換わらずに相談係 AI へ渡る（K3 の注記）。
- 箱の中の GitHub への道に、まだ塞いでいない道がある（中身は PO の非公開の記録）。今の守りは 1 枚と数える。段3に進む条件 U9 で確かめ、1 つでも外れたらこの方式を止めて再設計する。
- Claude GitHub App の導入先が今は全部のリポジトリで、届く範囲が広い。段3の前に、指定したリポジトリだけに絞る（U10。絞ること自体と一覧は PO の判断待ち。PO が絞らないと決めたら段3に進まず再設計する）。
- 持ち主のスマホへの通知（PushNotification）と claude.ai の skill を拒否できるかは、段3の試験 T0b で確かめる。拒否できなければ指示書で禁じ、ここに残るリスクとして書き足す。
- クラウドのセッションの保存は 30 日（PO が学習への利用をオフにする設定。実施はまだ確かめていない。U5）。

## 守り方

- CI: 分類の無い列と、理由の無い allow で落ちる（T10）。443 の server ブロックの数と 421 の include の数が合わなければ落ちる（T7）。
- デプロイ: 最初に ai_cloud を外し、最後の trap で毎回作り直して持ち主の権限を付け直す。結果は ai_cloud_meta.build_log に 1 行書く。
- 週次点検（毎週月曜 09:30）: 点検記録が無い週を K6 で数える。
- 鍵: CASE_AGENT_TOKEN は 90 日で更新する（正本は GitHub secret）。CASE_ADMIN_TOKEN・OPS_API_TOKEN は手元の Keychain だけに置く。
- 指示書の正本は docs/ai-agents/ops-incident-agent.md の 1 か所。専用リポジトリの写しは CI で正本とのハッシュ一致を確かめる。
