## What（何を決めたか）

1. v102 の解析で、読み取りを頼む先が一時的に断ったとき（HTTP 429・500・502・503・504）は、その場で2秒後・8秒後に送り直す。合計の待ちは90秒まで（PR #4854）。
2. それでも駄目なら、10分ごとの見回りで5分たった分をもう一度送る。試行は合計3回まで、作られてから24時間まで、1回の見回りで20件まで（PR #4854）。
3. 3回とも失敗した分と、24時間を過ぎた分は「諦めた」として、次の見回りで管理者用の Discord に1回だけ知らせる。
4. 毎週月曜 09:10 に、直前7日の「断られた数・送り直しで終わった数・諦めた数」を管理者用の Discord に送る。0件の週も送る。
5. v102 以外の解析の経路は送り直さない。

## Why（なぜ）

- 一時的な断りは、時間をおけば通ることが多い。2026-10-27 の HTTP 503 の8件は、人がやり直すまで止まっていた。
- 送り直しを入れただけでは、諦めた分にだれも気づけない。2026-10-29 の点検で、続ける仕組み8項目のうち4項目が欠けていた（[recon.md §1](../handoff/api-error-retry-governance/recon.md)）。
- 知らせと週の数は、このリポジトリの既存の型（Redis で1回だけ送る、月曜に件数を送る）で足りる。DB の変更をしないので、本番の反映が止まる危険を増やさない。
- SDK 全体の送り直し設定は、翻訳など全部の経路に効いてしまうので選ばなかった。

## 受け入れるリスク

- その場の送り直し（2秒・8秒）の成功回数は DB に残らないので、週の数に入らない。
- 定期処理そのものが止まったことを自動では警告しない。月曜の知らせが届かないことで気づく。
