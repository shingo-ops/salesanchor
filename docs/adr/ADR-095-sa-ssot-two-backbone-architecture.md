# ADR-095: SSOT原則と「2本背骨」アーキテクチャ（ADR-SA-01）

## Status
Accepted（2026-06-03）

本ADRセット（ADR-095〜ADR-106）はすべてこのADRが前提となる最上位原則を定める。
正本: `SalesAnchor_データ設計記録_2026-06-03.md`（全24章）。
本ADRセットを貫く最上位原則（SSOT）: 同じ事実（住所・単価・在庫数など）の保管庫は**常に1か所**。他は全部そこを参照する／自動計算する。手入力での二重持ちは禁止。

## Date
2026-06-04（起案: Hikky-dev / PO: shingo-ops）

## Context（背景）

Sales Anchor は B2B トレカ輸出向けのマルチテナント CRM。顧客は一度きりではなく**成約後に何度もリピートする常連客型**（1顧客＝時系列で複数注文）。

現行スプレッドシートは同じ事実（取引金額・連絡先・会話要約等）を複数タブに手入力で二重持ちし、ズレ・肥大化（リード管理61列）を招いている。

---

## Decision（What / Why / Scope）

### 確定した設計

1. 全設計を **SSOT（保管庫は1か所）** で統一する。
2. データの背骨を **2本** とする：
   - **①顧客マスタ（誰に売るか）**
   - **②商品・在庫マスタ（何を売るか）**
3. 2本が交わる**交差点＝「注文」**。注文から **見積書・請求書・出荷予定・顧客実績** を**自動生成／自動計算**する。
4. **CRM＝顧客（ストック）／SFA＝商談（フロー）** と役割を分ける。受信箱のカルテはSFA、顧客マスタは永続のCRM。

### 仕組み（意図）

人が手入力するのは各マスタの「属性」だけ。下流（書類・累計実績）は全て参照/計算で導出。単価を商品/在庫側で1か所直せば、以後の全書類に反映される。

### 用語定義（全ADR共通）

| 用語 | 定義 |
|---|---|
| A（自社在庫） | 在庫の実物を自社が保有。アプリが数量を管理。 |
| B（仕入元フィード） | 在庫は外部の仕入元が保有。フィードで価格・在庫が届く。アプリは数量を触らない。 |
| 提供元（仕入元） | 在庫の出どころ。自社（A）も外部（B）も「提供元」の一種。発送元でもある。 |
| 生オファー | 全提供元の全提供可能商品（在庫マスタの真実＝SSOT）。 |
| 集計フィルタ | 同一商品の重複提供元を1つに畳むテナント設定の採用ポリシー。 |

## 実装上の注意（誤実装防止）

- **注文に商品名・単価・住所を「コピー保存」しない。** 参照（ID）で持つ。例外は「スナップショットが必要な箇所」だけ（→ADR-101 配送先スナップショット）。
  - スナップショットと二重持ちは別物：前者は「その時点の確定値の保全」、後者は「同じ生き値を複数箇所で手管理」。混同しない。
- 顧客実績（累計取引額・LTV・会話数・最終会話日時）は**カラムに手入力させない**。注文・会話ログからの集計で出す。

## KGI / KPI（達成度の測定）

### KGI（最終ゴール状態 ＝ ここに到達すれば設計成功）

1. **SSOT成立** … 同じ事実の二重持ち・手入力がゼロ。1か所の変更が全下流（書類・実績）に自動反映。
2. **ポカヨケ成立** … 設計で防ぐと決めた事故が実運用で発生しない（下記KPIの事故系が全て0）。
3. **自動化成立** … 受注→見積→請求→入金→発送→完了→P&L が手入力なしで流れる。
4. **保守性成立** … 作成者以外が運用・一次対応・改修できる（ドキュメント＋ログ＋UIが揃う）。

### KPI（測定指標）

| # | 指標 | 目標 | 測り方 | 参照ADR |
|---|---|---|---|---|
| 1 | 誤テナント登録 件数 | 0 | 登録時のテナントがトークン由来かを監査 | ADR-097 |
| 2 | オーバーセル（二重売り）件数 | 0 | A在庫の利用可能<0 が起きた回数 | ADR-099 |
| 3 | 請求書と実配送先の不一致 件数 | 0 | 注文スナップショットと出荷先の突合 | ADR-101 |
| 4 | 二重持ちしている事実の数 | 0 | 同一事実を手入力で複数箇所保持していないか | ADR-095 |
| 5 | 自動計算項目への手入力上書き 件数 | 0 | 実績・P&L・会話集計が書込可能になっていないか | ADR-096/104 |
| 6 | 解析：提供元別 除外率／平均確信度 | 監視・しきい値内 | 解析ログから算出。悪化でドリフト検知 | ADR-100 |
| 7 | 集計同期のビュー化 | 成立 | 集計を実テーブル保存せず動的導出か | ADR-099 |
| 8 | 関税・送料のハードコード箇所 | 0 | キャリア×国×テナント設定化されているか | ADR-101/106 |
| 9 | 発注最適化Lv2による平均原価率 | 改善（％） | Lv2提案の採用前後の原価率差 | ADR-102/104 |
| 10 | 受注処理リードタイム（入金確認→発送） | 短縮 | ステータス遷移時刻の差分 | ADR-103/104 |
| 11 | 保守性：作成者以外が運用可能か | 成立 | 解析ログ＋失敗通知＋ナレッジUI＋一次対応手順の有無 | ADR-100 |

**実装上の注意:**
- KPIは**システムが自動計測できる形**で実装する（手集計にしない＝SSOT思想と一致）。
- 事故系（1〜5・8）は「発生したら即アラート」が理想。
- 6・9・10は解析ログ／ステータス遷移時刻／発注実額から自動算出。ダッシュボード化は後日でよいが、**計測の素データ（ログ）は最初から残す**（後から復元できない）。
- これらKPIは**設計指示書の受け入れ条件（Acceptance Criteria）**として再利用する。

## 付録1 — 未決事項（後日確定。実装前に要決定）

1. **A+B混合時の価格・採用ルール**（1注文で同一商品を複数提供元から引く場合の価格・提供元採用）。
2. **集計フィルタ／引当の採用条件に「発送速度・即日可否」を追加**（即納提供元を優先）。
3. **仕入元マスタの項目定義**（代行手数料・取り寄せ送料・リードタイム・カットオフ・発送代行可否・対応運送会社／手数料の構造＝固定額・%・重量別）。Lv2発注最適化・発送計算が依存。
4. **キャリア別の送料・関税の正確な数式**（FedEx/DHL/UPS×国×テナント。エビデンス確立）。
5. **Wise APIの本格調査**（自動入金確認を狙う場合。現状は手動＋PDF＋メール送金）。
6. **報酬（歩合）の計算ルール**（%/定額/役割別。テナント設定）。

## 付録2 — 要設計サブシステム（別ADRを起こす。本セッション未設計）

1. **会話ログの解析と翻訳** … 受信メッセージの翻訳（原文言語→日/英）＋商談解析（温度感・意図・要約）。会話ログの「翻訳文・商談解析」を埋めるAIサブシステム。外部AI連携＝ADR-025 3点セット対象。
2. **多チャネルの取り込み（webhook/API）** … 6チャネル（Messenger/Instagram/WhatsApp/Discord/Telegram/Email）の受信を会話ログへ取り込み＋名寄せ。※Meta連携は別パートナー実装中。ADR-098は「保存ID・リンク生成」を定義済み、取り込み本体は本項で別途設計。

## 付録3 — 別トラック（データ設計外・思想共通）

- **デザイントークン SSOT 基盤** … 色・文字・余白を1か所に集約し1変更で全画面反映。KGI＝全UIがトークン経由、KPI＝適用率100%/直書き違反0/変更工数。実装者がAIエージェントのため lint＋CLAUDE.md で自動ガバナンス。ADR-101のテンプレ「ブランド色変数」と地続き。
