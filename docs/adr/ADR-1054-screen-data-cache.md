# ADR-1054: 画面が取ったデータの写しを 1 か所（TanStack Query）に置き、前に見た画面をすぐ出してから裏で取り直す

| 項目 | 内容 |

| 備考 | PO 決定 2026-10-31: 「LINEみたいな使い心地」の意味は押した瞬間に開く速さ（選択「1」）、135 画面すべての作り方を先に設計（選択「2」）、全画面の基準は一律 2 秒（選択「3」）、ほかの人の変更は全画面で数秒（選択「1」）、在庫表の時間は全画面の後に決め直す（選択「3」）。起案は設計担当（Claude Opus）。Accepted になるまで実装（design.md §3-4 の段 1 以降）は始めない |

## What（何を決めたか）

- 画面の部品に `@tanstack/react-query` 5 系を 1 つ足す。写しの置き場は `frontend/src/lib/query/` の QueryClient 1 個だけにし、ほかの場所で作らない。
- 取り方は `useApiQuery` 1 つだけ。中で今の `api.get`（frontend/src/lib/api.ts）を呼び、通信・送り直し・401 の扱いは api.ts のまま。TanStack 側の送り直しは 0。
- 写しは「出すだけ」。staleTime 0 で、画面を開くたび・タブに戻るたびに必ずサーバーから取り直す。写しはメモリだけに持ち、ブラウザの保存に書かない。使われない写しは 30 分で捨てる。
- 写しの名前（key）は利用者の uid と取りに行く道すじで分ける。利用者が変わったら（ログアウトを含む）、開いている画面に知らせる順で写しを全部消す。
- ほかの人の変更は ADR-1016 の合図のまま受け、合図を受けた画面は自分の写しを取り直す。合図の名前の正本は今のまま backend/app/realtime/topics.py。
- 取り直し中は中身を消さず、既存の金型 Spinner を小さく出す。新しい金型・新しい CSS は作らない。

## Why（なぜ）

- 今は 96 本の画面ファイルのうち 62 本が、開くたびに中身を消して読み込み中の印を出す（recon §4 U1・u1-count.py で再現できる）。前に見た画面に戻っても最初から待つので、押した瞬間に開く感じにならない。
- 写しを手元に持つ部品は今 0 件（frontend/package.json）。画面ごとに自前で持たせると写しが散らばる。PO の条件「データを分散させない」に合わせ、置き場を 1 か所に決める。
- TanStack Query は、写しをすぐ出して裏で取り直す・合図で取り直す・まとめて消す、の 3 つが揃っている。外部事例では画面移動時の追加通信が 0 になった実測がある（docs/handoff/line-like-speed/sources.md B の X1）。
- 別の人がログインすると前の人の中身が一瞬見えた失敗例と、消しても開いている画面に知らせない失敗例がある（同 X3・X4）。だから uid で key を分け、消す順を決める。
- SWR も同じ形を作れるが、全部消して開いている画面に知らせる手順を自前で書く量が多い（design.md §3-6）。

## ADR-1016 との関係

- ADR-1016 の決定（通り道 1 本・合図に中身を入れない・画面は既存の API で読み直す・useRealtimeRefresh(topics, reload)）は変えない。
- この ADR は reload の中身を「その画面の写しを取り直す」にするだけ。自分のタブの書き込みは合図で来ないので、書き込みが成功したら同じ取り直しを画面が自分で呼ぶ。
- 在庫表の読み直しの間隔（5 秒＋0〜3 秒のずれ・ADR-1016 改訂 2026-10-18）は変えない。在庫表は K4 の 5 秒の判定から外し、全画面の後に PO と決め直す。

## Scope

- Included: frontend の写しの置き場・取り方・消し方、画面の移し替え（10 画面ずつ）、測る仕組み（tests/prod-check の記録係）、読み込み中に中身を消す形を数える CI の検査
- Excluded: DB・migrations・deploy.yml・本番 scripts、ログインの仕組み、閲覧ページ（viewer/）、打っている途中が見える同時編集。合図を足す backend の便（design.md §3-3 段 5）は便ごとに別の設計と審査

## Evidence

- evidence: docs/handoff/line-like-speed/recon.md・design.md・u1-count.py・sources.md
- confidence: medium（今の作りと数はファイルと命令の結果で確認。0.1 秒の目標が届くかは段 0・段 2 の測定でまだ確かめていない）
- tradeoff: 新しい部品が 1 つ増える。30 分以内に戻った画面は一瞬だけ前の中身が出る（直後に取り直して差し替える）

## Consequences

### Positive

- 30 分以内に戻った画面は、前の中身がすぐ出る
- 写しの置き場と消し方が 1 か所に決まり、画面ごとにばらばらに持たない

### Negative / Tradeoff

- 画面 62 本以上を移すので便の数が多い
- 写しの消し忘れがあると、別の人の中身が見える危険がある（段 1 の試験 K5 で 0 件を確かめてから画面を移す）

## Exceptions

- なし。staleTime を 0 より大きくする、ブラウザの保存に写しを書く、などの変更はこの ADR の改訂（PO の決定）が要る

## Follow-up

- 段 0 で測る仕組みを足し、今の値を基準として記録する
- 段 5 の最後に、在庫表の時間を PO と決め直す
