## What（何を決めたか）

1. 新しい機械のログインを許可できる人に「同じ会社のオーナーの役（system_key=owner）の人」を足す。admin 役（運営用）と一般の社員は入れない。自分の依頼は許可できない（オーナー自身は運営が許可する）。
2. オーナーに知らせるのは、待っている社員が待ち画面の「会社の管理者に頼む」を押したときだけ。1依頼で1回。頼んだ時刻を依頼の表の1列（admin_requested_at）に残す。
3. オーナーが見られ・許可できるのは、自社の社員が頼んだ、期限内の、待っている依頼だけ。会社の絞り込みは public.users と JOIN して行い、依頼の表に会社の列は足さない。
4. 許可の書き込み（状態・許可した人・本人確認のメモ）は運営とオーナーで1つの関数を使う。decided_via は既存の 'admin'。オーナーか運営かは監査の event 名と許可した人で分かる。
5. 鈴の数は表から生で数える。知らせの写しの行は作らない。
6. スタッフ登録の重複の文言は、他社か自社かを言い分けない。
7. 会社の列があるのに RLS が無い public の表を、migration の実 DB 試験で止める。許可一覧は理由つきで1か所に置き、CI と本番の毎日点検が同じ一覧を読む。
8. 本番で毎日1回、接続役・BYPASSRLS の役・RLS の無い表を点検し、緑でも赤でも管理者用 Discord に送る。
9. 見張りのファイルを変える PR は、pull_request_target で動く必須チェックが、PO の「GO #番号 <今の head の SHA>」コメントがあるまで止める。この見張りは PR のコードを動かさない。

## Why（なぜ）

- しんごさん1人が全社の締め出しを解く形だと、しんごさんがいない時間に社員が働けない。オーナーは元々自社の社員を作る・止める権限を持つため、許可を任せても権限は広がらない。
- 新しい機械のたびにオーナーへ知らせると、知らせが増え、社員の居場所が毎回伝わる。社員が頼んだときだけにする（PO 決定）。
- 依頼の表に会社の列を足すと、人の会社の正本が2か所になる（ADR-1008 に反する）。
- 監査（2026-11-05）で、他社に届く道は 0 本だが、新しい表の RLS 漏れ・本番の分け方の崩れ・見張りの外しを止める機械が無かった。今の見張りは pull_request で動くため、PR が自分で外せる（GitHub 公式文書: pull_request は PR のマージ用の写しで動き、pull_request_target は基のブランチの定義で動く）。

## 影響

- 新しい列 1（migration・危険 PR）、新しい受け口 3、画面 1、必須チェック 1（Ruleset の変更は PO の permit-danger）、毎日の Discord 1通。
- 受け入れる弱み: メールは全社で1つのため、スタッフ登録が「できない」こと自体から誰かが使っていると推測はできる。文言で会社の別を言わないところまでとする。

## 戻し方

- 便ごとに PR を戻す。列は `ALTER TABLE public.auth_login_requests DROP COLUMN IF EXISTS admin_requested_at`。必須チェックは ruleset から外してから workflow を消す（どちらも PO の許可が要る）。
