# ADR-1006: 商品コードを PM-00001 形式の連番にそろえ、品番の照合は型番（mark）だけで行う

| 項目 | 内容 |
|------|------|
| ステータス | Accepted（PO 2026-10-05「1,はい」。実装は未着手） |
| 日付 | 2026-10-05 |
| 起案 | しんごさん（PO）+ Claude Opus（設計パートナー） |
| 関連 | Amends ADR-1002（§4 product_code 自動採番の形式）、ADR-1001、ADR-155 |

---

## ひとことで

`products.product_code` を、意味を持たない連番 `PM-00001`（ハイフン＋5桁）にそろえる。既存の全商品の番号も振り直す。旧コードは別の列に残す。公式の品番（型番）は `mark` だけが持つ。LINE 解析の品番の照合は、`mark` だけで行う。

## 背景（2026-10-05 実測。根拠は docs/handoff/product-code-pm5/recon.md）

- PO の決定（2026-10-05）
  - 「商品の固有IDはPM-00001の連番に統一したい」
  - 形の確認（PM-00001、5桁）に「はい」
- 今の product_code（本番 1,347行）は形がそろっていない。
  - WS-* 450、OP-* 174、YGO-* 159、接頭辞なし 111、UA-* 109、PM＋4桁 83（PM0007〜PM0297）、DB-* 67、DGM-* 63、SV* 49、HOL-* 29、GD-* 18、PKM-* 12、LOR-* 11、NULL 12
- ADR-1002 §4 は、自動採番を `'PM' || lpad(nextval('product_code_seq'),4,'0')` と決めた。ただし本番の列に DEFAULT は無く、sequence は一度も使われていない。採番は今もアプリ層の `_next_pm_code()`（`PM{num:04d}`、9999 が上限）で行っている。
- 品番の照合に product_code を使っている箇所
  - v6：Gemini が書き写した品番の文字を、`mark→id` の表で引く。product_code が一致する商品があれば、それで上書きする（tcg_analyzer_svc.py:1219-1224, :1431）。
  - v7：投稿の文に、品番か型番が含まれていれば候補にする（extraction_judgement_svc.py:140-148）。
- 実測
  - Gemini が書き写した品番 5,759件のうち、product_code にだけ一致するものは 0件。投稿に出る品番は、すべて mark にもある。
  - v6 の表には並べる順の指定が無い（:1220-1222）。同じ mark を持つ商品が複数あると、どれに決まるかは DB が返す順しだいで、今も決まっていない。
    - 共有されている mark は 34組（99商品）。本番の Gemini の書き写しのうち 181行が当たる。正規化すると 46組。
    - そのうち 29組（95行）は、上書きする商品が無く、今も決まり方が定まらない。
    - 残りの5組（PCJ・SVI・SV2a・PROMO・ARCHRD、86行。うち SV2a が 76行）だけが、product_code の上書きで決まっている。
  - v7 では、product_code「ARD」が「CARD」の中に当たり、ambiguous が出ていた。product_code を照合から外すと、v9 の試験で ambiguous から matched が 5件、崩れは 0件だった。
- product_code を振る経路は2つあった。
  - `tcg_product_master_svc._next_pm_code()`（PM＋4桁）。
  - `routers/products.py:379, 407-410`（PD-{id:05d}）。
  - 形がそろわない原因になっている（SSOT 違反）。
- 毎回流し直される migration `20260604_010000_seed_product_marks.sql` が、名前で一致した商品の mark を上書きしている（:23-25、MEGAドリームex を M3 に戻した。2026-10-05 02:38Z）。
  - mark を型番の正としてそろえる前に、これを無効にする必要がある（別の PR で、migration の変更として PO の GO を待つ）。
- 店頭の在庫のシート（GAS）は、PM 系のコードを product_id として持っている。人が入力したもので、IMPORTRANGE で取り込んでいる。DB の product_code と自動で同期する処理は、コードからは見つからなかった（未確認として扱う）。

## 決定

1. **固有 ID の形**
   - `product_code` は `PM-` に5桁の連番を付けた形にする（PM-00001〜PM-99999）。
   - DB の sequence と DEFAULT で採番する。ADR-1002 §4 の形式（PM＋4桁）は、本 ADR で置き換える。
   - アプリ層の `_next_pm_code()` と `routers/products.py` の `PD-{id:05d}` は廃止する。採番は DB の DEFAULT の1か所にまとめる（SSOT）。
2. **既存の商品の振り直し**
   - 全商品（有効と無効の両方）に、`id` の昇順で PM-00001 から振る。
   - 旧コードは新しい列 `legacy_product_code` に保存する（NULL 以外は一意）。旧コードは店頭のシートや過去の記録と対応させるために使う。
3. **型番は mark だけが持つ**：公式の品番は `mark` に入れる（ADR-155）。product_code には意味を持たせない。
4. **品番の照合は mark だけで行う**
   - v6：`rawcode_to_id` は、有効な商品の中で一意な mark だけから作る。product_code での上書きはやめる。共有されている mark は、品番では決めずに、検索の語の照合に回す。
   - v7：`_code_candidate_basis` から product_code を外し、mark だけを見る。
5. **データの値の変更**
   - 振り直しは、PO の合意のもとで、本番のデータの変更の手順で行う（DRY-RUN → COMMIT、件数の照合、rollback を用意）。
   - 列の追加と DEFAULT の設定は、migration で行う（構造の変更のため。ADR-155 で許される）。

## 理由

- ID と型番の役割を分ける。ID は変わらない連番、型番は公式の品番にする。今の product_code は両方を兼ねていて、形がばらばらである。
- 照合を mark だけにすると、v6 で決まり方が DB の順しだいになる問題を、仕組みの側でなくせる。
- 5桁にするのは、4桁の上限 9999 を避けるため（今 1,347行）。

## 弊害・トレードオフ

| 弊害 | 対処 |
|---|---|
| 店頭のシートの PM 系の product_id と、DB の新コードが食い違う | `legacy_product_code` で対応を辿れるようにする。シート側の付け替えは別の便にし、PO が判断する |
| v6 で、共有されている mark の品番の照合が変わる | 本番の 5,973件で試算した（2026-10-05）。<br>・変わるのは 110件（1.8%）。<br>・103件は、品番の照合による上書きが無くなり、Gemini の選択がそのまま残る（ST01 36・SP 23・M3 23・PROMO 10 ほか）。<br>・7件は、検索の語の照合に回る。<br>・SV2a は Gemini の選択と同じなので、変わらない。<br>どちらが正しいかは原文が必要なため、切り替えの前に PO と目で確かめる |
| CHECK 制約と、既存の試験の fixture のコード（SENTINEL など）がぶつかる | CHECK は振り直しの後に、別の migration で付ける。共有の試験の fixture には入れない |
| 振り直しの前に作った CSV の書き出しが古くなる（revision のハッシュに product_code を含む） | 振り直しの前後で、書き出しを作り直すよう案内する |
| CSV の書き出しや画面に出る「コード」が変わる | 取り込みは id で行を特定しているので壊れない（tcg_product_roundtrip_svc.py:223,358）。画面の表示は新コードになる |
| Gemini の選択の記録などに、旧コードの文字が残る（5,493行） | 解析では使っていない（tcg_analyzer_svc.py:1277-1279）。過去の記録として残す |
| 作品の参照の digest が変わる | マスタを編集するときは、いつも起きる今の動きである。試験の時間を避ける |

## 外部・過去事例の参照と我々への応用

- 外部事例：サロゲートキー（意味を持たない ID）と業務キー（公式の品番）を分けるのは、一般的なデータベースの設計の原則である。特定の導入事例の数値には依存しないため、外部の事例は挙げない。
- 過去事例
  - ADR-1002：ID を integer に一本化した。
  - 2026-10-04 と 10-05 のマスタの修正（#3966・#3968・#3969）：記号の誤り（M3）や二重登録が、照合の誤りを生んでいた。product_code と mark の二重の持ち方が、こうした誤りの温床だった。

## 維持の仕組み

- 守り手：設計担当（Opus）。商品の登録時に mark の重複を検査する仕組みを作るかどうかは、PO が判断する。
- product_code の形の検査：CHECK 制約 `product_code ~ '^PM-[0-9]{5}$'` を、振り直しの後に付ける。

## 実施順序

```
PR-0: seed_product_marks migration の無効化（mark の上書きを止める）
    ↓ デプロイ後、MEGAドリームex の mark を M2a に直し直す（データの変更）
PR-1: migration A（legacy_product_code の列と一意の索引のみ）
    ↓
PR-2: コードの変更（v6 は一意の mark だけ、v7 は product_code を見ない、採番は DB に一本化、seed_inventory の参照）＋試験
    ↓ デプロイ後
データの変更: 全商品の振り直し（legacy への複写、PM-00001〜、sequence の setval）DRY-RUN → COMMIT
    ↓
PR-3: migration B（DEFAULT と CHECK）
```

- PR-0〜PR-3 はどれも本番に影響する。マージには PO の「GO #番号」が要る（ADR-136）。
- 各段のあとに、本番で読み取りの確認をする。

## 受入条件

- [ ] 全商品の product_code が `^PM-[0-9]{5}$` で、一意である。旧コードが legacy_product_code にある。
- [ ] 新しく登録した商品に、DB の sequence で次の番号が振られる。
- [ ] v6 と v7 の照合が、product_code を参照しない（コードと試験）。
- [ ] v9 の試験で、崩れが 0件（mark だけの照合の試算）。
- [ ] 過去のジョブの再解析の試算で、品番で決まっていた行の変化の件数と正答を、PO が確かめる。
- [ ] pytest が全部通る。デプロイが成功し、smoke の試験が通る。
