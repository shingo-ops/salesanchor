# ADR-100: 取り込み・解析パイプライン（提供元メッセージ→生オファー）（ADR-SA-06）

## Status
Accepted（v1は事実記録、v2は方針）

## Date
2026-06-04（起案: Hikky-dev / PO: shingo-ops）

## Context（背景）

提供元ごとに商品名・状態・価格・数量の書き方がバラバラ。現状は GAS スプレッドシートで Gemini 2.5 Flash が解析し共通フォーマットに整形→集計して生オファーにしている。個人開発の「とりあえず動く」状態で、精度・保守性・説明可能性に課題。

運用シート参照: `docs.google.com/spreadsheets/d/1or39_glwYtF9OfOxXizN8ZjcUKL0hNIeW3qP3nCx3AI`

---

## Decision（What / Why / Scope）

### v1＝現行の事実（GAS実装）

#### フロー

```
提供元の原文
  └→ Gemini解析
        参照1: 商品マスタ（商品特定の辞書）
        参照2: 提供元別個別ナレッジ（書き方の癖ルール）
        └→ 整形データ ＋ 除外リスト
              └→ 集計
                    └→ 生オファー（在庫マスタ＝SSOT）
```

#### 除外ロジック

以下の行は集計に入れず除外リストへ：
- 価格なし
- `[サーチ済み]` 等の除外キーワード
- 商品名・数量が不明瞭

#### 実装仕様（GAS）

- 列＝提供元
- 行2-7固定（2=時刻/3=原文/4=整形/5=除外/6=AIコメント/7=個別ナレッジ）
- onEdit即時＋一括＋18h自動削除
- 6hキャッシュ・429リトライ
- 商品の正規化は**商品マスタが正**（Category・名称はマスタに従う）

---

### v2＝VPS版の方針

#### 1. 解析ログを永続化

| ログ項目 |
|---|
| 原文 |
| マッチ商品＋確信度 |
| 抽出値 |
| 使用ナレッジ版・モデル版 |
| 成功 or 除外理由 |

**18h自動削除は廃止**（改善データを捨てない）。

#### 2. 構造化出力

商品ID・確信度・抽出値・判断理由を出力。整形テキストだけにしない。

#### 3. ドリフト検知

提供元ごとの除外率・確信度を監視 → 悪化や新提供元を自動フラグ。

#### 4. 改善ループ（人を残す）

失敗例からナレッジ修正案を提案 → **人が承認** → 精度向上。

#### 5. ナレッジ管理UI

商品マスタ・提供元別ナレッジをDB＋画面で管理。

#### 6. ADR-025の3点セット

取り込み本体＋状態検証＋失敗通知を必ず実装。

### 仕組み（意図）

製造業のポカヨケ・カイゼン（不良記録→原因追跡→工程改善）をAI解析に適用。「なぜその商品と判定したか／なぜ除外したか」を記録して継続改善。提供元が増えても書式が変わっても検知・改善でき、属人性を排して他者でも保守運用可能。

---

## 実装上の注意（誤実装防止）

- **完全自動の自己書き換え（AIが自分のルールを勝手に更新）は採用しない。** 「**検知は自動／修正は提案＋人が承認**」。黙って壊れるのを防ぐ（ポカヨケ）。
- v1の **18時間自動削除をそのまま移植しない**（改善データの源を消す）。VPSでは永続ログ＋寿命管理に置換。
- 商品の正規化は商品マスタを唯一の辞書とする（解析結果がマスタと食い違う場合はマスタ優先）。
- 解析失敗の**通知が現状弱い**（GASは6行目出力のみ）→ v2で必ず通知を実装。
