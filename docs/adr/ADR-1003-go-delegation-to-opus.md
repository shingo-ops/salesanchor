# ADR-1003: GO 発行を Claude Opus 設計担当へ常時委譲する（例外あり）

| 項目 | 内容 |
|------|------|
| ステータス | Accepted |
| 決定日 | 2026-09-29 |
| 決定者 | Shingo（PO） |
| 関連 | ADR-136（GO 手順・承認フロー v2の一部を上書き） |

---

## What（何を決めたか）

GO（危険変更・ユーザー影響変更・外部API変更のマージ前承認）の発行権限を、PO（Shingo）単独から、**Claude Opus 設計担当へ常時委譲**する。ただし以下の「例外」に該当する変更は、常時委譲の対象外とし、従来どおり PO 本人の GO が必須のままとする。

- 委譲の GO を PR 本文の `### GO記録` に記録する場合、`GO発行者` は「POの委任に基づくClaude Opus発行」と記載する
- `scripts/check-process-artifacts.js` の `AUTHORIZED_GO_ISSUERS` にこの発行者名を追加する

## Why（なぜ変えるか）

PO 本人しか GO を出せない従来の運用（ADR-136 §承認フロー v2 ④）では、GO とマージのたびに作業が PO の応答待ちで止まっていた。PO は 2026-09-28「マージもあなたの役割である、GOは私の承認必須だがGO許可したのでマージデプロイまではあなたの管轄である」と発言し、続けて 2026-09-29「GO発行もあなたに権限委譲したいのでルールを変更してくれ、元のルールから変更して次のセッションからキャッチアップできるようにしてくれ」と明示的に委譲を決定した。委譲の形として「常時委譲＋例外あり」を PO 自身が選択した（2026-09-29）。

## 委譲の条件（すべて満たすこと）

委譲による GO（発行者「POの委任に基づくClaude Opus発行」）を出せるのは、次のすべてを満たす場合に限る。

1. 必須の CI がすべて通る
2. Reviewer エージェントが APPROVE している
3. PO に3行まとめ（対象・変更内容・バックアップ確認）を報告済み

## 例外（PO 本人の GO が必要）

以下に該当する変更は、Claude Opus への常時委譲の対象外とし、**PO 本人の GO（`GO発行者` が `shingo-ops` または `Shingo`）が必須**のままとする。

- DROP TABLE / DROP COLUMN を含む migration
- 大量 DELETE
- secrets の変更
- Ruleset・Branch Protection の変更
- `.github/workflows/workflow-lint.yml` の変更
- 外部 GUI（Cloudflare・Firebase 等）の操作
- main / develop への force push

`scripts/check-process-artifacts.js` は、変更ファイルがこれらの例外パス（`.github/workflows/workflow-lint.yml`）に該当する場合、または migration ファイルの追加行に `DROP TABLE` / `DROP COLUMN` を含む場合、`GO発行者` が委譲名義（「POの委任に基づくClaude Opus発行」）であれば fail させる。既存の `DANGEROUS_PATTERNS`（危険パス判定）と同じ regex 方式で判定する。

大量 DELETE・secrets 変更・Ruleset/Branch Protection 変更・外部 GUI 操作・force push は、現状 `check-process-artifacts.js` が機械検証できる対象ではない（ファイル diff だけでは判定不能、または GitHub API / 外部操作を伴う）。これらは CLAUDE.md「不可逆操作は必ず PO 確認」の運用（`scripts/permit-danger.sh` 等）で従来どおり人手で担保する。

## 委譲の解除

PO が「委譲停止」と発言した時点で、常時委譲は終了する。停止したことは `docs/handoff/go-record-transcription/opus-delegation.md` に記録する。解除後は ADR-136 の元のルール（GO 権限は PO 単独）に戻る。

## Supersedes（上書き範囲）

ADR-136 §承認フロー v2 の「④ GO 権限は PO（Shingo）単独」の部分のみを上書きする。承認フロー v2 のそれ以外の手順（チャットで3行サマリを提示 → GO受領 → PR本文へ転記 → gate が機械検証）はそのまま維持する。

## 弊害・トレードオフ

- 委譲により、PO の確認なしにマージが進む範囲が広がる。上記「例外」の範囲設定と、CI緑＋Reviewer APPROVE＋3行報告の3条件で歯止めをかける
- 委譲名義の GO 記録は、機械検証（`AUTHORIZED_GO_ISSUERS` allowlist）のみで本人性を証明しない。誤用・濫用のリスクは PO の「委譲停止」発言でいつでも解除できることと、ADR-1002 の振り返り運用（governance監査）で軽減する

## 外部・過去事例

該当なし＋理由: この委譲は自社の PO-Dev 間の承認運用設計であり、外部事例よりも自社の GO 記録運用実績（ADR-136 §承認フロー v2 の実装・運用実績）を優先する。

## 維持の仕組み

- 守り手: `scripts/check-process-artifacts.js`（`AUTHORIZED_GO_ISSUERS` の allowlist 検証・例外パスの fail 判定）
- 委譲の状態記録: `docs/handoff/go-record-transcription/opus-delegation.md`（開始・範囲・解除の記録）

## 追記（2026-10-28）検査の実装の現状

この節は決定（「例外」節の 7 項目）を変えない。「例外」節の後半にある「機械で見る範囲」の説明が、その後の検査の強化（docs/handoff/rule-enforcement/design.md の R6a〜R6d、PR #4823・#4826・#4829・#4830）で実装より狭くなったため、今の実装を記す。判定の正本は `scripts/check-process-artifacts.js` の `requiresPoOnlyGo` である。

- 見る対象のファイル: `migrations/` 配下に加え、`scripts/migrate_*.py` と `scripts/run_all_migrations.sh`（`isMigrationPath`）。
- 削除の文: 「例外」節の 1 項目目に挙げた表と列の削除に加え、同じく構造を消す文（スキーマ・データベース・外部テーブル等の削除、列の語を省いた列の削除）も本人 GO が要る側に倒す。
- 大量 DELETE: migration の中の TRUNCATE と、条件の無い DELETE（中身の無い条件を含む）は機械で見て本人 GO が要る側に倒す。条件のある DELETE の件数は見ない（従来どおり手順で担保）。
- workflow-lint: 拡張子 `.yaml` と表記のゆれも同じ扱い。
- 判定のやり方: 正規表現の一致だけでなく、SQL の字句（引用符・コメント等）を読んで見分ける。読み切れない入力は本人 GO が要る側に倒す。
- 発行者: 発行者名に委任を示す語が入るものは、本人の GO として扱わない（`validateGORecord`）。
- 機械で見ないもの（従来どおり手順で担保）: secrets の変更、Ruleset・Branch Protection の変更、外部 GUI の操作、main・develop への force push。

## 追記（2026-11-02）本番サーバー上の作業の委任

### 決定

PO が合意した設計の作業手順に書かれた操作は、Claude Opus が無制限鍵（`~/.ssh/manual-only/id_ed25519`）で本番の機体（prod1・prod2）に入り、PO の都度の GO なしに実行してよい。AGENTS.md「VPS 直作業禁止」節の「作業ごとに PO の GO」の、この範囲だけを上書きする。

### PO 発言の原文

- 2026-11-02「私は非エンジニアで技術知識はないので要件定義と設計までは携われるがその後はOPUSが取り仕切りプロジェクトの開発を完走させてもらう必要があるのだがその体制に必要な権限が揃っているか？」
- 2026-11-02 選択肢「1」（合意した設計と、審査に合格した作業手順に書いた操作に限り、Opus が本番のサーバーで自分で実行できる許可を足す。実行の前に必ず控えを取る。毎週の点検で実行した中身を確かめる）
- 2026-11-02「非エンジニアの私が途中で介入しなければ行けないのはボトルネックになると考えている、合意したことは再度許可を取りに来なくてもいいし、要件定義や設計時点でしっかりと事実調査と現状把握をして危険な部分は事前説明をするようにしなければならない」

### Why（なぜ変えるか）

2026-10-26〜11-02 の実測で、自動の安全判定に止められて PO の `!` 実行が要った操作のうち、本番サーバー上の書き込み・停止が 7 件あった（試験の入力置き・移行の詰まり解消・DB の接続切り・容器内の停止・backup.sh・初回パスワード発行・オーナーのアドレス変更）。どれも PO と合意済みの設計の中の操作で、PO の判断を要する新しい中身は無かった（根拠: ~/CC報告ファイル-keep/autonomy-inventory/20261102.md §2 の A）。同じ形の許可を期限付きで足した試験（FNT-1・FNX-1）では、手順書の行は PO の手なしで流れた。

### 条件（すべて満たすこと）

1. 操作が、PO の決定を記録した設計（design.md・ADR）に属する作業手順（RUNBOOK・カード）に、そのままの行として書かれている。
2. その作業手順が、審査役（reviewer・model opus）の APPROVE を受けている。
3. 設計の段階で、その操作の危ない点（戻せるか・止まる時間・影響する利用者）を PO に普通の言葉で説明してある。
4. 実行するのは Opus 本人だけ。調査・実装の担当（クラウドの Sonnet を含む）には無制限鍵を使わせない。
5. 書き込み・停止・再起動の前に控えを取る（DB は backup.sh、ファイルは写し）。控えの場所を記録に書く。
6. 実行ごとに `~/CC報告ファイル-keep/prod-ops/YYYYMMDD.md` に1行ずつ書く: 日時（JST）・機体・作業手順のパスと行・審査の根拠・控えの場所・結果。毎週の同意と権限の点検でこの記録を読み、手順書に無い行が無いかを確かめる。

### 除外（従来どおり PO 本人の GO が必須）

- 上の「例外」の各項目と、AGENTS.md「不可逆操作は必ず PO 確認」の操作（表の削除・大量 DELETE・ファイルの一括削除・本番 Docker volume の削除・secrets の変更 など）
- 作業手順に無い行、作業手順の値を書き換えた行
- 鍵・パスワード・トークンの表示・作成・変更、SSH・ファイアウォールの設定の変更、人間の鍵の変更
- 見張り（フック）と権限の設定を弱める変更
- 実行の結果が作業手順の想定と違ったときの次の操作（止めて PO に普通の言葉で報告する）

### 弊害と対処

- PO の目を通らずに本番の書き込みが走る。→ 条件 1〜3 で、危ない点は設計の段階で PO に説明済みのものに限る。条件 6 の記録を毎週の点検で読む。
- 手順書の誤りがそのまま本番に出る。→ 条件 2 の審査と、条件 5 の控えで戻せるようにする。
- 解除: PO の「委譲停止」の発言で、この追記も終わる。

### 機械での反映

Claude Code の自動の安全判定に、上の条件と除外を書いた許可の行を1つ足す（~/.claude/settings.json の autoMode.allow。権限の記録帳 ADR-1034 に、この PR 番号を根拠として記録する）。自分の権限を広げる設定の変更は自動判定が止めるため、反映は PO が `!` で1回だけ行う。
