## What（何を決めるか）

1. `_merge_supplier_products`（backend/app/services/tcg_analyzer_svc.py:1964）の付け直しで、行が「新しく現行になる」のは次のどちらかのときだけにする。満たさない行は FALSE にする。
   - (i) 同じ仕入元のより新しい投稿に、同じ商品の行（仮の行を含む）が無い。
   - (ii) その行の (投稿, 商品, 状態) が、付け直しの前から現行だった。
2. すでに現行の行はこの規則では落とさない。
3. 控え（前から現行だった組）は v102 の再解析と再抽出ツールだけが渡す。件の削除と取り消しでは切る（削除は再解析ではなく、ADR-158 の G5「削除した件が最新だった組は次に新しい投稿の件を戻す」を守るため）。
4. 本番の確認済み 2 件（現行のまま新しい投稿に隠れるべき行）だけを、監査行つきの SQL で FALSE にする。未確認の 626 件は直さない。

## Why（なぜ）

- v102 と v6 の書き込みは `ON CONFLICT (extraction_item_id) DO UPDATE` で `is_current` を SET しない（backend/app/services/line_analysis_v102_svc.py:760-769）。既存の行は古い値を持ち越し、新しく作った行は既定の TRUE で入る。
- 再解析で行の状態や商品が変わると、前の組が `extra_pairs` として「触れた組」になり、古い投稿が先頭に戻って、新しい投稿に隠れていた行が TRUE になる（復活）。
- 本番では確認できたもので 2 件（配信中）。残り 626 件は痕跡が消えていて復活かどうか判定できない（design.md §7）。

## 守ること（2026-09-25 d24d13249 の設計）

商品×状態の組ごとに最新の投稿の行が現行、という規則は変えない。古い投稿にしか無い状態の行（例: 新しい投稿に A/Single だけがあるとき、古い投稿の A/Damaged）は残る。この ADR が止めるのは「再解析で戻ってくる」ことだけ。

## 選ばなかった案

- **規則を「商品ごとに最新の投稿の行だけ現行」に変える**: 9/25 の設計を壊し、PO が n とした。
- **再解析のたびに全投稿を付け直す**: 配信が広く動き、K2（痕跡の無い行の変化 0）を守れない。
- **is_current を SET に入れて UPSERT のたびに書き直す**: 人の判断（件の削除など）で動かした値を上書きするおそれがある。
- **未確認 626 件も一括で直す**: 設計どおり残っている行が混ざり、配信が減る。判定できるまで直さない。

## 確かめ方

design.md §5 の K1〜K5。試験はサンドボックス（docs/handoff/revival-guard/sandbox/）で現行 SQL と案を同じ入力で比べ、4 場面（R1・R3a・R3c・R5）だけが変わり、ほかは同じであることを確認済み。本物の pytest と外部事例は【未確認】。
