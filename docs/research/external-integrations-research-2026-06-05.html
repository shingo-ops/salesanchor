1. 本書の位置づけ（ADR の現状方針）

リポジトリの ADR を調査したところ、キャリア直接連携・Google Drive 連携を具体的に定めた ADR はまだ存在せず、いずれも「将来の別 ADR で扱う」「後日確定」という位置づけでした。関連する既存方針は以下のとおりで、本レポートはその別 ADR 起案のための前提資料です。

  • ADR-021（受注管理）：発送は eLogi（発送代行）が現行メイン。OrderFlow の eLogi CSV（19 カラム固定）を維持。出力アダプタ層を抽象化し、追加キャリア（DHL / FedEx / ヤマト等）の CSV / API 連携は別 ADR で個別追加する設計（本 ADR は Scope 外）。ラベル PDF / CSV の保存先候補に Google Drive（VPS local / S3 等と並ぶ未確定の選択肢・判断委任事項 Q7）。
  • ADR-021：Spreadsheet 過去データ移行で サービスアカウントによる Google Sheets / Drive 直読を既に採用（＝GCP プロジェクト・サービスアカウント基盤が既存）。
  • ADR-093 / 094（売上管理）：「Google Drive エクスポート追加」が将来項目。
  • ADR-095 / 101 / 103：キャリア別の送料・関税の正確な数式は「キャリア連携の段（後日）」と保留。
重要な含意：「直接キャリア連携」は eLogi（発送代行アグリゲーター）でカバーできない要件が出た場合の選択肢です。直接連携は各社とも法人配送契約が前提で、国内2社（ヤマト・佐川）は商談・審査・数か月のリードタイムを要します。まずは CSV 連携（eLogi / 各社 CSV）＋ Google Drive 保存から着手し、API 直結は段階的に追加するのが ADR-021 の抽象化方針とも整合します。

3. salesanchor 向け推奨ロードマップ

ADR-021 の「eLogi-first ＋ 出力アダプタ層を抽象化」方針に沿った段階導入案です。

Phase 0｜Google Drive 保存基盤（最速・審査負荷最小）

  • 既存 GCP プロジェクト＋既存サービスアカウントを流用し、サービスアカウント＋自社共有ドライブ（Workspace）に帳票・ラベル PDF/CSV を保存。
  • ADR-021 のラベル保存先（Q7）の有力解。OAuth の機微スコープ審査・CASA を回避できる。
  • テナントが「自社 Drive に保管したい」要望が出たら、ユーザー OAuth（drive.file スコープ）を追加する二段構え。

Phase 1｜国際 3 社の API 直結（セルフサーブ寄り）

  • UPS / FedEx は OAuth 2.0 でセルフサーブ登録可。アカウント契約があれば最短。共通の「OAuth トークン取得＋キャッシュ」クライアントを 1 つ用意し、Rate/Ship/Track/Pickup を Bearer で叩く構成。
  • FedEx の Ship（ラベル発行）は Shipping Label Certification が必須（サンプルラベル提出→審査 約3営業日）。リードタイムを工程に織り込む。
  • DHL は MyDHL API（DHL Express）1 本で見積/ラベル/追跡/集荷を充足。DHL 側のレビュー承認が入る。

Phase 2｜国内 2 社（ヤマト・佐川）

  • いずれも法人契約＋商談＋数か月のリードタイム＋従量/月額課金。即時 API キー発行はできない。
  • 第一歩は CSV 連携（ヤマト B2クラウドへの CSV 取込／佐川 e飛伝Ⅲ への CSV 取込）。API 直結（ヤマト B2クラウドAPI／佐川 送り状発行API）は本格運用フェーズで別途申込。
  • 送料の事前計算 API は両社とも公式に確認できず → 運賃表（タリフ）をアプリ側に保持して算出する設計が現実的。
  • ヤマト「配送連携API」は「EC事業者→購入者への発送」用途は対象外の制約があるため、事業者→顧客発送は B2クラウド/B2クラウドAPI が正規ルート（商談で要確認）。
共通：各社とも sandbox / production を環境変数で切替、認証情報・API バージョン文字列も設定値化。ADR-021 の出力アダプタ層（キャリアアダプタ）に各社実装を載せ、eLogi と並列に差し替え可能にする。

4. Google Drive

用途

導入難易度 低 ★

請求書/発注書 PDF、発送ラベル PDF/CSV を Drive に保存・整理・共有（files.create アップロード、フォルダ自動作成、permissions 共有リンク発行、files.list 検索）。

前提

  • 既存の Google カレンダー連携プロジェクトをそのまま流用可。Drive API を追加で有効化するだけ（新規プロジェクト不要）。
  • 同意画面（現名称 Google Auth platform）・OAuth クライアントも流用可（redirect URI 追加）。ADR-021 の移行用サービスアカウントも同一プロジェクト内なら認証基盤として流用可。
  • 標準利用は現状無償（後述の通り 2026 年内に超過課金導入予定）。

API 利用までの手順

  1. Cloud Console「APIs & Services」で Google Drive API を有効化。
  2. OAuth 同意画面（Branding / Audience）を確認。User Type は External（外部テナント向け SaaS）。
  3. 「Data Access」で必要最小スコープを宣言 → drive.file（非機微）を強く推奨。
  4. OAuth クライアント（Web アプリ）を作成 or 既存に redirect URI 追加。
  5. 審査要否を確認（下記）。Testing 状態なら審査前でも最大 100 名のテストユーザーで動作可。

認証方式（2 パターンの違い）

観点A. 各テナントの Drive に保存（ユーザー OAuth 2.0）B. 自社サービスアカウントに保存（推奨）
保存先テナント各社の Google Drive自社管理の共有ドライブ
認証Web Server OAuth 2.0 ＋ refresh token をテナント別保管サービスアカウントの JWT 認証
ストレージテナント側容量を消費サービスアカウントは自前ストレージを持てず My Drive 直書き不可 → 共有ドライブ必須（Workspace）
ドメイン全体委任(DWD)不要共有ドライブ直書きなら不要（Google は DWD 回避を推奨）
審査テナント毎の同意。drive.file で軽減自社ドメイン内完結で外部審査の影響小
最大の落とし穴：サービスアカウントはストレージ容量を持たずファイルを所有できない。ADR-021 のサービスアカウントを書き込みに転用すると My Drive 直書きは 403（quota exceeded）になる → Workspace の共有ドライブへ書き込む構成が正解。

主要 API・推奨ライブラリ

  • アップロード：POST /upload/drive/v3/files（uploadType=resumable 推奨）。Python は MediaFileUpload(..., resumable=True) を files().create() に渡す。
  • フォルダ作成：files.create で mimeType=application/vnd.google-apps.folder。
  • 共有：permissions.create（type=user/anyone, role=reader 等）→ files.get の webViewLink を取得。
  • 一覧/検索：files.list（q クエリ）。
  • 推奨ライブラリ：google-api-python-client + google-auth(-oauthlib)（FastAPI 向け公式推奨。既に Calendar 連携で導入済み）。

本番公開・審査要件

  • drive.file のみ採用 → 最も軽い。制限付きスコープ審査も CASA も不要（公開時の「未確認アプリ」警告除去にブランド検証は推奨）。
  • drive（フル）等の制限付き（Restricted）スコープ採用時は OAuth App Verification ＋ CASA セキュリティ評価（LOA 承認日から 12 か月毎の再評価）が必要。
  • サービスアカウント方式（パターン B）は自社ドメイン内完結のため、これら外部審査を大きく回避できる。

料金・制限・最新の変更点

  • 2026 年内に「クォータ超過分の課金」導入予定（90 日前告知）。2026-05-01 以降の新規プロジェクトは新クォータ体系。
  • 書き込みレート 3 req/秒/アカウント上限（引き上げ不可） → 帳票一括出力はキューイング＋指数バックオフ必須。
  • Workspace アップロードは 750 GB/日、最大ファイル 5 TB。
  • drive.file 移行を Google が公式推奨。UI 用語が刷新（旧「OAuth consent screen」→「Google Auth platform」）。

公式リファレンス

  • Choose Drive API scopes（2026-04-20）— developers.google.com/workspace/drive/api/guides/api-specific-auth
  • Upload file data（2026-04-20）— …/guides/manage-uploads
  • Usage limits（2026-05-01）— …/guides/limits
  • Manage sharing（2026-05-07）— …/guides/manage-sharing
  • Restricted scope verification / CASA（2026-05-26）— …/restricted-scope-verification
  • Server-to-Server（サービスアカウント/DWD, 2026-03-23）— …/oauth2/service-account

5. FedEx

用途

導入難易度 中 ★★
機能使う API用途
送料見積Rates and Transit Times（/rate/v1/rates/quotes）日本→海外の送料・所要日数を見積に反映
ラベル発行Ship（/ship/v1/shipments）国際 Air Waybill ＋税関書類（Commercial Invoice 等）生成
追跡Track（/track/v1/trackingnumbers）配送ステータス表示（最大 30 件/req）
集荷Pickup（/pickup/v1/pickups）集荷依頼の作成

前提・登録手順

  • FedEx アカウント番号（9 桁・法人配送契約）が必須。Ship はアカウントに紐づく。
  • Developer Portal でユーザー登録（無料）→ Organization 作成 → shipping/billing account 登録 → Project 作成（利用 API を選択）→ Test 用 Client ID / Secret 発行。
  • 事業者タイプ：自社運用＝FedEx Shipper。テナントごとに別アカウントを持たせる SaaS 提供形態なら Integrator Provider＋csp_credentials（child_key/secret）を検討。

認証方式

  • OAuth 2.0。POST /oauth/token（grant_type=client_credentials）で access_token 取得。有効期限 60 分。
  • 各 API は Authorization: Bearer <token>。
  • 注意 トークン生成は IP 単位で厳しいスロットル（超過で 403 を 10 分）。token を ~55 分キャッシュ必須。
  • Base URL：Sandbox apis-sandbox.fedex.com / Production apis.fedex.com。

テスト / 本番移行・認証（Certification）

  • Test key は Project 作成時に自動発行（テスト用 shipping account 付き）。
  • Certification 不要：Rate / Track など → Production 移行のみで本番キー利用可。
  • Basic Certification 必要：Pickup, Address Validation など（サポートへ連絡し本番キー有効化）。
  • Shipping Label Certification 必要：Ship API（ラベル発行）はこの認証が必須。Label Cover Sheet 提出 → サンプルラベルを 600 DPI 以上でスキャン提出 → Bar Code Analysis Group が約 3 営業日で評価 → 承認後に本番有効化。

料金・制限・最新の変更点

  • コア API（Rate/Ship/Track/Pickup）は無料（配送実費は別）。レート制限 1,400 tx / 10 秒 / Project、超過で 429。
  • 締切 旧 SOAP（Web Services）は廃止進行中。一般顧客は 2026-06-01 までに REST へ移行必須（新規実装は最初から REST なので影響なし）。
  • 国際発送は税関書類・HS code・IATA 規制対応が Ship リクエストに必要。

公式リファレンス（参照 2026-06-05）

  • Getting Started — developer.fedex.com/api/en-us/get-started.html
  • API Authorization (OAuth) — …/catalog/authorization/docs.html
  • Rate / Ship / Track — rate ・ ship ・ track
  • API Certification — …/project/certification.html
  • SOAP→REST 移行（締切 2026-06-01）— Migrate Act Now

前提・登録手順

  • 有効な DHL Express 法人アカウント（アカウント番号付き）が必須。未契約なら口座開設フォーム → DHL コンサルタント対応 → 資格情報発行。

  • アカウント番号は Developer Portal の ID や API キーとは別物（DHL の請求書に記載）。桁数は公式に明記なし → DHL Express 担当に要確認。

認証方式

  • MyDHL API（DHL Express）は Basic 認証（API Key / Secret を Base64 して Authorization ヘッダにプリエンプティブ送信）。
  • Shipment Tracking - Unified は DHL-API-Key ヘッダ方式。
  • DHL 全社では Basic → OAuth 2.0 へ段階移行中だが、MyDHL API は現状 Basic。認証層は抽象化しておくと将来移行に強い。

テスト / 本番・最新の変更点

  • テスト：https://express.api.dhl.com/mydhlapi/test（1 日 500 回上限）→ 本番：…/mydhlapi。
  • 本番キー（API Productive Key）は DHL の資格検証成功を条件に発行（純粋なセルフサーブ自動発行ではない）。
  • MyDHL API REST 版は v3.3.0（2026-05-31 公開）。新規実装は REST 採用（SOAP/XML はレガシー）。
  • API 自体の従量課金の明示はなく、発送実費は DHL Express 契約料率（Rating が自社口座料率を返す）。

8. ヤマト運輸（クロネコヤマト）

用途

導入難易度 高 ★★★
一般公開のセルフサーブ REST API は乏しく、すべて法人（掛売り）契約＋ヤマトビジネスメンバーズ（YBM）登録＋商談（営業窓口）経由が前提。即時 API キー発行型ではない。

前提・契約要件

  • 法人（掛売り＝請求書払い）契約が必須。対象は法人/各種団体/個人事業主。
  • YBM への登録が必須（登録・利用は無料）。B2クラウド・各種 API は YBM 内サービス。
  • API 利用は別途「契約」が必要（「開発環境のみの利用は不可」）。

連携手順（最新）

  1. 掛売り（法人）契約 → 審査。
  2. 仮パスワード発行 → YBM 本登録 → サービス追加。
  3. 「YBM For Developers」から仕様書 DL（要 YBM ログイン）。B2クラウドAPI は簡易版仕様書を公開ページからも DL 可。

10. 横断的な実装メモ

  • キャリアアダプタ層（ADR-021）：eLogi と同列に各社実装を差し替え可能な抽象インターフェイス（見積/ラベル/追跡/集荷）を定義し、その配下に各社アダプタを実装。
  • OAuth トークン管理：FedEx（60 分）・UPS（実効 1 時間）は token を必ずキャッシュ（毎リクエスト発行は IP スロットルで 403）。期限の数分前に先回りリフレッシュ＋401 時フォールバック。
  • 環境切替：各社 sandbox / production を環境変数で切替。API バージョン文字列（UPS の v24xx 等）・アカウント番号も設定値化。
  • 送料計算：国際 3 社は Rate API で取得可。国内 2 社（ヤマト・佐川）は送料計算 API が公式に確認できず → 運賃表をアプリ側に保持して算出（ADR-095/101/103 の「キャリア別数式は後日」と接続）。
  • 帳票・ラベル保存：Google Drive（サービスアカウント＋共有ドライブ）を Phase 0 で先行整備すると、各社ラベル PDF/CSV の保存先が確定し ADR-021 Q7 を解消できる。
  • 国内 2 社のリードタイム：契約＋商談＋約 3 か月（ヤマト）／申込承認 1〜2 週間（佐川 送り状発行API）。営業窓口への着手は早めに。まずは CSV 連携で価値を出す。
不確実点（実装着手前に各社へ要確認）：
  • DHL アカウント番号の桁数（公式に明記なし）。各社 API の従量課金有無・レート上限の正確値。
  • ヤマト「配送連携API」の用途制約（事業者→顧客発送の可否）と B2クラウドAPI の認証方式。
  • 佐川 送り状発行API / ヤマト各 API の認証方式（契約後の仕様書で開示）。
  • マルチテナント時の各社アカウント構成（自社 1 アカウント集約 か テナント別か）。FedEx は Integrator Provider モデルの要否。
