# 標準ワークフロー（STANDARD-WORKFLOW）— 正本

> これは開発の標準手順の**唯一の正本**。全環境（web / terminal / Codex）はこの1冊を指す。
> 変更は **PR＋PO承認** のみ。決定の理由は ADR（`docs/adr/`）を参照。

---

## 0. 目的と原則
- **目的**：どの環境発でも、同じ手順で・**本物の成果物が揃ってから**実行に入る状態を保つ。
- **優先順位**：**品質 > コスト > 速度 > 自律性**。
- **大原則**：
  - **準備9割**（着手前の設計・現状把握に資源を厚く置く）。
  - **誰がやっても同じ結果**になる粒度で成果物を作る。
  - **不明ゼロ・推測ゼロが実行の条件**（不明が残るうちは実行に進まない）。

---

## 1. 標準フロー（毎回・例外なし）
実装の起動トリガーは**設計のハンドオフ**。ADRのpushでは発火しない。確実性は**検証ゲート**が担保する。

| Phase | 担当 | 内容 |
|---|---|---|
| **1 KGI設定** | Planner＋PO | 何を実現するかを**定量のKGI**で定義。**PO承認が必須ゲート** |
| **1.5 設計仕様書（あるべき姿）の確認・作成** | Planner＋PO | 対象開発では、該当する**設計仕様書（あるべき姿）を正本として先に読む**。無ければここで**作成**し、無いまま recon へ進まない。現状が理想と食い違う場合は現状に寄せず**理想形へ近づける**方向で設計する。対象/免除の線引きと索引は直下「§1.5」を参照 |
| **2 現在地把握（recon）** | architect | 実コードを **file:line で突合**し事実を出す。**推測禁止**。**着手前に必ず既存 ADR を検索**（機能キーワードで `git grep -i "<keyword>" docs/adr/` ＋ [`docs/adr/FEATURE-INDEX.md`](adr/FEATURE-INDEX.md) を引く。ADR は自動ロードされない＝指さないと見落とす）。証拠は `docs/handoff/<仕事名>/recon.md` |
| **3 実現方法の設計** | Planner | **(a)** 外部・過去事例から学び**我々への応用**を検討（深さは規模/新規性/リスクに**比例**。小規模は「該当なし＋理由」でよいが**検討自体は省略不可**）。**(b)** 技術How・KPI・弊害/トレードオフ・計画票・継続を**高粒度**で。各受け入れ基準に**検証方法を紐づける** |
| **4 実装** | Generator | レビュー済み設計から実装・PR作成。フロント視覚＝参照に厳密一致 |
| **5 検証ゲート** | Reviewer＋Evaluator | コード＋UI差分（Playwright）＋テスト/CI。二者APPROVE＋全必須チェック通過で develop マージ |

### 1.5 設計仕様書（あるべき姿）の正本ルール

設計仕様書（あるべき姿）＝その領域の理想形を定義した文書。一覧（索引）は [`docs/specs/README.md`](specs/README.md)（例：商品マスタ＝`docs/specs/product-master/README.md`）。

- **先に読む／無ければ作る**：対象開発では、KGI設定の直後・recon の前に該当仕様書を最初に読み、recon・設計をその理想形に沿って進める。該当仕様書が無い場合は recon へ進む前に作成する（無いまま先へ進まない）。
- **理想優先**：現状が理想形と食い違っても、現状に合わせず理想形へ近づける方向で設計する。
- **対象（仕様書が必須）**：危ない変更（`migrations/`・`deploy.yml`・本番 `scripts/`）を含む開発／索引に載る領域に触れる開発／新しいデータ構造・マスタ・新機能を作る開発。
- **対象外（従来どおり）**：§5 の免除に当たるもの（純粋な書類・メタデータ、バグ修正・CI修復・リファクタ等の自律クラフト）。
- **リンク必須**：recon.md・design.md・PR本文に、参照（または新規作成）した設計仕様書へのリンクを必ず載せる。

---

## 1.6 文書の親子リンクと素人向け説明（親子構造ルール）

すべての設計仕様書（親）と、その recon.md / design.md（子）は、次を満たす。

- 子→親: 各子文書の冒頭に、親（仕様書）への相対リンクを1本置く。
- 親→子: 親文書に、ぶら下がる子文書の一覧リンクを置く（双方向リンク）。
- 素人向け1行説明: 各文書の冒頭に、専門用語を使わず「この文書は何か」を1行で書く。

具体例（型見本）: docs/specs/doc-parent-child/ および docs/handoff/doc-parent-child/ を参照。

本ルールは文章規約（お作法）であり、関所による機械強制ではない。強制化する場合は別途 recon→設計→GO を経る。

## 1.7 維持の仕組み欄（全designに必須・空欄不可）

すべての design.md は、末尾に「## 維持の仕組み」欄を必ず置く。空欄不可。

- 守り手: <関所ファイルの相対パス>（例: .github/workflows/migration-guard.yml）
- 対象: この設計の何が壊れると困るか
- 関所なしの場合: 「人手で守る」＋理由を明記（空欄不可）

本欄は関所（process-artifacts gate）が機械検査する。検査は「欄と守り手の非空」「守り手パスの実在」のみ（初期は警告、安定後に停止へ引き上げ。PR番号2600未満は猶予）。中身の適切性（その守り手で本当に守れるか）は人のレビューで確認する。

### 1.7 開発記録の3段階振り分け（着手前の門番判定）

すべての開発は、着手する者（設計パートナー・実装役を含む）が着手前に、索引 [`docs/specs/README.md`](specs/README.md) で当該領域の既存仕様書を確認し、次の3区分のいずれかを判定してから進める。

| 区分 | 判定基準 | 必要な記録（成果物） |
|---|---|---|
| 新規テーマ | 索引に類似のあるべき姿が無い、新しい領域・データ構造・機能 | フルセット一式（§1.5の設計仕様書＋recon・design等の子文書一式） |
| 既存の延長・修正 | 索引に載る既存テーマの範囲内の変更 | 新規作成せず、既存テーマの子ども履歴・進捗表に追記 |
| 軽微（1行修正等） | 設計判断を伴わないごく小さな変更 | 台帳1行＋PRのみ |

一律フルセットは形骸化するため採らない。区分の判定に迷う場合は不明点プロトコル（§3）に従いPOに確認する。区分ごとの必要物の詳細な物差しは `docs/specs/design-partner-loop/README.md` の「KGI-3 段階別チェックリスト」を参照（節番号でなく名称で辿る）。

## 2. 成果物の完了定義（"在るだけ"を認めない）
**成果物＝KGI達成に資するもの。** 在るだけ・中身が空のものは成果物と認めない。各成果物は以下を満たして初めて「揃った」とする。
- **KGI**：定量・PO承認済み。
- **recon証拠**：実コードへの **file:line 引用**を含み、その引用先が**実在する**こと。**既存 ADR 検索の結果**（該当 ADR 名、または「grep 済み・該当なし」）を明記すること。保存先 `docs/handoff/<仕事名>/recon.md`。
- **Phase 3 設計**：各受け入れ基準に**検証方法（テスト/ゲート/Evaluator）のリンク**があること。設計→recon→ADR が**相互参照**していること。**「外部・過去事例の参照と我々への応用」欄が記入済み**であること（小規模は「該当なし＋理由」可。**空欄は不可**）。

## 完了の定義

タスクが「完了」と認められるのは、次の4つがすべて揃った状態に限る。

1. 変更が PR として本番ブランチ（develop 経由で main）にマージされている。
2. その PR で、必要な自動チェック（自動テスト・該当する外部APIスモーク・process-artifacts gate）がすべて緑だった。
3. 危険な変更（migrations/・deploy.yml・本番 scripts 等）を含む場合、GO 記録がある。
4. 人が実際に動作確認を行い、不具合がないと判断している。確認内容（何を・どう確認し、問題がなかったか）を docs/ai-agents/evidence-registry.md に記録している。

- **ユーザーに影響する変更**（現状の実体: `frontend/src/` / `backend/app/routers/` / `backend/app/services/` / `backend/app/auth/` / `backend/app/tasks/` / `backend/app/discord_gateway/` / **PR-C の外部API検出で見つかる変更**）は、**本番に出す前に Shingo の GO 記録が必須**。現行フローでは、まず feature PR で GO を満たして develop に入れ、その後 release PR で main へ昇格する。
- **人の動作確認の当面の確認環境**は本番のみ。確認は tenant_006（QA）または tenant_001（空テスト）で行い、tenant_004（HIGH LIFE JPN 実データ）には絶対に触れない。ローンチ後は別サーバーの dev 環境で事前確認に移行する。

次は完了と認めない。
- 自己申告のみ（「できました」の宣言だけ）。
- モック（にせもの）テストが緑なだけで、実動作・人の確認がない。

tasks/todo.md・.claude-pipeline/active-work.md の「完了（DONE）」移動は、上記4つを満たした事実の記録である。実証がないまま完了へ移してはならない。

## KGI/KPI 粒度基準
- KGIはPOが画面・出力で○×を一義に判定できる粒度で書く。
  抽象語（統一/改善/正常/復帰）禁止→観測可能な事象に分解。
- KGI達成の道のりをKPIに分解し、各KPIを数値で測る。
- KPIもKGIと同粒度で設計。
- PO不満=KGI/KPI粒度が粗い／実装不備=設計粒度が粗い→ともにPlanner責任。

## 役割と粒度
- Generatorは単純作業のみ。判断の余地を残さない。
- Plannerは file:line＋変更前後コード＋触らない範囲＋○×基準まで設計する。
- Generatorの実装ミス = Plannerが余地を残した設計責任。

## 3. 不明点プロトコル
1. 推測で埋めない。
2. 取得手段を尽くす（実機・origin・file:line）。
3. それでも残れば「**不明**」と明示し、**POに相談**（判断を仰ぐ／提案は歓迎）。
4. **不明を残したまま実行しない。**

---

## 4. やり方の違い（準備はどちらも必須）
**どこで・誰がやっても、§1の標準フロー（KGI→recon→設計）と §2の完了定義は必ず満たす。** 実装役（Generator）が How をその場で自己流に決めることは**不可**。準備を省けるのは §5の免除（自律クラフト）に限る。
- **terminal**：1つの Claude Code セッションが設計〜実装まで通すことがある。役割が1人に集まるだけで、**KGI/recon/設計の成果物は必ず作る**。
- **handoff**：Planner（web/Shingo）が設計を別の Generator に渡す。Generator は忠実実装する。
- ※旧 `ADR-012`／`ADR-113` の「Generator が How を自律設計／ADR は What/Why のみ」とする部分は、**本SOPが上書きする**（準備を飛ばす運用は廃止）。

## 5. 免除と特例（標準フロー不要・または軽量/緊急）
**黙って素通り（自動スキップ）は、純粋な書類・メタデータのみ**（変更ファイルのパスで判定。リストに無いものは"要検査"側に倒す＝安全側既定）。それ以外（実コードに触れる変更）は、本検査か下記の特例による。

- **低リスクのコード**：自己申告の**自律クラフト**（バグ修正・CI修復・リファクタ）で軽量化可。**記録必須・無申告の素通り不可・governance監査**。
- **危ない変更**（DBマイグレーション・`deploy.yml`・本番スクリプト）：**自己申告は不可**。特例は**認可された人間の承認**でのみ開く。
  - **些細**：承認 → 軽い扱い（記録）。
  - **緊急**：承認 → 先行マージ＋**宿題を期限内に後追い提出**（"宿題待ち"として記録、期限超過は自動警告・エスカレーション）。
  - **develop へのマージ＝本番投入可の宣言**（ADR-135）：`migrations/`・`deploy.yml`・本番 `scripts/` を含む実装は、PO の GO が出るまで feature ブランチで待機し develop にマージしない。develop は待合室ではなく出荷口。GO 待ちの作業は feature ブランチが待合室。

**承認役＝認可された人間（役割）。現状：PO（Shingo）＋ 開発パートナー。** 承認者は記録される。承認役の増減は PR＋承認で管理（属人化させない）。

**GO 記録の軽量ルール（2026-06-12 確定）**: Shingo が GO を出した時点で、そのPRに `GO: Shingo YYYY-MM-DD` のコメントを残す。どのセッションから見ても承認の所在が一目で分かるようにする。別セッションで承認した場合は design.md または handoff に同形式で事後記録する。

※パスの具体リスト（書類側／危ない側）と検査の実装は KPI2 設計に置く。

## 6. 関所（ゲート）＝ 確実性の所在
すべての出口（develop へのマージ）に**1つの必須ゲート**を置く。揃わない／本物でない／不明が残るものは通さない。
- **検査**：成果物が揃い・本物（§2）・不明ゼロ（§3）・ADR参照あり、または**免除宣言**あり。
- 全環境の出口はこの1つ＝**環境非依存でカバー**。

---

## 7. 全環境への適用
- **正本はこのファイル1つ。** 各入口はコピーせず、ここを**指す／同期する**。
  - **ターミナル**：`CLAUDE.md`（自動ロード）に要約＋このファイルへのリンク。
  - **web**：プロジェクト指示に要約＋場所、GitHub Sync でこのファイルを取り込む。
  - **Codex**：このファイルを参照（稼働時に配線）。
- **属人的な独自変更は禁止。** 変更は次項の手順のみ。

## 8. 変更・継続
- このファイルの変更は **PR＋PO承認** のみ（バージョン管理）。
- ゲートの除去・弱体化は**不可逆操作扱い＝PO確認必須**（勝手に外せない）。
