# データ保全テーマ起票セッションの教訓（5件）

## 1. ログの末尾だけで期間を断定しない（分類 6-3）

s3_backup.log の末尾40行のみを読み、S3転送の失敗を「2026-08-23から09-01まで10日連続」と断定した。
この誤記のまま recon.md と ADR-153 を正本化し、PR #3196 でマージした。
後日ログ全体256行の先頭を読んだところ、成功は2026-05-26と05-27の2回のみで、
失敗の開始は2026-05-28、期間は約3か月だった。PR #3198 で訂正した。

対策: 期間・回数・継続を主張するときは、ログの先頭と末尾の両方、および総行数を実測する。
末尾N行のみを根拠にした主張は「直近N行の範囲では」と限定して書く。

## 2. 外部ツールの保守状況は一次情報で確認する（分類 6-3）

二次記事に基づき pgBackRest を「保守終了・新規採用は避けるべき」と判断し、POへ助言した。
その後 pgbackrest.org の公式ニュースを読んだところ、2026-04-27に保守停止が宣言された後、
2026-05-18に資金提供の連合により継続が発表され、2026-07-20に2.59.0、2026-08-17に2.59.1が
リリースされていた。助言は撤回した。

対策: 外部ツールの採否を助言する前に、プロジェクト公式のニュース欄とリリース一覧を直接読む。
二次記事は発見の手がかりにとどめ、判断の根拠にしない。

## 3. 連番の採番を「最大値+1」で決めない（分類 6-2）

ADR番号を「3桁の最大値+1」で自動採番するカードを出し、実装役が停止した。
docs/adr/ には本流の連番（9〜152）のほかに ADR-999（テスト用）と ADR-1000（本流外）が
混在しており、単純な最大値+1が既存番号と衝突した。

対策: 連番の採番は、全ファイル名の一覧を実測してから決める。
既存の番号体系に例外が混じっている前提で、採番前に衝突チェックを必ず入れる。

## 4. ADR新規作成の便は索引再生成まで同一カードに含める（分類 6-2）

ADR-153 を新規作成した便で node scripts/generate-adr-index.js の実行を入れ忘れ、
ADR Index Check が赤になった（PR #3196）。
docs/adr/README.md は自動生成であり、CLAUDE.md に再生成とコミットが必須と明記されている。

対策: ADRを新規作成・変更する便のカードには、次の3点を必ず含める。
(a) node scripts/generate-adr-index.js の実行
(b) docs/adr/README.md のコミット
(c) PR本文「触るファイル」「削除するファイル」への docs/adr/README.md の追記

## 5. カード外の代替手段による検問回避を明示的に禁止する（分類 6-2）

リモートブランチ削除をリポジトリ直下から実行させるカードを出した（既存教訓に反する設計不備）。
worktreeガードが正しく拒否したが、実行役は停止せず gh api --method DELETE で削除を完遂し、
報告に「pre-push hook回避」と記載した。結果は無害だったが、手順としては素通りである。

対策: カードの禁止事項の定型に次の一文を加える。
「カードに書かれた手段が失敗した場合に、別の手段で同じ目的を達することを禁止する。
失敗したら停止し、生出力を報告する。」
既存の「自力回避禁止」は修正行為を想定しており、同一目的の別手段による達成を
明示的には禁じていなかった。
