# design:受注管理(業務画面)— ページの見せ方

> この文書は何か(素人向け1行説明):受注管理ページの骨格(サイドメニュー・一覧・次の操作の導線)をどう見せるかを、図3枚と文章で定めた設計書です。

親(あるべき姿+KGI)へのリンク: [README.md](./README.md)

## 1. スコープ
本designは親スコープ=「ページの見せ方」のみを定める。各ステータスページの機能面と見た目の詳細は子文書が定義する(README「親子の分担」参照)。

## 2. recon(現状把握)
PO指示(2026-07-04発話「理想の設計は現状を考慮せずに作成する」)により、現行UIとの突合は本designでは行わない。現状UIとの差分把握は実装便のreconで実施する(実装前の必須工程)。

## 3. 設計判断(7点・PO承認済み 2026-07-04)
1. ステータスは左サイドメニュー常設(上部タブは用いない)。各項目に滞留件数バッジを表示する。
2. サイドメニュー先頭に「すべて」横断ビューを置く。すべては子を持たず親の骨格のみで完結する(各Orderの所属はちょうど1つのまま。すべては閲覧窓であり二重所属ではない)。
3. 検索(注文番号・顧客名)と並び替えを、一覧上部の共通骨格として全ステータスページに置く。
4. 一覧の共通6列(注文/顧客/金額/支払期日/ステータス/次の操作)を親が固定する。子は列を追加できるが、この6列は削らない。
5. 「次に行う操作」への入口は2箇所:ページ上部のガイド領域と、各行の「次の操作」ボタン。押した後の画面・文言・機能は子が定義する。
6. ステータスバッジを全行に常時表示する(K3)。
7. 操作完了でステータスが自動で置き換わり、Orderは次のステータスページへ移動する(K1・置き換わりモデル)。

## 5. 弊害・トレードオフ(空欄不可)
1. サイドメニュー常設は横幅を消費し、一覧の列が窮屈になる。モバイル幅ではメニューを畳む必要がある(§7設計送り1)。
2. 「すべて」を置くことで、親が骨格を持つビューは7+1=8つに増える。
3. 共通6列の固定は、子が一覧以外の形式(例:カード並び)を採る自由を制限する。必要になったら親の改定PRで対応する。
4. design収納(本便)と実装の間に時間差がある。実装前に現状UIとのrecon突合が必須。

## 6. 外部・過去事例
ステータス別ビュー+滞留件数バッジ+行内アクションは、一般的なEC・受注管理画面で広く使われる定石であり、操作の学習コストを下げる。特定製品の画面模倣はしない。

## 7. 設計送り事項
1. モバイル幅でのサイドメニュー表示方法(畳み方)。
2. 「商品到着」を取引完了と扱うかの確定(kgi.md 設計送り2)。
3. トラブル/キャンセル解消時の復帰先ステータス(kgi.md 設計送り3)。
4. 売上・古物商対応の用語定義の恒久的な置き場(kgi.md 設計送り1)。

## 8. 受入基準(検証方法つき)
kgi.md の K1〜K8 を受入基準とする。K1〜K4・K6は実装後に画面確認・SQLで、K5・K7・K8は文書grepで○×判定する(各KGIの「測り方」欄を検証方法とする)。
