受信箱の顧客カルテから帳票・フォームを送る操作の、あるべき画面と挙動（To-Be）をまとめた設計。

## 2. To-Be設計（図）

- leadの3段階と段階別ボタン: ./to-be/lead-stages.svg
- 入口プルダウン（カルテ下ボタンから出し分け）: ./to-be/entry-pulldown.svg
- 作成系フロー（発行から確認ページ承認で送信）: ./to-be/create-flow.svg
- フォーム系フロー（英語テンプレと和訳の確認から送信・記録）: ./to-be/form-flow.svg
- アサインパネル（暫定・sales-management送り）: ./to-be/assign-panel.svg

挙動の要点:
- カルテ下に「請求書・フォームを送る」ボタン1つ。leadの3段階で出せる項目を出し分ける。項目はタップした瞬間にその挙動が始まる。
- 作成系（見積・請求書）は既存の作成ページ（quote-invoice）へ渡し、発行すると確認ページが開き、承認して初めて相手に送られ、会話に送信済みとして並ぶ。
- フォーム系は英語テンプレ本文とフォームのリンクを送る。送信者には和訳を並べて表示。送信前に軽い確認を1行挟む。送付はテナント・担当者・相手を紐付けて記録し、会話に通常メッセージとして並べて記録する。
- アサイン確定はロール付きスタッフから営業担当を選んで確定し、割り当て・DB記録・商談中への切替・（連携時のみ）Discord通知を行う。効果の説明文はUIに出さない。

## 3. 弊害・トレードオフ（空欄不可）

- 確認ページ・軽い確認を挟むぶん送信に1手増える（誤送防止と引き換え）。
- 作成系は作成ページへ画面遷移するため受信箱から一時離れる（戻り導線で緩和）。
- 3段階の出し分けは商談ステージ（CRM）のデータに依存する。そのデータが無いと機能しない（接点を sales-management に設計送り）。
- 英語デフォルトと和訳表示は翻訳テーマの仕組みに依存する（未整備なら和訳が出ない）。

## 4. 外部・過去事例

該当なし＋理由: 社内ツールの送付導線であり、既存テーマ（quote-invoice 等）への接続が主。外部事例より自社の既存正本との整合を優先する。

## 5. 受入基準（各基準に検証方法を紐づけ）

kgi.md の KGI 1-7 に紐づく。各項目の測り方・合格ラインは kgi.md に記載（画面でのマルバツ確認、記録の非空確認）。実装フェーズで各基準に検証方法（テスト / ゲート）を design 差分で紐づける。

## 維持の仕組み

守り手: 人手で守る
対象: 3段階の出し分け・送付記録の非空・参照境界（中身作りや入金確認を新規実装しないこと）が壊れると困る。
関所なしの場合の理由: 本文書は実装前の仕様書。実装時に、出し分けはフロントのテスト、記録の非空はバックエンドの制約・テストで守る設計を recon 差分で定める。索引の維持は docs/specs/README.md 登録済み。
