# WhatsApp — 操作感（動き・速さ・画面のつながり）

> この文書は何か（専門用語なしの1行）: 押したときに何が起きるか、どれくらいの速さで起きるかを数字にした記録。見た目ではなく「使った感じ」の記録。

親: [README.md](README.md) / 見た目の寸法: [whatsapp-reproduction-spec.md](whatsapp-reproduction-spec.md)

- 記録日: 2026-10-11 / 端末: 1080x2340px・密度480dpi
- 録画は使っていない（この端末に動画を解析する道具が無いため）。代わりに**Androidが持つ描画フレームの記録**（`dumpsys gfxinfo <アプリ> framestats`）と**端末内で計った経過時間**を使った。

## 取得に使ったコマンド

```bash
# 画面の書き換え速度と、操作中の全フレームの時刻
adb shell dumpsys gfxinfo com.whatsapp reset   # 記録をリセット
adb shell input tap <x> <y>                    # 操作を1回だけ行う
adb shell dumpsys gfxinfo com.whatsapp framestats

# アプリを開くまでの時間（Android標準の計測）
adb shell am start -W -n com.whatsapp/.Main

# タップから目的の画面が出るまでの時間（端末内で計測。adb往復の影響を受けない）
adb shell 'T0=$(date +%s%N); input tap <x> <y>; while :; do \
  case "$(dumpsys window | grep -m1 mCurrentFocus)" in *Conversation*) \
  echo $(( ($(date +%s%N)-T0)/1000000 )); break;; esac; done'
```

`framestats` の列は `IntendedVsync`（描き始める予定の時刻）と `FrameCompleted`（描き終わった時刻）を使い、ナノ秒からミリ秒に換算した。50ms以上の間隔が空いたところで区切り、連続して描いている区間を「ひとまとまりの動き」として数えた。

## 1. 画面の書き換え速度

| 項目 | 実測 |
|---|---|
| フレーム間隔 | **8.33 ms** → **120 Hz の画面** |
| 1フレームの処理時間 | 中央値 **3.3 ms** / 平均 4.1 ms / 最大 36.3 ms |
| 8.33ms を超えたフレーム | 7 / 113 件 |

**要点**: 1フレームあたりの予算は8.33msで、WhatsApp は中央値3.3msで描いている（予算の4割）。余裕を持って作られている。

## 2. 操作ごとの速さ

| 操作 | 連続して描いたフレーム数 | かかった時間 |
|---|---|---|
| アプリを開く | — | **54 ms**（`am start -W` の WaitTime） |
| 一覧の行をタップ → 会話の画面が出る | — | **98 ms**（端末内で計測） |
| 会話を開く動き（描画が落ち着くまで） | 108 | **586 ms** |
| **戻る（会話 → 一覧）** | 10 | **85 ms** |
| タブ切替（チャット → コミュニティ） | 76 | **628 ms** |
| タブ切替（コミュニティ → チャット） | 76 | **628 ms** |

**要点1**: **戻るが圧倒的に速い**（85ms）。開くとき（586ms）の7分の1。戻る操作には動きをほとんど付けず、即座に前の画面を出している。

**要点2**: タブ切替は**両方向で76フレーム・628msが完全に一致**した。偶然ではなく、決まった長さの動きが設定されている。

**注意**: 「連続して描いた区間」は**動きそのものと中身の読み込みの両方**を含む。動きだけの長さは次の節で分離した。

## 2-2. 動きの向きと加減速の曲線（録画をフレームに分解して測定）

`adb shell screenrecord` で遷移を録画し、`ffmpeg` でフレームに分解して、各フレームが最終画面に対して**どれだけ横にずれているか**を相関で求めた（設定変更は行っていない）。

```bash
adb shell screenrecord --time-limit 6 --bit-rate 8M /sdcard/mo.mp4   # 録画しながら操作
adb pull /sdcard/mo.mp4 && adb shell rm /sdcard/mo.mp4
ffmpeg -i mo.mp4 -vf scale=270:-1 -vsync 0 frames/f%04d.png          # フレームに分解
ffprobe -select_streams v:0 -show_entries frame=pts_time -of csv=p=0 mo.mp4  # 各フレームの時刻
```

録画は 1080x2340 / 108フレーム（画面が変わったときだけ記録されるため、6秒で108枚）。

### 会話一覧 → 会話の画面

| タップからの経過 | 新しい画面の横ずれ | 完成度 |
|---|---|---|
| 0〜157 ms | （まだ現れない） | 0% |
| 200 ms | 132 dp | 16% |
| 241 ms | 76 dp | 30% |
| 283 ms | 48 dp | 43% |
| 324 ms | 28 dp | 52% |
| 366 ms | 16 dp | 61% |
| 407 ms | 8 dp | 67% |
| 450 ms | 4 dp | 76% |
| 491 ms | **0 dp（着地）** | 94% |

**確定した3つの事実**

1. **最初の約150msは画面が動かない。** タップした行の反応（波紋）だけが出て、その間に画面遷移は始まっていない。変化した画素の範囲も行の内側に限られていた（境界 x=9〜261、全幅ではない）。150ms を過ぎると全幅（x=0〜269）が変わり始める。
2. **新しい画面は右から左へスライドして入る。** 横ずれが 132 → 76 → 48 → 28 → 16 → 8 → 4 → 0 dp と減っていく。**各段階でずれがほぼ半分**になる＝強い減速（指数的に減衰する ease-out）。縦のずれは全区間3px以内（＝上下の動きは無い）。
3. **フェードは併用していない。** 画面全体の明るさの比は全区間 1.00〜1.02 で一定。透明度を変える動きではなく、純粋な平行移動。

**再現するときの値**: タップから約150ms は押した行の反応のみ。その後、新しい画面を画面幅の分だけ右にずらした位置から 0 へ、**約300〜330ms かけて強い ease-out で**動かす。上下の動きとフェードは付けない。

完成度が100%に届くのは3.6秒後だが、これは中身（相手の情報カードなど）の読み込みが続いているためで、動き自体は491msで終わっている。

## 2-3. スクロールの手触り（PO許可 2026-10-11）

操作: `adb shell input swipe 540 1600 540 700 80`（勢いよく上へ払う）。録画をフレーム分解し、前のフレームからの縦移動を相関で求めた。

| 観測 | 値 |
|---|---|
| 1フレームの移動量 | 80〜92px = **27〜31dp**（フレーム間隔8.3ms） |
| 速さ | 約 **3,400 dp/秒** |
| 指を離した後も動き続けた時間 | 払う操作は80ms、動きは **213ms** 続いた＝**フリング（慣性）がある** |
| 総移動量 | 2,324px = **775dp** |
| 停止 | 213ms から約25msで停止 |

**測れなかったこと（理由つき）**: **慣性の減速曲線は観測できなかった。** 速度が一定のまま急停止しており、これは自然な減速ではなく**リストの終端に到達したため**。この端末の会話は7件（スクロールできる量が775dp）しかなく、減速を観測できる長さがない。長い一覧（会話が数十件ある状態、または長い会話）でなければ測れない。

**終端の跳ね返り**: 停止後に縦位置の戻りは観測されなかった。Android 12 以降の端では「跳ね返り」ではなく**内容を伸ばす表現**を使うため、縦位置の相関では捉えられない。別の方法（端の画素の伸び量を測る）が必要。

## 2-4. キーボードが出たときのレイアウト変化（PO許可 2026-10-11）

操作: 入力欄をタップしてキーボードを表示（`mInputShown=true` で確認）。**文字は入力していない**（入力欄の中身は撮影後もプレースホルダ「メッセージ」のまま）。閉じるのは戻る。

| 部品 | キーボード前 | キーボード後 | 変化 |
|---|---|---|---|
| 会話の画面全体（`conversation_root_layout`） | 高さ 728dp | 高さ **431dp** | **縮む（−297dp）** |
| 本文エリア（`conversation_layout`） | 高さ 672dp | 高さ **375dp** | 縮む（−297dp） |
| 入力欄の帯（`footer`） | y=2128 / 高さ56dp | y=1236 / 高さ56dp | **297dp 上へ移動・高さは不変** |
| 入力枠・絵文字・添付・カメラ・送信 | — | — | すべて同じ量だけ上へ移動・大きさ不変 |
| メッセージの吹き出し | y=1573 | y=1108 | **155dp 上へ移動**（キーボードの高さより少ない） |
| 日付の区切り | あり | **消えた** | 縮んだ表示範囲の外に出た |

**キーボードの高さ = 892px = 297.3dp**

**再現のための3つの決まり**

1. **本文エリアを縮める。かぶせない。** キーボードの上に入力欄を浮かせるのではなく、画面の高さそのものを再計算している。
2. **入力欄はキーボードの上端に吸着**し、高さ（56dp）と中の部品の大きさは一切変わらない。
3. **一覧は下端に吸着したまま再配置**される。吹き出しが155dpしか動かなかったのは、エリアが縮んだ分だけ下端基準で詰め直されたため（キーボードの高さ297dpと同じだけ動くわけではない）。

## 3. タップ数と画面のつながり

| 今いる画面 | 操作 | 行き先 | タップ数 |
|---|---|---|---|
| 会話一覧 | 行をタップ | 会話の画面 | 1 |
| 会話一覧 | 行の**顔写真**をタップ | プロフィール写真（行とは別の当たり判定） | 1 |
| 会話一覧 | 下部ナビをタップ | 別のタブ | 1 |
| 会話一覧 | 右上の︙ | メニュー（6項目・入れ子なし） | 1 |
| 会話の画面 | 戻る | 会話一覧 | 1 |
| 会話の画面 | 上部バーの相手名をタップ | 連絡先情報 | 1 |
| 会話の画面 | 右上の︙ | メニュー（8項目・入れ子なし） | 1 |
| 会話の画面 | 吹き出しを長押し | 選択モード（上部バーが置き換わる） | 1（長押し） |
| 別の会話に移る | 戻る → 行をタップ | 会話の画面 | **2** |

**画面の深さは3段**（一覧 → 会話 → 連絡先情報）。メニューに入れ子（サブメニュー）は無い。

## 4. 当たり判定が入れ子になっている

会話一覧の行は、**押せる範囲の中にもう1つ押せる範囲がある**。

- 行全体（360x76dp）をタップ → 会話を開く
- その中の顔写真の列（72x68dp）をタップ → プロフィール写真

つまり「行はまるごと押せる」を守りながら、顔写真だけは別の行き先を持たせている。再現するときはこの入れ子を再現しないと操作感が変わる。

## 5. 状態の変化（観測できたもの）

| 変化 | 観測 |
|---|---|
| 未読 → 既読 | 会話を開く前は行に未読バッジ（20x20dp）があり、開いた後は**その部品が構造データから消えた**。行の高さは変わらない |
| 通常 → 選択モード | 長押しで**上部バーだけが置き換わる**。入力欄・吹き出し・下の余白はそのまま残る。画面遷移は起きない |
| 選択モード → 通常 | 戻るで解除。選択モードの部品（`action_mode_close_button`）が消えることで確認した |

## 6. 中身が無いときの画面（空の状態）

| 画面 | 空のときに出るもの |
|---|---|
| コミュニティのタブ | 絵（228x212dp）＋ 見出し ＋ 説明 ＋ 行動を促すボタン（312x48dp）＋ 「例を見る」リンク。部品は58個 |
| メッセージが0件の会話 | 相手の案内カード（`info` 286x78dp）と `contextCardLayout`（300x310dp）。**吹き出しは0個**で、長押しの対象も存在しない |

**要点**: 空のときに「何も無い」とは出さず、**絵・説明・次にやることのボタン**を必ず置いている。

## 7. アプリを開き直したときの挙動

`am start com.whatsapp/.Main` でアプリを前に出すと、**常にコミュニティのタブ**が選ばれた状態になる（`community_fragment` の有無で確認）。直前に見ていたタブを覚えていない。チャット一覧を出すには下部ナビを1回押す必要がある。

## 8. 割り込みの作法

会話の上部バーから連絡先情報へ進む途中で、**プライバシーのお知らせ**が下から被さって出た（`PrivacyDisclosureContainerActivity`）。

- 形: 下から出るシート。つかみ手（`wds_bottom_sheet_handle_view` 32x24dp）＋ 見出し ＋ 箇条書き3つ ＋ 脚注 ＋ 全幅のボタン（312x48dp）
- 作法: **目的の画面は裏で既に開いており**、お知らせを閉じるとそのまま目的の画面が現れた。目的地へ行く前に別画面へ飛ばすのではなく、**目的地の上に重ねている**

この OK ボタンは設定変更に当たる恐れがあるため押していない（戻るで閉じた）。

## 9. この文書で取れていない操作感

| 項目 | 理由 |
|---|---|
| 動きの向きと加減速（横スライドか・曲線か） | フレームの時刻は取れるが絵の変化は追えない。画面の動きを遅くする設定変更が必要で PO 許可待ち |
| 慣性の減速曲線 | §2-3 のとおり、会話が7件では終端に達してしまい観測できない。会話が数十件ある一覧が必要 |
| 端での「伸び」の量 | Android 12 以降の端の表現。縦位置の相関では捉えられず、端の画素の伸びを測る別の方法が必要 |
| 読み込み中の表示 | 観測できる場面を作れていない（1度だけ一覧が「読み込み中…」に戻る現象を段階1で観測済み） |
| エラー時の表示 | 意図的に失敗させる操作が禁止されているため取得不能 |
| 送信したときの反応 | 送信は §0-5 で禁止 |
