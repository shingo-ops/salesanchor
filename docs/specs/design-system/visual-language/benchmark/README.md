## PO 決定（2026-10-11）

この観察メモを salesanchor に写すときの扱いについて、PO から次の4点の判断を受領した。実装は段階3以降で行う。

| # | 決定 | 影響 |
|---|---|---|
| 1 | **Android の dp 値をそのまま CSS px として採用する**（76dp → 76px） | 既存の段に無い値（行の高さ76px・本文開始72px・行内上下余白15px）は**トークン追加の提案**として design.md に起案する（`design.md` §5 の手順） |
| 2 | **吹き出しは PC と スマホ で分ける** | PC は既存の `--radius-bubble-out/in`（20.8px・Messenger由来）を維持。スマホは本メモの実測（角丸約10dp＋左上に7dp張り出す尾）を使う。画面幅による値の切替は親テーマ §C で重複違反に当たらない |
| 3 | **一覧の区切り線は PC もスマホも「線なし」に統一する** | **ADR-064（Accepted）が `--inbox-separator #e4e6eb` で線を引いているため、ADR-064 の改訂起案が必要**。本PRでは決定の記録のみとし、改訂は別PRで起案する |
| 4 | 残りの操作感（スクロール・キーボード）を先に取得する | 取得済み。[whatsapp-ux-behavior.md](whatsapp-ux-behavior.md) §2-3・§2-4 |

## 先行ADRとの関係（重要）

**[ADR-064「Inbox Meta Business Suite 完全再現レイアウト」（Accepted）**が既に存在し、受信箱は Meta の実測値で再現済み。担当範囲が違うため競合ではないが、照合すると差が出る。

| 観点 | ADR-064 | 本メモ |
|---|---|---|
| 対象 | **Meta Business Suite の PC（web・3カラム）** | **WhatsApp / Meta Business Suite の スマホ（Android アプリ）** |
| 単位 | CSS px | dp（PO決定1により px として採用） |
| アバター | 48px | 直径48dp → **一致** |
| 会話名 / 日付 | 15px / 13px | 文字枠 21.7dp / 16.3dp。一般的な行間から逆算して矛盾しないが、**フォントサイズ自体は測れていないため「一致」とは言えない** |
| 区切り線 | `--inbox-separator #e4e6eb` で引く | **引いていない**（WhatsApp は隙間ゼロで連続、Meta は白のまま）→ PO決定3 |

## 測り方（4つを組み合わせる）

1. **部品の構造データ**（`adb shell uiautomator dump`）: 部品の位置・大きさ・押せるか・アプリ内部の名札。**親子の座標の差から余白を計算**できるので、再現用の寸法はここから出す（[whatsapp-reproduction-spec.md](whatsapp-reproduction-spec.md)）。
2. **写真の画素の測定**（`adb exec-out screencap -p` → 自作の集計）: 色、文字の実際の高さ、区切り線の有無。構造データに色は入っていないため必須。
3. **許可された操作での画面移動**: 一覧の項目を開く／戻る／タブ切替／メニューを開いて閉じる の4つだけ（手順書 §0-4）。
4. **描画フレームの記録**（`adb shell dumpsys gfxinfo <アプリ> framestats`）: 操作ごとのフレーム数と所要時間。**録画なしで動きの速さが測れる**（[whatsapp-ux-behavior.md](whatsapp-ux-behavior.md)）。

**撮影の前に必ず前面のアプリを証拠で確認する**（`dumpsys window` の `mCurrentFocus`。メニューが開いていると `PopupWindow` になるため、その場合は `mFocusedApp` で判定）。目的のアプリが前面だと確認できなければ撮らずに中止する。この関所を入れる前に1度、ターミナルの画面を測定対象と誤認した事故があったため、手順に組み込んだ。

## この方法の限界（越えられない壁）

| 取れないもの | 理由 |
|---|---|
| フォントサイズ | 構造データに含まれない。画素から測れるのは「書かれている文字に依存するインクの高さ」までで、下限値にしかならない |
| アプリが「重要でない」と印を付けた部品 | 構造データは支援技術向けの木構造を使うため、その印が付いた部品は最初から現れない |
| Meta Business Suite の部品の意味 | 名札がほぼ付いていない（1件は `(name removed)`）。位置と大きさは測れるが、何の部品かは断定できない |

## 横断して分かったこと（両アプリ共通の型）

| 観測事実 | WhatsApp | Meta Business Suite |
|---|---|---|
| 一覧の行の高さ | 228px = **76dp** | 234px = **78dp** |
| 押せる範囲 | 行全体（全幅） | 行全体（全幅） |
| 行と行の区切り線 | **無い** | **無い**（境目の画素は背景と同じ） |
| 一覧の上の検索/絞り込み | 検索バー 高さ48dp | 絞り込みチップ 高さ43dp |
| 下部ナビ | 4項目・帯80dp・1タブ90x80dp・アイコン32dp・選択の下地64x32dp | 5項目・各56x44dp・中央の丸ボタン48x48dp |
| 長押しの操作メニュー | 上部バーを選択モードの帯に置き換え（アイコン48x48dp・144px刻み） | （未取得） |
| 右上の︙メニュー | 項目の縦間隔144px=48dp・文字枠一定幅164dp・サブメニュー無し | （未取得） |
| 表示テーマ（観測時） | 暗い（背景 `#0a1014`） | 明るい（背景 `#ffffff`） |

**要点1 — 押す場所**: どちらも「小さな部品を押させない」設計で、**一覧は行をまるごと押させる**。行の高さは 76〜78dp に収束している。

**要点2 — 区切り**: 区切り線は使わず、余白と背景色で行を分けている。

**要点3 — 48dp という単位**: WhatsApp はアイコンボタン（48x48dp）、メニュー項目の間隔（48dp）、検索バーの高さ（48dp）、入力欄の高さ（48dp）が**すべて48dp で揃っている**。一覧の行（76dp）と下部ナビのアイコン（32dp）は別の段。

### 訂正記録（2026-10-11）

本表の下部ナビについて、当初「アイコン枠48dp」と記載したが**誤りだった**。`action_tile_icon`（連絡先情報画面の操作タイルのアイコン 64x48dp）と混同していた。構造データを再確認した正しい値は次のとおり。

| 部品 | 実測 |
|---|---|
| 下部ナビの帯 | 360x80dp |
| 1タブの当たり判定 | **90x80dp**（360 ÷ 4項目） |
| アイコン | **32x32dp** |
| 選択中の下地（`navigation_bar_item_active_indicator_view`） | **64x32dp** |
| ラベル | 高さ19dp（アイコンの下、帯の上から49dpの位置） |
| 内訳 | 上12 ＋ アイコン32 ＋ 隙間5 ＋ ラベル19 ＋ 下12 = **80dp** |

**要点4 — メニューの出し方**: 操作は「その場にポップアップを浮かせる」より「**上部バーを置き換える**」「**右上から1枚のパネルを出す**」の2通りに限られ、入れ子のサブメニューは無い。

**要点5 — 配色**: 明暗を切り替えても**役割ごとの面積比が変わらない**（地79.6%/79.7%、2段目の面5.2%/5.2%、強調色1.5%/1.7%）。面は**2段だけ**、強調色は**画面の1.5〜1.7%**しか使わない。主要文字の明度差はライト17.9:1・ダーク18.0:1でほぼ同一（[whatsapp-color-structure.md](whatsapp-color-structure.md)）。

**要点6 — 操作感: 120Hz の画面で、**戻るは85ms（ほぼ即時）、会話を開くのは586ms、タブ切替は両方向とも628msで完全一致**。戻る操作には動きを付けず、進む操作にだけ動きを付けている。1フレームの処理は中央値3.3ms（予算8.33msの4割）。

**要点7 — 当たり判定の入れ子**: 一覧の行（押せる）の中に顔写真（押せる）が入っている。行＝会話を開く、顔写真＝プロフィール写真。「行はまるごと押せる」を守りつつ例外を1つだけ作っている。

**要点8 — ビジネスプロフィール**: 営業時間は「曜日ごとの行＋折りたたみの矢印」で**1枚のカードに収めている**。項目ごとに別画面へ飛ばさない（[whatsapp-business-contact-info.md](whatsapp-business-contact-info.md)）。

## 我々（salesanchor）との差（事実のみ。対処は design.md で設計する）

- 受信箱をスマホ幅（390px）で測った段階1の結果は、押す場所が44px未満の部品が **33/52件**（[../../../../handoff/app-visual-language/stage1-baseline.md](../../../../handoff/app-visual-language/stage1-baseline.md)）。
- お手本2本は、同じ問題を「部品を大きくする」ではなく「**行全体を押せる範囲にする**」で解いている。
- 390px 幅で `.inbox-right-panel` が画面外（y=844）に積まれている状態は、お手本の「スマホは1列で画面を切り替える」とは異なる。
- 参考: WhatsApp 自身も44dp未満の押せる部品を持つ（右上の︙が40x48dp、アップデートのタブでは11件）。**ゼロが目的ではなく、主要な操作導線を行単位にすることが要点**。

## 守った決まり（手順書 §0）

- 元データ（写真・構造データ）は**リポジトリに入れていない**。スマホ内の専用フォルダ1つ（`/root/vl-benchmark-raw/`）にまとめてあり、この PR がマージされたあとに削除する。
- 人の名前・メッセージ本文・電話番号・メールアドレス・アカウント名は**書いていない**。部品表は文字情報を出力しない作りにしている（メニュー項目など、アプリが固定で持つUI表記のみ例外として記載）。
- 文字入力はしていない（`adb shell input text` はロック解除の暗証番号にのみ使用。PO許可 2026-10-10。ベンチマーク対象アプリへの入力は一切なし）。
- 送信・削除・転送・アーカイブ・ブロック・通話・録音・設定変更・ログアウトは一切していない。通話履歴のタブは撮影のみで、履歴の項目はタップしていない。
- **顧客の未読の会話は開いていない**（開くと既読が相手に伝わり取り消せないため）。未読バッジの有無を構造データで判定し、未読が無い会話のみを開いた。吹き出しと長押しメニューは、PO が自分の第2の番号から送った**テスト用の会話**で取得した（2026-10-11）。
- 長押しメニュー・右上のメニューは表示して撮るだけにとどめ、**項目は1つも選んでいない**。閉じた後に構造データを再取得し、選択モードの部品が消えていることを確認した。
- 連絡先情報へ進む途中で出たプライバシーのお知らせ（OKボタン付き）は、設定変更に当たる恐れがあるため**OKを押さず**「戻る」で閉じた。
- Meta の案内カードは「閉じる」と明示されたボタンのみを押した。「投稿を作成」は押していない。
