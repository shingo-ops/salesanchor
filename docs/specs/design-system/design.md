## 5. design（技術How・3層＋2つの支え）

| 層 | 理想のルール | 素人向けに言うと |
|---|---|---|
| 層1 トークン | 生値（#hex・px等）が書けるのはトークン正本ファイル1つだけ。名前は用途ベース（例: --color-brand-primary） | 色見本帳は1冊だけ。みんな見本帳の番号で呼ぶ |
| 層2 共通部品 | プルダウン・検索欄・ボタン・アイコン・テキスト表示形式（日付・金額の書式含む）は1部品=1定義ファイル。差分はprops（variant/size）で吸収し、複製・上書き禁止 | 部品の金型は各1つ。形を変えたければ金型を直す |
| 層3 ページ | 部品をimportして使うだけ。ページ内での部品再定義・生値ベタ書き禁止 | 画面は部品を並べるだけ。自作改造しない |
| 支え1 カタログ | 全共通部品と使用例を1画面で見られる部品一覧を常備（KGI④） | 部品の見本帳 |
| 支え2 関所 | CIがページ側ソースの生値ベタ書きと部品重複定義を機械検出しfail。トークン・部品定義ファイルのみ許可リスト（KGI⑤） | 直書きしたら自動で止める見張り番 |

参照は常に一方向: トークン → 共通部品 → ページ。逆流・飛び越し（ページが生値を直接持つ）を禁止する。

## 6. 弊害・トレードオフ（空欄不可）
1. 自由度の低下: ページ固有の「ここだけ微調整」がやりにくくなる。意図した制約だが、
   正当な例外（外部サービス埋め込み等）は関所の許可リストで逃がす運用が要る＝許可リスト管理コストが発生。
2. 移行コスト: 既存ページの生値・独自部品を金型へ寄せる作業量は、recon実測まで不明。
3. props肥大リスク: 「1部品=1定義」に寄せすぎると1部品の引数が膨らみ読みにくくなる。
   variant数の上限は移行designで決める。
4. 既存 component-standard.md を移設しない弊害: 置き場が親ディレクトリ外に残り一見分散して見える。
   双方向リンク＋索引で辿れることを担保して許容（移設はリンク切れリスクの方が大きい）。
