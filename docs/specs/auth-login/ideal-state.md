# あるべき姿 — ログイン方式

この文書は、ログイン方式について PO が言った言葉だけを残す正本です（Planner・Generator は書き換えない）。

親: [README.md](README.md)

## PO の言葉（2026-10-13 チャット）

- 「パスワードのログイン設定だがfirebaseが最適化？今後、authenticationや生体認証でのログイン認証も追加したいと考えている」
- 「サーバー内に自作でセキュリティ管理テーブルを作成したほうが良い？」
  - Opus は ADR-138（パスワード保管の廃止）を根拠に「作らない方がよい」と回答した。
- 「生体認証を追加したいのでfirebaseをから自社サーバー内でのパスワード管理に切り替えてほしい、fableにも設計の相談をする」
- 「配線とDBのSSOTは遵守してデータを分散させることは禁止。フロントエンドのパーツもデザイントークンとデザインシステム を遵守して、金型登録のないハードコードを禁止する。推測で自身で判断したり不透明無まま進めることは禁止、分からないことは聞いてくれ。確立したなら進める。」
- 移行時のパスワードについて、Opus が「全員に1回だけ新しいパスワードを設定してもらう方式でよいか（y/n）」と確認した。
  - PO の回答は「y,新規パスワードを発行する、ただしメールアドレスではなくこの端末のファイルに書き出して見れるようにしておいてほしい」。
- 移行後の再設定について、Opus が「パスワードを忘れた・端末をなくした場合も、管理者が発行してファイルに書き出す方式でよいか（y/n）。n なら本人がメールで再設定できる仕組みも作る」と確認した。
  - PO の回答は「n」。
- 認証アプリ（6 桁コードの二段階認証）を今回の移行に入れるかについて、Opus が y/n で確認した。
  - PO の回答は「n,二段階認証は次の便で、二段階認証については任意で設定する項目にする」。
- 新しいパスワードの発行範囲について、Opus が「public.users で使用中（is_active=true）の 10 人全員に発行し、それ以外には発行しない」でよいかを y/n で確認した。
  - PO の回答は「y」。
- パスキー（顔・指紋の鍵）の範囲について、Opus が「app.salesanchor.jp 専用にしてよいか（y/n）」と確認した。
  - PO の回答は「y」。
- Opus が「この設計と成功の基準（5 項目）で承認してよいか（y/n）」と確認した。
  - PO の回答は「y」。
