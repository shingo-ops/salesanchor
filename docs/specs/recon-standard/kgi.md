# KGIと観点ひな型 — recon（現状把握）

親（表紙）へのリンク: [README.md](README.md)

> この文書は何か（専門用語なしの1行）:
> あるべき姿を○×で測るKGIと、毎回のreconで必ず埋める調査観点のひな型。

## KGI（○×で測る・全6項目。測る単位＝1回のrecon成果物）

| # | 合格条件 | 測り方 | 合格ライン |
|---|---|---|---|
| ① | その領域の必須調査観点リストを事前に定め、各観点に回答したか | 回答済み観点 ÷ 必須観点 | 未回答 0 |
| ② | 事実主張すべてに file:line か「実測コマンド＋生出力」が付いているか | 根拠づき主張 ÷ 全事実主張 | 満数 |
| ③ | 推測・伝聞だけの主張が無いか | 推測のみの主張数 | 0 |
| ④ | 数える前に関連ADR・除外ファイル（例 index.css＝ADR-067）を確認し、本物／ノイズに仕分けたか | 仕分け済み数え上げ ÷ 数え上げ総数 | 満数 |
| ⑤ | あるべき姿の各項目を現状と対照し「一致／不足／余剰」の3値で全項目分類したか | 未分類項目数 | 0 |
| ⑥ | 実装者の自己申告を、設計パートナーが別経路で1回検算したか | 検算済みrecon ÷ 採用recon | 満数 |

KPI: 達成KGI数 ◯/6。

## 観点ひな型 v1（どの領域にも効く共通の最低ライン・7観点）

これは最低ラインであり上限ではない。各領域で不足する切り口は追加する。②③の「部品」が各領域で何を指すかは、その領域のrecon冒頭で1行定義してから使う。

1. 全体像: 対象領域のファイル群・エントリポイント・データの流れを file:line で列挙する。「どこに何があるか」の地図を出す。
2. 共用部品: 共通利用される部品・関数・トークン・定数を洗い出し、定義元と参照元を示す。
※「部品」は領域ごとに何を指すか冒頭で定義する。例（フロント）: ①UI部品 ②デザイントークン ③フォーマッタ関数の3種。定義を省くとトークン等を見落とす。
3. 非共用部品: 共用でない個別実装を洗い出し、「本来は共用にできるのに個別化しているもの」の候補を挙げる。
4. ルールの所在: その領域を統べる規約（ADR・正本・lint・CI）を特定し、関連ADRと除外対象を数える前に確認する。
5. 維持の仕組み: そのルールを今、何が守っているか（関所／hook／人手）を示し、守り手が無い箇所を名指しする。
6. 設計図との対照: あるべき姿の各項目を現状と突き合わせ、「一致／不足／余剰」の3値で全項目分類する。「余剰」は設計図に無い既存物を指し、捨てるのでなく「優れているので残す（→あるべき姿に採用）／不要なので除く」のどちらかを必ず判定する。
※観点6の根拠は file:line でなく「あるべき姿の記述 ↔ 現状値」の対照表（差分表）でよい。1項目=1行で、一致/不足/余剰の判定と現状値を並べる。
7. ノイズと境界: 数え上げに混じる偽物（PR番号・コメント）を仕分け、今回「見ない」と決めた範囲を明記する。

## 設計送り事項
- 守り手はCI関所（便2で設計・実装）。recon.md が7観点の見出しを持ち、各観点の下に file:line 形式の行を最低1本持つかを機械判定する。中身の良質さはKGI⑥（設計パートナーの独立検算）とPO目視で担保する。
- 保留（次パイロット後に共通化を判断）: フロントのパイロットで「参照の一方向性（トークン→部品→ページの逆流検査）」「観点4を棚卸しと準拠照合の2段に分割」が有用と判明。ただし1領域のみの知見のため、別領域パイロットで共通化の可否を確認してから共通ひな型へ格上げする。
