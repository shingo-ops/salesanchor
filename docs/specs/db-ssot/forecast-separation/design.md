# 予測値の分離（forecast-separation）— 設計図

> この文書は何か（専門用語なしの1行）:
> 売上予測を「手入力の見立て」と「実績からの自動計算」の2種類に分け、別々に持つ理想形の設計。混在による上書き事故を防ぐ。親テーマ「DB設計のSSOT化」の子。

親: ../README.md ／ あるべき姿・KGI: ../ideal-state.md, ../kgi.md

## 1. なぜ分けるか（背景）
売上予測には性格の異なる2種類が存在する。手入力の見立て（勘・参考材料）と、実績からの自動計算（根拠ある正確な値）。この2つは格が違い、1つの欄に混ぜると手入力値が計算値を上書きする（またはその逆）事故が起きる。現状DBでは leads と companies の両方に monthly_forecast 系の欄があり、二重定義になっていた（K1違反）。

## 2. あるべき姿（この子の理想形）
- 予測値の棚を2つに分ける。
  - 棚A（手入力の見立て）: 見込み客（lead）の段階に持つ。人が手で入力。空でもよい。用途は新規営業の優先度づけ。あくまで参考材料の1つ。
  - 棚B（自動計算の実績値）: 会社（company）の段階の値。用途は売上見込みの合計・CRM。根拠ある本命値。
- 棚Bは値を保存しない。発注履歴（受注の記録）から、必要なときにその場で計算して導く。
  → 正本は「発注履歴」ただ1つ。予測値を別に保存しないので、古い予測が残る余地がない（SSOTに忠実）。
- 棚Aと棚Bは別の場所に持ち、相互に上書きしない。
- どちらの予測も必ず持ち主（リード）にひもづく。

## 3. なぜそうするか（KGIとの対応）
- K1（重複ゼロ）: 手入力と自動計算を分離し、同一欄の二重定義を解消。leads/companies の monthly_forecast 二重を撤廃。
- K2（正本1か所）: 棚Bの正本は発注履歴に一元化。予測値そのものは保存しない。
- K5（持ち主にたどり着ける）: 両予測ともリードに必須ひもづけ。

## 4. 稼働前の前提
- 本番未稼働。既存データは捨てて理想形で新規構築してよい。現状のデータ分布（leads側の予測欄は空 0/56、companies側は使用 9/51）に設計を引きずらない。

## 5. まだ決めていない（実装時に詰める）
- 棚B「その場で計算」の具体的な計算式（発注間隔・1回の発注量・金額の重み付け）。
- 棚A（手入力の見立て）を、見込み客が会社に成長した後も履歴として残すか（見立てが当たったかの検証用）。
- assigned_to（担当者）は予測値と別物。本設計の対象外・別途扱う。
