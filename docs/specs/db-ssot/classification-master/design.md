# 分類値の台帳化（classification-master）— 設計図

> この文書は何か（専門用語なしの1行）:
> 国・流入元・顧客規模などの分類値を、自由入力ではなく「台帳から選ぶ」形にして表記ゆれを防ぐ設計。共有台帳＋テナント独自台帳の2階建て。親テーマ「DB設計のSSOT化」の子。

親: ../README.md ／ あるべき姿・KGI: ../ideal-state.md, ../kgi.md

## 1. 現状（調査で確定した事実・2026-07-10 tenant_004実測）
- 分類欄は19個あり、すべて character varying（自由入力）。台帳への外部キー接続は0本。
- 対象例：country / lead_source / channel_type / estimated_scale / customer_type / prospect_rank / industry / priority_focus / type / status×4。
- 既存台帳は public に countries / tcg_series_master / tcg_type_master / product_attribute_masters のみ。国の台帳はあるが leads.country は参照せず自由入力。
- 営業系の分類（流入元・規模・種別・ランク・業種）の台帳は未存在。
- products_category_classification_backup はバックアップ残骸。正規台帳でないため整理・除外対象。
- discord関連ID（discord_dm_channel_id 等）は分類値ではなく識別番号のため対象外。

## 2. あるべき姿（この子の理想形・PO指示 2026-07-10）
### 2-1. 台帳化の基本
- 複数の選択肢を持つ分類値は、すべて台帳（マスタ）に値を登録し、フロントはその値からプルダウンで選ぶ。自由入力は禁止（＝表記ゆれゼロ）。各分類欄は台帳を参照で持つ（コピー禁止）。
- スプレッドシートの「データ入力規則のプルダウン（参照シート）」と同じ考え方。

### 2-2. 2階建て（共有＋テナント独自）
- 共有台帳（public）：アプリ全体で共通の固定値（国・標準の流入元・標準ランク等）。運営が管理し全テナント共通。
- テナント独自台帳：各テナントが独自の値を追加・修正・削除できる（テナントスキーマ側）。
- フロントは共有＋独自を合わせた選択肢から選ぶ。

### 2-3. テナント独自値の安全な削除（増殖防止）
- 削除操作は即消さず「非表示」にする（論理削除）。プルダウンからは隠すが、DBには残す。
- 非表示にした日を起点に90日経過し、かつどのデータからも参照されていない値のみ、自動でDBから本削除する（定期実行）。
- まだ参照しているデータがある値は本削除しない（過去データが迷子にならない）。
- 共有台帳（public）の値はこの自動削除の対象外（運営管理）。
- 非表示中の値を一覧・復活できる「ゴミ箱」ページを用意する。

### 2-4. ステータス（状態）の扱い
- ステータスも台帳化の対象とし、選択肢の種類は台帳で固定する（表記ゆれ防止）。
- ただし「今どのステータスか」を人が手で選ぶか、出来事から自動で決めるかは、別途の論点（手動ステータス廃止の方針）として実装時に詰める。台帳化と自動判定は両立可能。

## 3. なぜそうするか（KGIとの対応）
- K4（台帳から選ぶ・表記ゆれゼロ）：全分類値を台帳参照にし、自由入力を廃止。
- K1/K2（重複ゼロ・正本1か所）：分類値の正本を台帳に一元化。各データはコピーせず参照。
- SSOT：共有値は共有台帳1か所、独自値はテナント台帳1か所。

## 4. 稼働前の前提
- 本番未稼働。既存の自由入力欄は捨てて、台帳参照の形で新規構築してよい。

## 5. まだ決めていない（実装時に詰める）
- 共有台帳と独自台帳を別テーブルにして画面で合体するか、1テーブルに「共有/独自」区分を持たせるか（技術判断）。
- 自動削除（定期実行）の具体的な実行基盤（cron等）。
- 各分類欄を「どの台帳」に対応させるかの最終マッピング一覧。
- ステータスの手動/自動判定の線引き（上記2-4）。
