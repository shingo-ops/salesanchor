# 本丸実装の計画（implementation-plan）— 設計図

> この文書は何か（専門用語なしの1行）:
> 会話・金額・戸籍・分類の4設計図を、実際のDBとコードに反映する「順序と手順」の計画。何をどの順でreconし、どう安全に移行するかを定める。親テーマ「DB設計のSSOT化」の子。

親: ../README.md ／ 各設計図: ../classification-master/, ../conversation-unification/, ../money-consolidation/, ../forecast-separation/

## 1. 大前提（最強の武器）
- 本番未稼働。既存データは捨ててよい＝複雑なデータ移行が不要。理想構造で作り直し、コードを新構造に向けるだけで済む。
- 現状のデータ分布に設計を引きずらない。

## 2. 実装の順序（下から積む）
下の土台から順に積む。土台を後回しにすると、上の層が参照先を持てず組めない。

### STEP1: 分類マスタ（台帳）を建てる ← SSOTの土台
- 全ての分類値（国・流入元・規模・種別・ランク・業種・ステータス）の正本となる台帳を作る。
- 2階建て：共有台帳（public）＋テナント独自台帳。フロントは両方から選ぶ。自由入力廃止。
- 独自値の安全削除（非表示→90日→参照ゼロのみ自動本削除・ゴミ箱ページ）。
- これが最初。他STEPのテーブルはこの台帳を参照するため。

### STEP2: 戸籍（lead→deal→company→contact）
- 顧客の実体情報（name/email/phone等）の重複を解消し、正本を1か所に定めて背番号で繋ぐ。
- 全ての親。金額も会話もここに紐づくため、金額・会話より先。

### STEP3a: 金額（order集約） / STEP3b: 会話（1テーブル統合）
- 戸籍の上に乗る層。並行可能。
- 金額：請求・仕入=order正本、見積=lead/deal正本、各金額1か所・参照のみ。
- 会話：2テーブルを1つに統合、全窓口共通、全会話がリードに紐づく。

## 3. 各STEP内の作業手順（4段・共通）
1. recon：対象テーブルと、それを使う全コード箇所の精密調査（file:line）。
2. 実装設計：テーブル構造・コード改修点・移行手順を design.md に確定。設計時に仕様が固まり、実装中に判断が生じない状態にする。
3. dry-run：本番相当での予行（BEGIN→変更→確認→ROLLBACK）。
4. 移行：バックアップ→PO自筆GO→本実行→実測確認。

## 4. やらないこと（この計画の範囲外）
- 人事（スタッフ・シフト等）、在庫、送料は本テーマ外。別テーマで扱う。

## 5. まだ決めていない（各STEPのrecon時に詰める）
- 各STEPの具体的なテーブル定義・コード改修の詳細（実装設計フェーズで確定）。
- STEP3a/3bの並行実行の可否（戸籍完了後に判断）。

## 6. 維持の仕組み
- 本ファイルの変更はPR＋PO承認のみ。process-artifacts gate が管理。
